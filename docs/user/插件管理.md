# 插件管理

Harness 当前支持把本地目录或 zip 作为 Plugin 校验并复制安装。可识别三类格式：

- Agent Plugins 1.0：根目录包含声明官方 1.0 schema 的 `plugin.json`。
- Claude Code Plugin：包含 `.claude-plugin/plugin.json`，或在明确指定
  `--format claude-code` 时使用 Claude 默认目录结构。
- Qwen/DevAgent Extension：根目录包含 `qwen-extension.json` 或
  `devagent-extension.json`。当前支持 `qwen-code` 静态识别、安装后的只读资源快照、虚拟路径、
  trusted Context、Qwen Agent catalog，以及 enabled+trusted Agent 的受控 `SubagentStop` 门禁和子
  Agent 交互；安全 Markdown Commands/Skills 和 ZA38 stdio MCP 已进入 canonical runtime，其他 MCP transport 仍是静态 preview。

当前版本已经把 Plugin 中有效的 Skill、MCP、Markdown Command、Harness Agent/Policy/Team
以及 Claude `agents/*.md`、command Hook、stdio LSP、Monitor 接入 Host 启动快照。Claude
尚未适配的 Hook handler/event、socket LSP 和其他实验组件只进入兼容报告，不会执行。不能把
“已安装”或“已启用”理解为所有组件已经生效；请查看每个组件的 `status`、`effective` 和
`diagnostics` 字段。

Qwen/DevAgent 的最终兼容矩阵如下：

| 组件 | 当前状态 | 用户可见结果 |
| --- | --- | --- |
| 根清单、目录/ZIP 安装 | 已适配 | `auto` 或 `--format qwen-code` 可校验与安装；目录和 ZIP 使用同一安全链路 |
| Context | 已适配并生效 | trust+enable 后作为低可信、不可变参考进入主 Agent 和对应 Plugin Agent |
| Agents | 已适配并生效 | 进入实际 `agents.list` 和 Managed 委派；颜色与权限请求可审计，但不能越过 Host Policy |
| `SubagentStop` | 已适配并生效 | matcher 命中时进入受控终态门禁；异常和构造漂移失败关闭 |
| Commands | 已适配并生效（安全子集） | trusted+enabled 后以 `/za38-init`、`/za38-sdd`、`/za38-index` 等自然名进入 Slash 菜单；坏条目仍只显示 non-runnable preview |
| Skills | 已适配并生效（安全子集） | `za38-framework` 进入 canonical SkillRegistry；根 `references/` 通过同一 snapshot 的虚拟只读路径读取 |
| MCP | 已适配并生效（ZA38 stdio 安全子集） | trusted+enabled 后进入 canonical MCP snapshot；坏项在 `mcp.status.diagnostics` 中隔离，其他 transport 仍只预览 |
| Settings（Qwen/DevAgent） | 已适配并受控 | 通过 `plugins settings list/set/remove` 管理；只向有效 MCP/Hook/LSP child 注入声明值 |
| themes、channels、workflows 等 | 不支持或无效 | 只进入兼容报告，不产生运行能力；当前 ZA38 未声明 channels，本次交付不实现 Channel runtime |

因此“Qwen/DevAgent Extension 已兼容”只表示上表列出的受控子集；未支持 transport 和所有 invalid、unsupported、
disabled、untrusted 的 Command/Skill 仍只是 non-runnable preview，不能当作已经可以执行。
当前 ZA38 插件没有 `channels` 声明；本次兼容交付明确不实现 Channels。未来若插件产生真实
外部消息入口需求，需要先单独设计隔离、认证、Thread/Run 所有权、限流和关闭协议，不能直接加载插件 JavaScript。

Agent Plugins 1.0 的 portable core 只定义通用 `plugin.json`、`skills/` 和 `mcp.json`。
Harness 使用本地固定 schema 标识，不会在校验时联网下载 schema：

- `https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`
- `https://agent-plugins.org/schemas/1.0.0/mcp.schema.json`

`com.za38.harness` 是 Harness 私有 extension namespace，负责 Command、Agent、Policy 和
Team 等额外能力；这些能力不是 Agent Plugins 1.0 portable core 的标准组件。Claude Plugin
仍由独立 Adapter 处理其 `commands/`、`agents/`、Hook、LSP、Monitor 和 `.mcp.json`。
双 manifest 包必须保持 name/version 身份一致，但两套 MCP 配置仍按各自格式解释：portable
`mcp.json` 使用 1.0 closed schema，Claude `.mcp.json` 可以保留 Claude 的 `timeout` 等既有字段，
不能通过放宽 portable schema 来兼容它们。

希望直接体验全部已支持能力时，使用仓库内的
[Harness Full Demo Plugin](../../examples/plugins/harness-full-demo/README.md)。该 Demo 同时包含
Skill、Command、MCP、Agent、Policy、Team、Claude command Hook、stdio LSP 和 Monitor，并给出
从校验、安装、启用到逐项验证和卸载的完整步骤。

## 校验和安装

先校验，不写入本机 PluginStore：

```bash
harness plugins validate ./my-plugin
harness plugins validate ./my-claude-plugin.zip --format claude-code
```

`--format` 支持 `auto`、`agent-plugins-1.0`、`claude-code` 和 `qwen-code`。`auto` 只在根目录
存在专属清单时识别 Qwen/DevAgent，不会根据普通 `commands/`、`skills/` 或 `agents/` 目录猜测
Qwen。两个 Qwen 家族清单同时存在，或 Qwen/DevAgent 清单与 portable/Claude manifest 共存时，
会返回 `PLUGIN_FORMAT_CONFLICT`。`qwen-extension.json` 或 `devagent-extension.json` 没有声明
`commands`、`skills`、`agents` 时，都会扫描包根目录中实际存在的同名默认目录。`settings` 按
Qwen `ExtensionSetting` 的 `name`、`description`、必需 `envVar` 和可选 `sensitive` 校验，
值可通过 Settings 管理面显式配置；channels、themes、workflows 等首版非范围字段会明确报告
`unsupported`；Qwen `contextFileName` 缺省或 `[]` 时只报告实际存在的根 `QWEN.md`，
显式 string/string[] 路径会执行包内普通文件校验，DevAgent 仍使用非空字符串路径；畸形 MCP、Hook
或单文件 Skill 会报告 `invalid`，不会被计入有效库存。

安装或列出 Plugin 时，`resource_snapshot(s)` 会显示 Commands、Skills、Agents、MCP、Context 和
Hook 的静态数量与包内来源；`plugins.list.static_preview` 以及 `initialize.static_command_preview`、
`skills.list.static_preview`、`agents.list.static_preview`、`mcp.status.static_preview` 会把
Commands、Skills、Agents、MCP 分别暴露给既有列表消费者。未启用的 ZA38 安装记录对应数量是 3、1、3、1，
所有条目标记为 `disabled`、`static`、`non-runnable` 和 `read_only`，不会启动外部进程。信任并启用后，
三个 Agent、三个合法 Command、一个合法 Skill 和一个合法 ZA38 stdio MCP 进入 effective catalog，Agents/Commands/Skills/MCP preview
去除对应有效条目；坏 Markdown、坏 MCP server、被停用或未信任的条目继续留在 preview，且
`runnable: false`。preview 按组件 runtime 接入状态过滤，不会把 portable、Claude、Hybrid 投影到第二套
catalog。
模型可见路径统一为 `/.harness/plugins/<plugin-id>/...`；Qwen/DevAgent Skill 只捕获顶层 `references/*.md`、
以及声明为运行时依赖的其他安全普通文件。净化后的安装 store 可以保留包内非敏感原始素材，
但 `references/origin/` 等开发原始素材不进入运行时只读快照，Skill 的
`../../references/...` 关系仍可解析，不伪造 Skill 私有 `references/`。MCP/Hook 的快照资源只展示静态形状，未 trust 的 Plugin 不会启动进程；快照摘要不会
返回本机 store 路径。这里的 `runnable: false` 描述只读快照资源本身：未接入或未信任的 Qwen MCP 不会启动；
合法且 enabled+trusted 的同步 `SubagentStop` 会从已安装清单重新构造为受控 HookRunner 定义，不能
通过静态快照直接执行脚本。

安装会重新执行同一套校验，并把内容复制到 `~/.harness/plugins/store/` 的内容寻址只读版本：

```bash
harness plugins install ./my-plugin
```

安装结果始终为 `enabled: false`。Context-only 的合法 Qwen 包因 Context 已接入 canonical `ContextLifecycle`
而可以在确认 fingerprint 后启用；启用前后仍不会读取未 trust 的 Context。Harness 不从原目录原地运行 Plugin，后续修改原目录不会改变
已安装版本；要使用新内容需重新安装。

目录和 ZIP 都先复制到私有 staging，再进行 manifest、组件、路径、链接、大小和压缩比检查；通过后
才复制到内容寻址的只读 store。`validate` 只读 staging，不创建 registry 记录；`install` 写入
registry，但不会自动信任或启动任何进程。一个规范有效但没有 Harness 可用组件的包仍可安装为
disabled，启用时返回 `PLUGIN_NO_EFFECTIVE_COMPONENT`，这不是 portable 格式无效。

从本地 Git/其他 VCS checkout 安装时，staging 会按目录项名称先排除 `.git`、常见 VCS 目录、OS 临时
元数据、`.env`/`.env.*`、`.npmrc` 等本地配置；不会先读取这些文件正文。ZIP 中同名条目使用相同的安全
忽略策略。排除后的净化包才计算 digest、文件数和资源快照；排除范围之外的符号链接、hardlink、socket、
FIFO 或其他 special file 仍会稳定拒绝。安装结果和 Protocol 摘要不会包含被排除文件内容或宿主秘密。

## 查看兼容报告

```bash
harness plugins list
harness plugins inspect <plugin-id>
```

组件状态含义：

| 状态 | 含义 |
| --- | --- |
| `supported` | 当前版本已经接入运行时 |
| `adapted` | 外部格式已转换；报告中计数的受支持子项已接入，但外部格式可能还有未支持子项 |
| `unsupported` | 已发现且明确不执行，不会静默忽略 |
| `invalid` | 组件格式或路径无效；该组件不生效，包内其他有效组件仍可使用 |

`compatibility: ready/recognized/partial/invalid` 是组件状态的汇总。管理结果只显示来源文件名、内容
digest 和能力指纹，不返回来源目录、store 或 data 的宿主绝对路径。

状态的关键区别是：`invalid` 表示核心或组件配置不能安全解释，`unsupported` 表示格式可识别但
Harness 当前不执行，MCP 启动/连接/认证失败则属于运行时诊断，不会把静态包倒退为 invalid。
单个 Skill、MCP server 或 Claude 子项失败只影响对应条目；同包其他有效组件仍可进入下一次 Host
快照。

## 显式启用

从 `validate`、`install` 或 `inspect` 结果复制完整 `capability_fingerprint`：

```bash
harness plugins enable <plugin-id> \
  --capability-fingerprint <64位SHA-256>
```

指纹不匹配，或 Plugin 没有任何可用组件时，启用会被拒绝。重新安装新版本后会自动回到 disabled，
防止新增 MCP、Hook、网络、可执行文件或 Agent 能力沿用旧确认。停用不需要指纹：

```bash
harness plugins disable <plugin-id>
```

当前 enabled catalog 在 Host 启动时只读取一次。启用、停用、更新或删除后需要重启 Harness；
当前 Host、已经建立的 Thread 和正在执行的 Run 都不会被原地改写。

`capability_fingerprint` 是当前组件库存和能力类别的 SHA-256 确认值，不是发布者签名。
重新安装或能力库存变化都会撤销旧 trust；必须重新 `inspect` 并确认新的 fingerprint。
registry 只承认当前版本；未发布期间旧开发构建产生的旧版本 registry 不会被读取或迁移，会按
“版本或结构无效”失败关闭。如需恢复，先完整退出 Harness 和 sidecar，删除 `~/.harness/plugins`
后重新安装插件。

## Plugin Settings

受信任且已启用的 Qwen/DevAgent 插件可以声明 `name`、`description`、`envVar` 和可选
的 `sensitive`。`envVar` 必须存在且合法；Qwen setting 的值可以不配置，缺值不会从
当前 Shell 环境补入。设置值只保存到当前用户的系统 credential manager，metadata 只
保存脱敏绑定和状态，不进入插件 registry、catalog snapshot、fingerprint、Protocol、
Transcript、日志或插件文件。没有可验证的 credential backend 时操作会失败关闭。
Phase 4B 的 macOS Security.framework、Linux Secret Service 和 Windows Credential Manager
适配器都必须先通过能力探测；任何 API、权限或并发安全性无法证明时保持
`SETTINGS_BACKEND_UNAVAILABLE`，不会降级到明文文件或当前 Shell 环境。

### 查看设置摘要

```bash
harness plugins settings list --scope user
harness plugins settings list --scope workspace --workspace /path/to/workspace
```

列表只返回 `env_var`（精确 canonical `envVar`）、展示字段、scope、脱敏
`store_state`/`runtime_state`、revision 和 pending 摘要，不返回值、account、路径或
credential manager 内容。当前 Qwen 映射中，list 返回的 `env_var` 就是 set/remove 所需的
`<setting-key>` 位置参数；Protocol 不返回名为 `setting_key` 的 summary 字段。不存在的
scope 逻辑 revision 为 `0`，不会因为 list 偷偷创建文件；`runtime_state` 表示当前
Host/generation，`store_state` 表示 live store，因此刚 set/remove 后可显示已存储但
`pending_restart`。

### 设置和删除

```bash
harness plugins settings set --scope user \
  plugin/local/example ZA38_API_TOKEN \
  --package-digest <从 settings list 取得的64位SHA-256> \
  --declaration-digest <从 settings list 取得的64位SHA-256> \
  --expected-store-revision 0 \
  --secret-stdin
harness plugins settings remove --scope user \
  plugin/local/example ZA38_API_TOKEN \
  --package-digest <从 settings list 取得的64位SHA-256> \
  --declaration-digest <从 settings list 取得的64位SHA-256> \
  --expected-store-revision 1
```

`set` 和 `remove` 都必须先用 `list` 取得同一 scope 的
`package_digest`、`declaration_digest` 和 `expected_store_revision`；并发修改会返回
`SETTINGS_STORE_REVISION_CONFLICT`，HC-158 不提供无条件覆盖。Plugin ID 和 setting key
是两个位置参数，digest/CAS 使用具名 option；未知 option、缺少 option 值、重复 option
以及 list/remove 携带 `--secret-stdin` 都会在 CLI 解析期失败。`--workspace` 与 `--cwd`
是同一工作区选择的互斥别名，同时提供会失败关闭。交互 TTY 使用 no-echo；
非交互必须显式使用唯一公开标志
`--secret-stdin`，从 stdin 有界读取一个值。敏感和非敏感 setting 使用完全相同的输入
规则，值禁止出现在 argv，也不会在任何响应或错误中回显。上限外返回
`SETTINGS_VALUE_TOO_LARGE`，上限内的 NUL、非法编码或额外 stdin record 返回
`SETTINGS_VALUE_INVALID`。

工作区值覆盖用户值，但声明、package、工作区 root、信任策略或 credential backend
身份漂移会使旧值失效并要求重新设置。set/remove 只对下一次 Host/generation 生效，
当前 Run 不热更新。有效 Qwen MCP、Hook、LSP child 只收到该插件已配置且通过 denylist
的 declared env；Commands、Skills、Agents 不接收 Settings env。`PATH`、`NODE_OPTIONS`、
`PYTHONPATH`、`LD_*`、`DYLD_*` 等 process-control 变量和当前 Shell fallback 都被拒绝。
卸载按 user index 清理该插件及其已登记的全部 workspace scope；部分失败保留可重试
状态，不枚举 credential backend，也不影响未登记的 workspace。

## 使用 Plugin Skill 和 MCP

重启 Harness 后，Plugin Skill 会使用不会覆盖其他来源的 canonical ID：

```text
plugin/<source-id>/<plugin-name>/<skill-name>
```

例如 `plugin/local-a1b2c3/secure-review/review`。它会出现在 `/skills` 和 `/` 补全中，也可以像现有 Skill
一样附到下一条消息。Skill 的 `allowed-tools` 只作为请求记录，不会绕过 Harness 的 Policy 或
工具审批。

Plugin MCP 会与 `~/.harness/config.toml` 中的 MCP 一起进入同一个连接快照。`/mcp` 状态里的
`source` 会显示 `plugin:<plugin-id>`；Server 名使用 `plugin__...` 前缀，因此不会覆盖普通用户
配置。Qwen Hook/LSP 的 bare executable 会在运行时 catalog 中解析并冻结为受控绝对路径；Qwen Hook command 还会冻结为
executable 和 argv，并通过 exec 启动，不重新经过 POSIX shell，因此带空格或 Windows 反斜杠的脚本路径不会被改写。
子进程不继承 `PATH`、`NODE_OPTIONS` 或动态加载器等进程控制变量；Claude/portable Hook/LSP 保留既有的最小 `inherit-path` 语义。
Plugin MCP 仍由 canonical manager 提供最小 allowlist 环境，不接受 manifest 任意注入进程控制变量。Qwen/DevAgent 的 ZA38 stdio 首个运行子集只接受 `type=stdio`，并逐字段校验 command、args、cwd、env、timeout；
只展开 `${extensionPath}`、`${workspacePath}`、`${/}`、`${pathSeparator}`。未知 token、宿主绝对路径、越界、缺失目标和超限
会在 `mcp.status.diagnostics` 中稳定报告，坏 server 不会阻断同包其他 server。

portable stdio 的 `command` 必须是单一 executable token；`args`、`env` 和 `cwd` 只做一次
`${PLUGIN_ROOT}`/`${PLUGIN_DATA}` 替换，未知 placeholder 保持字面值，`cwd` 不能越出包 root 或
Plugin data。Streamable HTTP/SSE 使用字面 URL 和 header；非 loopback HTTP 必须使用 HTTPS，认证
失败只显示为该 server 的运行时失败。插件不能通过 manifest 伪造两个保留环境变量。

Claude `commands/*.md` 和 portable Harness extension Command 会出现在 Slash 菜单中，名称固定为：

```text
/plugin:<source-id>:<plugin-name>:<command-name>
```

例如 `/plugin:local-a1b2c3:secure-review:audit src/auth.ts`。参数原样传入 Command；Markdown
正文只在 Agent 端按需读取，CLI 不接收正文、脚本或本机路径。Plugin Command 不能覆盖 `/help`、
`/mcp` 等内置命令，也不能自行扩大工具权限。

Qwen/DevAgent 的安全 Markdown Command 使用文件自然名；子目录使用 `:`。例如 ZA38 插件启用后，输入
`/za38` 可以补全：

```text
/za38-init
/za38-sdd
/za38-index
```

CLI 的单一 CommandRegistry 解析后提交原始 slash invocation、stable command ID、已解析的命令名和参数；
Plugin Command 还会通过 `commands.bind` 把同一 Registry 对当前 Skill snapshot 选出的 exact
`command_id → resolved_name` 绑定给 Host，再把原文和该解析结果作为同一 invocation contract 发送。Host 只按 stable ID
绑定当前 snapshot 中的 effective command record，校验 raw invocation、CLI 命令名和参数与 exact binding 的一致性，不复制
builtin、alias 或冲突优先级表，也不重新解析 UI 命令；因此插件声明 `help` 但 Registry 选中 `/bad.help` 时，未选中的
`/help` 会 fail closed，不创建伪造 Run。Host 从当前 Run 的不可变安装 snapshot
展开 `{{args}}` 一次。没有占位符时，参数追加到正文末尾；正文中的 `!{shell}`、`@{file}` 不在此阶段
解释而会使该条目 non-runnable。运行中重新安装或停用不会改变当前 Run，下一次 Run 才使用新的 catalog。
`za38-framework` Skill 与 Command 使用同一 trusted snapshot；其顶层 `references/*.md` 只能通过虚拟只读路径读取，
`references/origin/` 不可见，
不会额外获得 Shell、网络、MCP 或写入权限。

该 binding 使用 Protocol v3 minor 6，`commands.bind` 的最小 minor 也是 6。CLI 会先读取 initialize 的协商结果：
协商到 v6 才登记 Plugin Command；旧 v5 Agent 存在插件命令时返回稳定升级错误，不会调用旧端不存在的方法；没有插件命令时，普通非插件运行沿用既有兼容路径。新 Host 对低于 6 的连接也会在执行前返回 `PROTOCOL_MINOR_REQUIRED`。

Plugin Command 的运行事件在当前未发布的 Protocol v3.7 中还会携带严格脱敏的 provenance：
`run.started.payload.command_provenance` 和 `skill.loaded.payload.provenance` 只含
`plugin_id`、`package_digest`、`command_id`、`snapshot_id`，不含命令正文、安装目录或宿主绝对路径。
`skill.loaded` 只有已安装 Plugin Skill 会附加这份摘要；内置、项目和用户 Skill 保持原有不带 provenance
的事件形状，不会用空 package digest 冒充 Plugin 来源。
这是 v3.7 既有 HC-158 实现的 schema 修复，不是新的 CLI 命令；CLI 与 Agent 会通过生成的同一 validator
校验它们。协商到 v3.6 或更低的旧连接若选择 Plugin Command，会在运行开始前得到稳定的
`PLUGIN_COMMAND_PROTOCOL_MINOR_REQUIRED`，不会写入 Transcript、调用模型或收到未知事件字段；普通旧 minor
Run 与 v3.6 的 `commands.bind` 仍可用。

## 使用 Plugin Agent 和 Team

重启 Harness 后，已启用 Plugin 中有效的 Harness Agent 或 Claude `agents/*.md` 会作为主
Agent `task` 工具的可选角色。用户直接用自然语言要求“让 security-reviewer 审查认证边界”即可；
模型只能选择已经注册的 Agent ID 和任务文本。Agent 使用 Managed 模式，拥有独立
AgentEngine、child execution 和 checkpoint namespace。

Claude Agent 的 `tools` 只是该角色请求的最大工具集合，还会与父 Agent、审批模式和 Host
硬边界取交集。`Read/Glob/Grep/Write/Edit/Bash/Agent` 使用固定映射；未知 Claude Tool 会让
该 Agent inactive，不会猜测。`model: inherit` 继承父实际模型；`sonnet/opus/haiku` 优先使用
同名 Harness ModelProfile，未配置时同样安全继承。其他模型名必须精确匹配已配置 Profile。
Agent 只能读取其 `skills` 和 `mcpServers` 显式声明的组件；未声明时为空，不会继承主 Agent
看到的全部 Skill 或用户 MCP。

Qwen/DevAgent 的 `agents/*.md` 使用专用 frontmatter Adapter，不套用 Claude 方言。当前保留
`name`、`description`、`color`、`approvalMode: default|plan|auto-edit|yolo`，并按独立源枚举映射
`permissionMode: default→default、plan→plan、acceptEdits/auto→auto-edit、dontAsk→default`，同时验证
源码可证明的工具、模型和 turn 配置；未知字段、类型错误和 `bypassPermissions` 会在启用前标为
`invalid`。信任并启用后，三个 ZA38 executor 会出现在实际
`agents.list`；`DEVAGENT.md` 作为 `REFERENCE/STABLE` 低可信 Context 进入主 Agent 与对应 Plugin
Agent 的 Run snapshot 各一次。Context 不能覆盖 Core Policy、工具、审批或 workspace 边界。

`agents.list` 和 `agents.inspect` 的摘要会同时返回 `color`、`approval_mode`、`permission_mode`（没有
对应值时为 `null`）；这些字段只用于列表展示和审计，不会直接授予权限。它们与 Python/TypeScript
Protocol schema 一致，因此 Qwen Agent 列表会经过与 portable/Claude 相同的 Host dispatch 校验。

Qwen Agent 的 `approvalMode/permissionMode` 只是能力请求上限，最终结果取 Plugin 请求、父 Agent
当前权限和 Host/workspace policy 的交集。未声明工具时默认只请求 `read_file`、`glob`、`grep`；
auto-edit 不等于绕过审批，写入、Shell、网络、MCP 和 delegation 仍必须经过 Harness 正常 policy。

启用并信任 Qwen/DevAgent Plugin 后，合法的 `SubagentStop` command Hook 会在 matcher 命中的
Plugin Agent 最终输出返回父 Agent 前进入受控门禁。父 Run 会通过现有交互通道显示“提交”“继续修改”
和“一次性跳过”：继续修改和提交都会在同一个 child execution/checkpoint 开始下一回合，提交回合
只注入“执行提交门禁所需提交”的用户选择指令；一次性跳过才直接放行当前门禁。三种选择都不会
改变 Plugin/Host policy，提交回合中的 Shell/Git 仍必须走正常 EffectivePolicy、工作区保护和审批。Hook 输入不包含密钥、环境秘密、宿主
store 路径或无界 transcript。Hook 畸形、非零、超时、取消、无交互客户端和连续第九次阻断都会
失败关闭。只有 Adapter/runtime 共用 matcher、command、timeout、shell、async 和受控字段校验均通过，且安装报告标记为 `adapted/effective` 的同步 Qwen `SubagentStop` 才会进入 runtime；invalid、unsupported、范围外事件、`async:true`、`env/args` 未支持字段、runtime 转换失败或匹配 gate 没有同步结果时不会被当作“没有 Hook”，而是稳定失败关闭。Qwen MCP 仅有 ZA38 stdio 安全子集进入 canonical lifecycle；Harness 不连接真实 Qwen MCP，也不执行真实外部 Hook
脚本进行本地验收。Qwen 的 `PreToolUse`、`PostToolUse`、`PostToolUseFailure` 也复用同一 Tool seam：Pre 只能阻断，Post 的
`additionalContext` 只是一次性低可信模型输入，PostFailure 不会改写原始工具错误；Prompt、Session、Compact、Permission、Todo、Message
等无 Host seam 的事件继续 unsupported。Hook feedback 按 Thread/Run/execution 隔离：child release 只清自身，顶层 Run release 清同一 Run 的全部未消费反馈；已取消的模型边界不会调用模型。Phase 2 的离线证据包含仓库内真实 fake newline-delimited stdio MCP：通过 Adapter 和 canonical manager 验证 initialize、tools/list、tools/call、取消和 close；其余 patch fake 只验证 manager seam 和 generation replacement，不连接真实 ZA38 MCP。

Qwen command Hook 的 `timeout` 使用 Qwen 原生毫秒单位：未填写时为 `60000`（60 秒），允许
`1..600000`（1 到 600 秒），进入 Harness runtime 后统一转换成秒。`0`、负数、布尔值、字符串
和超过 `600000` 的值会稳定显示为 invalid；Claude/portable Hook 继续使用原有秒单位，不受这次
Qwen 转换影响。Controller 的 Plugin Command 菜单、手输和选择后 Enter 使用同一启动握手 Registry，
因此菜单中显示的 `/za38-sdd` 会沿同一 stable command ID 正常提交，并保留用户原始调用文本。

portable Harness extension 的 `teams/*.yaml|json` 会转换为固定任务 DAG。当前后端已经支持
依赖、并行上限、写任务互斥、失败策略、父取消和恢复规则。使用以下命令查看和运行：

```text
/agents
/teams
/teams show <team-id>
/teams generate <team-id> <lead-agent> <worker1,worker2> [max-parallelism]
/teams run <team-id> <任务描述>
/teams status <run-id>
/teams cancel <run-id>
```

`generate` 只根据当前已注册 Agent 创建“并行分析 → lead 汇总”的预览，不接受客户端上传任意
Policy、模型或工具列表；查看预览不会启动 Team。生成预览在当前 Host 关闭后消失，已启动 Run
的状态存入 SQLite，可在重启后查询。Team 不会自动创建自由聊天 mailbox。

## 使用 Claude Hook、LSP 和 Monitor

显式启用 Plugin 并重启 Harness 后，以下组件会进入受控运行时：

| 组件 | 当前可用范围 |
| --- | --- |
| Hook | Claude `PreToolUse`、`PostToolUse`、`PostToolUseFailure`，以及 Qwen/DevAgent 的三类 Tool Hook 和 `SubagentStop`；Qwen 只接受受控 command shell form |
| LSP | Claude 与 Qwen stdio server；支持 definition、references、hover 和 diagnostics |
| Monitor | shell command；stdout 作为有界、不可信的辅助上下文 |

Qwen `lspServers` 只接受 stdio；inline 配置或包内 JSON 会先逐项校验 command、args、cwd、env、timeout、workspaceFolder 和
`extensionToLanguage`，只展开 `${extensionPath}`、`${workspacePath}`、`${/}`、`${pathSeparator}`。未知 token、socket/HTTP、宿主绝对路径、
workspace 越界、缺失或 symlink 目标、环境控制变量和扩展名冲突会留在诊断中且不启动；查询只能通过既有 `lsp` 工具，不能发送任意
JSON-RPC。超时、取消、关闭或重新绑定 generation 后，旧 LSP client 会被清理。

`PreToolUse` command 返回 exit code 2，或输出 Claude 格式的
`permissionDecision: "deny"`，会阻止目标 Tool。Hook 有超时和输入输出上限，只继承最小环境；
不会得到模型 API Key。LSP 仅处理工作区内文件，按扩展名懒启动；socket transport 不执行。
Monitor 由 Host 启动并在 Host 关闭时终止整个子进程组，输出不会被当成可信系统指令。

当前不支持 prompt、agent、HTTP、MCP-tool Hook、其他 Claude/Qwen Hook 事件、socket/HTTP LSP，以及
themes、output styles、dependencies、channels、workflows 和通用 `bin/` 的运行语义。
包含这些内容的 Plugin 可以安装，但相应子项会在兼容报告中显示 `unsupported`。

## 删除

```bash
harness plugins remove <plugin-id>
```

默认移除安装记录并清理该 Plugin 的 Settings credential，但保留
`~/.harness/plugins/data/` 下的 Plugin 持久数据。只有用户明确要求时才额外清除 Plugin data：

```bash
harness plugins remove <plugin-id> --purge-data
```

`--purge-data` 按已安装记录绑定 Plugin 身份清理 Settings；即使 Plugin 已停用或信任
失效，也不会因不在运行时 catalog 中而遗留已保存的 credential。若清理范围发生冲突或
部分失败，Harness 会保留安装记录并返回可重试结果，不会假报已清除。

内容寻址 store 的未引用旧版本当前保留为不可变孤儿，后续由独立清理机制处理。

## 文件系统安全边界

目录和 zip 安装都会先进入私有 staging。Harness 拒绝：

- symlink、hardlink、device 和其他特殊文件；
- 绝对路径、Windows drive path 和 `..` 路径穿越；
- 超过文件数量、单文件、总大小、目录深度或 zip 压缩比上限的包；
- 损坏的 registry 或与 digest 不一致的 store 内容。

Plugin 安装不是操作系统 sandbox。MCP、受支持的 command Hook、stdio LSP 和 Monitor 已实施
最小环境、输入输出边界和 Host 关闭生命周期，但它们仍是用户明确确认 `process` 能力后启动的
外部进程或网络服务；通用 `bin/` 和报告为 `unsupported` 的组件不会执行。

常见稳定错误码包括 `PLUGIN_SCHEMA_UNSUPPORTED`、`PLUGIN_MANIFEST_FIELD_INVALID`、
`PLUGIN_MCP_SCHEMA_UNSUPPORTED`、`PLUGIN_COMPONENT_INVALID`、`PLUGIN_NO_EFFECTIVE_COMPONENT`、
`PLUGIN_CAPABILITY_CONFIRMATION_REQUIRED`、`PLUGIN_STORE_TAMPERED` 和
`PLUGIN_REGISTRY_INVALID`。先看错误码和 `inspect` 结果，不要把详细路径、环境变量值、
header 或 Plugin 正文贴到日志和 Issue。

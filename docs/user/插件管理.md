# 插件管理

Harness 的 Plugin 管理在 Shell CLI 中完成。安装来源可以是本地目录或 zip；安装会先复制到受管的本地存储，再由下一次启动的 Host 加载。Harness 自动识别以下格式：

- Agent Plugins 1.0 portable；
- Claude Code Plugin；
- Qwen/DevAgent Extension；
- 同时包含 portable 与 Claude 入口的 Hybrid Plugin。

格式差异由 Adapter 处理，TUI、Web 和 Agent runtime 不需要按格式选择入口。

## 推荐流程

从 Plugin 源码目录之外的一个已存在工作区执行：

```bash
harness plugins install /path/to/plugin --cwd /path/to/workspace
harness --cwd /path/to/workspace
```

`install` 会展示本次将写入的名称、版本、实际可用组件和警告。只有 `stdin`、`stdout`、`stderr` 同时是真实 TTY 时才会出现确认；输入 `y` 或 `yes` 才继续，其他输入、取消、EOF 和管道输入都会拒绝操作并返回 `PLUGIN_CONSENT_REQUIRED` 或取消错误。没有 `--yes` 绕过确认的选项。

安装确认成功后，插件在所选作用域直接启用，不需要再执行第二条 `enable`。Harness 不从原始源码目录运行插件；安装后修改源码不会改变已安装版本，要使用新内容请执行 `update`。

TUI 与从同一交互进程打开的 Web 使用同一个 Host 和启动 catalog。Plugin Command、Skill、Agent、Context、MCP、Hook 和 LSP 进入现有消费者；没有 Plugin 管理面板、安装弹窗或 Settings secret 控件。

## 命令

```text
harness plugins validate <source> [--format auto|agent-plugins-1.0|claude-code|qwen-code]
harness plugins install <source> [--scope user|workspace]
harness plugins list [--scope user|workspace] [--enabled-only]
harness plugins inspect <name> [--scope user|workspace]
harness plugins enable <name> [--scope user|workspace]
harness plugins disable <name> [--scope user|workspace]
harness plugins update <name> [--source <source>]
harness plugins remove <name> [--purge-data]
```

正常管理命令使用插件名称；不需要复制内部 ID、内容摘要、声明摘要或 registry revision。`list`、`inspect`、`enable`、`disable`、`install` 以及 Settings 命令省略 `--scope` 时均使用 `user`。只有显式传入 `--scope workspace` 才读取或写入 workspace override；workspace scope 必须绑定一个已经存在的工作区。`update` 和 `remove` 是安装 artifact 级操作，不接受 scope。

`validate` 是可选的安装前诊断，`--format` 只用于明确的开发诊断；正常 `install` 和 `update` 自动识别格式。`list` 和 `inspect` 的状态只有四种：

| 状态 | 含义 |
| --- | --- |
| `loaded` | 插件已启用，所有报告为有效的受支持组件已进入启动 catalog。 |
| `disabled` | 插件仍安装，但当前作用域停用；任何组件都不会进入 consumer。 |
| `warning` | 至少一个组件已进入 consumer，同时另有条目被跳过或失败。 |
| `failed` | 插件已安装但没有组件能够安全进入 consumer。 |

组件列表只包含实际进入 canonical consumer 的组件。坏条目、不支持的 transport、缺失资源或转换失败只产生脱敏 warning，不会伪装成可执行 Command、Skill、Agent 或 MCP。

## 作用域

用户作用域对任意后续工作区生效：

```bash
harness plugins install /path/to/plugin --scope user --cwd /path/to/workspace
harness plugins list --scope user --cwd /path/to/workspace
```

workspace 作用域只对绑定工作区生效：

```bash
harness plugins install /path/to/plugin --scope workspace --cwd /path/to/workspace
harness plugins list --scope workspace --cwd /path/to/workspace
harness plugins list --scope workspace --cwd /path/to/another-workspace
```

workspace override 优先于 user activation。停用或删除后，已经运行的 Host、Thread 和 Run 继续使用启动时的 immutable snapshot；当前 Host 不监听 registry，不热刷新，也不会重新向当前 Thread 注入 Context。关闭 Harness 后再启动新 Host，才会读取新的 activation、artifact 和 Settings。

## Settings

Qwen/DevAgent Plugin 可以声明 Settings。声明本身只进入脱敏管理列表；值不会出现在 argv、Protocol response、日志、Transcript、Plugin registry 或普通文件中。

```bash
harness plugins settings list
harness plugins settings list <name> --scope workspace --cwd /path/to/workspace
harness plugins settings set <name> <setting> --secret-stdin
harness plugins settings remove <name> <setting>
```

Settings 命令省略 `--scope` 时使用 `user`。交互式真实 TTY 使用无回显输入；非交互调用 `set` 时必须显式使用 `--secret-stdin`，值从 stdin 有界读取，不能放进命令行参数。list/set/remove 都不会输出 secret。

已配置值只在下一次 Host/generation 启动时交给该 Plugin 的有效 MCP、Hook 或 LSP 子进程。Commands、Skills、Agents 不接收 Settings 环境变量；`PATH`、`NODE_OPTIONS`、`PYTHONPATH`、动态加载器变量和当前 Shell fallback 也不会被设置值覆盖。没有可验证的 credential backend 时操作会 fail closed。

## 启动后可见能力

### Commands 与 Skills

Plugin Command 和 Skill 使用现有的 CommandRegistry、SkillRegistry 与 Run 链路。Qwen/DevAgent 的 Markdown Command 使用文件自然名，例如：

```text
/za38-init
/za38-sdd
/za38-index
```

Claude、portable 和 Hybrid Command 使用带 Plugin 来源的 canonical 名称。参数由现有命令绑定协议交给 Host，Command 正文只在 Host 的启动 snapshot 中按需读取；Plugin 不能覆盖 `/help`、`/mcp` 等内置命令，也不能扩大 Tool Policy。

### Agents、Context 与 Team

有效 Agent 会出现在现有 `/agents` 与 `agents.list` 中，并继续使用 Harness 的模型、审批、工具和 workspace policy。Plugin Agent 的 `tools`、`approvalMode` 或其他权限字段只是请求上限，最终权限仍取父 Agent 与 Host policy 的交集。

Qwen/DevAgent 的 Context 作为低可信、不可变的参考块进入新的 Run snapshot，不能覆盖 Core Policy、工具、审批或 workspace 边界。它不会因为另一个 Shell 的安装、停用或更新而进入已经运行的 Thread。

portable/Hybrid 的 Team 定义继续走现有 `/teams` consumer；查看定义不会启动外部进程，Team Run 仍由 Harness 的正常 cancellation、policy 和持久化规则管理。

### MCP、Hook、LSP 与 Monitor

有效 MCP 会与用户配置合并到同一个 Host MCP generation。插件 Server 使用隔离的 canonical 名称；连接失败只影响对应 Server，不阻断其他组件。自动化测试使用 fake connection，不会启动真实 ZA38 MCP。

支持的 Hook、LSP 和 Monitor 由启动 catalog 构造并由 Host 统一关闭：

| 组件 | 受支持范围 |
| --- | --- |
| Hook | Claude 的受控 Tool Hook，以及 Qwen/DevAgent 的受控 command Hook 和 `SubagentStop`。 |
| LSP | Claude 与 Qwen 的受控 stdio server，使用既有 LSP 工具查询。 |
| Monitor | Hybrid/Claude 的受控 background command；输出只是不可信辅助上下文。 |

命令、参数、路径、超时、环境和 workspace 边界会在 Adapter/runtime 两侧校验。Socket、任意 HTTP、越界路径、symlink、未知 placeholder、坏 JSON、超时和非零退出会被隔离或 fail closed；不支持的组件不会被当成可执行能力。自动化验收不运行真实 Plugin Hook/LSP/Monitor。

## 更新和删除

```bash
harness plugins update <name> --source /path/to/plugin-v2
harness plugins remove <name>
harness plugins remove <name> --purge-data
```

`update` 替换已安装 artifact，并保留 activation；`remove` 删除安装记录并清理该插件登记的 Settings。默认保留 Plugin data，只有明确传入 `--purge-data` 才清理 data。两者都只影响后续新 Host；当前 Host 的 Skills、Commands、Agents、Context、MCP、Hook 和 LSP generation 不会被中途改写。

## 安全边界

目录和 zip 会先进入私有 staging，再进行 manifest、大小、路径、压缩比和特殊文件校验。Harness 拒绝 symlink、hardlink、设备文件、socket、FIFO、绝对路径、Windows drive path、`..` 穿越以及超限文件。

Plugin 安装不是操作系统 sandbox。能进入 runtime 的外部进程仍受 Host 的 command、环境、输入输出、审批、workspace 和关闭生命周期约束；通用 `bin/` 或报告为无效/不支持的组件不会执行。请不要把 Plugin 正文、环境变量值、credential 内容或本机路径粘贴到日志和 Issue。

## 本地 ZA38 手工验收

自动化测试只使用仓库 fixture、临时 HOME、fake backend/process，不连接网络、不调用真实模型、不读取真实凭据，也不执行真实 ZA38 MCP/Hook/LSP。需要人工验证时，可在一个真实终端按以下路径操作：

```bash
# SOURCE_DIR 位于 WORKSPACE_DIR 之外，WORKSPACE_DIR 必须已存在
harness plugins validate "$SOURCE_DIR"
harness plugins install "$SOURCE_DIR" --cwd "$WORKSPACE_DIR"
harness plugins list --cwd "$WORKSPACE_DIR"
harness --cwd "$WORKSPACE_DIR"
```

启动新的 Harness 后观察现有 `/`、`/skills`、`/agents`、`/mcp` 和既有工作流中的实际组件；Shell 管理命令退出后再做 disable/update/remove，并重新启动一个 Host 检查新状态。不要在自动化环境或无确认的生产工作区执行 Plugin 外部组件。

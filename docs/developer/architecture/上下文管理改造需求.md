## 1. 结论

本次改造不是只移植一种压缩算法，而是组合两层能力：

- 以 **Qwen Code 的上下文连续性闭环**为主干：完整记录与模型投影分离，完整压缩形成检查点，压缩后重新恢复运行上下文；
- 以当前工作区 **Claude Code 非官方还原快照的分级压缩策略**为补充：先做低损耗微压缩，重新计量后再决定是否做完整摘要；空闲时间只是微压缩的一条辅助触发条件。

```text
完整会话记录
→ 当前模型工作投影
→ 评估上下文压力
→ 必要时微压缩
→ 重新计量
→ 必要时完整压缩
→ 校验、提交检查点并恢复运行上下文
→ 继续同一 Thread
```

在此架构上：

- Qwen 决定“记录、投影、完整压缩、恢复和继续运行”的生命周期；
- Claude Code 决定“何时先轻量处理、何时升级为完整压缩”的分级策略，以及旧工具结果的选择与近期保留原则；
- 为后续 Grok 风格长期记忆检索保留实际可复用的上下文注入位置；
- 不采用 OpenCode 的 Context Epoch、baseline + update 事件链作为主架构；
- 使用 Harness 当前的 Python、LangChain、LangGraph、AgentEnginePool 和 SQLite，不引入参考项目运行时依赖。

## 2. 当前问题

当前 Harness 已具备 Prompt、预算、工具结果归档、摘要、失败熔断和手动压缩能力，并已经按 50% / 60% / 80% / 90% 水位执行报告、工具结果脱水、摘要和强制摘要。但仍有五个顶层问题：

1. `PromptEpoch` 在 Thread 第一次运行后永久不变。当前 Thread 内修改 `.harness/AGENTS.md`、Skill 或核心 Prompt 后，后续 Run 仍使用旧内容。
2. 在 HC-103 前，`SkillRegistry` 是进程级不可变快照；启动后 Skill 发生变化会被判定为篡改，要求重启 Harness。HC-103 将其调整为 Host 管理、顶层 Run 刷新的 immutable catalog snapshot。
3. LangGraph `messages` 同时承担可恢复历史和模型工作上下文。压缩通过 `RemoveMessage(REMOVE_ALL_MESSAGES)` 改写它，完整 UI 历史与模型投影没有独立事实来源。
4. 当前阈值判断、工具结果脱水、完整摘要和 LangGraph 历史改写耦合在同一个中间件中。达到完整压缩水位后会直接摘要，没有形成“先尝试低损耗回收、重新计量、仍不足再摘要”的统一决策链。
5. 压缩主要生成“摘要 + 最近消息”，缺少一条统一的压缩后恢复链，无法保证最新项目指令、Skill 和结构化运行状态重新进入上下文。

## 3. 术语

| 术语 | 白话解释 |
| --- | --- |
| 规范记录 | Thread 中实际发生的用户消息、助手结果、工具结果和压缩事件；它用于恢复、回放和审计，不因压缩而被覆盖 |
| 模型工作投影 | 本次真正发给模型的有限历史；可由最新压缩结果和其后的新记录构成 |
| Run 上下文快照 | 某次 Run 实际使用的系统上下文，包括核心规则、能力边界、环境、AGENTS、Skill 和可选动态内容 |
| 上下文压力快照 | 某次模型调用前对当前投影的测量结果，包括总输入量、可回收工具结果数量与大小、剩余预算和可选空闲时长 |
| 微压缩 | 不调用摘要模型，只清理或替换旧的、可从 Artifact 恢复的工具结果；目标是低成本释放空间并尽量保留原始对话结构 |
| 完整压缩 | 调用模型把较早的工作投影整理为结构化摘要，并形成新的压缩检查点 |
| 空闲触发 | 顶层 Run 恢复对话时，因长时间未活动而额外尝试微压缩；它是缓存与传输优化条件，不代替 Token 水位 |
| 压缩检查点 | 一次成功压缩产生的模型工作投影、覆盖边界、算法版本和 Token 信息 |
| 顶层 Run | 用户向某个 Thread 提交一次新请求；不包括同一 Run 内的工具结果续跑、重试和 Interaction 恢复 |

## 4. 目标与非目标

### 4.1 目标

- 当前 Thread 在下一次顶层 Run 使用最新的 AGENTS 和 Skill。
- 每次 Run 内上下文保持不变，避免工具循环中途切换规则或能力。
- 按“权限层级优先、同层越稳定越靠前”组装系统上下文。
- 保留完整规范记录，压缩只改变模型工作投影。
- 将现有多水位能力收敛为独立、可测试的上下文压力策略。
- 建立“压力判断 → 微压缩 → 重新计量 → 完整压缩 → 状态恢复”的闭环。
- Thread 恢复时同时恢复完整 UI 历史和正确的模型工作投影。
- 保留现有 Artifact、完整工具调用边界、节省率校验、熔断和溢出恢复能力。
- 为未来的长期记忆检索提供真实的 Run 级注入位置，但不在本阶段实现记忆系统。

### 4.2 非目标

- 不实现向量数据库、Embedding、记忆提取、Dream 或跨 Thread 记忆治理。
- 不复制 Qwen 的 TypeScript/JSONL 实现；Harness 继续使用 SQLite 和 Python。
- 不实现 Claude 专用 `cache_edits`、Prompt Cache API 或其他厂商私有能力。
- 不实现 OpenCode Context Epoch 或将上下文变化写成对话消息链。
- 不在本阶段新增 Session 分支、Rewind、后台预压缩或新的 Agent 能力。
- 不把 Claude 快照中的内部实验能力、缺失实现或固定数值直接复制到 Harness。
- 不决定摘要 Prompt 的最终措辞、具体水位、工具压力阈值、空闲时长和近期保留数量；这些参数在开发任务阶段按模型预算与测试确定。

## 5. 功能需求

### REQ-CTX-001：会话内刷新系统上下文

每次顶层 Run 开始前，Harness 必须重新观察当前支持的上下文输入，并为该 Run 生成不可变快照。

验收条件：

- 修改用户级或项目级 `.harness/AGENTS.md` 后，无需新建 Thread 或重启进程，下一次顶层 Run 使用新内容。
- 确认删除某个 AGENTS 文件后，下一次顶层 Run 不再注入该来源。
- 同一 Run 已开始后，即使文件继续变化，该 Run 的模型调用和工具续跑仍使用启动时快照。
- Context 刷新失败发生在模型调用前，并提供可诊断结果；不得一半使用旧内容、一半使用新内容。

### REQ-CTX-002：稳定前缀与权限顺序

系统上下文必须先按权限层级排序，再在同一层中按变化频率排序。目标顺序为：

```text
1. 核心策略与 DeepAgents 基础规则
2. 实际执行、审批、Sandbox 与工具能力边界
3. 稳定环境信息
4. 用户级和项目级 AGENTS
5. 当前 Skill 索引
6. Run 级动态内容和未来长期记忆检索结果
7. 模型工作投影与当前用户输入
```

验收条件：

- AGENTS、Skill 和长期记忆始终是低于核心安全规则的不可信上下文，不能扩大工具或文件权限。
- 未变化的前缀必须按确定顺序和确定文本重新生成，避免无意义的 Prompt Cache 抖动。
- 工具 Schema 的实际能力视图和提示词中的能力说明必须来自同一 Run 准备结果。

### REQ-CTX-003：Skill 在当前 Thread 生效

Skill Catalog 必须从“进程永久快照”调整为“可重新扫描、每次 Run 绑定一个不可变快照”。

验收条件：

- 修改 Skill 的说明或正文后，下一次顶层 Run 可以使用新版本，不要求重启 Harness。
- Run 中显式选择的 Skill、System Prompt 中的 Skill 索引、`/.harness/skills/...` 虚拟读取和 AgentEngineProfile 必须引用同一个 Skill 快照。
- Skill 快照变化导致 AgentEngineProfile 变化时，新 Run 使用新 AgentEngine；已经运行的 Run 继续使用旧快照并正常结束。
- 非法 front matter、symlink、路径穿越和读取时摘要不一致仍然失败关闭。
- 只修改 Skill 文本不能绕过 EffectivePolicy 或增加真实工具能力。

### REQ-CTX-004：规范记录与模型工作投影分离

Harness 必须建立 Append-only 的 Thread 规范记录。LangGraph checkpoint 降级为运行状态和模型投影缓存，不再作为完整会话的唯一事实来源。

验收条件：

- 用户消息、完成的助手消息和工具结果以稳定顺序保存，重复 Run 或重复事件不会重复追加。
- 大型工具结果可以通过不可变 Artifact 保存原文，但规范记录必须保存内容摘要、哈希和 Artifact 引用，不能只留下无法解释的占位文本。
- 压缩前后的 `threads.open` 均能返回完整的用户可见历史，而不是只返回“摘要 + 最近消息”。
- 模型投影使用最新有效压缩检查点及其后的规范记录；没有检查点时使用规范记录生成。
- 旧压缩检查点继续保留用于审计，但只有最新有效检查点参与下一次模型输入。

### REQ-CTX-005：分级压力决策与微压缩

Harness 必须把“是否需要处理上下文”与“如何执行压缩”分离。压力决策至少观察三个维度：

```text
整体压力：当前投影 Token / 本次模型可用输入预算
工具压力：可恢复旧工具结果的数量与估算 Token
空闲条件：仅顶层 Run 首次模型调用使用的可选时间条件
```

验收条件：

- 总体水位必须保持“报告 < 微压缩 < 完整压缩 < 硬限制”的稳定顺序，具体值按模型输入预算计算，不在本需求中冻结。
- 工具压力可以在总体水位较低时提前触发微压缩；纯文本或决策密集型历史没有足够可回收工具结果时，允许跳过微压缩。
- 每次模型调用前都可以评估大小压力；空闲条件只在顶层 Run 的首次模型调用评估，不得在工具续跑、模型重试或 Interaction 恢复时重复触发。
- 达到完整压缩水位时仍先尝试一次确定性微压缩；必须基于微压缩后的投影重新计量，只有仍超过完整压缩水位才生成摘要。
- 微压缩只处理模型工作投影，不改写规范记录；只清理旧的、可从 Artifact 恢复的工具结果，并保持工具调用与结果配对。
- 微压缩必须保留最近若干个符合条件的完整工具结果，至少保留一个；已替换的结果再次评估时必须幂等。
- 空闲条件触发但没有可回收内容时不得制造空的压缩事件，也不得改变模型投影。
- Claude Code 的厂商专用缓存编辑不进入 Harness；只采用普通 LangChain 消息和现有 Artifact 能实现的分级决策、内容替换与近期保留原则。
- 每次决策必须记录触发原因和压缩前后压力摘要，但不得记录完整 Prompt 或工具原文。

### REQ-CTX-006：Qwen 风格的完整压缩闭环

完整压缩必须按下面的统一主链工作：

```text
微压缩后的模型工作投影
→ 生成结构化摘要
→ 校验摘要与节省量
→ 原子提交压缩检查点
→ 重新附加当前运行状态
```

验收条件：

- 自动压缩、手动 `/compact` 和一次溢出恢复复用同一个完整压缩服务，但保留不同触发语义。
- 自动压缩遵循“微压缩后仍超过完整压缩水位才摘要”；手动 `/compact` 可以绕过自动水位并明确请求完整压缩；溢出恢复只允许一次受控重试。
- 空摘要、截断摘要、投影膨胀、节省不足或模型失败时，不提交新的压缩检查点。
- 成功压缩必须记录来源边界、算法版本、Token 前后值和 Artifact 引用。
- 多次压缩从“最新压缩检查点 + 新增记录”继续生成，规范记录始终不被覆盖。

### REQ-CTX-007：压缩后和恢复后的连续性

系统上下文与历史投影必须独立恢复，压缩结果不能永久固化 AGENTS、Skill 或其他可刷新资源。

验收条件：

- 压缩后下一次模型调用重新使用当前 Run 的系统上下文快照。
- 重新打开旧 Thread 时，UI 从规范记录恢复，模型从最新压缩检查点与新增记录恢复。
- 当前已有的结构化状态中，至少 Todo、执行/审批模式和 Artifact 引用能够在压缩后确定性恢复；不存在的后台任务或 Agent Team 能力不得伪造占位实现。
- 恢复过程不得跨 Project 或 Thread 读取 Artifact、Skill 快照或上下文记录。

### REQ-CTX-008：持久化、审计与旧数据迁移

每个已受理 Run 必须能回答“它使用了哪一版上下文”，并安全处理当前 v6 数据。

验收条件：

- RunExecutionBinding 或等价的持久化绑定记录 Run 上下文快照 ID。
- 上下文快照保存有序块的摘要、版本和最终系统提示指纹；不得保存凭据或泄露不必要的绝对路径。
- v6 Thread 首次迁移时，以当前 LangGraph checkpoint 建立 legacy 初始投影，并明确标记更早规范记录可能不完整；不得伪造完整历史。
- 现有 Context Artifact 和 Summary 继续可读。
- Schema 升级前必须形成可恢复备份或等价回滚保障；生产路径迁移后不双写旧 PromptEpoch。

### REQ-CTX-009：长期记忆扩展位置

本阶段只允许为长期记忆复用现有 Run 级动态上下文机制，不实现独立的空接口体系。

验收条件：

- 未来 Memory Provider 可以在顶层 Run 准备阶段返回一个受长度限制、带来源和摘要的动态上下文块。
- 记忆块排在核心规则、能力边界、AGENTS 和 Skill 之后，不得影响权限计算。
- 记忆结果属于 Run 上下文快照并可审计，但不会被写进规范对话消息或永久冻结到 Thread。
- 首轮检索、显式刷新和压缩后检索等触发策略留给长期记忆需求文档决定。

## 6. 非功能需求

### 一致性

- 同一 Run 的 Prompt、Skill 虚拟文件、工具 Schema 和 AgentEngineProfile 必须来自同一次准备结果。
- 压力判断、微压缩后的重新计量和完整压缩必须针对同一份有序模型投影；不得混用旧 Token 估算决定下一步。
- 规范记录、压缩检查点和 Run 绑定通过类型化生命周期接口写入；调用方不得组合表级操作。

### 安全

- 工作区路径、AGENTS、Skill、Artifact 和未来记忆内容都按不可信输入处理。
- 动态上下文只能补充信息，不能修改审批、Sandbox、WorkspaceBoundary 或 EffectivePolicy 的执行结果。
- 持久化记录不得包含 API Key、Header 值、认证 Query 或其他秘密。

### 性能

- 每次 Run 的自动刷新优先使用文件元数据与 SHA-256 摘要判断变化；内容未变化时不得重建 AgentEngine。
- 提示词排序必须确定，稳定前缀在字节级尽量保持一致。
- 微压缩足以回到完整压缩水位以下时不得继续调用摘要模型。
- 压力计算允许使用保守估算，但必须保留输出预算和估算误差余量，并由溢出恢复兜底。
- 规范记录和大型工具原文避免无界重复存储，继续复用 Artifact。

### 可观测性

- `context.updated` 或等价诊断至少能区分资源刷新、压力报告、压力型微压缩、空闲型微压缩、完整压缩、溢出恢复、跳过和失败。
- 诊断信息可以说明上下文快照、压缩检查点、投影来源、触发原因和压缩前后估算，但不得暴露完整 Prompt、原始路径、工具原文或秘密。

## 7. 核心验收场景

1. **AGENTS 热更新**：同一 Thread 第一轮使用版本 A；修改文件后第二轮使用版本 B；第一轮审计仍指向 A。
2. **Skill 热更新**：第一轮运行期间修改 Skill；第一轮继续使用旧快照，第二轮使用新快照及对应 AgentEngineProfile。
3. **工具压力提前回收**：总体水位尚未达到完整压缩线，但旧工具结果超过压力阈值；只执行微压缩并保留最近结果，不生成摘要。
4. **逐级升级**：投影达到完整压缩水位；先微压缩并重新计量，若仍超线则在同一次模型调用前执行完整压缩。
5. **微压缩足够**：投影达到完整压缩水位，但微压缩后已回到线下；本轮不调用摘要模型。
6. **空闲恢复**：长时间未活动后启动新的顶层 Run；只在首次模型调用评估空闲条件，工具续跑和重试不重复触发。
7. **压缩与 UI 分离**：执行自动压缩后，模型只看到压缩投影，`threads.open` 仍返回压缩前的完整用户可见历史。
8. **多次压缩**：连续生成两个压缩检查点，恢复时只使用第二个检查点和之后的新记录，两个检查点和原始记录都可审计。
9. **压缩失败**：摘要为空、超长或不节省 Token 时，原投影继续可用，规范记录不变。
10. **旧 Thread 迁移**：v6 数据可恢复并继续对话；界面明确以现有 checkpoint 为旧历史起点，不声称已重建缺失记录。

## 8. 需求评审清单

- [x] 接受 Qwen Code 为整体主设计，OpenCode 不作为主体。

# Harness Code 扩展与插件机制设计方案

状态：核心能力已实现；ZC-141 portable core 已按 1.0.0 规范完成收尾复核；Claude 全量组件兼容仍按支持矩阵逐项演进

调研与代码审计日期：2026-07-31

目标：让用户通过一个可安装、可审计、可停用的 Plugin 接入 Skill、MCP、Command、Agent、Hook 等能力；直接兼容 Claude Code Plugin；支持根据多个 Agent 定义生成协作 Agent 和 Agent Team。

关联任务：[HC-091](../task/archive/HC-091-建立角色级ResolvedAg.md)～[HC-102](../task/HC-102-实现单实例WebHandoff.md)

## 一、背景

### 1.1 要解决的问题

方案提出时，Harness Code 已经具备一些分散的扩展能力：

- 可以从内置、用户和项目目录加载 Skill；
- 可以通过 TOML 或 `/mcp add` 接入 MCP Server；
- 可以复用不同配置的 AgentEngine；
- 已有 Agent 和 ExecutionPolicy 的静态领域模型；
- TUI 已有可扩展的 CommandRegistry 类型。

当时的主要问题是：

```text
Skill 有自己的目录扫描和状态
MCP 有自己的配置与连接状态
Command 目前只有内置定义
AgentCatalog 没有进入生产执行链
默认子 Agent 绕过 Harness 的 AgentEngine 与执行记录
Plugin 安装、信任、启停和更新完全不存在
```

本方案后续实施解决了这些问题；当前完成情况以第五节支持矩阵为准。

### 1.2 设计目标

本方案要实现以下结果：

1. 用户只面对一种扩展包：`Plugin`。
2. 一个 Plugin 可以包含 Skill、MCP、Command、Agent、Policy、Hook 和 Team。
3. 通用 Plugin 使用开放的 Agent Plugins 1.0 结构。
4. Claude Code Plugin 可以原样安装，不要求作者重新打包。
5. 不同外部格式最终转换成同一套 Harness 内部定义。
6. Plugin 声明的权限只能被收紧，不能扩大 Harness 或父 Agent 的权限。
7. 每个 Agent 使用独立的模型、Prompt、能力视图、执行状态和 AgentEngine。
8. 多个 Agent 可以组成动态协作组，也可以生成固定任务依赖的 Agent Team。
9. Plugin 更新、停用或删除时，不破坏正在运行的 Run。

### 1.3 不在本方案中做的事情

- 不允许普通 Plugin 把任意 Python、TypeScript 或 Bun 模块导入 Harness 主进程。
- 不让 Plugin 直接访问模型密钥、SQLite、ThreadPersistence 或内部 Python 对象。
- 不把 Skill 的 `allowed-tools` 或 Agent 的 `permissionMode` 直接当成授权。
- 不让 Team 文件重新定义 Agent 的模型、Prompt 和权限。
- 不为了兼容旧的内部类名或测试入口保留两套生产路径。

### 1.4 核心术语

| 名称 | 含义 |
| --- | --- |
| Plugin | 可安装、校验、启停、更新和删除的扩展包 |
| Component | Plugin 内的一项能力，例如一个 Skill、MCP Server 或 Agent |
| Adapter | 把 Agent Plugins、Claude Code 等外部格式转换成 Harness 内部定义的解析器 |
| Catalog Snapshot | 某一时刻所有已启用 Plugin 及其组件组成的不可变快照 |
| AgentDefinition | 一个角色的静态定义，描述用途、Prompt、模型请求和能力请求 |
| ResolvedAgentSpec | AgentDefinition 与实际模型、有效 Policy、工具、Skill、MCP 和执行环境合并后的唯一解析结果 |
| Delegation Group | 主 Agent 可以按任务动态选择的一组子 Agent |
| TeamDefinition | 多个 Agent 之间的固定任务、依赖、并行上限和失败规则 |
| TeamRun | 一次 TeamDefinition 的实际运行状态 |

Agent 与 Team 的关系是：

```text
AgentDefinition = “这个角色是谁、可以做什么”
TeamDefinition  = “这些角色怎样一起完成工作”
TeamRun         = “这次协作执行到了哪里”
```

## 二、各项目的扩展机制对比

### 2.1 对比结果

以下结论来自官方规范、官方仓库或官方文档。

| 项目 | 扩展包结构 | 主要能力 | 值得结合的部分 | 不适合直接照搬的部分 |
| --- | --- | --- | --- | --- |
| [Agent Plugins 1.0](https://github.com/agentplugins/agent-plugins-spec) | 根 `plugin.json`、`skills/`、`mcp.json`、client extension namespace | Skill、MCP | 作为通用 Plugin 基础格式；结构简单；支持客户端私有扩展；组件失败隔离 | 不包含安装、市场、信任、Agent 和 Team 的统一语义 |
| [Agent Skills](https://github.com/agentskills/agentskills) | `<skill>/SKILL.md` 和可选资源目录 | 可复用知识与工作流 | 与 Harness 当前 SkillRegistry 和虚拟文件按需读取方式高度一致 | `allowed-tools` 只能表示请求，不能自动授权 |
| [MCP](https://github.com/modelcontextprotocol/modelcontextprotocol) | 独立 Server，通过 stdio、HTTP 等传输连接 | 外部工具、资源和提示能力 | 继续复用当前 `langchain-mcp-adapters` 和连接管理 | MCP 进程不是沙箱，启动进程本身必须受信任 |
| [Claude Code Plugins](https://github.com/anthropics/claude-code/tree/main/plugins) | `.claude-plugin/plugin.json`，约定目录自动发现 | Skill、Command、Agent、Hook、MCP、LSP、Monitor、settings、marketplace | 生态成熟；组件丰富；Plugin Agent 可直接用于 subagent 和 Agent Team | 格式属于 Claude 产品；变化快；主仓库不是开放许可证，不能复制其实现 |
| [Claude Agent Teams](https://code.claude.com/docs/en/agent-teams) | 运行时生成 team config、task list 和 mailbox | lead、独立 teammate、任务依赖、互相通信 | 独立上下文、共享任务、成员控制和团队终态值得借鉴 | 当前仍是实验功能；运行时文件不是可分发 Plugin 标准；首版不应先复制 mailbox |
| [OpenAI Codex](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md) | Plugin catalog、marketplace、Skill、MCP、App、Hook | 安装、目录、认证和 thread 选择 | 证明不可变 catalog、Plugin 安装和 MCP 生命周期可以与 Coding Agent Host 结合 | 产品面和 Rust 架构不同；部分 Plugin API 仍标注开发中 |
| [Gemini CLI Extensions](https://github.com/google-gemini/gemini-cli/blob/main/docs/extensions/reference.md) | `gemini-extension.json`，本地/Git 安装 | MCP、Command、Skill、Hook、Agent、Policy、Theme | copy-on-install、user/workspace scope、环境变量 allowlist、Policy 只能收紧 | 不应在 Harness 运行层再引入一套 Gemini manifest 语义 |
| [Qwen Code](https://github.com/QwenLM/qwen-code/blob/main/docs/users/features/commands.md) | Extension 管理和 Claude/Gemini 生态入口 | Skill、MCP、Command、Agent、Hook、多 Agent Review | 跨产品导入和多 Agent Review 证明有明确用户价值 | 安装安全确认不足；Harness 必须提供独立 trust 流程 |
| [OpenCode](https://opencode.ai/docs/plugins/) | 本地或 npm JS/TS Plugin | Hook、Tool、事件和运行时修改 | 说明 Hook 与自定义运行时有价值 | 任意 JS/TS 进程内执行不符合 Harness 企业安全边界 |

### 2.2 可以组合使用的部分

这些规范和项目解决的是不同层面的问题：

```text
Agent Plugins 解决：通用包长什么样
Agent Skills 解决：Skill 文件长什么样
MCP 解决：外部工具怎样通信
Claude Adapter 解决：现有 Claude 生态怎样直接接入
Harness 解决：安装、信任、权限、AgentEngine、执行树和 Team 怎样运行
```

因此推荐组合：

```text
Agent Plugins 1.0
├─ Agent Skills → Harness SkillDefinition
├─ MCP config   → Harness McpServerDefinition
└─ Harness client extension
   ├─ CommandDefinition
   ├─ AgentDefinition
   ├─ ExecutionPolicyDefinition
   ├─ HookDefinition
   └─ TeamDefinition
```

Claude Code Plugin 不要求作者转换成上面的目录。Harness 通过 Claude Adapter 把它映射到相同内部定义。

### 2.3 最终选择

本方案不选择单一项目作为全部标准，而是采用：

1. Agent Plugins 1.0 作为可移植基础。
2. Agent Skills 作为 Skill 标准。
3. MCP 作为外部工具协议。
4. Harness client extension 补充 Agent、Policy、Command、Hook 和 Team。
5. Claude Code Plugin 作为一级兼容格式。
6. Gemini、Qwen 等格式以后只增加 Adapter，不进入运行层。

## 三、整体思路

### 3.1 一个内部模型，多个外部 Adapter

整体结构如下：

```text
Agent Plugins 1.0 ───────────┐
Claude Code Plugin ──────────┼─→ PluginFormatAdapter
未来 Gemini/Qwen Adapter ────┘          ↓
                                  PluginContribution
                                          ↓
                               ExtensionCatalogSnapshot
                               ├─ SkillDefinition[]
                               ├─ McpServerDefinition[]
                               ├─ CommandDefinition[]
                               ├─ AgentDefinition[]
                               ├─ PolicyDefinition[]
                               ├─ HookDefinition[]
                               └─ TeamDefinition[]
                                          ↓
                           Harness 唯一生产装配与执行路径
```

外部格式只在 Adapter 层出现。Server、AgentEngine、RunCoordinator、TUI 和 SQLite 不直接判断一个组件来自 Claude 还是 Agent Plugins。

### 3.2 为什么必须统一转换

如果不同格式各自进入运行层，会出现：

- Claude Agent 使用一套工具过滤，Harness Agent 使用另一套；
- TUI 显示的能力和实际构图能力不一致；
- AgentEngineProfile 按一份配置计算，builder 按另一份配置执行；
- Plugin 更新后 MCP 已变，旧图仍持有旧工具；
- 未支持的 Claude 字段被静默忽略。

统一转换后的规则是：

```text
外部文件
  → Adapter 解析与校验
  → canonical definition
  → Policy 与模型解析
  → ResolvedAgentSpec
  → AgentEngineProfile 和 AgentEngine builder
```

`AgentEngineProfile` 和 builder 必须消费同一个 ResolvedAgentSpec，不能再分别解析。

### 3.3 Plugin 的安装与生效流程

```text
本地目录 / zip / 企业市场 artifact
  → 解包或复制到 staging
  → 检测格式
  → 校验 manifest、路径、组件和兼容性
  → 计算 package digest 与 capability inventory
  → 展示来源、组件和风险
  → 安装为 inactive
  → 用户或 managed policy 签发 trust grant
  → enable
  → 发布新的 ExtensionCatalogSnapshot
```

安装不等于启用。任何包含 MCP、Hook、LSP、Monitor 或可执行脚本的 Plugin，都必须在启用前展示风险。

### 3.4 不可变快照与生命周期

Plugin Manager 发布不可变快照：

```text
PluginManager
  → ExtensionCatalogSnapshot
      ├─ Skill snapshot
      ├─ MCP snapshot
      ├─ Command snapshot
      ├─ Agent/Policy snapshot
      └─ Hook/Team snapshot
```

快照变化时：

- 新 Run 和新 child execution 使用新快照；
- 已开始的 execution 固定旧快照 ID；
- 受影响 AgentEngine 进入 draining；
- 未受影响的角色继续复用原 AgentEngine；
- 旧 AgentEngine 在没有 lease 后关闭；
- 不在正在运行的图上原地增加或删除工具。

### 3.5 权限只允许收紧

Plugin 文件只表达能力请求：

```text
managed/global boundary
  ∩ 父 Agent delegation envelope
  ∩ 目标 Agent Policy
  ∩ Plugin trust grant
  ∩ 当前 workspace/sandbox boundary
  = EffectiveExecutionPolicy
```

同一个有效能力视图必须同时控制：

1. 模型看到的 Tool Schema；
2. Agent 可以读取的 Skill；
3. Agent 可以使用的 MCP Tool；
4. 实际 Tool 执行前的 Policy Guard；
5. AgentEngineProfile 指纹；
6. AgentExecutionBinding 中记录的执行事实。

### 3.6 Agent 协作分成两层

#### 动态协作组

```text
main
├─ security-reviewer
├─ test-reviewer
└─ performance-reviewer
```

主 Agent 根据任务选择一个或多个 Agent。子 Agent 有独立上下文，完成后把结果返回调用方。没有共享任务表和成员互聊。

适合：

- 一次性代码搜索；
- 专项审查；
- 生成测试建议；
- Planner → Executor → Reviewer 的层级派发。

#### 固定 Agent Team

```text
security ─┐
          ├─→ synthesis
tests ────┘
```

Team 有显式任务依赖、并行上限、失败规则、取消传播和持久化终态。

适合：

- 多个成员长期并行；
- 明确的任务 DAG；
- 成员需要独立重试或取消；
- 进程恢复后继续未完成任务。

大多数场景先用动态 delegation。只有 delegation 无法满足时才创建 Team。

## 四、扩展机制的完整标准结构与完整示例

### 4.1 推荐标准

Harness 原生 Plugin 采用：

```text
Agent Plugins 1.0 portable core
        +
Harness client extension
```

Agent Plugins 标准部分负责 Skill 和 MCP；Harness client extension 负责 Agent、Policy、Command、Hook 和 Team。

本章描述当前已实现的 canonical 标准与明确非范围；ZC-141 规范追踪矩阵和 Task 的真实测试证据记录每项要求的实现位置、fixture、验证结果与剩余环境阻断。

下面暂用 `com.za38.harness` 作为示例 namespace。正式实施前必须替换为项目实际控制域名对应的稳定反向域名。

### 4.2 完整目录结构

```text
secure-review/
├── plugin.json
├── skills/
│   └── review-checklist/
│       ├── SKILL.md
│       └── references/
│           └── checklist.md
├── mcp.json
├── com.za38.harness/
│   ├── commands/
│   │   └── secure-review.md
│   ├── agents/
│   │   ├── security-reviewer.yaml
│   │   ├── test-reviewer.yaml
│   │   └── review-lead.yaml
│   ├── instructions/
│   │   ├── security-reviewer.md
│   │   ├── test-reviewer.md
│   │   └── review-lead.md
│   ├── policies/

│   ├── teams/

│   ├── hooks/

│   └── scripts/

```

目录职责：

| 路径 | 作用 |
| --- | --- |
| `plugin.json` | Plugin 身份、版本和 Harness extension 入口 |
| `skills/` | Agent Skills 标准目录 |
| `mcp.json` | Agent Plugins 1.0 MCP 配置 |
| `commands/` | 用户可调用的 Slash Command |
| `agents/` | AgentDefinition |
| `instructions/` | Agent Prompt 正文 |
| `policies/` | Agent 的权限上限 |
| `teams/` | TeamDefinition，引用 Agent ID |
| `hooks/` | 生命周期 Hook |
| `scripts/` | Hook 或 MCP 使用的包内脚本 |

### 4.3 `plugin.json`

```json
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
  "name": "secure-review",
  "version": "1.0.0",
  "description": "Security and test review with specialist agents",
  "license": "Apache-2.0",
  "extensions": {
    "com.za38.harness": {
      "schemaVersion": "1.0.0",
      "commands": "./com.za38.harness/commands",
      "agents": "./com.za38.harness/agents",
      "policies": "./com.za38.harness/policies",
      "teams": "./com.za38.harness/teams",
      "hooks": "./com.za38.harness/hooks/hooks.json"
    }
  }
}
```

这里没有把 Agent、Team 直接塞进 manifest。manifest 只声明组件目录，具体定义仍是独立、可校验的文件。

### 4.4 Skill

`skills/review-checklist/SKILL.md`：

```markdown
---
name: review-checklist
description: Review code changes for security, regressions, and missing tests.
license: Apache-2.0
metadata:
  version: "1.0.0"
allowed-tools: Read Glob Grep
---

Review only evidence visible in the repository.

1. Identify the changed behavior.
2. Check trust boundaries and untrusted input.
3. Check failure handling and rollback behavior.
4. Check whether tests cover success, failure, cancellation, and recovery.
5. Report file paths and evidence; do not invent findings.
```

`allowed-tools` 是作者声明的期望工具，不自动产生授权。

### 4.5 MCP

`mcp.json`：

```json
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/mcp.schema.json",
  "mcpServers": {
    "repo-index": {
      "type": "stdio",
      "command": "npx",
      "args": [
        "-y",
        "@example/repo-index-mcp",
        "--data",
        "${PLUGIN_DATA}/index"
      ],
      "cwd": "${PLUGIN_ROOT}",
      "env": {
        "MODE": "read-only"
      }
    }
  }
}
```

启用前必须展示将要运行的 `npx` 命令。企业环境可以禁止裸 PATH command，要求使用包内二进制或内部镜像。

### 4.6 Policy

`com.za38.harness/policies/read-only-review.yaml`：

```yaml
id: read-only-review

tools:
  allow:
    - read_file
    - glob
    - grep
  deny:
    - write_file
    - edit_file
    - execute

filesystem:
  read:
    - "**/*"
  write: []

shell:
  enabled: false

network:
  enabled: false

approval:
  mode: on-risk

delegation:
  enabled: false
```

Policy 是该角色允许使用的最大范围，最终还要与全局和父 Agent 权限取交集。

### 4.7 AgentDefinition

`com.za38.harness/agents/security-reviewer.yaml`：

```yaml
id: security-reviewer
description: 检查认证、授权、秘密、注入和信任边界
instructions: ../instructions/security-reviewer.md

model:
  strategy: inherit

policy: read-only-review

skills:
  - review-checklist

mcpServers:
  - repo-index

limits:
  maxTurns: 12
```

`com.za38.harness/instructions/security-reviewer.md`：

```markdown
你是安全审查员。

检查请求范围内的代码，只报告有文件证据、可执行修复的安全问题。
不要修改文件。每个问题必须包含文件路径、风险原因和建议修复。
```

`com.za38.harness/agents/test-reviewer.yaml`：

```yaml
id: test-reviewer
description: 检查回归风险、生命周期和测试覆盖
instructions: ../instructions/test-reviewer.md

model:
  strategy: inherit

policy: read-only-review

skills:
  - review-checklist

mcpServers:
  - repo-index

limits:
  maxTurns: 12
```

`com.za38.harness/instructions/test-reviewer.md`：

```markdown
你是测试审查员。

识别缺少测试覆盖的可观察行为，重点检查错误、取消、恢复和并发。
不要修改文件。输出按优先级排序的测试建议和仓库证据。
```

`com.za38.harness/agents/review-lead.yaml`：

```yaml
id: review-lead
description: 汇总多个审查员的结果并删除重复或无证据结论
instructions: ../instructions/review-lead.md

model:
  strategy: inherit

policy: read-only-review

limits:
  maxTurns: 8
```

`com.za38.harness/instructions/review-lead.md`：

```markdown
你是审查负责人。

合并安全和测试审查结果，删除重复、推测或没有文件证据的结论，
最终输出一份按优先级排序的简洁报告。
```

### 4.8 TeamDefinition

`com.za38.harness/teams/secure-review.yaml`：

```yaml
id: secure-review
description: 并行检查安全与测试，再统一汇总

tasks:
  - id: security
    agent: security-reviewer
    input: "{{request}}"

  - id: tests
    agent: test-reviewer
    input: "{{request}}"

  - id: synthesis
    agent: review-lead
    dependsOn:
      - security
      - tests
    input: |
      用户请求：
      {{request}}

      安全审查结果：
      {{tasks.security.result}}

      测试审查结果：
      {{tasks.tests.result}}

maxParallelism: 2
failurePolicy: continue-to-synthesis
```

这个 Team 的运行顺序是：

```text
用户请求
  ├─→ security-reviewer ─┐
  └─→ test-reviewer ─────┼─→ review-lead → 最终结果
```

TeamDefinition 只引用 Agent ID，不复制 Agent 的 Prompt、模型和 Policy。

### 4.9 Command

`com.za38.harness/commands/secure-review.md`：

```markdown
---
name: secure-review
description: 使用安全与测试 Team 审查指定路径或当前改动
argument-hint: [path-or-diff]
execution:
  type: team
  target: secure-review
---

审查 $ARGUMENTS，并为每个结论提供仓库文件证据。
```

安装后命令使用 Plugin namespace：

```text
/secure-review:secure-review packages/agent
```

### 5.2 Skill：HC-099 已接入 Plugin 启动快照

#### 当前已经支持

`packages/agent/harness_agent/skills.py` 已经支持：

- builtin、user、project、market 四类目录来源，以及 PluginManager 显式提供的 Plugin 来源；
- canonical ID；
- 不可变 Skill snapshot；
- `SKILL.md` 按需读取；
- 资源路径、symlink 和大小限制；
- `/.harness/skills/` 虚拟路径；
- enable、disable、install、remove；
- TUI Skill 选择器和显式调用。

#### 已实现方式

当前生产链路：

```text
ExtensionCatalogSnapshot
        ↓
PluginSkillSource[] → _parse_manifest(dialect)
        ↓
SkillRecord[] → SkillRegistry snapshot
        ↓
/.harness/skills/ 按需读取
```

具体修改：

1. `PluginManager` 从已捕获的 enabled catalog 生成 `PluginSkillSource[]`，`SkillRegistry` 不扫描 PluginStore。
2. `_parse_manifest()` 保留 Harness 严格模式，并增加 portable/Claude dialect。

4. Skill ID 为 `plugin/<source-id>/<plugin-name>/<skill-name>`。

6. `allowed-tools` 只保存为 `requested_tools`，不改变 Policy 或审批。
7. `/.harness/skills/` 改用最长 canonical 前缀解析，多段 Plugin ID 的正文和资源继续通过统一 `read_file` 读取。
8. 单个坏 Skill 只写入 diagnostics；同包其他有效 Skill 和 MCP 继续装配。

- Claude Plugin Skill 可原样加载；
- 一个坏 Skill 不影响同包其他 Skill 和 MCP；
- Plugin 更新后旧 execution 继续使用原快照。

### 5.3 MCP：HC-099（含 ZC-099）与 HC-141 统一连接快照

#### 当前已经支持

`packages/agent/harness_agent/extensions/mcp.py` 已经支持：

- `McpServerConfig`；
- stdio、HTTP、SSE 等配置；
- `McpConfigSnapshot`；
- `McpConnectionManager`；
- MCP Tool 转 LangChain Tool；
- `/mcp add`、`/mcp remove` 和状态查询；
- MCP snapshot digest 进入 AgentEngineProfile；
- 配置变化后重建连接。

#### 已实现方式

新增统一构建器：

```text
用户 TOML McpServerConfig
        +
PortableMcpAdapter(mcp.json)
        +
ClaudeMcpAdapter(.mcp.json / inline)
        ↓
namespaced McpServerDefinition[]
        ↓
McpConfigSnapshot
        ↓
McpConnectionManager
```

实现细节：

1. Server 名规范化为 `plugin__<source>__<plugin>__<server>`，因此不能覆盖普通用户 MCP。
2. Agent Plugins Adapter 读取 root `mcp.json`，用本地 closed schema 校验 stdio/streamable-http/SSE，
   只在 args/env/cwd 中展开 `${PLUGIN_ROOT}` 和 `${PLUGIN_DATA}`；URL/header 中的 placeholder 被拒绝。
3. Claude Adapter 读取 `.mcp.json`、manifest path 和 inline `mcpServers`，展开
   `${CLAUDE_PLUGIN_ROOT}`、`${CLAUDE_PLUGIN_DATA}`、`${CLAUDE_PROJECT_DIR}`，保留 Claude 自有 timeout 语义。
4. package digest 写入 `source_fingerprint`，Plugin 内容变化会改变 MCP/AgentEngine fingerprint。
5. Plugin stdio 子进程使用最小环境变量 allowlist，不继承模型密钥等任意 Host 环境。
6. 每个 Server 独立转换和连接；坏 Server、unsupported transport 或连接/认证失败产生独立 diagnostic/status，
   不阻断同包 Skill 和其他 Server。
7. Host 使用同一 catalog 同时构建 Skill 与 MCP；用户 `/mcp add/remove` 重建连接时重新合并固定的 Plugin MCP，不会将其丢失。
8. Plugin HTTP/SSE 使用 `follow_redirects=False` 的 client factory，Claude 与 portable 仍各自保留
   placeholder、environment 和 timeout 语义；MCP add/remove 已使用 generation owner/borrower 和定向 draining。

#### 仍未实现

- Plugin MCP OAuth 与凭据 UI（ZC-141 明确非范围）；
- WebSocket transport（Agent Plugins 1.0 portable core 明确不支持）；
- 运行中的 Plugin reload（当前管理契约在下一次 Host 启动生效）；
- 删除 `McpConnectionManager` 的测试兼容 sequence 构造入口。

#### 验证

- 一个 Plugin MCP 启动失败不影响其他 Server 和 Skill；
- placeholder 不递归展开且不能逃逸 Plugin root/data；
- Plugin MCP 看不到模型密钥；
- Tool namespace 不冲突；
- disable/update 后新 execution 不再取得旧工具；
- Host 退出不残留 stdio 子进程。

ZC-141 的当前 140 项 focused/expanded 测试已覆盖上述 portable core 与 Plugin runtime 边界；OAuth UI、
WebSocket 和运行时 reload 不作为本任务的失败项。

### 5.4 Agent：portable 与 Claude Agent 已进入生产执行

#### 当前已经支持

`agent_catalog.py` 和 Plugin Adapter 当前已经具备：

- `AgentDefinition`；
- `ExecutionPolicyDefinition`；
- Policy 交集；
- 模型 Profile 引用校验；
- Prompt、Schema、路径、大小和 symlink 校验；
- 不可变 catalog 摘要；
- portable Harness extension 的 YAML/JSON Agent 与 Policy；
- Claude `agents/*.md` front matter、Prompt 正文和显式 Tool 映射；
- `model: inherit`、显式 ModelProfile，以及 sonnet/opus/haiku 的安全继承回退；
- Plugin Manager 从同一个 enabled catalog 生成显式 Agent source。
- HC-092 已实现 Tool、MCP、Skill、文件读写、Shell、网络和 delegation 的只收紧交集；
- 同一个 `EffectiveCapabilityView` 同时裁剪模型 Tool schema、Skill/MCP 子集和实际 Tool 执行；
- 能力视图及有效 Policy 指纹已经进入 `ResolvedAgentSpec` 和 AgentEngineProfile。

#### 生产链路

```text
ExtensionCatalogSnapshot
  → PluginManager.agent_sources()
  → AgentCatalog(Builtin + Plugin AgentDefinition + ExecutionPolicy)
  → resolve_plugin_agent_spec(parent envelope) / resolve_builtin_child_view()
  → ResolvedAgentSpec
  → DelegationTarget(mode=Managed/Inline)
  → AgentEnginePool / Inline child graph
```

主 Agent 构图时把当前 active Agent ID 加入 delegation allow-list。模型仍只通过 `task`
选择 Agent ID 和任务文本，不能从 Prompt 指定模型、Policy、执行模式或工具。Managed adapter
用 child execution ID 生成独立 checkpoint namespace，运行结束后释放 run/engine/MCP lease。

Claude Tool 只使用明确映射；未知名称产生 `CLAUDE_TOOL_UNMAPPED` 并停用该 Agent，不猜测相近
Harness Tool。`permissionMode` 不是授权入口（Plugin 定义不能放宽审批），`tools` 是目标角色上限，最终还要与父 Agent 和
Host 硬边界取交集。Plugin 子代理需要人工 Interaction 时保持 fail closed。
内置角色 `general-purpose` 和 `explore` 统一进入 `AgentCatalog`（排在 Plugin 前面），`general-purpose` 继承父 MCP/Skill 与工具集并在父 default 下内部按 auto-edit 放宽审批，`explore` 严格限制为 5 个只读工具且启动免审批。
Plugin Agent 只取得其 `skills` 与 `mcpServers` 显式声明的组件子集；缺省是空集合，不会继承父
Agent 的全部 Plugin Skill 或用户 MCP。子集及其受限 MCP snapshot digest 会进入 Profile。

#### 仍未实现

- Claude `effort`、background、memory 的完整运行语义；
- 通用用户自定义模型 alias 表；当前同名 Profile 优先，标准 Claude 家族名缺少同名 Profile 时继承父模型；
- Plugin 运行中热加载；管理操作仍在下一次 Host 启动生效。

Agent 列表/详情已经通过 `agents.list`、`agents.inspect` 和 `/agents` 交付。响应只返回
ID、名称、描述、来源、active 状态和诊断，不把 Prompt、绝对路径或 Plugin 正文发给 CLI。

#### 验证

- 同一个 ResolvedAgentSpec 跨 Thread 复用 AgentEngine；
- 改一个角色只失效该角色 AgentEngine；
- Agent 的模型、Policy、Prompt 或能力子集变化会改变 Profile；
- Thread、Run、Team 组合和任务正文不进入 Profile；
- 只读 Agent 看不到也无法伪造写工具调用。

### 5.5 Delegation：HC-096 已建立受控 Inline/Managed seam

#### 当前状态

生产图仍向模型暴露兼容 `task` 工具，但调用已先进入 `AgentDelegator`。内置
`general-purpose` 作为可信短期 worker 使用 Inline；需要独立模型、Policy、并行、恢复或
Plugin 边界的角色由 Managed target 使用 AgentEnginePool。

#### 修改方式

已实现：

```text
AgentDelegator.execute(DelegateAgent)
  → 校验 target Agent 与父级 delegation 边界
  → 接受 child execution
  → 系统选择 Inline / Managed
  → Managed 才 AgentEnginePool.acquire()
  → 保存终态
  → 返回结构化结果并释放 lease
```

`DelegateAgent` 携带父 execution、target、任务、timeout、父取消 token 和幂等键；不能携带
执行模式、任意模型或扩大后的工具集合。`DelegationTarget` 由 Host 注册并固定模式、模型、
Policy、definition 和 Engine Profile 事实。父 token、timeout 或 runner 异常都会终结 child，
Managed adapter 的 run/engine/resource lease 在 `finally` 中释放。

#### 验证

- 相同 Managed Profile 复用同一 AgentEngine，Inline 不创建独立 lease；
- 父窄子宽时子 Agent 权限被收紧；
- 父 Run 取消会取消所有排队与执行中的 child execution；
- child 并发硬上限为 4，超额自动排队并在前序完成后执行；
- child 超时、失败和取消都会在 finally 释放并发槽位与资源。

### 5.6 Agent Team：HC-097 已建立固定 DAG 协调层

#### 当前已经支持

已经建立：

```text
TeamCoordinator
├─ TeamDefinition
├─ TeamRun
├─ TeamTask[]
├─ maxParallelism / budget
├─ failure / cancellation policy
└─ terminal state
        ↓
AgentDelegator
        ↓
AgentEnginePool
```

实现规则：

1. TeamCoordinator 不构建和缓存 AgentEngine。
2. 每个 TeamTask 通过 AgentDelegator 启动 Agent。
3. 任务依赖必须是 DAG，循环在运行前拒绝。
4. Team 状态只保存 task 与 execution 引用。
5. Agent 消息、PromptEpoch 和 checkpoint 仍由各 execution 保存。
6. 首版不增加自由 mailbox。
7. 同 workspace 的写任务必须经过 HC-094 已交付的 Host 共享工具锁串行执行；稳定资源域出现后再演进 scheduler。
8. 父 Run 取消时，Team、Task 和成员 execution 必须一起收敛。

`TeamDefinition` 在受理时使用 Kahn 算法拒绝循环；`TeamCoordinator` 支持
`fail-fast`、`continue` 和 `continue-to-synthesis`。只读任务在 Team 与父 Policy 的较小
并行上限内执行，写任务在 Team 层互斥，实际文件/MCP/Shell Tool 仍经过 Host 的共享读写锁。
恢复时已完成任务不会重跑；结果未知的只读任务可以用稳定幂等键重试，结果未知的写任务以
`TEAM_WRITE_OUTCOME_UNKNOWN` fail closed，避免重复写入。

portable Harness extension 的 `teams/*.yaml|json` 已由 `PluginManager.team_definitions()` 转成
同一个 TeamDefinition；坏 Team 只产生隔离诊断。
`generate_fanout_team()` 还可以从已校验 AgentDefinition、显式 lead 和 worker 列表生成
“并行分析 → 汇总”的 TeamDefinition 预览；它不会从自由 Markdown 猜测角色关系。

#### 产品入口

HC-101 已把协调层接到产品入口：

- `teams.list`、`teams.inspect` 返回固定 Team、Host 生命周期内的生成预览和持久化运行状态；
- `teams.generate` 只接受已注册的 lead、worker、并行度和稳定 Team ID，由 Host 生成
  fanout-then-synthesize DAG，客户端不能上传任意 `TeamDefinition`；
- `teams.run` 异步受理，成员仍逐个经过 `AgentDelegator` 和 Managed `AgentEngine`；
- `teams.cancel` 只取消目标 Team Run；
- `/teams` 提供列表、详情、生成、启动、状态查询和取消。

生成预览只存在于当前 Host 生命周期；已经启动的 Team Run 写入项目指纹隔离的 SQLite，
Host 重启后仍可通过 `teams.inspect` 查询。当前仍未实现统一 token/cost budget，也按设计不
实现自由 mailbox。

#### 根据 Agent 生成 Team

Plugin 安装后可以自动生成动态 Delegation Group：

```text
plugin agents
  → coordinator = main
  → allowedAgents = 所有 active AgentDefinition
```

固定 Team 不从自由 Markdown 自动猜测。它通过以下方式生成：

```text
/teams generate secure-review review-lead security-reviewer,test-reviewer 2
/teams show secure-review
/teams run secure-review 检查认证实现、测试覆盖和安全边界
/teams status <run-id>
/teams cancel <run-id>
```

`generate` 返回 DAG 预览，用户查看后再显式执行 `run`；CLI 不会仅因打开或列出 Team 就启动
成员进程。

#### 验证

- 只读成员安全并行；
- 写成员服从 workspace scheduler；
- 依赖完成后才解锁后续任务；
- 循环依赖拒绝；
- 成员失败按 failurePolicy 处理；
- 恢复不会重复执行已经完成的写任务；
- Team 只有一个终态。

CLI `CommandRegistry` 已支持：

### 5.8 Hook、LSP 和 Monitor：HC-102 已交付受控运行子集

#### Hook

当前已把 Claude command Hook 接到 Tool 生命周期：

```text
PreToolUse / PostToolUse / PostToolUseFailure
  → Claude 兼容 input JSON
  → HookRunner
  → exit code 与 stdout JSON 解释
  → allow / deny / diagnostic
```

支持 shell form 和 `command + args` exec form；`${CLAUDE_PLUGIN_ROOT}`、
`${CLAUDE_PLUGIN_DATA}`、`${CLAUDE_PROJECT_DIR}` 在加载时解析。`PreToolUse` 的 exit 2 或
`permissionDecision=deny` 会阻止工具调用；普通非零退出只产生诊断。stdin/stdout/stderr、
超时和进程关闭都有上限，子进程只得到最小环境，不继承模型密钥。

当前不支持 prompt、agent、HTTP、MCP-tool Hook，也不支持 command Hook 的其他 Claude 事件。
这些子项在 compatibility report 中显示 `unsupported`，不会被静默执行。

#### LSP

当前使用 Host-owned `PluginLspManager`：

- Plugin 只声明 command、args、语言映射和初始化参数；
- 首次调用 Harness `lsp` 工具时按文件扩展懒启动 stdio server；
- 已接入 initialize、didOpen、definition、references、hover 和 diagnostics；
- 文件必须位于当前 workspace，多个 Plugin 不能争用同一扩展；
- Host 负责超时、LSP framing、shutdown/exit 和子进程清理；
- socket transport 当前明确为 `unsupported`。

#### Monitor

Host-owned `MonitorManager` 已实现：

- 每个 Monitor 是受控长期子进程；
- stdout 按行进入有界 ring buffer，再作为“明确不可信的 Monitor 数据”注入模型上下文；
- 单行、总行数和进程生命周期均有上限；
- Host close 时终止整个子进程组；
- Plugin 只有在安装后显式确认包含 `process` 的 capability fingerprint 并启用，Monitor 才会启动。

首版不会自动重启 Monitor，也不会把 stdout 伪装成可信系统指令。

### 5.9 Plugin 安装、存储和信任：HC-098 已交付第一阶段

新增：

```text

├── model.py

├── manager.py
```

存储结构：

```text

```

当前已经实现：

- copy-on-install；
- store 版本安装后只读；
- 内容寻址 digest；
- 目录与 zip 使用私有 staging，安装使用 digest 路径和原子 rename；
- registry 有 revision 和文件锁；
- registry 只使用当前 canonical v2 record；无 registry 的新 Host 不创建 Plugin 目录或
  `registry.lock`；未发布期间旧开发构建的 v1 registry 按版本或结构无效失败关闭、删除重建
  （v1→v2 迁移机制已于 2026-08-14 移除，见 ZC-141 设计文档历史记录）；
- 默认卸载保留 data；
- `--purge-data` 单独确认；
- 拒绝 symlink、hardlink、device、绝对路径、`..` 和 archive bomb。
- Agent Plugins 1.0、Claude manifest、Claude manifestless 和双 manifest 自动识别；
- 逐组件 `supported/adapted/unsupported/invalid` 报告；
- install 默认 disabled，enable 必须确认当前 capability fingerprint；
- 启用前重新计算 store digest，registry 损坏时 fail closed。

当前 trust 记录绑定：

```text

+ plugin identity
+ package digest
+ capability fingerprint
+ user scope
```

重新安装任何新 package 都回到 disabled；新增 MCP、Hook、网络、可执行命令、Agent 或 worktree
请求会改变 capability fingerprint。publisher signature、managed scope/policy revision、依赖求解、
Git/HTTP/marketplace 来源和孤儿 store GC 尚未实现。

### 6.1 Claude Code 作为一级兼容目标

Harness 不能只兼容旧版 Skill、MCP 和 Agent，然后宣称“兼容 Claude Plugin”。必须提供组件级 compatibility report。

### 6.2 “直接安装”的定义

用户可以执行：

```bash
harness plugins validate ./my-claude-plugin --format auto
harness plugins install ./my-claude-plugin
```

或者：

```bash
harness plugins install ./my-claude-plugin.zip
```

原包不需要：

- 新增 Harness manifest；
- 移动目录；
- 改写 Agent Markdown；
- 把 `.mcp.json` 转成 TOML；
- 复制 Skill 到 `~/.harness/skills`；
- 重新打包。

Harness 自动识别 `.claude-plugin/plugin.json`，由 `ClaudeCodePluginAdapter` 完成转换。

Claude 当前允许省略 manifest。对于 manifestless Plugin：

- 显式 `--format claude-code` 时按 Claude 默认目录识别；
- `--format auto` 只在目录具有明确 Claude 组件且没有冲突 manifest 时识别；
- Plugin 名从安装目录派生；
- 不能因为没有 manifest 就退化成只加载 Skill。

### 6.3 Claude Plugin 结构映射

| Claude 路径/字段 | Harness 映射 | 当前状态 |
| --- | --- | --- |
| `.claude-plugin/plugin.json` | InstalledPlugin metadata 和 component paths | supported |
| `skills/<name>/SKILL.md` | SkillDefinition | supported |
| `commands/*.md` | CommandDefinition；内部按 command-skill 执行 | supported |
| `agents/*.md` | AgentDefinition | supported |
| `workflows` | 组件库存 | unsupported，不执行 |
| `hooks/hooks.json` / inline hooks | HookDefinition | adapted，仅三个 Tool 事件的 command handler |
| `.mcp.json` / inline `mcpServers` | McpServerDefinition | supported |
| `.lsp.json` / inline `lspServers` | LspServerDefinition | adapted，仅 stdio |
| `monitors/monitors.json` | MonitorDefinition | adapted，有界后台进程 |
| `settings.json` 的 `agent` | 组件库存 | unsupported |
| `outputStyles` | 组件库存 | unsupported |
| `themes` | 组件库存 | unsupported |
| `bin/` | 组件库存 | unsupported；不会加入 PATH |
| `dependencies` | 组件库存 | unsupported；尚无依赖求解 |
| `userConfig` | Plugin 用户配置声明 | unsupported，只报告 |
| `channels` | ChannelDefinition 库存 | unsupported，不建立外部连接 |
| `defaultEnabled` | metadata | recognized；Harness 仍强制 install 后 disabled |

### 6.4 Claude Skill 兼容

Claude Skill 常用字段包括：

- `name`；
- `description`；
- `when_to_use`；
- `argument-hint`；
- `disable-model-invocation`；
- `user-invocable`；
- `allowed-tools`；
- `disallowed-tools`；
- `context`；
- `agent`。

Adapter 负责字段语义转换：

```text
disable-model-invocation → modelInvocable = false
user-invocable          → userInvocable
argument-hint           → argumentHint
allowed-tools           → requested preapproval，不是授权
disallowed-tools        → capability deny
$ARGUMENTS              → Harness command/skill argument
${CLAUDE_SKILL_DIR}     → 已校验 Skill root
${CLAUDE_PROJECT_DIR}   → workspace root
```

Claude 的 `allowed-tools` 可以请求“本轮免重复审批”，但只有用户签发对应 trust grant 后才能生效；全局和 Agent Policy 仍可拒绝。

### 6.5 Claude Agent 兼容

Claude Agent Markdown：

```markdown
---
name: security-reviewer
description: Reviews authentication and trust boundaries
tools: Read, Glob, Grep
model: inherit
skills:
  - review-checklist
maxTurns: 12
---

You are a security reviewer...
```

字段映射：

| Claude 字段 | Harness 处理 |
| --- | --- |
| `name`、`description`、body | Agent ID、用途和 Prompt |
| `tools` | 最大请求工具集合，再与 EffectivePolicy 取交集 |
| `disallowedTools` | 永远作为 deny |
| `model: inherit` | 继承父级实际 ModelProfile |
| `model: sonnet/opus/haiku` | 优先使用同名 ModelProfile；未配置时安全继承父实际 Profile |
| 其他 `model` 值 | 必须精确引用 Harness ModelProfile，否则该 Agent inactive |
| `effort` | 当前解析但不改变模型参数，兼容报告/诊断不得声称已生效 |
| `maxTurns` | 已进入 AgentDefinition 与 Profile 指纹；运行时 turn budget 待预算层接入 |
| `skills` | 同一 Plugin snapshot 内的 canonical Skill ID |
| `memory` | execution-scoped memory policy |
| `background` | 受父 Run 管理的后台 child execution |
| `isolation: worktree` | worktree execution environment |
| `color` | TUI 展示元数据 |
| `permissionMode` | Plugin Agent 中不作为权限入口 |
| agent-local `hooks`、`mcpServers` | Claude 对 Plugin-shipped Agent 本身也限制这些字段；Harness 给出诊断，不借此扩权 |

Claude Tool 名使用显式映射：

```text
Read  → read_file
Glob  → glob
Grep  → grep
Write → write_file
Edit  → edit_file
Bash  → execute
Agent → delegate_agent
```

未知 Tool 不模糊猜测。Adapter 返回 `CLAUDE_TOOL_UNMAPPED`，该 Agent 保持 inactive，直到管理员提供明确映射。

### 6.6 Claude MCP 兼容

HC-099 当前支持：

- `.mcp.json`；
- manifest inline `mcpServers`；
- stdio、HTTP 和 SSE；
- `${CLAUDE_PLUGIN_ROOT}`；
- `${CLAUDE_PLUGIN_DATA}`；
- `${CLAUDE_PROJECT_DIR}`；
- Plugin/Server/tool namespace；
- enable、disable 和连接诊断；启停在下一次 Host 启动生效。

Claude Adapter 转换后仍进入统一 `McpConfigSnapshot`，没有建立 `ClaudeMcpManager`。WebSocket、
OAuth/凭据 UI 和运行中 reload 尚未实现，兼容报告不能把这些能力标为已生效。

### 6.7 Claude Hook 兼容

Claude 当前 Hook 事件包括但不限于：

- `SessionStart`、`SessionEnd`；
- `UserPromptSubmit`、`UserPromptExpansion`；
- `PreToolUse`、`PermissionRequest`、`PostToolUse`、`PostToolUseFailure`；
- `SubagentStart`、`SubagentStop`；
- `TaskCreated`、`TaskCompleted`；
- `TeammateIdle`；
- `PreCompact`、`PostCompact`；
- `WorktreeCreate`、`WorktreeRemove`；
- `Notification`、`ConfigChange`、`FileChanged`。

Claude Hook handler 支持 command、HTTP、MCP tool、prompt 和 agent。

Harness 当前已经交付的兼容链路是：

```text
Harness Tool lifecycle event
  → ClaudeEventAdapter 生成 Claude 兼容 stdin JSON
  → HookRunner 执行 command handler
  → ClaudeResultAdapter 解释 stdout JSON、stderr、exit code 和 timeout
  → 转成 Harness allow / deny / diagnostic
```

具体支持矩阵：

| Claude Hook 能力 | 当前状态 | 说明 |
| --- | --- | --- |
| `PreToolUse` command | adapted | exit 2 或 JSON deny 阻断 Tool |
| `PostToolUse` command | adapted | Tool 成功后运行并记录诊断 |
| `PostToolUseFailure` command | adapted | Tool 失败后运行并记录诊断 |
| shell form、exec form | adapted | exec form 使用 `args`，不经 shell 拼接 |
| prompt、agent、HTTP、MCP tool handler | unsupported | 验证报告逐项显示，不执行 |
| 其他 Hook event | unsupported | 尚未建立对应 Harness 生命周期事件 |
| `updatedInput`、`ask`、`defer` | unsupported | fail closed，不假装兼容 |

实现不只是把 Hook command 扔给 shell：它解释 `PreToolUse` 拒绝、exit code、JSON 输出，
限制输入输出与超时，并在 Host close 时终止子进程。这样“安装成功”和“组件实际生效”才不会
混为一谈。

### 6.8 Claude Agent Teams 兼容

Claude Agent Teams 是运行时功能，不是 Plugin 中可以预先分发的固定 team config。官方运行时 team 文件位于用户目录，由 Claude 会话生成和维护。

因此 Harness 的正确兼容方式是：

1. 直接导入 Claude Plugin 的 `agents/*.md`。
2. 自动生成一个 Delegation Group，使主 Agent 可以派发这些角色。
3. 用户可以用自然语言要求创建 Team。
4. Harness 根据 AgentDefinition 生成 TeamDefinition 预览。
5. 用户确认后由 TeamCoordinator 运行。
6. 不导入 `~/.claude/teams/*` 和 `~/.claude/tasks/*` 运行状态。

Claude Agent Team 的体验映射：

| Claude Team 能力 | Harness 对应能力 |
| --- | --- |
| lead | 根 Agent 或 Team 入口任务 |
| teammate 独立上下文 | 独立 Agent execution namespace |
| shared task list | TeamTask 持久化 |
| task dependencies | TeamDefinition DAG |
| teammate model | ResolvedAgentSpec 模型绑定 |
| teammate tools | EffectiveCapabilityView |
| member cancel/retry | TeamCoordinator 状态机 |
| team status | TUI `/teams` |
| mailbox | 首版不实现；先使用结构化 task input/result |

如果后续真实场景证明成员必须直接互聊，再设计 mailbox。不能为了表面兼容先引入第二套 Thread 和文件轮询。

### 6.9 Compatibility report

每个发现的组件必须有明确状态：

```text
supported
adapted
unsupported
invalid
```

示例：

```text
Format: claude-code-plugin
Adapter baseline: 2026-07-30
Compatibility: partially-compatible

Skills:   3 supported
Commands: 2 supported
Agents:   4 supported
MCP:      1 supported
Hooks:    2 adapted
LSP:      1 unsupported

Blocking issue:
  CLAUDE_LSP_RUNTIME_UNAVAILABLE
```

只要存在 `unsupported`，默认不能显示 `fully-compatible`。Plugin 可以安装为 inactive，但不能静默声称全部生效。

### 6.10 双 manifest Plugin

一个包可以同时包含：

```text
plugin.json
.claude-plugin/plugin.json
```

处理规则：

1. Agent Plugins manifest 决定 portable Skill/MCP。
2. Claude Adapter 补充 Agent、Command、Hook、LSP 等 Claude 私有组件。
3. 同一路径组件只加载一次。
4. 两份 manifest 的身份或版本冲突时拒绝。
5. 不通过优先级猜测作者意图。

## 八、总结

最终方案可以概括为：

```text
一个 Plugin 产品概念
  +
Agent Plugins 1.0 通用基础
  +
Claude Code 一级兼容 Adapter
  +
一个 ExtensionCatalogSnapshot
  +
一个 ResolvedAgentSpec 执行事实
  +
AgentDelegator 和 TeamCoordinator 两层协作
```

当前代码不是从零开始：

- Skill 运行、MCP 连接、AgentEnginePool、RunCoordinator 和 ThreadPersistence 已经具备；
- Agent/Policy 类型和动态 Command 类型已有基础。

当前已经完成：

- Plugin 安装、信任、不可变 catalog 和多格式 Adapter；
- Plugin Skill、MCP、Command、portable/Claude Agent；
- 角色级 ResolvedAgentSpec、只收紧 Policy 和 Managed delegation；
- 固定 TeamDefinition、Plugin Team Adapter、TeamCoordinator 和 `/agents`、`/teams` 产品入口；
- Claude command Hook、stdio LSP 与有界 Monitor 运行层。

仍缺少的是：

- prompt/agent/HTTP/MCP-tool Hook、其他 Hook 事件和 socket LSP；
- settings、output styles、themes、dependencies、channels、workflows 等 Claude 扩展组件；
- Team 统一 token/cost budget；
- Git/HTTP/marketplace 来源、依赖求解与运行中 Plugin reload。

因此当前版本已经可以安全安装 Claude Code Plugin，并让其 Skill、MCP、Command 和
`agents/*.md`，以及受支持的 command Hook、stdio LSP 和 Monitor 在下一次 Host 启动进入统一
运行快照。不能把这一结论扩大为 Claude 的全部 Hook handler、socket LSP 和实验组件都已
生效；compatibility report 会按子项明确标为 `adapted`、`unsupported` 或 `invalid`。

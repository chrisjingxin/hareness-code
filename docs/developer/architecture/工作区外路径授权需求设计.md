# 工作区外路径访问授权需求设计

- 状态：方向已定（开放问题已于 2026-08-05 决策，见第 7 节），待拆实施任务
- 日期：2026-08-05
- 方向决策：结合 claude-code 与 qwen-code 的五种审批模式改造工作区外访问——不再一律硬拒绝，改为按模式弹窗询问或放行；用户授权时把**该路径所在的目录加入白名单**，后续同目录访问免弹窗。

## 1. 背景与问题

Harness Code 目前对工作区（`--cwd` 指定的项目根目录）外的文件访问采取"硬边界"策略，由 `packages/agent/harness_agent/policy/workspace_boundary.py` 的 `WorkspaceBoundaryMiddleware` 实现：

1. **工作区外读取/搜索（`read_file`、`ls`、`glob`、`grep`、`lsp`）在所有审批模式下硬拒绝**，包括 `yolo`，没有任何交互手段可以放行。用户读 `~/.harness/config.toml`、相邻仓库、共享库目录等合法场景会被直接卡死，模型只能收到错误 ToolMessage 后换路径。
2. **工作区外写入（`write_file`/`edit_file`/`delete_file`/`delete`）在 `default`/`auto-edit`/`auto` 模式会弹审批框**，但审批通过后生成的"永久允许"规则是**工具级通配**：`_generate_permission_rule`（`packages/agent/harness_agent/host/run_coordinator.py`）对文件类工具生成 `resource="*"` 的 allow 规则。这等于批准一次越界写入后，该工具对**任意路径**的后续调用都免弹窗——授权粒度过宽，实际上拆掉了整条写边界。
3. **没有任何"额外工作目录/路径白名单"机制**：配置中没有允许路径列表字段，没有 `/add-dir` 类命令，用户无法声明式地授权工作区外目录。

问题本质：边界只有"全禁"和"全放（工具通配）"两个极端，缺少竞品普遍具备的**目录级渐进授权**能力。

## 2. 竞品做法调研

### 2.1 五模式对照（本次改造的直接依据）

本项目与 qwen-code 同为五种审批模式（`plan / default / auto-edit / auto / yolo`）；claude-code 的模式集合不同但语义可对应。三家在工作区外读写上的行为：

| 本项目模式 | qwen-code 同名模式 | claude-code 对应模式 | qwen 越界读 | qwen 越界写 | claude 越界读 | claude 越界写 |
| --- | --- | --- | --- | --- | --- | --- |
| `plan` | plan | plan | 弹窗（读属 info 类不拦） | 拦截 | 弹窗 | 弹窗 |
| `default` | default | default | 弹窗 | 弹窗 | 弹窗 | 弹窗 |
| `auto-edit` | auto-edit | acceptEdits | 自动允许 | **自动允许** | 弹窗 | **仍弹窗**（仅工作区内写免弹窗） |
| `auto` | auto | （内部 auto 分类器） | 自动允许（读工具安全白名单） | LLM 分类器裁决 | 分类器裁决 | 分类器裁决 |
| `yolo` | yolo | bypassPermissions | 自动允许 | 自动允许 | 自动允许（敏感文件仍弹窗） | 自动允许（敏感文件仍弹窗） |

两家共同的基线：**越界访问的默认动作是"问"而不是"禁"**；差异主要在 auto-edit 对越界写的尺度（qwen 放行、claude 坚持弹窗）。

### 2.2 qwen-code 的授权落库方式（白名单原型）

- 路径校验带 `allowExternalPaths` 开关：越界路径不抛错，交给权限决策链（工具默认权限 → settings 规则 → 审批模式）。
- 弹窗选项区分作用域：`Yes, allow once` / `Always allow <动作> in this project`（写项目 settings.json）/ `Always allow <动作> for this user`（写用户 settings.json）。
- **"Always allow" 生成目录级规则**：取被访问文件所在目录，生成形如 `Read(//D:/data/**)`、`Edit(//tmp/abc/**)` 的规则，持久化后立即生效。这就是"把工作区外路径加入白名单"。
- 另有 `/directory` 命令、`--include-directories` 等声明式扩展入口（本期不实现，见第 7 节）。

### 2.3 claude-code 的授权落库方式（对照）

- 越界读会话授权生成 `Read(//dir/**)` 规则；越界写会话授权 = 切 acceptEdits + 把目录加入工作目录集合。
- 永久授权经 `/add-dir` 的 remember 选项写入 settings 的 `permissions.additionalDirectories`。
- `bypassPermissions` 全放行，但敏感文件（`.git`、shell rc、settings）仍强制弹窗——与本项目"敏感路径免疫 bypass"思路一致。
- grok-build 无路径加白交互（读全放行、写按模式），不作为本次对齐对象。

## 3. 目标与非目标

**目标**

1. 工作区外的读写访问按审批模式分流：可弹窗授权，授权结果是**目录级白名单**，而不是工具级通配。
2. 白名单支持会话级（进程内存）与持久级（project 层 `.harness/settings.json`）两种作用域，复用现有规则评估与存储机制。
3. 修复"永久允许生成 `resource="*"` 通配规则"的粒度过宽问题。
4. 保持现有硬保护不放松：deny 规则绝对优先、敏感路径强制弹窗、符号链接/UNC/`..` 防护、子 Agent 越界硬拒绝。

**非目标**

- 不引入 OS 级沙箱（Landlock/Docker 等），工作区边界仍是应用层 containment。
- 不改动 `execute`/MCP 工具的路径策略（由各自机制负责）。
- 不做声明式扩展工作区（`includeDirectories`/`--add-dir`/`/directory`），已决策为后续任务（Q5）。

## 4. 总体方案

### 4.1 核心概念

**路径白名单**：一组目录级 allow 权限规则，记录"该目录下的文件访问已被用户授权"。载体是现有 `PermissionRule`（tool + resource + effect + scope），resource 从通配 `*` 改为**被访问文件所在目录**的路径模式（如 `D:/data/*`，Q4 已决策）。不新造"额外工作目录集合"数据结构，边界判定与审批预检都消费同一套规则，保持单一 canonical 路径。

白名单不改变"工作区"的定义：工作区内操作仍走原有虚拟后端与免弹窗逻辑；白名单只影响**越界访问的去向**——命中白名单的越界访问由边界中间件直接对真实路径执行（复用现有越界直写通道，新增对称的直读通道），未命中的按模式弹窗或放行。

### 4.2 行为矩阵（改造后，已决策）

| 模式 | 工作区外读/搜索 | 工作区外写 | 决策来源 |
| --- | --- | --- | --- |
| `plan` | **弹窗询问**（Q1；命中白名单直接执行） | 硬拒绝（维持现状；写入先被计划模式白名单拦截，不产生弹窗） | 对齐 qwen：plan 允许读证据 |
| `default` | **弹窗询问**（命中白名单直接执行） | 弹窗询问（命中白名单直接执行） | qwen / claude 一致 |
| `auto-edit` | **自动允许** | **弹窗询问**（Q2；不采 qwen 的自动放行，对齐 claude acceptEdits 的保守尺度） | claude acceptEdits |
| `auto` | **自动允许**（读工具本就在安全白名单） | 进入现有四层过滤器/分类器裁决（维持现状） | qwen auto |
| `yolo` | **自动允许**（Q3；解决"yolo 可越界写却不能越界读"的语义不自洽） | 直接写（维持现状） | qwen yolo / claude bypass |

所有模式下：deny 规则命中 → 硬拒绝不弹窗；敏感路径（`.git`、`.bashrc` 等）→ 即使命中白名单也强制弹窗（写）；`apply_patch` 越界维持硬拒绝。

### 4.3 授权流程（输入 → 判断 → 执行 → 输出）

以 `default` 模式下模型请求读取工作区外文件为例（写流程同理，plan 模式见备注）：

1. **输入**：工具调用（工具名 + 绝对路径），到达 HITL 组合预检（`runtime/agent.py` 的 `_make_approval_preflight`）。
2. **判断**：
   - 路径在工作区内 → 按原流程（读工具不进审批，直接执行）。
   - 路径越界 → 按模式与规则裁决：
     - `auto-edit`/`auto`/`yolo` 的越界读 → 不弹窗，直接放行；
     - deny 规则命中 → 不弹窗，执行层硬拒绝；
     - allow 规则命中（白名单目录）→ 不弹窗，执行层直读/直写；敏感路径写例外仍弹窗；
     - 其余（`plan`/`default` 越界读、`default`/`auto-edit` 越界写等）→ 弹窗，审批卡片描述中展示完整目标路径。
3. **执行**（用户选择后）：
   - `approve_once`：本次放行，不记录规则；
   - `approve_thread`：生成目录级规则存入会话内存；
   - `approve_always`：生成目录级规则写入 project 层 `.harness/settings.json`；
   - 放行后本次调用由边界中间件直接对真实路径执行（读走新增的直读通道，写沿用现有直写通道）。
4. **输出**：工具结果返回模型；后续访问同一白名单目录的文件时，预检直接放行，不再弹窗。

备注：`plan` 模式下 HITL 仅为越界读工具开启（见 4.6），写入类工具不进入审批集合，仍由 `PlanModeMiddleware` 先拒绝，不会产生"批准了也执行不了"的假审批。

### 4.4 白名单规则的生成与匹配

**生成**（修改 `_generate_permission_rule`）：

- 文件类工具（读与写）：resource = 目标文件**所在目录**的路径模式。例如批准读取 `D:/data/config/app.toml` 生成 `{"tool": "read_file", "resource": "D:/data/config/*", "effect": "allow"}`。
- `execute`/`monitor`：维持按命令首词收敛，不变。

**匹配**（修改 `_extract_resource`）：

- 读工具（`read_file`/`ls`/`glob`/`grep`/`lsp`）目前返回 `*`，改为返回规范化绝对路径（`glob`/`grep` 返回显式搜索根目录；省略 path 时默认工作区内，不涉及越界）。
- 写工具已返回 `file_path`，补充路径规范化（resolve 符号链接、统一分隔符），保证与规则生成侧使用同一路径形态。
- `fnmatch` 的 `*` 可跨 `/` 匹配，因此 `D:/data/*` 覆盖该目录下所有层级，与 qwen-code 的 `Read(//dir/**)` 语义等价。

**路径规范化要求**：规则生成、规则匹配、边界判定三处必须使用同一规范化函数（resolve 符号链接 + 大小写归一 + 分隔符统一），否则 Windows 大小写和 8.3 短名可能造成白名单绕过或误判。

### 4.5 越界直读执行层

现有越界直写通道（`_perform_outside_write_file` 等）绕过虚拟后端直接操作真实路径；越界读放行后需要对称的**直读通道**，因为 deepagents 的虚拟后端根目录固定在 workspace，无法解析外部路径。越界直读的使用方：

- `plan`/`default`：白名单命中或审批通过后的越界读；
- `auto-edit`/`auto`/`yolo`：全部越界读（无需审批）。

实现选择（推荐前者）：

- **方案 A（推荐）**：在 `WorkspaceBoundaryMiddleware` 中新增越界直读实现，与越界直写对称。改动自包含，不动 deepagents 依赖；可分两步：先支持 `read_file`/`ls`，`glob`/`grep` 越界暂缓（保持硬拒绝并提示改用 `read_file`/`ls`，二期补齐）。
- **方案 B**：让后端支持多根虚拟映射。改动深入 deepagents 内部，成本高，放弃。

### 4.6 plan 模式开启 HITL 通道（Q1 带来的结构变化）

现状 `interrupt_on_for_approval_mode` 对 plan/yolo 一律返回 None（不创建 HITL）。Q1 要求 plan 越界读弹窗，因此：

- plan 模式的 HITL 集合 = 只读工具（`ls`、`read_file`、`glob`、`grep`、`lsp`），配合预检：**仅当越界且未命中白名单时返回 True 弹窗**；工作区内读返回 False 不弹窗。
- 写入类工具不进 plan 的 HITL 集合，`PlanModeMiddleware` 的写入拒绝语义不变；`yolo` 仍不创建 HITL（越界读由执行层直接放行）。
- plan 模式的审批同样按 approve_once/thread/always 记录白名单规则，与其他模式一致。

### 4.7 不变的安全边界

以下行为不在本次改造范围内放松：

- deny 规则绝对优先，白名单 allow 不能覆盖；
- 敏感路径（`sensitive_paths.py`）即使命中白名单仍强制弹窗；
- UNC 路径、`..` 穿越、符号链接逃逸的防护维持原样（白名单判定同样先 resolve 再比较）；
- `apply_patch` 越界维持硬拒绝（补丁跨多文件，不做定向放行）；
- 子 Agent（`task` 派发）不接审批弹窗，越界读写维持硬拒绝；
- `/.harness` 虚拟命名空间的只读约束不变。

## 6. 验收标准（可观察结果）

1. `default` 模式读取工作区外文件：弹出审批卡片，描述中包含完整目标路径；选"允许一次"后该次读取成功返回文件内容。
2. 同一次弹窗选"本线程允许"：该次成功，且同一目录下其他文件的读取在本次会话内不再弹窗；重启进程后再次弹窗。
3. 选"永久允许"：项目 `.harness/settings.json` 的 `permissions` 数组新增一条 resource 为该目录模式的 allow 规则；新会话读取该目录文件不弹窗。
4. `plan` 模式读取工作区外文件弹窗；批准后读取成功；`plan` 模式写入工作区外仍被直接拒绝且不弹窗。
5. `auto-edit`/`auto`/`yolo` 模式读取工作区外文件不弹窗直接成功；`auto-edit` 模式越界写仍弹窗。
6. 越界写入授权后生成目录级写规则；对该目录外的路径写入仍弹窗；`settings.json` 中不再出现文件工具 `resource="*"` 的规则。
7. 工作区内读写行为与改造前完全一致：读不弹窗，写按原模式矩阵执行。
8. deny 规则命中的路径即使用户曾授权仍被硬拒绝；敏感路径命中白名单仍弹窗。
9. 通过白名单目录内指向工作区外的符号链接访问、UNC 路径、含 `..` 的路径仍被拒绝。

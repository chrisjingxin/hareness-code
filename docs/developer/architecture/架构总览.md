# 架构总览

Harness Code 采用“多个表现层 + Project-scoped Python Agent Host”的本机结构：

```text
OpenTUI / 无头 CLI ── JSON-RPC v3 / stdio JSONL ──┐
                                                  ├─ Python AgentHost
Web ─────────────── JSON-RPC v3 / WebSocket ──────┘   ├─ ThreadPersistence
                                                       ├─ AgentEnginePool
                                                       └─ RunCoordinator
```

- `packages/cli/`：参数解析、Python sidecar 生命周期、React/OpenTUI 渲染与交互。
- `packages/protocol/`：v3 canonical JSON Schema、生成的 TypeScript/Python 类型、常量和运行时校验。
- `packages/agent/`：Project-scoped AgentHost、ProtocolConnection、配置、持久化和 Agent Core。

配置来源、TOML v1 契约和项目配置的可信边界见 [配置架构](配置架构.md)。Agent、模型、
执行策略、Thread 选择与 Run 历史的长期领域边界见 [ADR 0001：Agent 领域对象、生命周期与兼容映射](adr/0001-agent-domain-model.md)；当前实现与目标 canonical model 的差异必须通过兼容 adapter 和迁移任务收敛，不能以新增 Thread 私有 AgentEngine 绕过。

上下文连续性的下一阶段需求和顶层方案已完成评审，分别见
[上下文管理改造需求](上下文管理改造需求.md)与
[上下文管理顶层设计](上下文管理顶层设计.md)，实施状态以
[ZC-098](tasks/ZC-098.md)～[ZC-104](tasks/ZC-104.md) 为准。在这些任务完成前，
本文明确区分已落地的 ZC-098 Transcript/迁移能力与仍在实施的 ZC-099～ZC-104；
未完成任务不得被描述为完整交付能力。ZC-099 当前生产准备路径已经以
`RunContextSnapshot` 取代 Thread 永久 PromptEpoch，旧 PromptEpoch 仅保留为兼容迁移形状。

## 企业 OpenTUI 依赖

CLI 固定 Bun `1.2.19`、企业 `@opentui/core` / `@opentui/react` `0.4.3`、React `19.2.6` 和 `react-reconciler` `0.33.0`。其中 `@opentui/react` 以 `react-reconciler@^0.33.0` 作为传递依赖；`@types/react-reconciler@0.32.0` 仅为企业当前可用的编译期声明。完整直接/传递依赖契约见 `../project/dependency-versions.json` 与企业环境生成的 `bun.lock`。

Core `0.4.3` 的 native library 由其 `@opentui/core-<platform>-<arch>` optional package 提供。企业源必须镜像当前 runner 对应的包，Bun 负责选择；项目不携带 OpenTUI 源码快照、自建 FFI artifact 或 Zig 构建脚本。

TUI 启动时注册 `packages/cli/src/tui/platform/assets/syntax/` 内随源码分发的 Tree-sitter WASM parser 与查询文件。`<markdown>` 使用这些离线资源显示 Agent 输出与 fenced code；网络不可用或未知语言时保持可读降级，审批和 IPC 不受影响。

Python 服务端 stdout 只能输出换行分隔的 JSON-RPC；日志必须进入 stderr 或结构化事件。不得让 TUI 直接依赖 Agent 内部实现，也不得把业务决策放进 `cli`。协议变更必须同时修改两端和跨进程测试。

## JSON-RPC v3 与 Host 生命周期

CLI 启动参数在进程创建时绑定 workspace 与 config；`initialize` 只协商版本、调用能力 `requests` 和 Interaction 处理能力 `handles`，客户端不能提交 `cwd/config_path`。CLI Connection 是 Host owner；CLI EOF 关闭 Host、全部 WebSocket、active Run、AgentEnginePool 和 ThreadPersistence，不再提供 `shutdown` operation。

`run.start` 必须携带 SDK 生成的 `thread_id/run_id`。同一 Thread 最多一个 active Run，不同 Thread 可以并发；相同 Run ID 和相同请求是幂等重试，内容不一致返回 `RUN_ID_CONFLICT`。发起 Run 的 Connection 是唯一 owner，独占审批、问答和取消权限。其他 Connection 只能通过 `threads.watch` 观察；该操作仅在 Thread 空闲时原子返回历史并登记未来事件。

Agent 输出统一为 `event` notification。信封包含 `event_id/type/thread_id/run_id/sequence/timestamp_ms/payload`；sequence 只排序 Event，不包含只发给 owner 的 Interaction，因此所有观察者看到相同且连续的序列。审批和问答分别使用 `interaction.approval`、`interaction.question` 反向 request，JSON-RPC ID 是唯一关联身份。

Run 的受理、Thread busy/幂等、owner 校验、取消、Interaction resume、DeepAgents stream、唯一终态和 AgentEngine lease 由 `harness_agent.host.run_coordinator.RunCoordinator` 统一拥有。`AgentHost` 只把协议参数转换为 `StartRun/RunRef/ConnectionRef`，在发送 accepted response 后消费 `RunExecution.events` 并负责多 Connection fanout；因此 stdio 与 WebSocket 不会各自实现一套 Run 生命周期。

`/web` 先让 TUI watch 当前空闲 Thread，再由 owner 调用 `host.attachment.create`。Python 只在 `127.0.0.1` 随机端口监听 WebSocket；token 60 秒过期、单次使用、绑定 HTTP Origin，并限制 attached Connection 的 capability ceiling。Web 静态资源由 CLI 提供，endpoint、token 和 thread ID 只放在 URL fragment。

完整生命周期决策见 [ADR 0002：Project-scoped Agent Host、多个 Connection 与单 Run owner](adr/0002-project-host-multi-connection.md)，统一术语见根目录 [CONTEXT.md](../../../CONTEXT.md)。

## TUI Slash Command Registry

交互式命令由 `packages/cli/src/tui/application/commands.ts` 的不可变 `CommandRegistry` 统一声明。每个 CommandDefinition 包含稳定 ID、canonical 名称、别名、来源、展示类型、参数提示、capability/thread/idle requirements 和安全元数据；帮助、补全、菜单、解析与未知命令建议都只能从该 Registry 导出。Builtin 不可被同名或别名覆盖，后续 Skill、MCP、Plugin Loader 只能构造新的 catalog snapshot。

握手的 `enabled_capabilities` 被收敛为 TUI Runtime 状态。缺少 capability 的命令从菜单隐藏；需要 thread 或空闲状态的命令保留在菜单中但显示禁用原因，实际执行时仍按同一策略复核，防止状态在选择后发生变化。当前 `/continue` 是 `/resume` 的别名，解析后统一为 canonical `resume`；未知 `/command` 只显示本地建议，绝不作为 Prompt 提交。用户需要提交 `/` 开头的普通文本时以 `//` 转义。

`application/command-dispatcher.ts` 让现有 Builtin Handler 只按稳定 ID 返回 `notice`、`exit`、本地 Action、Picker、Dialog、RPC 或 Prompt 等 `CommandResult`；`application/controller.ts` 负责解释结果、编排 RPC 和维护 TUI 工作流。`app.tsx` 只把输入映射为 intent，再把 snapshot 交给 Presentation 组件渲染。`/new` 是新建 thread 的 canonical 命令，`/clear` 为兼容别名；活动 run 下通过确认 Dialog 后才取消，`/force-clear` 仅返回迁移提示。

## Project、Thread 与 Message

Harness 的持久化领域模型只有 `project`、`thread` 与 `message`。所有跨层身份字段统一为 `thread_id`；不建立 Harness 的 `session` 概念。LangGraph 原生要求的 `configurable.thread_id` 直接复用该字段。完整用户可见历史由 ThreadPersistence 的 append-only Transcript 保存；LangGraph checkpoint 只承担当前模型工作状态。

可恢复状态位于一个用户级 SQLite 文件 `~/.harness/threads.sqlite3`，而不是每个 project 或 thread 各自一个数据库。目录权限固定为 `0700`，新建数据库固定为 `0600`。原始 project 路径不写入数据库：服务端对规范化路径计算 SHA-256 `project_fingerprint`，并同时用于 `harness_threads` 索引筛选和 LangGraph checkpoint 的 `checkpoint_ns`：

```python
{
  "configurable": {
    "thread_id": thread_id,
    "checkpoint_ns": project_fingerprint,
  }
}
```

Harness 自有表包括 `harness_threads(project_fingerprint, thread_id, created_at_ms, updated_at_ms, first_message, latest_message, message_count)` 和 v7 的 `harness_thread_transcript`。两者均按 `(project_fingerprint, thread_id)` 隔离；Transcript 以稳定 `record_id`、单调 `sequence`、类型化 payload、内容摘要/长度和可选 Artifact 引用保存 user/assistant/tool/context 语义。`harness_threads` 只索引恢复选择器所需的摘要。`threads.list` 与 `threads.open` 仅在协商 `threads.read` 后可调用，只返回当前 project；JSON-RPC 客户端可以传递内部 `thread_id`，但 TUI 不得将其渲染或要求用户输入。

`harness --resume` 与 `/resume` 共用 TUI 浮层选择器。恢复时从 Transcript 读取完整 UI 历史，不把 checkpoint 当作 UI fallback；活动 run 或待处理交互期间禁止切换。v6 迁移只导入当时 checkpoint 能证明的消息，并以 `legacy_incomplete_history` 标记不完整边界。sidecar 关闭时提交并关闭 SQLite 连接，用户只能在 Harness 停止后手动删除主数据库及其 `-wal`、`-shm` 文件。

Python Agent 调用持久化时只依赖 `ThreadPersistence` 的生命周期操作：`accept_run` 在一个 `BEGIN IMMEDIATE` 事务中完成 Run binding、Thread 索引和用户 Transcript；`append_transcript_batch` 原子追加完整 assistant/tool 语义及大型工具 Artifact；`load_transcript`/`open_thread` 提供 UI 恢复，`load_run_state` 提供 Run 绑定恢复，`load_context_state` 只读取压缩策略状态，`load_latest_valid_compression_checkpoint` 与 `commit_context` 提供投影生命周期。SQLite 表、legacy 读取、schema bootstrap 和事务顺序都留在该 module 内部；`checkpointer` 与 `graph_config` 只作为 LangGraph 的 project-scoped adapter 暴露。

ZC-101 已新增 `ContextProjector` 和 Harness 自有的版本化
`CompressionCheckpoint`。每个新顶层 Run 在进图前都按以下唯一链路生成模型历史：

```text
最新有效 CompressionCheckpoint.projected_messages
+ source_record_sequence 之后的 Transcript tail
→ 校验 user / assistant tool-call / tool-result 原子组
→ 单向刷新 LangGraph messages 缓存
→ 追加当前 Run 已受理的 user 记录并执行
```

检查点保存覆盖边界、覆盖 Transcript 前缀的完整 typed digest、重写版本、严格编码的投影消息、Artifact 引用、触发原因和压力摘要。候选的 source sequence/digest、重写版本、消息 JSON、工具原子组或 Artifact project/thread 归属任一无效时，Projector 跳过它并尝试较早的有效版本。压缩产生的 Artifact、Summary、熔断状态和最终检查点在同一 SQLite 事务提交；Server 和 Middleware 不组合表级写入。`load_context()` 只保留为 LangGraph 缓存诊断/兼容测试入口，不是生产模型历史来源。

## AgentEngineProfile 与运行状态

### Agent 领域对象与当前实现

Harness 的长期 Agent canonical model 固定为 `ProviderDefinition`、`ModelProfile`、
`ExecutionPolicyDefinition`、`AgentDefinition`、`ThreadExecutionSelection` 和
`RunExecutionBinding`。其中 Provider/Model 来自 TOML adapter，Plugin Policy/Agent 来自已验证 Plugin catalog；ThreadSelection 是下一次运行的可变意图；
RunBinding 是每次实际执行的不可变历史。完整字段归属、优先级、生命周期和当前兼容映射以
[ADR 0001](adr/0001-agent-domain-model.md) 为准。

当前 TOML v1 的单个模型 Profile 仍同时承载 OpenAI-compatible 连接和模型参数；它是到
`ProviderDefinition + ModelProfile` 的输入 adapter，而非未来 Agent/Policy 的配置模板。
`runtime/execution_binding.py` 以一个纯函数集中解析根模型：本次请求优先，其次是最近 Run、
v5 legacy `executor` 绑定和 `models.default_profile`。解析结果同时提供 AgentEngine 所用模型、
脱敏 Protocol 展示和不可变 `RunExecutionBinding`，Server 与 ThreadPersistence 不再重复解释字段。
`/model` 仍会独立尝试同步未来默认值；v4/v5 的 Thread AgentEngine/模型绑定只读兼容，
无法恢复 Profile ID 时明确显示 legacy unknown。

AgentEngineProfile 是可共享 AgentEngine 的稳定、脱敏配置身份；它不是 thread
或用户会话。当前 v2 Profile Key 以 canonical JSON 的 SHA-256 计算，固定包含
角色 `agent_id`/definition fingerprint、`project_fingerprint`、topology ID/版本、模型角色配置
指纹、实际工具/Skill 能力视图、MCP、Sandbox、Policy、middleware 和 Prompt 模板指纹。
Key 记录中不保存原始工作区路径、模型 endpoint、Header、凭据或完整 Prompt；v1 record
仍可读取，但会标记为 legacy，不能进入新的 AgentEnginePool 或重新持久化。

MCP 由 `ConfigChangeService` 产生带文件 revision 的深度不可变 snapshot。AgentHost
在创建或热更新 AgentEngine 时同时截取该 snapshot 和 MCP 工具列表，AgentEngineProfile 的
MCP fingerprint 与实际 graph 输入因此保持一致；后续配置写入只创建新的 Profile，旧
AgentEngine 仍可完成当前 Run。指纹只保留 transport、command/URL 形状、args、超时以及
环境变量/Header 名称；认证 query 值会脱敏，普通 query 参数仍参与身份计算。

以下内容不参与 Profile Key，且必须保持在 ThreadPersistence/Checkpointer 或单次 Run
Context：`thread_id`、ThreadExecutionSelection、消息、RunContextSnapshot 正文、上下文摘要与 artifact、Todo、审批
状态、取消令牌、run ID、RunExecutionBinding 执行树以及未来的 Agent mailbox。相同 Profile 的 thread 因此可在
已由 AgentEnginePool 复用一张图，而稳定能力变化会构造新 Profile。

`ModelCatalog` 保存命名的 OpenAI-compatible Profile、默认 Profile 和现有配置角色绑定。
当前 Single Agent 只解析 root 模型，不把角色映射带入 AgentEngine；`[models.roles].executor`
仅用于读取 v5 legacy 快照。当前内置 `main` 由 `resolve_builtin_main_agent_spec()` 一次性汇合
模型、EffectiveExecutionPolicy、实际工具、Skill catalog、MCP snapshot、Prompt 和执行后端描述，
得到不可变 `ResolvedAgentSpec`。Profile 通过 `spec.runtime_profile` 生成，AgentHost 按 Profile key
取回同一个 spec 交给 builder 和 RunContext；不再维护独立的 `_AgentEngineBuildSpec` 解析路径。
后续 Planner/Executor/Reviewer 可复用相同 seam，但当前不加载 Plugin Agent。主 Agent 始终由 Python 内置路径构建；Plugin Agent、动态 Subagent
和固定 Workflow 均未进入当前生产路径，统一留存在 [新功能候选](../project/新功能候选.md)。
`ProviderClientPool` 仅按 endpoint/timeout 复用不携带认证信息的 HTTP transport；
每个 ChatOpenAI adapter 仍独立保存模型、认证和 Header。

ZC-095 已固定运行资源的 owner 边界：`AgentHost` 独占
`ProviderClientPool`、按不可变 snapshot 管理的 `McpConnectionManager` 和
`ThreadPersistence`；workspace/execution-environment owner 管理本地执行 backend 或
远端 sandbox/worktree。AgentEngine 只在 `AgentEngineResourceBundle` 中保存共享资源的
lease，关闭时释放 lease，不调用 Provider、MCP 或 sandbox 的 owner close；编译图、角色
wrapper、middleware 和 model binding 才属于 AgentEngine 自己。共享 handle 进入
`DRAINING` 后拒绝新借用，已有 execution 释放后由 owner 回收。

MCP 热更新先建立新 snapshot resource，并将旧 resource 排空；AgentHost 再按
`snapshot/profile fingerprint → affected AgentEngine → draining` 定向失效旧图。新的
execution 只能租用新 Profile，正在运行的旧图可以带着旧工具集合完成并释放。
`AgentEnginePool.invalidate()` 提供带稳定原因的显式定向失效 seam，供未来的 Skill、模型、
Policy、工具、middleware 或 Prompt snapshot producer 调用；当前已接入的 producer 只有
MCP 配置 snapshot 热更新，尚未有 Skill catalog 热刷新 producer，不能据此宣称端到端能力。
Pool 诊断额外返回脱敏
`agent_id`、资源 scope、drain reason、构建耗时和 scope 计数。

sidecar 以 AgentEngineProfile 为键从 AgentEnginePool 租用默认 Agent 图，而不再缓存
`thread_id -> Agent` 或 `thread_id -> ContextWindowMiddleware`。`RunContext` 是
一次 `astream`/`ainvoke` 调用的不可持久化输入，携带 `thread_id`、`run_id`、
`execution_id`、父 execution、`agent_id`、执行模式、RunContextSnapshot、审批模式、取消令牌和可选
Profile Key。图内
`RunContextSnapshotMiddleware` 在模型调用边界读取它并注入前缀；`ContextWindowMiddleware`
同样优先由它路由到目标 thread。若 LangGraph 的 `configurable.thread_id` 与
RunContext 不一致，调用会 fail closed。

### AgentExecution 与两种执行策略

一次用户请求仍然是一个 `Run`；一个 Agent 为完成一项任务经历的完整模型循环是一个
`AgentExecution`；单次模型调用、工具调用或 delegation 只是该 execution 内的操作，不单独
创建 execution。关系如下：

```text
Run
└─ AgentExecution(main)
   ├─ model / tool operations
   └─ delegation operation
      └─ child AgentExecution
```

所有 execution 共用稳定身份、父子关系、模型/Policy 事实、状态、取消和事件归属；执行基础设施
按隔离需求分为两种模式：

- `Inline`：可信、短期、同步的内置 worker，保留 DeepAgents 临时子图，不单独持有
  AgentEngine lease 或 checkpoint。
- `Managed`：根 `main` 以及未来独立角色/Plugin，拥有独立 AgentEngine、namespace 和可恢复状态。

当前已落地轻量 `AgentExecutionRegistry`：根 Run 创建 `root-<run_id>` execution，事件 envelope
携带 `execution_id`/`agent_id`，取消会收敛未终结 execution，Run 封口后不能追加 execution。
registry 以 `(thread_id, run_id)` 隔离，Coordinator 在封口后释放短期记录；已完成 Run 的幂等历史
仍由 `ThreadPersistence` 保存。子 Agent delegation、Managed 状态持久化和 checkpoint 隔离分别留给
后续任务，不把模型/工具调用提前建成 Step 表。

`/.harness/history` 不是图的固定 backend 成员。共享图在工具调用时按当前
RunContext 生成只读虚拟挂载，确保归档只能被所属 thread 读取。手动
`context.compact` 在短期 AgentEngine lease 内使用对应 Profile 的无 thread 私有成员压缩器，并以请求
中的 thread_id 读写 checkpoint；消息、PromptEpoch、归档、审批恢复和取消状态仍由
ThreadPersistence、Checkpointer 和 RunCoordinator 管理。

`agent_engine.AgentEnginePool` 已提供 Profile 级的核心生命周期：相同 Profile Key 的
并发 acquire 共享一个 single-flight 构建任务；`AgentEngineLease` 和
`AgentEngineRunLease` 分别保护租约、排队 run 与活动 run；状态严格经过
`MISSING → BUILDING → READY → ACTIVE/IDLE → DRAINING → CLOSED`。DRAINING
AgentEngine 拒绝新 lease，但既有 lease 可以完成或取消；只有 lease/run 均释放后才可
关闭。AgentEngine 的 `aclose()` 按“取消后台任务 → 刷新持久状态 → Tool → MCP →
Sandbox → AgentEngine 独占模型资源 → 释放共享 lease → 释放图引用”继续执行；其中
MCP/Sandbox 只有在被明确建模为 AgentEngine 独占 adapter 时才进入 Bundle，Host/workspace
共享 handle 不会被 AgentEngine 关闭。单项失败只记录并不会阻断后续释放。

sidecar 的 run 与 manual compact 均通过 Pool acquire/release；run 同时持有
`AgentEngineRunLease`。Pool 使用 `max_profiles`、空闲 TTL 与 LRU 只淘汰无 lease/run/queue
的未固定 IDLE AgentEngine；已接入的 MCP snapshot producer 变化时，受影响旧 Profile
定向进入 DRAINING，新 execution 不再复用它；普通 Thread 模型选择或 Profile 解析不会
推断并排空其他仍有效的 Profile。Host 关闭顺序是取消/收敛 run、关闭 AgentEnginePool
释放所有共享 lease、再关闭 MCP/workspace/provider owner，最后关闭 ThreadPersistence；
单个 AgentEngine 的关闭等待受 `close_timeout_seconds` 限制。本任务不改变现有 JSON-RPC 请求路径。

### Host 内工具并发

一个 `AgentHost` 在启动时固定绑定一个 workspace，并持有一把 `AsyncRWLock`。它在构建每张
默认 AgentEngine 图时注入 `ConcurrencyGuardMiddleware`，因此同一 Host 的不同 Profile 不会因
各自图内锁而绕过彼此：只读工具可以共享读锁，写工具、未知工具和 `task` 获取独占写锁。`task`
的默认子图可能写同一 workspace 且不继承父图 guard，所以父 `task` 调用在整个同步子图期间持锁。

HITL 在 ToolNode 实际执行前暂停并等待用户决定；锁只在审批恢复后的工具 handler 中获取，绝不
跨用户等待持有。不同工作目录通常由不同 Host 承载，彼此不互相阻塞。当前没有 worktree 或远端
sandbox 的稳定资源身份，故它们在同一 Host 内也保守共用此锁；不同进程同时操作同一物理目录同样
不受协调。若以后出现可识别资源域或吞吐瓶颈，再以独立任务替换为资源级调度。

`config.show` 额外返回 `runtime_pool_diagnostics`，因此 `harness config show` 是无需新
capability 的本地诊断入口。摘要包含 Pool 大小、状态计数、活跃 lease/run/queue、命中/未命中、
构建和关闭累计耗时、容量拒绝、按原因聚合的淘汰数、关闭失败数以及最近 64 条生命周期事件。
每条 AgentEngine/事件只使用 12 位 `profile_id`，绝不返回完整 Profile Key、工作区路径、Prompt、
模型 endpoint 或凭据。`memory.estimated_bytes` / `memory.rss_bytes` 目前恒为 `null` 且状态为
`not_collected`：真实内存采样需独立校准，当前 CI 以 AgentEngine 数及资源关闭断言保证容量上界。

用户级 SQLite schema v4 新增 `harness_runtime_profiles` 和
`harness_thread_runtime_profiles`；v5 新增 `harness_thread_model_bindings`；v6 新增
`harness_run_execution_bindings`。v6 在受理 Run 时将请求选择、脱敏实际 primary 绑定、AgentEngineProfile
摘要与首条消息索引置于同一事务，并按 `(project_fingerprint, thread_id, run_id)` 保证幂等；v7 新增 Transcript、legacy 历史边界元数据和 Context Artifact 的 `content_sha256`/`byte_length`。v6→v7 迁移先以 SQLite 写锁串行化并重读版本，再使用 SQLite backup API 留存主库备份；DDL/bootstrap/user_version 在一个事务内提交，失败或取消只 rollback，备份保留供人工回滚。
v8 新增 `harness_run_context_snapshots` 及 binding 的可空 `context_snapshot_id`；v7→v8 复用同一套两阶段备份、`BEGIN IMMEDIATE` 重读版本和单一后继 schema 事务，不复制迁移机制。旧 PromptEpoch 在迁移时只转换为 `legacy` snapshot 并回填旧 Run 引用，生产 Run 不再双写旧表。
v9 新增 `harness_compression_checkpoints`；它保留所有投影版本供审计，恢复时只选择 latest-valid。v8→v9 先补齐旧 Artifact 的内容摘要和字节数，再将当时可严格解码且工具组完整的 LangGraph 视图迁移为 `legacy/incomplete` 审计投影。legacy/incomplete 不参与正常模型投影选择，Projector 在有可用 Transcript 时始终从规范记录重建，只有显式审计读取才能取得该降级候选。损坏视图、缺失/越界 Artifact 或残缺工具组不会被升格为有效检查点，也不会伪造更早历史。

v10 为 CompressionCheckpoint 增加整条 `CommitContextRewrite` 的稳定 `commit_payload`：Artifact、Summary、ContextState、来源 sequence/digest 和 checkpoint 字段共同参与幂等判断。精确重试恢复首次提交结果；任一领域值不同都以冲突失败且不产生部分写入。所有持久化 JSON 均以严格 decoder 拒绝 NaN/Infinity，typed 消息和工具调用 ID/名称不做字符串强制转换。legacy 导入也遵守同一边界：非字符串 call/result ID、name、type、error 或 status 只写入明确的 invalid/unmatched 标记；任何 `arguments_status != valid` 的 call 都不进入 pending 关联。宽松 legacy 编码只存在于迁移事务的私有调用参数，普通单条/批量 Transcript 写入不能声明或伪造该能力；单条畸形记录不会中断整库迁移。
Profile 记录按 project 指纹与 Profile Key 去重，记录内的 `profile_version` 当前为 v2；新 Run 不再写入 Thread 的永久模型或 AgentEngine 绑定。
v5 及以前的绑定仅作为只读兼容回退；legacy bootstrap 不伪造 run/execution 身份，消息、checkpoint、legacy PromptEpoch 和 context 数据均保持原样。

## Skill 生命周期

Harness 启动时一次性扫描四类来源：内置 `harness_agent/built_in_skills/`、用户 `~/.harness/skills/<name>/`（兼容 `~/.harness/skills/local/<name>/`）、项目 `<workspace>/.harness/skills/<name>/` 和市场安装目录 `~/.harness/skills/market/<market>/<name>/<version>/`。项目 Skill 默认启用，不要求额外信任确认；用户可用 `harness skills disable` 暂停它。来源不会静默覆盖同名项，canonical ID 固定为 `builtin/<name>`、`user/<name>`、`project/<name>` 或 `<market>/<name>`；只有全局唯一时才允许短名称。

每个进程建立带 SHA-256 的不可变 catalog snapshot，运行期间不监听文件变化，以保持提示词 prefix caching 稳定。每个顶层 Run 将同一 immutable Registry 的 Skill 元数据按 canonical ID 排序注入 `RunContextSnapshot`（总长最多 4,000 字符）；正文、资源路径和运行时错误均不进入 system。Agent 通过统一的 `read_file` 按需读取 `/.harness/skills/<canonical-id>/SKILL.md` 或同根资源，不能调用专用的 `load_skill`/`read_skill_resource` 工具。ZC-099 不实现 Skill 热扫描；启用、停用、安装、更新和删除需要新的 Registry 生命周期，既有 Run 继续持有旧视图。启动后的 `SKILL.md` 篡改、非法 front matter、symlink 和路径穿越都会 fail closed。市场网络和认证不由核心实现，企业包可通过 `harness.skill_marketplaces` entry point 提供 Provider。

## RunContextSnapshot 与上下文预算

默认 Agent 的每个顶层 Run 都由 `ContextLifecycle` 重新读取当前支持的 AGENTS 和环境来源，并生成按权限层级、再按变化频率排序的不可变 `RunContextSnapshot`。核心策略、EffectivePolicy/Sandbox/实际工具能力和稳定环境位于低可信 AGENTS、Skill 索引及 Run 动态块之前；内容与顺序不变时使用相同 system fingerprint 和 snapshot ID。快照在 `accept_run()` 中与 binding、首条用户记录同一事务持久化，`RunContextSnapshotMiddleware` 在每次模型调用注入同一 system prompt；当前 Run 开始后的文件变化不影响它，下一 Run 才重新观察。旧 PromptEpoch 只作为 legacy snapshot 单向迁移，不是新 Run 的来源。

模型 Profile 的 `context_window_tokens` 默认 `128000`，输入预算为 `window - clamp(4096, 16384, ceil(window * 10%))`。`ContextPressurePolicy` 将测量与执行分开，并保持 50% report、60% micro、80% full、90% hard 的有序基线。默认策略由工具密集 fixture 校准为可回收工具结果达到 8,192 token 或 2 个时提前尝试 micro，文本密集 fixture 没有可回收工具时不会制造空归档；每次 micro 都保留最近 1 个候选，空闲辅助阈值为 900,000 ms（15 分钟）。这些值集中在 typed policy 配置中，不采用第三方的固定数值。

达到 full 水位时仍先在内存中归档旧的、已完成且可从 Artifact 恢复的工具结果，再以 `pressure_after` 重测；低于 full 才原子提交 `mode=micro` 检查点，仍超出时不提交中间 micro checkpoint，直接把新投影交给现有摘要路径。工具调用与结果原子组、Transcript 和最近候选保留规则不被破坏，已经是 Artifact 占位的结果再次处理为 no-op。空闲只由 Run 生命周期显式标记的顶层 Run 首次模型调用携带；工具续跑、重试、Interaction 恢复、子 Agent 以及缺失/异常时间戳均不会触发。

旧工具结果以工具名、首尾确定性预览、SHA-256 和 artifact ID 留在历史，原文仅写入本机 SQLite，并可由 `/.harness/history/<artifact-id>.md` 分页读取。空摘要、节省不足 20% 或失败均不改写历史；连续三次失败打开熔断器。网关溢出时先归档工具输出，再只允许一次摘要恢复重试。交互客户端可通过 `/compact` 调用 `context.compact` 强制生成一次摘要；它不受自动熔断器限制，但仍要求保存至少 20%，并保留最近两个完整 user turn。

服务端不发送厂商专用缓存字段。它记录 system/schema/历史重写指纹和动态预算；网关未报告缓存 usage 时状态为 `unknown`。协议的 `context.updated` 与 `run.completed.context` 把紧凑状态交给 TUI。

协议唯一来源为 `packages/protocol/schema/v3.json`。运行：

```bash
bun run protocol:generate
bun run protocol:check
```

生成的 `src/generated.ts`、`harness_agent/protocol/generated.py` 与 Python wheel 中的 Schema 副本禁止手改。生成器只遍历 Schema metadata 与 `$ref`；两端共同消费 `packages/protocol/fixtures/v3-contract.json`，并分别由 Ajv Draft 2020-12 与 `jsonschema` 在发送和接收 seam 校验。stdio 与 WebSocket 单帧上限均为 8 MiB，工具载荷上限为 1 MiB；Python stdout 只能输出 JSONL。

v3 一次性替换未正式发布的内部 v2，不维护 compatibility adapter。未来 replay、steer、外部工具和 hooks 必须通过 minor 版本与 capability 增量提供，禁止提前声明未实现能力。

历史协议与运行行为说明保存在 [实施状态](../research/archive/2026-07-14-za38-cli-implementation-status.md)；它只用于追溯，不是开发者文档入口。

## 执行后端与安全边界

默认 `tools.sandbox = false`，Python sidecar 使用本机 `LocalShellBackend`。TUI 必须清晰显示“本机执行 · 未隔离”。

本机模式在 `create_harness_agent()` 的主 Agent 和默认 `general-purpose` 子 Agent 中分别注册 `WorkspaceBoundaryMiddleware`。它在内置文件工具进入 backend 前执行以下规则：

- `ls`、`read_file`、`write_file`、`edit_file`（以及未来的 `delete`）只接受工作区内的绝对路径；唯一例外是 `read_file` 可读取受语法和 thread/project 归属双重校验的 `/.harness/` 虚拟路径。
- `glob`、`grep` 未指定 `path` 时从 backend 的 `root_dir` 即工作区搜索；指定时必须为工作区内的绝对路径。`glob.pattern` 和 `grep.glob` 禁止绝对路径和 `..` 路径段；它们以及 `ls`、写工具和 `execute` 都拒绝 `/.harness/`。
- 每个路径均通过 `Path.resolve(strict=False)` canonicalize 后再调用 `relative_to(workspace)`；因此现有父级符号链接、待创建目标的父级符号链接与链接环均不能逃逸。
- 拒绝返回 `ToolMessage(status="error")`，不会调用底层工具，也不会触发 HITL 审批。`WorkspaceBoundaryMiddleware` 不是 shell 沙箱，`execute`、MCP 和自定义工具不在其范围内。

不能只在主 Agent 注册此中间件：deepagents 自动的 `general-purpose` 子 Agent 有独立 middleware 栈。Harness Code 显式为默认子 Agent 注册自己的 `WorkspaceBoundaryMiddleware`，防止通过 `task` 绕过本机文件边界；并发协调则由父 `task` 持有的 Host 写锁覆盖整个同步子图，不能向子图重复注入同一把非重入锁。`AGENTS.md` 在每个顶层 Run 准备阶段读取一次，作为只读、不可信参考写入该 Run 的 snapshot；恢复同一 Run 不重新读取宿主文件，下一 Run 才刷新。

用户显式设置 `execution.backend = "remote"`、`HARNESS_SANDBOX=true` 或传入 `--sandbox` 时，服务端只接受由用户级或显式配置声明的 `execution.remote.factory`。该工厂必须返回 deepagents `SandboxBackendProtocol`，接收宿主工作区、provider 名称、逻辑远端目录和非秘密 `execution.remote.params`，负责企业认证、工作区同步、网络白名单和远端生命周期；失败时抛出配置错误，禁止回退到本机 backend。项目 TOML 在可信机制完成前会被整体拒绝，之后也不得自动导入远端 provider。

远端模式下 Agent 使用 provider 给出的逻辑工作目录，禁用宿主机 memory 和 skills，避免它们绕开远端执行边界。`js_eval`/QuickJS 已从 Agent 依赖和工具面移除。当前不实现 Docker、Podman 或本机容器 backend。未来接入企业 provider 时，必须补充同步、回写、取消、审计与网络策略的端到端测试。

## 审批模式

`harness_agent.policy.approval_mode` 是唯一的模式解析入口，规范值为 `plan`、`default`、`auto-edit`、`yolo`。它把旧 `ask` 归一为 `default`；未知值不抛出启动错误，而是安全降级并在 `ExecutionSettings.redacted()` 的 `security.approval_mode_warning` 中返回提示。

解析后的值沿 `load_config()` → `AgentHost._create_default_agent()` → `create_harness_agent()` 传递。`approval_policy` 集中提供以下策略，禁止由 TUI 或系统提示词自行解释权限：

- `PlanModeMiddleware` 以明确白名单在工具执行前返回 `ToolMessage`，未知工具默认拒绝；主 Agent 与默认 `general-purpose` 子 Agent 都注册该 guard。
- `WorkspaceBoundaryMiddleware` 仍在实际执行前强制校验；同一策略还作为 HITL 的 `when` 预检复用，因此越界文件调用不会先产生无意义的审批请求。
- `default` 拦截 `execute`、`write_file`、`edit_file`、`delete`、`task`；`auto-edit` 只移除写入/编辑拦截；`yolo` 不注册 Harness HITL。上下文归档和压缩由中间件自动维护，不暴露模型可调用的压缩工具，也不进入 HITL。

可选的 `ShellAllowListMiddleware` 只接受由 POSIX `shlex` 可可靠解析的单一命令。词法层禁止控制运算符、管道、重定向、子 Shell、命令替换、反引号、换行、NUL 与畸形引号；解析失败一律 fail closed。参数可以作为获准程序的普通参数传递，但中间件不解释程序自身语义。绝对路径必须与白名单条目完整匹配，禁止通过 basename 让工作区或临时目录中的同名程序冒充获准程序。同步与异步工具入口复用同一决策函数，并在拒绝时直接返回错误 `ToolMessage`，不调用 backend。

CLI 在交互模式才通过 `capabilities.handles` 声明 `approval` 与 `question`。无头 `-n` 模式不声明这些 handler，服务端遇到审批或提问会立即按拒绝/取消恢复，不发送反向 Interaction。该 fail-closed 行为是协议层的安全兜底，不应依赖表现层。

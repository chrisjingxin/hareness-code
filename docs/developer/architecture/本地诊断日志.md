# 本地诊断日志

## 1. 架构定位与四层分界

Harness Code 的可观测性与持久化数据严格划分为四个层次，各层职责、存储介质与生命周期相互隔离：

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 1. Transcript 业务事实层                                              │
│    - 存储：SQLite (harness_thread_transcript)                          │
│    - 内容：用户可见消息、完整工具调用与结果、大型工具 Artifact               │
│    - 职责：会话恢复 (threads.open)、UI 渲染与模型上下文投影基准             │
└────────────────────────────────────┬───────────────────────────────────┘
                                     │ 投影 / 压缩
┌────────────────────────────────────▼───────────────────────────────────┐
│ 2. CompressionCheckpoint 压缩检查点层                                  │
│    - 存储：SQLite (harness_compression_checkpoints)                    │
│    - 内容：已压缩消息摘要、覆盖 sequence/digest、重写版本、Artifact 引用     │
│    - 职责：ContextProjector 重建模型上下文时的 latest-valid 检查点       │
└────────────────────────────────────┬───────────────────────────────────┘
                                     │ 加载运行
┌────────────────────────────────────▼───────────────────────────────────┐
│ 3. LangGraph Checkpoint 图状态层                                       │
│    - 存储：SQLite (checkpointer / graph_config adapter)                │
│    - 内容：LangGraph 执行图节点瞬时状态                                  │
│    - 职责：驱动单次 Run 的步骤流转                                      │
└────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────┐
│ 4. Diagnostic Log 本地诊断日志层 (单向 Observer)                       │
│    - 存储：本地磁盘 ~/.harness/logs/<date>/ 进程独立 JSONL             │
│    - 内容：低流量、结构化、已脱敏的生命周期事件与关键耗时                │
│    - 职责：事后故障排查与性能分析；完全不参与恢复、幂等、裁决或业务判断 │
└────────────────────────────────────────────────────────────────────────┘
```

**关键不变式**：
- Diagnostic Log 是纯粹的**单向观察者**。它的写入失败、丢弃、轮转或文件损坏**绝不影响**业务执行、事务提交与会话恢复。
- SQLite 中不记录诊断日志，诊断日志中也不存储业务消息全文、Prompt 或源码。

## 2. 跨语言事件契约（Diagnostic Log v1）

日志事件由 `packages/protocol/diagnostic-log/` 中的单一 JSON Schema（`schema/v1.json`）定义，并通过代码生成器（`generate.ts`）同步生成 TypeScript 与 Python 契约。

### 2.1 Envelope 结构

每行日志为单条 UTF-8 编码的 JSON 对象：

```json
{
  "schema_version": 1,
  "timestamp_ms": 1787800000123,
  "level": "info",
  "event": "run.completed",
  "component": "agent",
  "process": {
    "pid": 41230,
    "started_at_ms": 1787799999000,
    "record_sequence": 42
  },
  "project_fingerprint": "a1b2c3d4e5f6... (64 hex)",
  "thread_id": "optional-thread-id",
  "run_id": "optional-run-id",
  "execution_id": "optional-execution-id",
  "parent_execution_id": "optional-parent-execution-id",
  "agent_id": "optional-agent-id",
  "tool_call_id": "optional-tool-call-id",
  "event_id": "optional-event-id",
  "event_sequence": 17,
  "activity_id": "optional-activity-id",
  "rpc_request_id": "optional-rpc-request-id",
  "fields": {
    "outcome": "completed",
    "duration_ms": 8421
  }
}
```

### 2.2 契约规则

1. **白名单约束**：Schema 与每个事件的 `fields` 设置 `additionalProperties: false`，拒绝任何未声明字段与自由文本 `message`。
2. **大小上限**：单条序列化后的 JSON 记录上限为 **8 KiB**（含换行）。超大记录在入队前被拒绝并累加 `oversize_count`，避免破坏底层文件。
3. **不可逆指纹**：工作区根目录通过平台 API 规范化后计算 SHA-256 得到 `project_fingerprint`，绝对路径绝不落盘。
4. **单调序列号**：`process.record_sequence` 在入队前分配且严格单调递增，中间若发生丢弃也不复用或回退序号。

## 3. 双端异步运行时（Runtime）

CLI（TypeScript）与 Agent（Python）实现了对等的进程内异步运行时：

```text
业务调用 log.info(event, fields)
  │
  ├── 1. 契约校验与 Context 合并（不可变 child log）
  ├── 2. 脱敏与限长截断
  ├── 3. 有界内存队列（非阻塞）
  │      ├── 正常容量：4096 条 / 8 MiB
  │      ├── 保留通道：128 条 / 256 KiB（专供 WARN / ERROR）
  │      └── 淘汰策略：DEBUG → INFO 依次丢弃，记录 logging.dropped
  │
  └── 4. 单后台 Worker / 异步 Batch Append 写入磁盘
```

### 3.1 运行时关键特性

- **非阻塞热路径**：`log.debug/info/warn/error` 仅执行内存校验与入队，不执行同步磁盘 I/O，不影响核心执行性能。
- **两级优先级队列**：在队列拥塞时，优先淘汰 DEBUG 记录，其次淘汰 INFO 记录；WARN 与 ERROR 享有独立的保留容量通道。
- **丢弃合并上报**：发生丢弃时，计数聚合为 `logging.dropped` 事件安全写入，不产生递归丢弃风暴。
- **有界 Flush 关闭**：进程退出时，`close()` 最多等待 **2 秒** 进行后台队列刷新；超时后安全降级，主进程不被挂起。
- **故障降级**：磁盘不可写、目录无法创建或写入异常时，运行时将内部状态标记为 `disabled`，后续日志调用静默丢弃，绝不抛出异常阻断业务流程。

## 4. 文件生命周期与三平台管理

日志文件存储于用户主目录 `~/.harness/logs/<YYYY-MM-DD>/`（Windows 下为 `%USERPROFILE%\.harness\logs\<YYYY-MM-DD>\`）。

### 4.1 文件分片与命名状态机

```text
[新分片打开] ──► cli-<pid>-<start_ms>-<seq>.active.jsonl
                        │
                        │ 满足轮转容量 (~16 MiB) 或进程正常退出
                        ▼
                [先 close() 关闭文件句柄]
                        │
                        ▼
                [rename() 重命名] ──► cli-<pid>-<start_ms>-<seq>.jsonl (Closed)
```

- **Active Segment**：正在被进程打开写入的文件，以 `.active.jsonl` 结尾。
- **Closed Segment**：已经关闭并重命名的文件，以 `.jsonl` 结尾。
- **Close-before-Rename**：必须先关闭文件句柄再执行重命名，彻底消除 Windows 平台上对打开文件重命名/删除失败的系统级限制。

### 4.2 容量与时间保留（Retention）

- **Closed-only 清理原则**：清理流程按天扫描目录，**仅删除已关闭的 `.jsonl` 文件**。正在写入或未关闭的 `.active.jsonl`（包含异常退出的 Orphan Active）绝不触碰。
- **平台权限**：
  - POSIX（macOS / Linux）：目录创建权限为 `0700`，日志文件权限为 `0600`。
  - Windows：使用系统用户级默认安全描述符，不依赖无操作的 mode bit。

## 5. 核心链路集成与脱敏红线

### 5.1 覆盖模块与事件命名

所有关键模块均在真实的开始、成功、失败与释放边界接入标准事件：

| 模块 | 关键事件 | 记录内容 |
| --- | --- | --- |
| **Process / Lifecycle** | `process.started` / `stopped` | 进程 PID、启动时间、平台与版本 |
| **IPC** | `ipc.initialize.completed`、`ipc.request.*` | 协商版本、方法名、RPC ID、耗时 |
| **Run** | `run.started` / `completed` / `failed` / `cancelled` | 终态、总耗时、主动耗时、等待耗时、Token 统计 |
| **Runtime Pool** | `runtime.acquire.*` / `release.*` / `pool_snapshot` | Profile ID、复用/新建、队列等待耗时、池容量 |
| **Model** | `model.attempt.started` / `completed` / `failed` / `retried` | 回合数、重试次数、首包耗时、模型总耗时、Token 统计 |
| **Tool** | `tool.started` / `completed` / `failed` | 工具名、工具类别（builtin/mcp/plugin）、执行耗时 |
| **Interaction** | `interaction.started` / `completed` | 交互类别（approval/question）、用户等待耗时 |
| **MCP** | `mcp.connection.started` / `completed` / `failed` | 配置服务名（`server_name`）、传输模式、工具数量 |
| **Skill & Hook** | `skill.read`、`hook.started` / `completed` / `failed` | Skill ID、读取类型、插件 ID、Hook 事件名 |
| **Context & Persistence** | `context.compaction.*`、`persistence.operation.*` | 压缩触发源、压缩动作、前后 Token、持久化操作耗时 |
| **Subagent & Compose** | `execution.started` / `completed` / `failed` | 阶段/子代理类型、Agent ID、关联层级 |

### 5.2 耗时口径精确拆分

性能分析严格区分不同的时间维度，避免将外部等待误计为模型或工具性能变慢：
- **总墙钟时间（Wall Duration）**：从 Run 受理到终态的绝对时间。
- **主动执行时间（Active Duration）**：排除所有等待后的 Agent 内部实际计算时间（并发执行区间取并集）。
- **Interaction 等待时间**：用户审批、问答弹窗等交互等待时间。
- **Retry 退避时间**：模型或网络重试过程中的 sleep 等待时间。
- **首包时间（First Chunk Duration）**：模型流式响应收到第一个有效 chunk 的耗时。

### 5.3 脱敏红线与 Canary 扫描验证

自动化测试中通过 `test_build_redline.py` 与 `test_mode_redline.py` 进行 Canary 渗透扫描：
- 将全局唯一的测试 Canary 字符串注入 Prompt、Assistant 正文、源码文件、工具入参及返回值、Shell 命令、文件绝对路径、原始协议帧、HTTP Header、环境变量、Secret 及异常堆栈中。
- 在 INFO 和 DEBUG 两种级别下运行完整执行链路，扫描生成的全部 JSONL 文件。
- **红线要求**：任何 JSONL 文件中一旦匹配到 Canary 即判为测试失败。

## 6. 离线查询引擎（Query Engine）

CLI 提供了完全离线的 `harness logs` 查询子命令：

```text
harness logs / --thread / --run
  │
  ├── 1. 离线文件发现与 Watermark 扫描（零 sidecar 启动，零 SQLite 访问）
  ├── 2. 安全多进程合并（按 project_fingerprint 过滤，校验 v1 Schema）
  ├── 3. 坏行容错（跳过半行/损坏行并计入 diagnostics）
  ├── 4. 视图投影：
  │      ├── 默认视图：中文摘要 + 准备层 + 历史折叠 + 最近一轮过程树 + 慢项
  │      ├── --flat 视图：逐事件中文表格 + Snapshot Keyset Cursor 分页
  │      └── --json 视图：版本化英文结构对象 (query_schema_version: 1)
  └── 5. 256 KiB / 200 条双上限保护
```

### 6.1 Cursor 分页与快照一致性

- **Keyset Snapshot Cursor**：分页 Token（opaque base64url）编码了查询快照的 project、selector、filter、各文件水位线（watermarks）、读取偏移（source positions）与最后排序键。
- **隔离新增**：翻页期间新追加的日志记录不会混入当前快照，保证翻页零重复、零遗漏。
- **拒绝树形拆分**：树形视图不按 event cursor 拆断父子节点，截断时引导用户切换到 `--flat` 平铺表格视图进行翻页。
- **安全失效保护**：当快照关联文件被轮转删除时返回 `CURSOR_EXPIRED`，当用户修改过滤条件时返回 `CURSOR_MISMATCH`，当伪造路径或包含 `..` 时返回 `INVALID_CURSOR`。

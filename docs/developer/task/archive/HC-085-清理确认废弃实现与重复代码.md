## 背景

当前生产执行路径已经固定为：

```text
AgentHost → AgentEnginePool → create_harness_agent() → DeepAgents graph
```

仓库中仍保留了几组为未来方向提前实现、但没有接入上述路径的代码。它们拥有完整类型、校验和测试，看起来像已经生效的领域能力，实际只在自己的单元测试中运行。

多 Agent 方向已经拆分为 HC-091～HC-097。`agent_catalog.py` 中的 AgentDefinition、ExecutionPolicy 和交集逻辑可能成为 HC-091/HC-092 的输入，因此本任务不再预设完整删除它；后续任务必须在真实 ResolvedAgentSpec 和执行 Policy seam 上决定保留哪些最小代码，并删除仍无调用方的 Plugin/parser 部分。

## 当前存在的问题

### 1. Unicode 安全实现没有生产调用方

`packages/agent/harness_agent/unicode_security.py` 约 568 行，没有生产或测试引用。审批 DTO、Shell guard、路径 guard 和 MCP handler 都没有调用它，因此该文件不能证明用户获得了 Unicode 风险保护。

### 2. ToolBatch 是另一套未启用的执行器

`packages/agent/harness_agent/concurrency.py` 中 `ToolBatch`、`partition_tool_calls()`、`execute_batches()` 和 `_execute_parallel()` 只在测试中使用。生产并发控制实际由 `concurrency_guard.py` 调用 `is_concurrency_safe()` 与 `AsyncRWLock` 完成。

两套并发模型同时存在，会让维护者误以为批执行器已经接管工具调度。

### 3. ThreadPersistence 存在字面重复实现

`get_model_bindings()` 与 `save_model_bindings()` 在旧版 `thread_persistence.py` 中各定义了两次。Python 后一个定义会覆盖前一个定义，因此前一份代码和对应行级理解没有运行意义。

### 4. 测试正在固化不存在的产品能力

`test_unicode_security.py` 和 `test_concurrency.py` 的部分用例只验证不可达 implementation。它们增加测试数量，却不能保护生产行为。

## 为什么现在要修改

- 后续模型绑定、Run lifecycle 和 Thread persistence 重构都会扫描这些 module；先删除伪领域可以显著降低错误依赖和 AI 导航噪声。
- 保留“已实现但未接入”的安全模块容易产生错误安全预期，比明确标记未实现更危险。
- 这些删除不需要产品决策、数据迁移或兼容 adapter，是其他 P0 前成本最低的基线清理。
- Agent catalog 已有明确后续调用方向，先整文件删除再重建同类类型只会制造无意义 churn；其裁剪必须由 HC-091/HC-092 的真实 interface 驱动。

## 目标状态

```text
当前生产需要
├─ concurrency.py
│  ├─ is_concurrency_safe()
│  └─ AsyncRWLock
├─ ThreadPersistence 当前有效方法
└─ create_harness_agent() 固定主 Agent

后续已立项
└─ HC-091/HC-092 在真实 seam 上裁剪并接入最小 Agent/Policy 定义

未来出现真实调用方
└─ 在真实 seam 上重新实现 Unicode 检测或新的跨 AgentEngine 调度
```

本任务不创建替代 module，也不提前改造 Agent catalog。

# HC-168 修复批量审批恢复

## 通俗说明

模型一次返回多个需要用户审批的动作时，Harness 会先冻结整批动作，再逐个向用户收集决定，最后把完整决定列表一次交回 LangGraph。当前实现却在收集 `approve_thread` 或 `approve_project` 时立即写入规则。恢复同一个 interrupt 时，HITL middleware 重新按这份新规则分类原始动作，导致原本 3 个 hanging tool calls 被重算成 1 个，LangChain 抛出 `Number of human decisions ... does not match ...`，工具无法继续。

本任务把规则提交边界移到恢复成功之后：收集阶段只记录待提交规则意图；同批串行循环可以通过一个仅限当前 Run 的 staged overlay 继续自动处理同类动作，但共享 Agent 图和 LangGraph 重放看不到这个 overlay。只有恢复命令被 HITL middleware 成功消费，规则才进入 session 或 project 真正的规则存储。

## 用户最终得到什么

- 一次包含多个文件写入和子代理派发的审批批次，用户逐项做出的决定与原始动作保持一一对应，批准后工具可以继续执行。
- 选择“本线程允许”或“本项目允许”仍可让同批后续同类动作按既有体验自动处理，但不会提前改变当前 interrupt 的重放分类。
- 恢复取消、恢复失败或决定没有被成功消费时，不会留下半成品 thread/project 权限规则；`approve_once` 和拒绝也不生成持久规则。

## 范围

1. `RunCoordinator` 的串行审批收集、规则暂存、提交与丢弃生命周期。
2. `ManagedAgentExecutor` 与 Build adapter 之间的“resume 成功消费”回调 seam。
3. 真实 AgentHost/LangGraph 边界的混合批次回归，以及规则提交失败、取消、幂等和非持久决定测试。
4. 审批架构不变量与 HC-168 文档链、任务看板、`tmp/handoff.md`。

## 非范围

- 不修改 LangChain 或 HumanInTheLoop middleware。
- 不修改 JSON-RPC 协议、TUI/Web UI、Interaction payload 或 approval 决策枚举。
- 不丢弃决定、不吞恢复异常、不改变 project 规则已有的 fail-closed 持久化语义。
- 不做无关审批策略重构，不改变 execution_stream 的 interrupt 提取职责。

## 可观察验收

- [x] `2 个 write_file + 1 个 task` 同一 interrupt 的恢复不再抛决策数量不匹配，三个工具调用身份与最终执行结果可核对。
- [x] 同批 `approve_thread` / `approve_project` 只在恢复成功消费后分别进入 session/project 规则；重放期间规则提供器仍看不到 staged overlay。
- [x] 恢复前取消、恢复异常和决定未成功消费会清空 staged intent；重复提交不会重复写规则。
- [x] `approve_once`、`reject`、`reject_with_feedback` 不产生权限规则；project 写入异常继续向 Run 失败路径传播。
- [x] focused pytest、相关 Agent 测试、`bun run typecheck`、`bun run project:check` 和 `git diff --check` 的结果写回本文与 handoff；未运行项单独列明。

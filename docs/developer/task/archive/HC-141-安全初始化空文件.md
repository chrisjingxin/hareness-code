## 背景

当前空文件可以通过 `read_file` 获得 Snapshot，但后续没有合法的文件工具路径：

- `write_file` 对已存在目标返回 `FILE_ALREADY_EXISTS`。
- `edit_file` 对空 `old_string` 返回 `INVALID_EDIT`。

这会让模型在“先读后改”和“只创建新文件”两条正确规则之间陷入无法恢复的循环。

## 用户结果

```text
读取已有空文件
  → 获得当前 Thread 的空内容 Snapshot
  → 表达初始内容
  → 展示有界 diff 预览并保留允许/拒绝选项
  → CAS 提交
  → 返回实际新 Snapshot
```

## 已确认设计

采用 [HC-141 规格](../../spec/HC-141-安全初始化空文件.md) 的受限 `edit_file` 语义：schema 保持
`file_path + snapshot_id + old_string + new_string`，仅当 Snapshot 和当前完整文本都证明文件
为空时，`old_string=""` 才表示把整个空文档替换为初始内容。非空文件的空匹配返回
`INVALID_EDIT`，不解释为文件开头、结尾或任意位置插入。

审批继续展示明确标记省略内容的有界 diff 预览；200 行、16 KiB 和终端高度不取消允许/拒绝
选项。完整拟议内容由 prepared plan、参数 fingerprint、Snapshot 和 CAS 绑定，而不是由可见
预览承担完整性校验。

## 范围

- Snapshot 文件工具 schema、prepare/approval/commit 路径与稳定错误语义。
- 空文件、批准期间外部变化、跨 Thread、超限和远端 CAS 回归。
- 模型 prompt、用户交互/故障排查和架构文档的语义同步。

## 非范围

- 不提供一般化的按行插入、批量 edits 或 `replace_all`。
- 不改变 `write_file` 的 create-only 保证。
- 不编辑 Notebook、二进制、图片或不可无损解码文件。

## 实施计划

1. 在现有 `edit_file` prepare 链路中纵向加入“空文档整体替换”分支：先完成参数 fingerprint、
   Snapshot scope 和当前 identity 校验，再只对规范文本仍为空的文档接受空 `old_string`；同步
   更新 schema 说明、稳定 `INVALID_EDIT` 恢复提示和 contract 回归，验证普通 exact-string、
   `write_file` create-only 与全部零写入边界不变。
2. 复用现有 `FileMutationService`、approval preflight 和 backend CAS 提交初始化计划；把审批文案
   明确为有界预览，并覆盖长初始内容截断仍可批准、同 Tool Call 改参、批准期间变化、BOM/mode、
   post-write Snapshot 和远端无 CAS 拒绝，证明没有第二条写盘路径。
3. 更新主/子 Agent 文件工具提示、用户交互与故障排查、架构总览及 HC-133 空文件 fixture，
   让模型只在已读空文件上使用空 `old_string`；运行 focused Python 和离线评测，只有用户明确
   授权真实企业 Profile 时才运行 opt-in 评测，并如实记录未运行项。
4. 对照 Design 复核完整 diff，运行 Agent 包全量、Bun test、typecheck、project:check 和
   `git diff --check`；记录实际证据、已知无关失败和无版本变更影响后再判断 Task 是否可完成。

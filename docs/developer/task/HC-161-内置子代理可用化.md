# HC-161 内置子代理可用化

## 背景与问题

Harness Code 对外文档声称内置了 `general-purpose`、`explore` 和 `plan` 三个子代理，但生产运行时只有 `general-purpose` 真正进入 `task` 工具。`explore` 和 `plan` 只存在于一套没有生产调用方的旧 Registry 中，因此模型调用 `explore` 时会得到“目标不存在”。

当前 `general-purpose` 虽然能运行，也没有完整继承父 Run 的审批边界。用户批准启动子代理后，child 内部的文件写入和命令执行不会再次进入父级审批，动态 deny rule 也可能被绕过。结果是“功能能跑”，但权限语义与主 Agent、用户文档和企业安全预期不一致。

本任务要把子代理从“代码里有名字”变成一条真实、可验证的生产能力：

```text
可信内置目录
  → 主 Agent 在 task 说明中看到可用目标
  → /agents 展示同一份名单
  → 执行时再次校验目标和权限
  → 创建隔离 child execution
  → 审批、取消、超时和最终结果正常收敛
```

## 用户最终得到什么

### `general-purpose`

- 主 Agent 可通过 `task` 把通用多步骤工作交给它，调用不再绕过 Harness 的受控 Delegation。
- 使用父 Run 已经选定的 ModelProfile 和同一份冻结 RunContextSnapshot；知道当前工作区、AGENTS.md、Skill 索引和审批模式，但不复制父对话历史。
- 实际能力取父 Agent 可用能力与内置角色边界的交集，不能自行扩权。
- 强制移除 `task`、`ask_user`、`enter_plan_mode`、`exit_plan_mode` 和 `memory_save`，防止嵌套委派、中断用户、改变主流程模式或静默写入跨会话记忆。
- 派出 `general-purpose` 在父 `default` 下仍要审批一次，卡片写明：可在工作区改文件，普通写入过程中不再问；`execute`、敏感路径、目录信任仍会问。派出之后 child 不得比父更松：父为 `default` 时内部按 `auto-edit`；父已是 `auto-edit` / `auto` / `yolo` / `plan` 时跟父走。dynamic deny 始终生效。仍弹出的审批卡显示 `general-purpose`、真实工具参数以及文件 diff；拒绝结果返回 child。

### `explore`

- 主 Agent 可通过 `task` 把代码定位、搜索和结构调查交给它。
- 只允许 `ls`、`read_file`、`glob`、`grep`、`lsp` 五个工具；写文件、Shell、网络、MCP、自定义工具、委派和交互工具既不出现在模型 schema 中，也不能通过伪造调用执行。
- 因为运行时已机械保证严格只读，启动 `explore` 不弹出 Agent 委派审批。
- 与 `general-purpose` 一样继承父 Run 冻结的 ModelProfile、工作区事实和 AGENTS.md，但不继承父消息历史，也**不**继承 Skill 索引或 MCP。

### 共同生命周期

- 两者都通过同步 `task` 返回最终结果；child 的私有消息和中间推理不写入父 Transcript。
- 委派深度固定为 1，子代理不能继续派生子代理。
- 同一父 Run 最多并发 4 个 child；排队与执行中的 child 均可被父 Run 取消。
- 超时必须是能中断实际 child 执行的硬 deadline；成功、拒绝、失败、取消和超时都释放占用的并发与运行资源。
- `/agents` 同时显示这两个内置 Agent 和当前启用的 Plugin Agent，模型可见说明、界面列表与执行解析来自同一个 canonical catalog。

## 范围

1. 建立 `general-purpose` 与 `explore` 的可信内置定义，并接入当前 `AgentCatalog`、`ResolvedAgentSpec`、`DelegationTarget` 与生产 `task` 构图链路。
2. 让同一个目录快照驱动模型可见的 Agent 说明、`/agents` 响应和执行时目标解析；未知或不可用目标稳定失败，不做默认猜测。
3. 为 child execution 派生独立、绑定子角色能力的工具与审批上下文，同时复用父 Run 冻结的模型、工作区事实和 AGENTS。`general-purpose` 另继承父的 Skill 索引与 MCP；`explore` 两者都不继承。
4. 打通 `general-purpose` 在 auto-edit 语义下仍需询问的 child Interaction（`execute`、敏感路径、目录信任）：真实工具身份和审批展示进入现有 TUI/Web 交互，审批结果返回原 child execution。工作区内非敏感写入不再弹窗。子代理过程时间线不在本任务父时间线展开，见 [HC-162](./archive/HC-162-子代理时间线.md)。
5. 对 `explore` 在工具暴露与执行入口实施同一份严格只读策略，并使其委派通过角色事实自动放行。
6. 固化深度、并发、取消、硬超时、终态和资源释放行为。
7. 删除没有生产消费者的旧 `runtime/subagents.py` Registry、未接入的 `plan` 内置声明，以及 `.harness/agents` 项目/用户自定义 Agent 的虚假文档路径；不保留 alias、fallback 或双写。
8. 更新用户文档、`/agents` 展示和相关架构文档，使公开说明与生产能力一致。

## 非范围

- 不交付 `plan` 子代理。
- 不实现项目级或用户级 `.harness/agents` 自定义 Agent；Plugin Agent 继续使用现有受信 Plugin catalog。
- 不增加子代理独立模型配置、model alias 或运行时模型切换。
- 不实现后台 SubAgent、结果轮询、恢复、fork、mailbox、Agent Team、IRC、worktree 或 peer-to-peer 通信。
- 不把 child 的完整中间消息、推理或工具结果写入父 Transcript；只补齐必要的审批交互身份和最终结果。点进子代理时间线查看过程是 [HC-162](./archive/HC-162-子代理时间线.md)，本任务不停点交付。
- 不扩大 `explore` 到网页调研、Shell 只读命令或 MCP 工具。

## 可观察验收

- [ ] 启动 Harness 后，`/agents` 同时列出 `general-purpose`、`explore` 和已启用的 Plugin Agent，并正确标识来源、用途和实际工具边界。
- [ ] 主 Agent 的生产 `task` 工具能看到并成功执行两个内置目标；模型可见名单与执行时可解析名单完全一致。
- [ ] 父为 `default` 时，`general-purpose` 工作区内非敏感写入不弹窗，`execute` / 敏感路径 / 目录信任仍弹；父为 `auto-edit` / `auto` / `yolo` / `plan` 时 child 不比父更松；dynamic deny 在 child 工具入口不可绕过。
- [ ] `general-purpose` 仍弹出的审批显示 child Agent、真实工具参数和文件 diff；拒绝后 child 可以继续调整并返回结果。Plugin child 需要 Interaction 时 fail closed，定义不能把审批改松。
- [ ] `explore` 的模型可见工具和实际执行入口都严格只有 `ls/read_file/glob/grep/lsp`；对写入、Shell、网络、MCP、自定义工具、`task` 和交互工具的伪造调用稳定拒绝。
- [ ] `explore` 委派不会产生 Agent 启动审批，但任何实现缺陷都不能让其获得非只读工具。
- [ ] 两个 child 使用父 Run 已冻结的 ModelProfile、工作区事实和 AGENTS.md，不携带父 conversation history，也不在运行中重新读取变化后的模型或目录配置。`general-purpose` 继承父 Skill 索引与 MCP；`explore` 的系统提示无 Skill 索引，schema/执行无 MCP 与 `tool_search`。
- [ ] 深度 1、并发 4、排队取消、执行中取消、硬超时和所有终态资源释放均有生产路径回归测试。
- [ ] 至少一条离线 E2E 从生产 graph 调用两个内置目标；至少一条使用真实 Harness 用户配置模型的开发 smoke 证明功能不是测试专用 Registry。
- [ ] 删除旧 Registry、`plan` 声明和 `.harness/agents` 虚假说明后，仓库中不存在第二条内置子代理发现或执行路径。
- [ ] focused tests、Agent 包全量测试、`bun run project:check`、`bun run typecheck` 和项目级测试通过，证据写回本 Task。

## 竞品调研带来的取舍

Qwen Code 和 Oh My Pi 都证明，子代理必须从统一目录真正进入生产 Tool，再在执行前重新校验，不能只靠配置文件或单元测试声称“已注册”。它们在独立 child runtime、取消、并发和审批事件传递上有成熟做法，值得借鉴。

两者也都存在不适合 Harness 的放宽：Qwen Code 的 Explore 仍有 Shell 等工具，Oh My Pi 的只读声明可能被扩展工具穿透，且 child 会把一次 `task` 审批当作含 Shell 在内的整体授权。Grok Build 则明确忽略 Plugin 的 `permissionMode`，禁止第三方把审批关掉。本任务借鉴生产链、隔离和生命周期；内置 `general-purpose` 最多放到 auto-edit，不抄 child yolo；Plugin 不能自行放宽审批。

详细证据见 [161-内置子代理可用化](../research/161-内置子代理可用化.md)。

## 需求核对纪要

写 Spec 前已确认，不改变用户结果，只收紧容易误会的表述：

1. `enter_plan_mode` / `exit_plan_mode` 仍在主 Agent 常驻工具里，但是图内空转，与 Compose 的 plan 阶段无关。本任务只禁止子代理调用，不删除主 Agent 这两个工具。
2. 「调用不再绕过受控 Delegation」指补齐 `explore` 进入生产 `task`，以及 child 工具/审批不再走默认子图或「批过 task 就放行」。不是说今天的 `general-purpose` 还没进 `AgentDelegator`。
3. Plugin Agent 的目录、Managed 派发和最终结果回传可用；需要审批或提问时仍 fail closed。本任务不修 Plugin Interaction。
4. 内置子代理不注册 `ask_user`。审批走现有单卡 Interaction；多请求排队，禁止后到的请求把先到的丢掉。
5. 两个内置角色的生产提示词改为本仓库中文定义，不再使用 DeepAgents 英文 stub 或未接入的旧 Registry 文本。
6. 审批不抄 Oh My Pi 的 child yolo。`explore` 因只读不弹窗。`general-purpose` 父为 `default` 时内部按 `auto-edit`（工作区普通写入自动，`execute`/敏感路径仍问），且不得比父更松。Plugin 维持 fail closed，不能自行放宽审批（对齐 Grok Build）。
7. `general-purpose` 继承父的 Skill 索引和 MCP（再减 Forced exclusions）。`explore` 不注入 Skill 索引、不继承 MCP、不注册 `tool_search`。

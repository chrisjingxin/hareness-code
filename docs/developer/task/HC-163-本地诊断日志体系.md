# HC-163 本地诊断日志体系

## 背景与问题

Harness Code 已有 Thread SQLite、Run 事件、AgentEnginePool 诊断、文件工具指标和一套仅供交互式 CLI/Web 使用的本地 JSONL logger，但它们尚未形成一条可用于事后排障和性能分析的完整链路：

- CLI logger 只覆盖少量 Web 生命周期，无头模式以及大多数 CLI、IPC、Run、Model、Tool 和持久化行为没有统一日志。
- Python Agent 广泛使用标准库 `logging`，但没有统一的结构、级别、字段白名单和落盘目的地；部分现有日志可能包含命令、路径或异常原文。
- CLI 把 sidecar stderr 无上限累积在内存中，正常退出时又不保留，既有内存增长风险，也会丢失关键 Agent 诊断。
- 现有 Run 总耗时、Pool 和文件工具指标分散且多数随进程退出丢失，无法还原一次 Run 为什么失败、慢在哪里。
- 当前同步 `writeSync` 适合少量 Web 事件，不适合扩展到核心执行热路径，否则日志本身会干扰要测量的性能。
- 当前日志路径和实现主要按 POSIX 语义形成，尚未把 Windows 的路径、权限和“打开文件不可删除/重命名”等行为纳入统一验收。

本任务要建立一条本地优先的诊断链路：

```text
CLI / Agent 运行事实
  → 版本化 Diagnostic Event 契约与字段白名单
  → 各进程有界异步队列
  → ~/.harness/logs 下的进程独立 JSONL
  → harness logs 离线合并与 Run 时间线
```

SQLite 仍只保存恢复 Thread 必需的产品事实。Diagnostic Log 是可轮转、可删除的观察数据，不能参与 Thread 恢复、运行裁决或业务状态重建。

## 用户最终得到什么

### 默认可观察

- TUI、无头模式以及所有实际启动 Agent 的管理命令默认记录低流量、结构化的 INFO/WARN/ERROR 日志。
- 一次 Build 或 Compose Run 能从日志中看出：进程与初始化、Run 受理和终态、Runtime 获取、Context 构建、每次 Model/Tool 终态、关键 Persistence/IPC 操作、重试与稳定错误码。
- 根 Agent、内置或 Plugin 子 Agent、MCP 和普通 Tool 使用同一套 execution 关联规则；不同实现不再各写一套互不兼容的自由文本。
- CLI 与 Agent 分别写入自己的文件，不并发写同一个文件；查询时按 project、thread、run、execution 和已有活动身份合并。

### DEBUG 排障

- 用户可通过 `[diagnostics].level = "debug"` 持久开启 DEBUG，也可用 `HARNESS_LOG_LEVEL=debug` 临时覆盖；环境变量优先。
- DEBUG 增加状态转换、Provider retry 决策、队列与资源池状态、脱敏异常栈和有界错误摘要。
- DEBUG 不是关闭脱敏的开关：Prompt、Assistant 正文、源码、完整 Tool 参数/结果、完整命令、绝对工作区路径、原始协议 frame、Header、环境变量和 Secret 在任何级别都不落日志。

### Run 查询与性能分析

- `harness logs` 完全离线读取本地日志，默认列出当前 workspace 最近 Run；它不启动 Python sidecar、不读取 Thread SQLite，也不因查询再产生一份诊断日志。
- `harness logs --run <run-id-or-prefix>` 合并 CLI/Agent 文件，输出人类可读的阶段时间线、失败点和慢项；`--json` 输出稳定结构化结果，供脚本或 AI 分析。
- `harness logs` 默认只列出最近 20 个 Run。`harness logs --run` 默认最多返回 200 条关键事件且总输出不超过 256 KiB；用户可用 `--limit` 调整单页条数，但单页最大 1000 条且仍受字节上限保护。
- Run 查询支持 `--level <debug|info|warn|error>` 最低级别、`--event <name-or-namespace>` 事件或命名空间、`--component <cli|agent>` 组件过滤。不同类型过滤条件按 AND 组合；`--event tool` 匹配 `tool.*`，`--event tool.failed` 只匹配该具体事件。
- 输出被截断时，人类视图必须显示匹配数、已返回数、已省略数和可复制的下一页命令；`--json` 必须返回 `matched_count`、`returned_count`、`truncated` 与 `next_cursor`。
- `--cursor <token>` 是服务端生成的 opaque keyset cursor，不是由用户填写的数值 offset。它绑定 Run、过滤条件、排序位置和首次查询的快照终点，后续页不混入查询期间新增的日志；变更过滤条件明确报 cursor 不匹配，对应日志已被 retention 回收时返回稳定 `CURSOR_EXPIRED`，不能猜测位置继续。
- 性能口径明确拆分：总墙钟时间、主动执行时间、用户 Interaction 等待、retry 等待、Provider 首个有效分片时间和用户首次可见活动时间。审批或退避不能伪装成 Model/Tool 自身执行变慢。

### 本地生命周期

- Canonical 目录直接切换为 `~/.harness/logs`；不再双写 `~/.harness/debug`，也不自动搬迁旧文件。
- 默认保留 14 天、总量上限 200 MiB、单文件约 16 MiB；达到任一上限时优先回收最旧的已关闭文件。
- 日志生产路径只做有界入队，不同步等待磁盘。队列拥塞时优先丢 DEBUG、再丢 INFO，为 WARN/ERROR 预留容量，并通过 `logging.dropped` 暴露有界丢弃计数；正常关闭执行有超时上限的 flush。
- 日志目录或文件不可用、写入失败、轮转失败和查询遇到坏记录都不能阻断 Harness 的主要功能。

## 三平台兼容边界

本功能必须在 macOS、Linux、Windows 上行为等价，而不是只保证 TypeScript/Python 可以编译：

- 用户目录通过平台 API 解析；macOS/Linux 使用 `~/.harness/logs`，Windows 对应 `%USERPROFILE%\.harness\logs`，不得手拼 POSIX 路径。
- 文件名、JSONL 编码、时间戳和 Run 查询不能依赖 `/` 路径分隔符、Unix signal、进程枚举、inode、`flock` 或仅 POSIX 可用的原子语义。
- Rotation/retention 不删除或重命名仍由任一进程打开的 active 文件；必须覆盖 Windows 对打开文件操作更严格的行为。
- POSIX 上继续验证目录 `0700`、文件 `0600`。Windows 使用运行时可提供的用户级访问边界并在文档中准确说明，不把无效的 POSIX mode bit 当成安全保证。
- CLI/Agent 进程文件发现、排序、损坏行跳过、正在写入文件快照读取和退出 flush 都需要三平台测试或 CI 证据。

## 范围

1. 定义独立于 JSON-RPC v3 业务 Event 的版本化 Diagnostic Event 契约，固定 envelope、事件目录、级别、字段类型、可选关联身份、错误结构、大小上限和跨语言一致性检查。
2. 为 CLI 与 Python Agent 建立各自进程内、共用契约的有界异步 writer；支持安全创建、轮转、保留、丢弃计数、有界 flush、失败降级和三平台文件生命周期。
3. 将 CLI logger 提前到所有实际启动 Agent 的入口，修复 sidecar stderr 无界累积和正常退出丢失；保持 CLI stdout 用户输出与 Agent stdout JSON-RPC 的严格纯净。
4. 收敛 Python 标准库日志：普通自由文本不能未经字段白名单直接进入 Diagnostic Log；现有包含命令、路径、资源和异常原文的调用迁移为安全事件或受控摘要。
5. 覆盖 Process/Initialize、Run、Model、Tool、Runtime、Context、Persistence、IPC 的核心低流量事件。INFO 记录终态与关键耗时，DEBUG 记录必要内部状态；不记录每个流式 frame 或 SQL statement。
6. 复用现有 `thread_id`、`run_id`、`execution_id`、`parent_execution_id`、`tool_call_id`、`event_id`、`sequence` 与 `activity_id`；Model 在 execution 内使用 `model_round` 和 `provider_attempt`。当前不引入 `session_id`、`trace_id`、`span_id`。
7. 新增 `[diagnostics]` 本地配置，当前只开放 level、保留天数、总容量和单文件容量；日志根目录保持固定，不允许配置任意输出路径。
8. 实现完全离线的 `harness logs`、`harness logs --run` 和 `--json`；默认限制为当前 workspace，支持 Run ID 唯一前缀、级别/事件/组件过滤、输出字节与条数双重上限，以及绑定查询快照的 keyset cursor 分页；安全合并多进程文件并报告损坏行与不支持的 schema。
9. 更新用户日志/故障排查文档与本地诊断架构，明确三平台路径、安全边界、性能口径、开启 DEBUG 和提交问题前的脱敏检查。

## 非范围

- 不实现远端 telemetry、遥测上传、OTLP、OpenTelemetry Collector 或企业集中采集。
- 不实现 Trace/Span、Perfetto、Chrome Trace 或新的产品 `session` 身份。
- 不实现 `harness doctor`，不让 `harness logs` 读取 SQLite、Prompt、Tool Artifact 或其他业务正文。
- 不向 Thread SQLite 新增性能字段，不把 Diagnostic Log 作为恢复、幂等或业务判断的事实来源。
- 不提供关闭脱敏、记录原始 Prompt/源码/Tool payload 的 DEBUG 模式或原文诊断包。
- 不记录每个流式 token/frame、每条 SQL statement 或无界第三方 stdout/stderr。
- 不提供默认或显式无界的 `--all` 输出；完整原始数据仍由用户直接读取对应 JSONL 文件，CLI 查询始终受条数和字节上限保护。
- 不开放自定义日志目录，也不实现日志远程共享、上传或自动 Issue 提交。
- 不迁移、双写或自动清理旧 `~/.harness/debug` 文件。

## 可观察验收

- [ ] macOS、Linux、Windows 上，TUI、无头模式和实际启动 Agent 的管理命令默认在用户级 `.harness/logs` 产生可解析 JSONL；CLI 用户输出和 Python JSON-RPC stdout 不包含日志文本。
- [ ] CLI 与 Agent 各自写独立文件，文件可通过安全 project/run/execution 身份合并；并发 Run、子 Agent 和 PID 复用不会把不同执行错误关联。
- [ ] 默认 INFO 日志能还原一条包含 Model 和 Tool 的 Build Run，也能还原 Compose、内置/Plugin 子 Agent、MCP 的共有执行边界；成功、失败、取消、重试和资源释放均有稳定终态。
- [ ] `[diagnostics].level` 可持久配置，`HARNESS_LOG_LEVEL` 可临时覆盖。DEBUG 相比 INFO 增加内部诊断，但自动化测试证明任何级别都不包含 Prompt、源码、Tool 参数/结果、完整命令、绝对工作区路径、协议原帧或测试注入的 Secret。
- [ ] Model 与 Run 性能事件分别提供明确的总时间、主动执行、Interaction 等待、retry 等待、Provider 首分片和首次可见活动口径；多回合和多次 provider attempt 不互相覆盖。
- [ ] 日志热路径不调用同步磁盘写入。慢磁盘和队列溢出测试证明 Agent 继续执行，DEBUG/INFO 按策略丢弃，WARN/ERROR 预留容量生效，并能看到 `logging.dropped`；正常关闭只做有界 flush。
- [ ] 默认 14 天、200 MiB 总量、约 16 MiB 单文件轮转生效；只回收已关闭旧文件。Windows 打开文件、POSIX mode、跨平台路径分隔符和并发 writer 均有定向测试。
- [ ] 日志目录/文件不可写、磁盘写失败、轮转/清理失败时 Harness 主功能继续运行，并通过仍可用的安全通道给出有界诊断；不会递归记录日志系统自身错误。
- [ ] sidecar stderr 不再无界累积。Agent 普通 warning/exception 能按策略进入本地诊断，插件 Hook/LSP/Monitor 的专用 stdout 协议和不可信输出边界保持不变。
- [ ] `harness logs` 不启动 sidecar、不访问 SQLite，默认列出当前 workspace 最近 20 个 Run；`harness logs --run <完整ID或唯一前缀>` 默认最多返回 200 条且不超过 256 KiB，支持最大 1000 条的 `--limit`、`--level`、`--event`、`--component` 过滤，`--json` 输出版本化结构和分页元数据。
- [ ] 长 Run 分页使用绑定 Run、过滤条件、排序位置和快照终点的 opaque keyset cursor，不以数字 offset 从头扫描；翻页期间新增日志不会造成重复或漏读，过滤条件变化稳定拒绝，日志已被回收时返回 `CURSOR_EXPIRED`。
- [ ] 查询正在写入的文件、半行、单条坏 JSON 和不支持 schema 时不会整体失败；结果明确报告跳过/不支持计数，不猜测未知字段。
- [ ] 旧 `~/.harness/debug` 不再接收新日志，用户文档明确旧文件不会自动迁移或删除；新目录在 POSIX 上保持 `0700/0600`，Windows 安全语义有准确说明。
- [ ] CLI、Agent、Protocol/事件契约、配置、用户文档和架构测试同步更新；三平台 CI 或等价可复现证据、focused tests、包级测试、`bun run project:check`、`bun run typecheck` 和项目级测试结果写回本 Task。

## 需求确认与方案取舍

2026-08-27 已完成第三方方案审视和逐轮需求确认，结论如下：

1. 接受“SQLite 产品事实 / Diagnostic Log 诊断事实”的分层，但不接受附件中“现有 INFO 已足够分析性能”的事实判断；当前实现只有局部 Web 日志。
2. 当前功能必须同时交付统一基础设施、核心链路事件和最小 `harness logs --run`，否则只有 JSONL 文件仍不足以方便观察。
3. INFO 默认覆盖所有执行模式，DEBUG 必须交付且永不关闭脱敏。
4. CLI/Agent 使用进程独立文件和共同 schema，不并发写一个文件；查询负责合并。
5. 日志必须异步、有界、可丢弃低级别事件，不能为了“完整”同步阻塞 Agent。
6. 目录直接切到 `~/.harness/logs`，不为未发布内部路径保留 alias、fallback 或双写。
7. 当前不引入 Trace/Span，但保留已有事件/活动身份和未来按证据扩展技术关联的空间。
8. `harness logs` 同时服务人类和机器分析，但只读 Diagnostic Log；跨 SQLite 的 `doctor` 留待未来真实案例驱动。
9. macOS、Linux、Windows 是同一交付范围，任何只在 POSIX 上成立的 rotation、permission 或文件占用假设都不能通过验收。
10. `harness logs --run` 必须默认有界；分页采用可验证快照一致性的 keyset cursor，而不是会随日志增长漂移的数字 offset。人类和 JSON 输出都必须明确是否截断以及如何继续。

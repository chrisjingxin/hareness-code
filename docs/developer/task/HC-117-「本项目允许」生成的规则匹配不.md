## 背景

用户在 TUI 中对一次工具调用点击「本项目允许」后，Python 侧 `RunCoordinator._record_approval_rule()` 会调用 `_generate_permission_rule()` 生成一条 allow 规则，经 `save_rule(scope="project")` 持久化到 `<项目>/.harness/settings.json`。下一次工具调用时，`_make_approval_preflight()` 的 L4 层通过 `evaluate_tool_rules()` → `evaluate_bash()` → `evaluate_bash_segment()` 匹配这些规则，命中 allow 就跳过弹窗。

对 `execute` / `monitor` 这类 Shell 工具，规则的 resource 由 `harness_agent/policy/bash_parser.py` 的 `extract_command_rule()` 从命令 AST 提取；匹配则由 `harness_agent/policy/bash_matcher.py` 负责，resource 含 `*` 时走 `matches_command_glob()`，不含 `*` 时走 `matches_command_prefix()`。

本任务位于 `default` / `auto-edit` 模式下 execute 工具的审批复用链路。

## 当前存在的问题

### 问题 1：规则末尾强制追加 " *"，导致规则匹配不上自己

`extract_command_rule()` 在命令带参数时无条件拼接 `" *"`：

```python
rule_parts = [cmd_name] + [c[0] for c in candidates[:2]]
return " ".join(rule_parts) + " *"
```

而 `matches_command_glob()` 把 `*` 转成 `.*?` 后做 `re.fullmatch`，`*` 前面的空格是被 `re.escape` 转义的**字面量**，必须真实存在。因此当被批准的命令中，规则保留的最后一个 token 恰好就是命令的最后一个 token 时，规则永远匹配不上原命令。

实测结果（`packages/agent/.venv` 环境）：

| 被批准的命令 | 生成的规则 | 重跑同一条命令能否命中 |
| --- | --- | --- |
| `dir "C:\...\新建文件夹"` | `dir "C:\...\新建文件夹" *` | 否 |
| `type "C:\...\hhh.txt"` | `type "C:\...\hhh.txt" *` | 否 |
| `git status` | `git status *` | 否 |
| `dir /b "C:\...\新建文件夹"` | `dir /b *` | 是 |
| `cd` | `cd` | 是 |

后果：用户点了「本项目允许」，规则确实写进了 `.harness/settings.json`，但下一次执行**完全相同**的命令仍然弹窗，用户感知为"本项目允许不生效"。`git status` 也中招，说明这不是 Windows 专属缺陷。

现有测试 `packages/agent/tests/host/test_approval_protocol.py::test_approve_always_persists_rule_to_project_layer` 只断言规则被写入文件，没有断言"规则能匹配回原命令"，因此未暴露该缺陷。

### 问题 2：路径参数被当作子命令，规则被绑死在具体路径上

`extract_command_rule()` 的设计假设是"根命令 + 子命令"结构（`npm install *`、`git commit *`、`docker compose up *`），第一个非 flag 参数会被保留进规则。对 `dir <路径>`、`type <文件>` 这类"根命令 + 位置参数"的形态，路径被当成子命令固化进规则，导致规则只对那一个路径有效，换个目录仍需重新审批。

### 问题 3：Windows 风格 flag 不被识别

`extract_command_rule()` 判断 flag 的条件只有 `text.startswith("-")`，`/b`、`/s`、`/w` 这类 Windows cmd 开关会被当作子命令候选。结果 `dir /b "<路径>"` 生成 `dir /b *`，而 `dir /w "<路径>"` 不匹配该规则，需要为每个开关分别审批。

### 问题 4：链式命令只生成首段规则

`extract_command_rule()` 在 AST 遍历中命中第一个 `command` 节点即 `return`，且 `_generate_permission_rule()` 的返回类型是单个 `PermissionRule`，从签名上就无法表达"一条链式命令对应多条规则"。对 `echo hello> "a.txt" && dir /b "<路径>"`，只产出 `echo hello *`，`dir /b` 段完全没有规则。而 `evaluate_bash()` 的汇总是合取式——所有段都 allow 才整体 allow，因此下次执行同样的链式命令依然弹窗。

评估侧（`evaluate_bash()` → `extract_segments()` → 逐段 `evaluate_bash_segment()`）本来就是按段判断的，生成侧却只看第一段，两侧不对称，这是本问题的实质。

### 问题 5：只读命令白名单只有 Linux/macOS 命令，缺 Windows

`harness_agent/policy/safe_commands.py` 的 `ALWAYS_SAFE_COMMANDS` 是纯 Unix 集合：

```python
ALWAYS_SAFE_COMMANDS: frozenset[str] = frozenset({
    "ls", "cat", "pwd", "whoami", "head", "tail", "wc", "sort", "uniq",
    "tr", "cut", "echo", "date", "uname", "df", "du", "free", "uptime",
    "which", "whereis", "file", "stat", "id", "groups", "hostname",
    "printenv", "basename", "dirname", "realpath", "readlink",
})
```

本项目需在 Linux、macOS、Windows 三平台使用，但这份名单只覆盖前两者，且连 macOS 专有的只读命令（`sw_vers`、`vm_stat`）也没有。Windows 侧 `dir`、`type`、`where`、`findstr`、`ver`、`tree` 等 cmd 命令，以及 PowerShell 的 `Get-ChildItem`、`Get-Content`、`Select-String` 等只读 cmdlet 全部缺失。

后果：同一个项目在 macOS 上开发体验正常，切到 Windows 就退化为"每条命令弹一次窗"，L3.1 快速放行层形同虚设。实测确认 `dir`、`type a.txt`、`where python`、`findstr foo`、`sw_vers`、`vm_stat`、`Get-ChildItem`、`Get-Content a.txt`、`Test-Path a` 当前全部返回 `is_safe_command() == False`。

解析层不构成障碍：实测 `get_command_root()` 对 PowerShell cmdlet 与 macOS 命令都能正确取到根命令，`extract_segments()` 也能正确处理 PowerShell 的 `;` 与 `|`，缺的只是名单本身。

`harness_agent/policy/shell_allow_list.py` 的 `_RECOMMENDED_SHELL_ALLOW_LIST` 同样只覆盖 Unix 生态，属于另一层独立硬拦截，需一并评估。

### 问题 6：协议标识符 `approve_always` 与实际作用域不符

该决策的实际语义是"把规则写入当前项目的 `.harness/settings.json`"，作用域是项目级而非全局永久。界面文案已在本任务之前先行改为「本项目允许」（`packages/cli/src/presentation-shared/interaction-policy.ts`），但协议标识符仍叫 `approve_always`，与文案和实现都对不上，读代码的人容易误以为它是全局生效。

涉及位置：`packages/protocol/schema/v3.json`、`packages/protocol/src/generated.ts`、`packages/agent/harness_agent/protocol/protocol_v3.json`、`packages/agent/harness_agent/protocol/generated.py`、`packages/cli/src/interactive/types.ts`、`packages/cli/src/presentation-shared/interaction-policy.ts`、`packages/cli/src/tui/application/adapter.ts`、`packages/cli/src/tui/presentation/timeline.tsx`、`packages/agent/harness_agent/host/run_coordinator.py`、`packages/agent/harness_agent/policy/rule_parser.py` 及两端相关测试。

### 复现路径

在 Windows 上以 default 模式启动，依次执行以下命令并每次选择「本项目允许」，可复现出如下 `.harness/settings.json`（问题 1 与问题 2 的直接产物）：

```json
{
  "permissions": [
    "Bash(cd)",
    "Bash(dir \"C:\\Users\\PC\\Desktop\\新建文件夹\" *)",
    "Bash(dir /b *)",
    "Bash(echo hello *)",
    "Bash(type \"C:\\Users\\PC\\Desktop\\新建文件夹\\hhh.txt\" *)"
  ]
}
```

其中第 2 条和第 5 条永远匹配不上任何命令，属于死规则。

## 为什么现在要修改

- 「本项目允许」是审批体系里唯一的跨会话降噪手段。它静默失效会让用户认为审批系统有 bug，并被迫反复批准同一操作，直接损害可用性。
- 缺陷是静默的：规则写盘成功、没有任何报错，用户与开发者都无法从日志判断原因，排查成本高。
- 死规则会持续累积在 `.harness/settings.json` 中，既污染配置文件，也让后续的规则管理/展示功能建立在脏数据上。
- 本项目需在 Linux、macOS、Windows 三平台使用，但白名单只覆盖 Linux/macOS 的一部分。同一份代码在 Windows 上退化为"逐条审批"，在 macOS 上也缺少平台专有的只读命令，与 default 模式的设计意图不符。
- `sort` 与 `date` 在 Windows 上分别可写文件和交互式挂起，是当前就存在的放行漏洞，必须随白名单改造一并修掉。

## 目标设计

### 1. 规则生成与匹配达成闭环

核心 invariant：**任何由 `extract_command_rule(cmd)` 生成的规则，必须能匹配 `cmd` 自身。**

已确认采用方案 B（详见 [HC-117 方案设计](../spec/HC-117-「本项目允许」生成的规则匹配不.md)「决策 3」）：`extract_command_rule()` 不再追加 `" *"`，改为输出纯前缀，走 `matches_command_prefix()` 的 token 前缀匹配。匹配侧的双分支保持不变，用户手写在 `settings.json` 里的含 `*` 规则仍走 glob。

方案 B 附带一层强制安全防护，已确认为双层（方案设计「决策 4」）：

- **约束 A（生成侧）**：不得生成裸根命令规则。`rm foo.txt` 去掉位置参数后只剩 `rm`，前缀匹配会让它命中 `rm -rf /`。因此维护一个"不得单独成规则"的根命令集合（`rm`、`del`、`mv`、`cp`、`chmod`、`dd`、`curl` 等），这些命令只剩裸根时不生成规则，本次批准只对当次生效。
- **约束 B（预检侧）**：在 `_make_approval_preflight` 的 `effect == "allow"` 分支加安全底线检查，但**按剥掉规则前缀后的剩余部分判定**，而非整条命令。

之所以两层都要，是因为已确认 allow 规则命中时 `evaluate_safety_floors()` 不会被调用，且 `default` 模式下没有任何执行层防线拦得住 shell 命令（`AutoDestructiveGuardMiddleware` 只在 `auto` 模式注册）。而两层各有盲区：约束 A 拦不住用户手写的宽规则，约束 B 拦不住 `rm -rf /`（其危险性来自参数，不触发任何底线）。

约束 B 必须按剩余部分判定，否则会直接毁掉本功能：底线中的 `exec_risk` 覆盖 `git commit`、`npm run`、`make`，若对整条命令判定，用户对 `git commit` 点「本项目允许」后规则将永远不生效。

### 2. 规则粒度

已确认决策（详见方案设计「决策 5」，含完整工作示例表）。由于方案 B 的前缀匹配要求规则必须是命令开头**连续的若干个词**，问题被简化为"保留前几个词"：

- 词分三类：**子命令词**（`^[A-Za-z][A-Za-z0-9_-]*$` 且不含 `.` `/` `\` `:` `~` `*` `?` `=`）、**开关**（`-` 开头，或在 Windows 平台上形如 `/b`）、**操作数**（其余，即路径、文件名、URL 等）。
- 命令根始终保留；从第 2 个词起遇到开关或操作数即停止；子命令词中**第一个无条件保留**，第二个及以后只有其后紧跟开关才保留；最多保留 3 个词。
- Windows 开关识别按平台门控，复用决策 2 引入的 platform 参数。Unix 上 `/` 开头是绝对路径，不能当开关。
- `run`/`exec`/`x`/`dlx` 之后的那个词必须保留（`npm run build` → `npm run build`），因为 `npm run` 等价于执行任意脚本。
- 环境变量前缀（`NODE_ENV=test npm run build`）在生成侧与匹配侧必须用同一个 `strip_wrappers()` 处理，否则规则不是命令的词前缀。

"第一个子命令词无条件保留"是关键：它区分了 `git status` 的 `status`（必须保留，否则规则退化为 `git` 会放行 `git push --force`）与 `npm install express` 的 `express`（应丢弃）。

### 3. 链式命令

已确认决策（详见 [HC-117 方案设计](../spec/HC-117-「本项目允许」生成的规则匹配不.md)）：链式命令必须先拆分、再逐段判断，生成侧与评估侧对齐。

`_generate_permission_rule()` 的返回类型由单个 `PermissionRule` 改为 `list[PermissionRule]`：对 `execute` / `monitor` 工具，先用 `extract_segments()` 拆段，每段各自经 `extract_command_rule()` 生成一条规则，全部记录。`_record_approval_rule()` 相应改为遍历写入（session 追加或 project 落盘）。

关键 invariant：**一次批准所产生的规则集合，必须让同一条命令在下次执行时整体命中 allow。** 由于 `evaluate_bash()` 是合取式汇总，只要有一段没有对应规则，整条命令就会重新弹窗——因此逐段生成不是优化，而是正确性要求。

### 4. 只读命令白名单覆盖三平台

本项目需在 Linux、macOS、Windows 三个平台上使用，白名单必须同时覆盖三者的只读命令。已确认决策与完整名单见 [HC-117 方案设计](../spec/HC-117-「本项目允许」生成的规则匹配不.md)「决策 2」，要点：

- 白名单按宿主 `sys.platform` 门控，而非把三平台命令无条件合并。原因是同名命令跨平台语义不同，合并会产生放行漏洞。
- Linux 追加 `free`、`uptime`、`lscpu` 等；macOS 追加 `sw_vers`、`vm_stat` 等；Windows 追加 cmd 的 `dir`、`type`、`where`、`findstr` 等与显式列举的 PowerShell 只读 cmdlet。
- `cd` 纳入通用集合：已确认 `execute` 每次调用新建 subprocess 且 `cwd` 固定为 workspace root，`cd` 不影响后续调用，等价于空操作。
- `where` 纳入 Windows 集合，并附 ScriptBlock 防护（命令段含 `{` 一律不放行），以覆盖 PowerShell 中 `where` 为 `Where-Object` 别名的风险。
- PowerShell cmdlet 必须显式列举，不得用"以 `Get-` 开头即只读"的前缀启发式；接受 ScriptBlock 的 `ForEach-Object`、`Where-Object` 等必须排除。
- 平台判定需可注入，使三平台名单都能在单一 CI 机器上被测试覆盖。
- 白名单命中只跳过弹窗，`evaluate_safety_floors()` 与 `has_dangerous_args()` 仍然生效（例如 `dir > out.txt` 仍需审批）。
- 评估 `shell_allow_list.py` 的 `_RECOMMENDED_SHELL_ALLOW_LIST` 是否需要同步补充，避免白名单放行后又被硬拦截层拒绝。

### 4.1 顺带修复两个既有的跨平台漏洞

排查白名单时发现，现有名单里有两条命令在 Windows 上行为与 Unix 不同，属于当前就存在的缺陷：

- `sort` 已在白名单中，但 Windows 的 `sort /O out.txt` 会**写文件**，等于自动放行了一次写操作。
- `date` 已在白名单中，但 Windows cmd 下无参数的 `date` 会**交互式提示修改系统日期**，在非交互执行环境下会让工具调用挂起。

两者都需在本任务一并处理。

### 4.2 附带发现：POSIX 分词破坏 Windows 路径

`safe_commands._tokenize_segment()` 用 `shlex.split()`（POSIX 模式），未加引号的 Windows 路径会被吃掉反斜杠：`dir C:\Users\PC\Desktop` 分词为 `['dir', 'C:UsersPCDesktop']`。该结果只用于 `has_dangerous_args()` 与 `_extract_git_subcommand()`，不影响根命令判定（走 tree-sitter），但危险参数检测建立在被破坏的 token 上，存在漏检风险。Windows 平台应改用非 POSIX 分词并补测试。

### 5. 脏规则处理：不做检测，改为可诊断日志

已确认决策（详见方案设计「决策 6」）：**不自动跳过、不自动改写**用户的 `settings.json`。

理由是"一条规则是否永远匹配不上"在一般情况下无法可靠计算——曾考虑用"规则能否匹配它自己去掉 ` *` 后的形式"判定，但会把用户手写的 `Bash(git *)` 误判为废规则。而废规则本身是安全的（顶多多问一次），用不可靠的自动化去修一个无害问题，风险大于收益。

改为两条诊断措施：

- 审批弹窗触发时，若存在同工具的 allow 规则却一条都没命中，向结构化日志写一条 debug 级记录（命令、参与匹配的规则、每条未命中的原因）。这直接回答"我点了本项目允许为什么还问我"。
- 启动时若某条规则 resource 同时满足"以 ` *` 结尾"和"包含 `:` 或 `\`"（旧版缺陷的确定性产物），记一条 info 日志提示可手工删除。仅提示，不改变行为。

### 6. `approve_always` 改名为 `approve_project`

按仓库当前的发布阶段原则（未正式发版，不保留内部兼容层），直接全量改名，不保留 alias、不做双写、不接受旧值。改完后仓库内不应再有 `approve_always` 字面量。

改名顺序：先改 `packages/protocol/schema/v3.json`，运行 `bun run protocol:generate` 重新生成 TypeScript 与 Python 两端的 generated 文件（注意仓库当前的 `validators.generated.ts` 已处于过期状态，改名前先跑一次 generate 让基线干净），再改两端手写代码与测试。

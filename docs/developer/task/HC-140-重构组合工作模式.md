## 背景

HC-138 已交付 Build / Compose 双 Mode、固定 `Understand → Plan → Build → Verify → Review` 状态机、真实验证 evidence、独立 Reviewer 和双端过程展示。这条路径在单个长 Run 内可靠，但把一次用户输入当作一个全新的 ComposeRun：每次 `ComposeRunAdapter.execute()` 都调用 `ComposeStateMachine.initial()`，所以用户输入“继续”也会重新进入 Understand。

对 MiMo Code 最新源码、当前 Harness 实现和企业模型约束的复核表明，问题不在于“是否使用状态机”，而在于流程身份和事实源选错：功能目标应跨多个 Run 持续，阶段应由当前产物是否有效决定；LangGraph checkpoint 只能保存模型执行状态，不能替代工作目标、人工确认、副作用结果和验证新鲜度。

本任务直接替代 HC-138 中“每条 Compose 消息启动一条固定五阶段 Run”的产品语义，不为旧内部类名、表形状或状态迁移保留 alias、fallback 或双写。HC-138 保留为历史实现记录；HC-139 已建立的过程可观察能力迁移到 Work Item / Activity projection。

## 用户最终得到什么

用户进入 Compose Mode 后，可以在同一个 Thread 中顺序完成多个研发 Work Item：

```text
Compose Thread（Mode 锁定）
├─ Work Item A：completed
├─ Work Item B：abandoned
└─ Work Item C：active
```

每个 Work Item 在用户工作空间产生一套可读、可编辑、可纳入 Git 的文档：

```text
docs/compose/<work-item-slug>/
├─ task.md
├─ spec.md
├─ plan.md
├─ todo.md
└─ report.md
```

用户分别确认 Task、Spec、Plan/Todo；之后实现、真实验证和独立 Review 自动闭环。用户中断、模型 429、CLI/Host 退出或进程崩溃后，系统从当前 Work Item 的安全边界继续，不重新理解已经确认的内容。

## 已确认产品决策

1. Compose 仍是独立 Mode，不改成 Build 中的 `/compose` 命令；Thread 首条有效消息受理后 Mode 锁定，普通交互不能从 Compose 切到 Build。
2. 一个 Compose Thread 可以顺序承载多个 Work Item，但同一时刻最多一个 `active|waiting_user|blocked` Work Item。
3. Work Item 完成或放弃后，新 coding 目标在同一 Thread 中创建新 Work Item，无需新建 Thread。
4. `/new-work`、`/abandon` 只在 Compose Mode 的补全、菜单、帮助和 UI 中可见；`/btw` 在 Build、Compose 都可见且只做临时只读问答。
5. `/abandon` 必须经过 typed confirmation；它终结 Work Item、取消当前 Activity，但不删除或回滚文档、代码、测试和审计记录。Esc/取消 Run 只中断当前执行，Work Item 仍可继续。
6. 自然语言由小上下文 `TurnIntentResolver` 分类为继续、修订当前任务、新任务、临时问题或不明确；分类器无权直接放弃任务或创建冲突 Work Item，歧义必须交给用户选择。
7. Compose 产物写入用户工作空间。默认根目录为 `docs/compose/`，只允许通过 `compose.docs_dir` 修改根目录；Work Item 内五个文件名固定。
8. SQLite 保存 Work Item、Activity、文档 digest、用户确认、effect intent/receipt、verification evidence 和 reviewer provenance；Markdown 保存需求与研发产物正文。数据库不复制 Markdown 全文。
9. 固定五阶段权威状态机删除，改为 readiness gate；UI 可继续显示阶段，但只是当前 readiness 的投影。
10. 需求、规格、计划三个门禁分别使用原版完整 Skill：先观察效果，不做精简、改写或摘要版私有方法资产。
11. 原版 Skill 随 Harness 固定打包到统一内置 Skill 目录，保留 upstream 来源、版本、license、digest 和完整附属资源；缺少 required Skill 时 fail closed。
12. Build 主 Agent、Compose Activity 和 Plugin Agent 统一经过 `ManagedAgentExecutor`，共享 AgentEnginePool、DeepAgents/LangGraph、execution stream、Policy、Tool、MCP、Sandbox、取消和 checkpoint。
13. Compose 首版只使用固定内置角色，不能自动选择 Plugin Agent；统一 executor 只提供显式绑定能力，自动 specialist routing 留给后续 Task。
14. Work Item 必须支持 Host/CLI 重启恢复。模型生成到一半的 token 不续写，只从 Activity 和 Tool effect 的安全边界恢复；结果未知的副作用必须阻塞而不是盲目重放。

## 目标流程

```text
用户 Turn
  → Mode / Command / Pending Interaction 确定性路由
  → TurnIntentResolver（仅自然语言歧义）
  → 载入或创建 ComposeWorkItem
  → 读取 docs/compose/<slug>/*.md + SQLite ledger
  → 重新计算 readiness
  → 选择第一个未满足或 stale 的 Activity
  → 强制加载该 Activity 的原版内置 Skill
  → 通过 ManagedAgentExecutor 执行
  → 校验产物、记录 digest / receipt / evidence
  → waiting_user | blocked | turn_budget | completed
```

readiness 顺序为：

```text
task_confirmed
  → spec_confirmed
  → plan_confirmed
  → todo_executable
  → implementation_current
  → verification_fresh
  → review_fresh
  → report_current
  → complete
```

Task、Spec 或 Plan/Todo 被用户或外部工具修改后，Runtime 重新计算 digest，并使所有依赖该 revision 的下游实现证据、验证、Review 和 Report 自动 stale。

## 范围

- `ComposeRun → ComposeWorkItem` 领域模型、SQLite schema、恢复、唯一未终结项和 terminal CAS。
- 工作空间 `docs/compose/<slug>/` 文档契约、digest、确认与 lineage。
- readiness resolver、Activity program、TurnIntentResolver、typed clarification 和副作用 receipt。
- 原版内置 Skill bundle、manifest、来源/license/digest 校验和 Mode/Activity 可见性。
- Build、Compose Activity、Plugin Agent 的统一 `ManagedAgentExecutor`；迁移 Plugin `graph.ainvoke()` 和 Compose Stage 专用 stream loop。
- Compose Thread Mode 锁定、Work Item 命令、`/btw` 临时上下文、共享 Command Registry 和 TUI/Web 一致投影。
- Task/Spec/Plan 三次用户门禁、实现/验证/Review/Report 自动闭环。
- 429、取消、Interaction、Host shutdown、崩溃、torn receipt 和工作空间外部修改恢复。
- 删除 HC-138 固定状态机 canonical 路径，迁移 HC-139 activity 可观察语义，更新用户与架构文档。

## 非范围

- Compose 自动选择 Plugin Agent、模型自由 routing specialist 或 Plugin 自定义 Mode。
- 同一 Thread 并发执行多个 Work Item，或暂停 A 后并行执行 B 的调度队列。
- 精简、重写、自动合并原版内置 Skill；首版只做原样打包和确定性调用。
- 从模型 token 中间位置续写，或对 outcome unknown 的外部副作用自动重放。
- 自动 commit、push、PR、远端 CI 或发布；除非未来 Activity 明确建模并经过既有审批。
- 为旧 ComposeRun 状态、旧内部接口或未发布 SQLite 数据保留兼容读取、双写或 fallback。

## 可观察验收

- Compose Thread 发送首条有效消息后不能普通切换到 Build；完成一个 Work Item 后可直接输入新目标并创建第二个 Work Item。
- 用户输入“继续”不会重新生成已确认 Task；修改 Spec 会使 Plan、实现、验证和 Review 按依赖失效；临时问题不进入 Work Item ledger 或后续 ContextPack。
- `/new-work`、`/abandon` 只在 Compose 显示，`/btw` 在两种 Mode 显示；手输不可用命令不会作为 Prompt 发送给模型。
- Task、Spec、Plan/Todo 都写入用户工作空间并分别经过 typed confirmation；实现前缺任一确认都不能继续。
- 429、用户取消、Host 重启和进程崩溃后恢复同一 `work_item_id`；已确认完成的 Tool effect 不重复，结果未知时显示 blocked 原因。
- Build、Compose Activity、Plugin Agent 的 graph 执行、stream、Interaction、取消和错误映射通过同一个 `ManagedAgentExecutor` 测试面；Compose 不自动调用 Plugin Agent。
- Verification 和 Review 必须绑定当前文档与 workspace revision；任一相关文件变化后旧 evidence 不再显示 fresh。
- Build 行为无回归，Compose 不扩大文件、Shell、网络、MCP、Sandbox、Skill 或 delegation 权限。
- Python/Protocol/TypeScript/TUI/Web/fake-model E2E、数据库迁移、崩溃恢复和项目级检查全部通过，用户与架构文档同步。

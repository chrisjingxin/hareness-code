# HC-167 目标闭环

需求已用 `grilling` 与用户分三轮确认（2026-09-03）。用户结果与验收以本文为准；后续 Spec 只能细化实现，不能改变本文确认的产品边界。

## 通俗说明

现在用户可以让 Agent 做一件事，但 Harness 没有一张跨多轮保存的“目标卡”，也没有独立验收员在 Agent 准备结束时逐条确认结果。Agent 说“完成了”与用户要求真的完成，仍是同一方的自我判断。

本任务在 Build 模式加入 `/goal`：

```text
/goal <自然语言目标>
  → 目标不清楚：问关键问题；小歧义：列明假设
  → Criteria Agent 生成可验证的验收条件
  → 用户接受 / 编辑 / 驳回 / 取消
  → 接受后保存目标并自动开始工作
  → 主 Agent 执行，准备结束时由独立 grader 验收
      未满足：把具体缺口交回主 Agent，在同一 Run 内继续修改
      全满足：Harness 校验 Run 与目标版本后提交 complete
      达到上限或验收异常：结束本 Run，目标保持 active
```

这里的“持续目标”不是后台任务。目标能跨 Run、重启和普通后续消息继续存在，但系统不会在没有用户动作时无限创建新 Run。只有新目标被接受、修订被接受、`/goal resume` 或用户发送普通 Build 消息时才继续工作。

## 当前问题

1. Build thread 没有持久目标和验收条件；上下文压缩或开启下一 Run 后只能依赖历史消息重新推断。
2. 主 Agent 可以自行声称完成，没有与当前目标版本绑定的独立验收门禁。
3. Harness 没有目标 proposal、审核、暂停、阻塞、恢复、替换与完成的共享状态，TUI/Web 也无法展示统一进度。
4. DeepAgents 已有 RubricMiddleware，但尚未接入 Harness 的 Run context、事件协议、只读验证工具、模型身份和 SQLite 生命周期。
5. dcode 把长期目标存在稳定 LangGraph thread checkpoint；Harness 根图 checkpoint 按 run/execution 隔离，照搬会让下一 Run 丢失目标或形成 SQLite/checkpoint 双真源。

## 用户最终得到什么

### 1. 完整 `/goal` 命令

Build 模式提供：

- `/goal <目标>`：创建新目标；已有目标时先生成替换 proposal，确认前旧目标继续有效。
- `/goal`、`/goal show`、`/goal status`：查看 objective、criteria、状态、note、revision、grader 模型与迭代设置。
- `/goal amend <意见>`：生成修订 proposal；确认后原子替换，并自动继续工作。
- `/goal pause`：保留目标，暂停自动携带和 grading。
- `/goal resume`：恢复 active，并自动启动 continuation Run。
- `/goal clear`：清除当前目标和待审 proposal，不删除 transcript、文件修改或历史评估审计。
- `/goal model [模型或 clear]`：默认 grader 跟随当前主模型，也可选择策略允许的独立 grader；clear 恢复继承。
- `/goal max-iterations <N 或 clear>`：默认 3，可调整但不得超过 20；clear 恢复默认。

Compose 不展示也不接受这些命令；不新增独立 `/rubric` 或启动参数 `--goal`。

### 2. 先把目标说清楚

Criteria Agent 先判断目标能否安全转成可验收结果：

- 小歧义：生成带显式 assumptions 的草案，用户在审核时确认或编辑。
- 会改变范围、方案或完成定义的大歧义：通过共享问答交互提出少量关键问题，回答后重新生成。
- 用户确认前只保存 pending proposal，不激活、不启动主 Agent、不运行 grader，也不覆盖旧目标。

验收条件在所有审批模式下都必须人工确认。Auto/YOLO 不能跳过这个门禁。

### 3. 跨 Run 的目标状态

一个 Build thread 同时最多有一个 accepted goal 和一个 pending proposal。accepted goal 具有：

```text
active ──pause──> paused ──resume──> active
active ──遇到外部阻塞──> blocked ──用户普通回复──> active
active ──当前有效验收全部通过──> complete
```

普通 Build 消息继续携带 active goal；`/btw` 等旁路问答不携带、不 grading。`/plan` 规划阶段能看到目标，但不进行完成验收；计划批准进入实现后恢复 goal grading。

运行中发出的 amend/pause/clear 不改变当前 Run 已冻结的 goal revision，而是排队到当前 Run 的安全终态后原子应用。新目标或修订被确认后，旧目标作为审计历史保留。

### 4. 独立验收与自动返工

主 Agent 自然停止时，由独立 grader Agent 读取：

- 用户确认的 criteria；
- 有界、脱敏的执行记录；
- 工作区文件的只读视图；
- 受沙箱和审批约束的验证工具及已有测试证据。

Grader 没有编辑文件、写入工作区或扩大权限的工具。它默认继承主模型，但使用独立调用、独立 system prompt、独立上下文和结构化输出；用户可为当前 thread 选择单独 grader 模型，实际模型指纹随评估记录保存并可查看。

只有 `needs_revision` 在同一 Run 内把 gap 交回主 Agent 继续工作。默认最多 3 次，达到配置上限时 Run 结束，目标仍为 active，等待下一次用户动作；不自动创建下一个后台 Run。

### 5. 可靠的完成判定

Agent 调用 `update_goal(status="complete", note=...)` 只是在提交完成说明，不能自行越过验收。即使 Agent 未调用该工具，只要 grader 的当前有效检查全部通过，Harness 也会自动完成目标。

提交 `complete` 必须同时满足：

1. goal 仍为 active，且没有等待应用的新 proposal；
2. 被检查的是当前 accepted goal revision；
3. grader 对全部 criteria 给出可确认的通过证据并返回 `satisfied`；
4. evaluation 属于当前 grading run 和当前顶层 Run；
5. 当前 Run 正常完成，未取消、未异常终止；
6. 持久化 CAS 提交时 revision 仍未改变。

历史或恢复出的 `satisfied` 只能展示，不能再次触发完成。`failed` 表示 rubric 本身无法正确验收，`grader_error` 表示验收执行失败；两者都不能把目标标为完成。Agent 确认缺少权限、凭据、外部状态或用户决策时，可把目标标为 blocked 并保存原因。

### 6. 用户始终看得见

TUI 与 Web 使用同一 Interactive Core 状态，至少展示：

- 输入框附近常驻的 goal objective、active/paused/blocked/complete 状态和必要 note；
- proposal 的接受、编辑、驳回、取消交互；
- `checking`、每轮 `needs_revision`、`satisfied`、`failed`、`grader_error`、`max_iterations_reached` 的 Timeline 事件；
- `/goal show` 中的 criteria、revision、实际 grader 模型与迭代上限；
- blocked/complete 的一次性对话播报，避免只有状态栏变化。

## 已确认产品决策

1. 首版只在 Build mode 提供 `/goal`；TUI 与 Web 同时交付，共用 Command Registry、Dispatcher、InteractiveController 与 selector，不做端内业务状态机。
2. 完整核心命令包括创建、show/status、amend、pause、resume、clear、model、max-iterations；不交付独立 `/rubric` 与 `--goal`。
3. 采用 dcode 的持续语义：目标跨 Run 持久，单 Run 内自动返工；达到迭代上限后停止，不跨 Run 后台无限执行。
4. Criteria Agent 对小歧义列假设，对大歧义提问；用户确认前 proposal 不激活。所有审批模式都必须人工审核 criteria。
5. 目标被接受、amend 被接受和 resume 后自动启动 continuation Run。
6. 普通 Build 消息继续 active goal；`/btw` 等旁路操作不参与。Plan 规划阶段看得到目标但不 grading，批准实施后恢复。
7. 已有 active goal 时，新 proposal 确认前旧目标继续有效；确认后原子替换并保留审计。
8. Grader 默认继承主模型，并支持 thread-scoped 独立模型选择；实际 grader 模型身份必须可持久化、可查看、可审计。
9. Grader 只读并可调用受控验证工具，继承 EffectivePolicy、Sandbox、workspace roots 与审批约束，不能获得主 Agent 的编辑能力。
10. 当前正常 Run 对当前 revision 返回 `satisfied` 后自动 complete；`update_goal(complete)` 只提供 note。默认 3 次，可配置，硬上限 20。
11. Agent 正在执行时的 goal mutation 排队到安全边界，不中断当前 Run，也不修改其冻结 revision。
12. `/undo` 撤销了支撑完成的代码或对话时，保留 goal 定义但使旧完成证据失效并恢复 active；`/redo` 后重新验收，不能直接复用旧 satisfied。
13. Goal、proposal、status 与 evaluation audit 的唯一长期真源是 Harness SQLite；LangGraph state 只保存当前 execution 的 rubric 临时状态。
14. 优先直接复用 DeepAgents RubricMiddleware；先用当前 0.6.8 做真实 graph 兼容性验证。满足需求就直接接入，不复制或 fork dcode/SDK 实现；只有缺少已确认能力且回归可控时才升级依赖。

## 范围

1. Goal、proposal、evaluation 的 Harness SQLite schema、Repository/Service、revision/CAS、恢复、清理与审计边界。
2. Build-only typed Goal Protocol：命令操作、snapshot projection、proposal review interaction、状态 mutation 与 evaluation events。
3. Criteria Agent 的结构化 readiness/proposal 输出、分级澄清、只读上下文预算和所有模式下的人工审核。
4. Run 受理时读取并冻结当前 goal revision，通过有界 `goal.state` Dynamic ContextBlock 投影到模型；不得向用户 transcript 写隐藏 goal 消息。
5. 复用 DeepAgents RubricMiddleware 完成单 Run grade/revise；接入 grader 模型角色、只读验证工具、custom stream 翻译、迭代设置和错误语义。
6. 当前 Run、grading run、goal revision、正常终态与 pending proposal 共同构成的 Completion Guard。
7. TUI/Web 的命令、review、持久 Goal panel、状态详情和 Timeline 反馈。
8. 与普通 Build 消息、`/btw`、`/plan`、运行中 mutation、thread 恢复、Host 重启、undo/redo、取消与失败的组合行为。
9. 用户文档、同名 Spec/Plan/Todo，以及完成时新增或增量更新 Goal、上下文、Slash Command 和 Run 生命周期架构文档。

## 非范围

- Compose mode 的 Goal 生命周期或把 ComposeWorkItem 与 Build goal 合并。
- 多个并行 active goals、目标依赖图、父子目标或通用 workflow engine。
- 跨 Run 后台 scheduler、无人值守无限续跑、token/费用/wall-clock 总预算调度。
- 独立 `/rubric` 命令、启动参数 `--goal`、无头模式专用 goal 入口。
- Auto/YOLO 自动接受 criteria。
- Grader 编辑代码、写文件、发送外部消息或继承主 Agent 全部工具。
- 直接复制 dcode 的 TUI `app.py`、checkpoint private channel 或 synthetic HumanMessage notice 实现。
- 为尚不存在的旧 Goal 数据、旧 RPC 名称或内部实验接口保留兼容 alias、双写或迁移分支。
- 自动 commit、PR、发布或在 goal 完成时自动清理用户代码。

## 可观察验收

- TUI/Web 的 Build 命令菜单均出现 `/goal`；Compose 下隐藏，手输也得到稳定的仅 Build 提示。
- `/goal 为 status 增加 JSON 输出且保留旧文本` 会生成 objective、assumptions 与逐条 criteria；用户可接受、编辑、带反馈驳回再生成或取消。大歧义先走共享问答，确认前主 Agent 不开工。
- accepted goal 在输入框附近持续可见；退出并重启 Host、重新打开同一 thread 后 objective、criteria、状态、note、revision、grader 设置与待审 proposal 均正确恢复，但不会因恢复本身自动开 Run。
- 接受新目标、接受 amendment 或 `/goal resume` 后自动开始一个 Run；普通 Build 消息继续该目标，`/btw` 不携带；paused/complete 不 grading。
- `/plan` 规划 Run 能看到 active goal，但不因计划文本通过 grader 而 complete；批准进入实现后恢复验收。
- 主 Agent 第一次停止但缺少某条条件时，Timeline 显示 grader gap，Agent 在同一 Run 自动修订；全部条件满足后显示 satisfied 并自动 complete。
- 默认第三次仍不满足时显示 `max_iterations_reached`，当前 Run 结束且 goal 保持 active；配置 1～20 生效，0、负数、布尔值、非整数和大于 20 被稳定拒绝。
- Grader 默认显示继承的实际主模型；`/goal model` 只允许策略许可的模型并持久到 thread，clear 后恢复继承。Grader 能读文件和运行受控验证，但无法调用编辑/写入工具或扩大审批、沙箱与路径权限。
- Agent 自报 complete、历史 checkpoint 中的 satisfied、旧 goal revision、已取消/失败 Run、grader error 或有待应用 amendment 时，目标都不会错误完成。
- active Run 中输入 amend/pause/clear 时，当前 Run 继续使用旧 revision；终态后 mutation 只应用一次。被替换目标及其 evaluation 可审计，不能回写覆盖新目标。
- `update_goal(blocked)` 保存阻塞原因；用户普通回复后目标恢复 active 并带上 prior blocker。`update_goal(complete)` 没有当前 satisfied 时只记录申请，不完成。
- `/undo` 撤销完成依据后 goal 恢复 active、旧 evaluation 失效；`/redo` 不直接恢复 complete，必须重新验收。
- `/goal clear` 清除当前 goal 和 pending proposal，但保留 transcript、工作区改动与历史 evaluation audit。
- DeepAgents 0.6.8 兼容性验证覆盖真实 graph 的 rubric mapping input、needs_revision 跳转、custom event、ContextWindow、RunContextSnapshot 与 checkpoint cleanup；若升级依赖，Agent/Compose/IPC 全量回归必须通过。
- Python 与 TypeScript 两端的 Protocol、持久化、状态恢复、并发/CAS、Run 终态、权限、TUI/Web selector 和命令测试通过；`bun run build`、`bun run typecheck`、`bun run test`、`bun run project:check` 全绿。

## 建议的可演示停点（供后续 Plan/Todo）

1. **目标事实与双端可见性**：Build 下能创建一份人工确认的 goal，TUI/Web 都显示状态，Host 重启后恢复；Agent 下一 Run 能看到冻结目标，Transcript 没有隐藏 notice。
2. **Proposal 与完整生命周期**：澄清、编辑、驳回、替换、pause/resume/clear、运行中排队和自动 continuation 全部可见可用。
3. **独立验收闭环**：真实 RubricMiddleware 产生 checking/gap/satisfied 事件，主 Agent 在同一 Run 自动返工，Completion Guard 正确提交或拒绝完成。
4. **模型、Plan 与历史操作收敛**：独立 grader 模型、只读验证、`/plan`、blocked、undo/redo 与完整恢复矩阵通过。

实现按停点交付；未经用户要求不得一次做完整份 Todo。

## 背景

HC-098 已建立本地目录/ZIP staging、Agent Plugins/Claude Adapter、内容寻址 store、registry、
管理 RPC 与显式启停；HC-099 已把启用插件的 Skill 和 MCP 接入 Host 启动快照。因此本任务不是
新建 Plugin 系统，而是把 Agent Plugins 1.0.0 提升为完整、一等的 portable 标准实现，并让已有
Claude、hybrid 与 Harness client extension 继续通过同一内部 descriptor/runtime 工作。

- Agent Plugins Specification 1.0.0；

  `bd383552095128f6effe895b9257cfd580a6d179`；

  `developers.googleblog.com/agent-plugins-package-your-skills-tools-and-more/`；

## 2026-08-14 增量修复计划与执行 Todo

> 评审发现 3 个与 Design 基线的偏差：hybrid 双 manifest MCP 缺少跨 manifest 隔离、
> 迁移隔离记录聚合状态错误、迁移诊断前缀改名导致 trust 撤销面过大。前两项不涉及用户决策，
> 按本计划直接修复（Design 已同步修订）；第三项的实现取舍待讨论，本计划不修改该行为。

### 问题与方案

1. **hybrid 一个 manifest 的 MCP 顶层致命错误会连带丢弃另一个 manifest 的全部有效 server**。
   `mcp_adapter.py` 的 hybrid 分支对 portable 与 Claude 加载都没有 try/except，任一异常被最外层
   按“整个 Plugin 的 MCP 失败”处理。修复：在 hybrid 分支对两个 manifest 分别捕获 `PluginError`，
   失败侧记录稳定诊断并产出空 server 集合，另一侧结果照常合并；单格式包行为不变。
   验证：新增 hybrid 双方向测试（portable 坏 + Claude 好、Claude 坏 + portable 好），断言有效侧
   server 仍进入快照且诊断包含失败 manifest 的错误码。
2. **迁移重索引失败的隔离记录显示 `recognized`，Design 聚合表要求 `invalid`**。
   隔离记录组件库存为空且带有 `PLUGIN_REGISTRY_REINDEX_FAILED` 诊断，但 `_aggregate_compatibility`
   只看组件报告。修复：聚合函数接受插件级 diagnostics，在无 effective 组件、库存为空且带迁移
   失败诊断时聚合为 `invalid`（`can_enable` 保持 false）；规范有效的空组件包仍为 `recognized`。
   验证：更新既有隔离测试断言 `compatibility == "invalid"`、`can_enable is False`，并确认
   `empty-components` fixture 的 `recognized` 断言不回归。

## 2026-08-14 范围收缩：移除 registry v1→v2 迁移

### 决策与理由

用户确认工程尚未正式发布、无需保留未发布期间旧开发构建产生的 v1 registry 数据；为避免长期
维护一条永不再触发的 legacy 路径（含其诊断文本比较带来的保守 trust 撤销语义，即评审发现项
第 3 点），v1→v2 迁移机制整体移除。registry 只有 v2 一种 canonical 形状，旧开发版 v1 文件按
版本或结构无效失败关闭（`PLUGIN_REGISTRY_INVALID`），用户删除 Plugin 根目录后重新安装。

### 移除清单

- 生产代码：`PluginStore.migrate_registry`、`LEGACY_REGISTRY_VERSION`、迁移备份常量和
  `registry_backup_path`、`_write_migration_backup`、`_restore_registry_bytes`、
  `_has_registry_version`；`PluginManager._reindex_registry/_reindex_plugin`、
  `_component_inventory`、`_component_diagnostics`、`_append_diagnostic`；
  `model._REGISTRY_REINDEX_FAILED_DIAGNOSTIC_PREFIX` 及聚合函数中的迁移隔离分支。
- 测试：`packages/agent/tests/test_plugin_migration.py` 整文件。
- 错误码：`PLUGIN_REGISTRY_MIGRATION_FAILED` 不再存在。
- 文档：Design 迁移节转为「已撤销的 registry v1→v2 迁移」历史记录；架构总览、扩展与插件机制
  设计方案、用户插件管理与故障排查文档同步改为“registry 仅承认 v2、旧版本失败关闭”的现状描述。
- 保留：组件校验与隔离、staging/digest/tamper 检测、锁与原子写、显式 trust 全部不变；
  `test_host_startup_without_plugins_does_not_create_default_registry_lock` 继续有效。

### 验证口径

- 删除后 Python 全量与聚焦测试、`bun run typecheck`、`docs:check`、`tasks:check` 全绿；
  真实命令与结果写入下方「本次真实验证」。

## 为什么现在要修改

当前产品和文档已经对外声明支持 Agent Plugins 1.0，但现有证据只证明 Adapter 和部分生产链路存在，
尚不能证明所有适用规范要求已经落实。如果继续在现有语义上增加更多 Plugin 功能，
解析、运行和 registry 历史会进一步分叉，后续 marketplace 或网络安装还会放大供应链与兼容风险。
本任务先在仅本地来源的边界内完成一次直接迁移，保持输入面可控，并为未来来源扩展留下稳定契约。

## 用户结果

```text
本地目录或 ZIP
  → 既有安全 staging
  → Agent Plugins 1.0.0 完整规范门禁与解释
  → Skill / MCP 分类型、分条目隔离校验
  → compatibility + can_enable + diagnostics
  → 规范有效即可安装为 disabled
  → 至少一个 effective 组件且显式确认 capability fingerprint 后启用
  → 下一次 Host 快照按同一份 canonical 描述运行
```

升级时（~~2026-08-14 撤销~~：registry v1→v2 迁移机制已整体移除，旧开发版 registry 按
版本无效失败关闭、删除重建，见下方范围收缩记录）：

```text
registry v1 + 不可变 store
  → 锁内读取并逐包复核 digest
  → 使用新 Adapter 重算 portable/hybrid 描述
  → 能力或可用性变化则 disabled + trust revoked
  → 原子写入新 registry 版本
  → 失败保留旧 registry，不产生半迁移状态
```

完整的状态、失败边界、安全不变式和撤销记录见
[ZC-141 设计方案](../spec/ZC-141.md)。

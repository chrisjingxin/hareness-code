# HC-162 子代理时间线

## 背景与问题

主 Agent 已经能派出 `general-purpose` / `explore`，派出卡片也能看懂「交给谁、做什么」。但子代理内部仍用一次性跑完的方式执行：父时间线看不到它在读哪个文件、跑哪条命令、卡在哪一步。用户等审批或等到 `DELEGATION_TIMEOUT` 时，只能看到一张派出卡和一句超时错误。

HC-161 规格 9.2 曾设想把子代理工具起止点打到父时间线。需求核对后改为：主时间线继续只用现有派出卡片，子代理的完整过程进自己的时间线，点卡片才能进去。这是独立用户价值，从 HC-161 拆出本任务；HC-161 停点 3（排队/取消/超时/拆旧）让路，本任务先做。

## 用户最终得到什么

主时间线的 `task` 派出卡片保持现在的样子（谁接手、任务、结论）。卡片可点。

点进去之后：

- TUI 和 Web 是同一套交互：进入该子代理自己的时间线，而不是在主对话里再铺一层工具。
- 能看到这个子代理正在或已经做过的思考、工具调用（沿用现有工具渲染：文件、命令、Markdown 结论等）。
- 运行中会跟着更新，不必等它结束或超时。
- 只能看，不能在子视图里接着跟子代理对话。
- Esc 或明确的返回操作回到主 Agent 时间线。多个子代理时，点对应那张派出卡进入对应时间线。
- 子代理需要审批时，仍在主会话底部 FIFO 出现「子代理 {id} 需要审批」，不把审批搬进子视图。

父 Transcript / 下一轮主模型上下文不吸收子代理的思考和完整工具结果。`task` 回给主模型的仍是最终文本或稳定错误码。

交互参考 MiMo Code：主时间线派出卡可点；进入后看该 actor 的消息切片；底栏或快捷键可回主会话。不照搬 MiMo 的独立 session、peer、token 费用条。

## 范围

1. 子代理运行时把过程事件送到 CLI（工具起止、有界参数、思考、文本），并带上 `agent_id` / `execution_id`，使界面能组装独立时间线。
2. TUI：点现有派出卡片进入该子代理时间线；Esc/返回回主对话；子视图只读。
3. Web：同一套交互，不另做一种浏览方式。
4. 主时间线不渲染子代理工具过程，只保留现有派出卡片（任务/结论）和既有审批身份。
5. 运行中实时更新；子代理结束后仍可点进查看当时的时间线。
6. 用户文档说明怎么从派出卡进入、怎么返回。

## 非范围

- 不在子视图里向子代理发消息、改提示词或切换模型。
- 不把子代理思考/工具正文写入父 Transcript，也不把它们当作主 Agent 下一轮上下文。
- 不实现后台 SubAgent、fork、resume、mailbox、Agent Team、worktree。
- 不改 HC-161 的审批松紧、explore 只读边界、Forced exclusions。
- 不做 HC-161 停点 3（并发排队 4、取消/超时硬化、拆旧 Registry/文档）。超时仍按现有 `DELEGATION_TIMEOUT`；本任务只让超时前能看见过程。
- 不新增用户可配的子代理超时或独立模型。

## 可观察验收

- [x] `bun run dev` 派出 `general-purpose` 或 `explore` 后，主时间线只有现有派出卡片，没有子代理的 `read_file` / `execute` 过程行。
- [x] 点该卡片（TUI 与 Web）进入该子代理时间线，能看到它自己的思考和工具；运行中新工具会出现，不必等结束。
- [x] 子视图不能提交对话；Esc 或返回后回到主时间线，派出卡片仍在原处。
- [x] 同时派出两个子代理时，点哪张卡进哪条时间线，不会串。
- [x] 子代理 `execute` 审批仍在主会话底部，标题仍带「子代理 {id}」；进子视图再回主会话，待处理审批不丢。
- [x] 子代理超时或失败后，仍能点进时间线看到超时前最后几步，主时间线结论/错误与现有派出卡片一致。
- [x] 主模型下一轮看不到子代理中间工具正文；`task` 结果仍是最终文本或错误码。
- [x] focused tests 覆盖协议事件、父时间线不混入 child 工具、TUI/Web 进入与返回；相关包测试与 `bun run typecheck` 通过，证据写回本 Task。

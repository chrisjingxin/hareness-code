## 服务的用户结果

用户明确要求以企业内弱模型为前提。本任务避免仅凭强模型经验决定工具 schema，确保后续大
改造建立在实际生产模型能稳定调用的接口上。

## 评测流程

```text
固定 workspace fixture + 目标变更描述
  → 候选工具 schema / system prompt
  → 实际弱模型或固定 tool-call replay
  → 在隔离副本执行 fail-closed simulator
  → 判定最终文件、错误恢复、token 和调用轨迹
  → 输出去敏聚合报告
```

## 实施步骤

1. 建立不少于 24 个去业务化 fixture，覆盖单行/区间/插入/删除/多 edit、重复文本、相似
   函数、长文件、超长行、空文件、BOM、CRLF、末尾换行和错误路径。
2. 为 read 后外部变化、审批前变化、提交前变化、跨 Thread、过期 Snapshot、未读范围、
   路径写错和 overlap 增加对抗用例。
3. 实现纯 simulator：不依赖生产工具即可验证候选参数、应用 proposed content 并判定是否
   错文件/错版本/错范围。
4. 比较三类候选：当前 exact-string 加强版、Snapshot 单 range、Snapshot `edits[]`；插入
   至少比较显式 action 与隐式 range，禁止最终保留双语法。
5. 自动测试使用 mock model / 固定 tool-call replay；真实模型命令必须显式指定 Profile、
   重复次数和输出目录，默认不运行。
6. 报告安全性、schema 合法率、任务完成率、恢复成功率、input/output token、工具调用数、
   重读次数和延迟，并给出置信区间而非单次结论。
7. 按 HC-131 的安全优先门槛选择一个接口；若 range 候选不优于基线，明确保留 exact-string
   并修订后续子任务，不为了已写方案强行采用 Snapshot 行编辑。
8. 把报告写入 `docs/developer/research/弱模型文件编辑评测.md`，把最终 schema、常量和决策
   更新到 `docs/developer/spec/HC-131-统筹弱模型优先的文件读写可靠性.md`。

## 安全与数据边界

- fixture 使用合成代码，不上传仓库真实业务源码作为评测 prompt。
- API Key 只按现有模型配置引用，日志/报告不得输出值、请求 header 或完整响应正文。
- 每轮在临时 workspace 副本执行，不修改当前仓库。
- 真实模型评测不是 `bun run test`/pytest 默认步骤，避免 CI 使用生产凭据。

## 明确不修改

- 不切换生产 Agent 工具，不修改 Capability/Approval。
- 不实现最终 MutationService 或 backend 写入。
- 不根据单个模型、单次运行或主观示例定方案。

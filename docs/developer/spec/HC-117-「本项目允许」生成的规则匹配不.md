## 决策 1：链式命令逐段生成规则

### 通俗说明

- **现在的状况**：用户对一次工具调用点「本项目允许」后，系统会把这次调用总结成一条"以后遇到类似的就放行"的规则存起来。但如果这次调用是一条用 `&&` 串起来的组合命令（例如"先写文件，再列目录"），系统只会给**第一小段**存规则，后面几段等于没批准过。
- **为什么这算 bug**：判断要不要放行时，系统是**逐段检查**的，而且要求**每一段都被批准**才整体放行。生成规则时只看第一段，检查时却要看全部段——两边不对称，结果就是用户明明批准过一模一样的命令，下次还是被拦下来问一遍，而且永远问不完。
- **准备怎么解决**：让生成侧和检查侧对齐。批准一条组合命令时，先按 `&&`、`||`、`;`、`|` 把它拆成若干段，每段各自生成一条规则，全部存下来。
- **改完后的变化**：批准过的组合命令，下次原样执行不再弹窗；单条命令的行为完全不变。

### 已确认现状

**评估侧已经是逐段的。** `packages/agent/harness_agent/policy/bash_matcher.py` 的 `evaluate_bash()`：

```text
完整命令
  → extract_segments()            拆成若干段
  → 每段 strip_wrappers()          剥离 sudo/env 等包装器
  → 每段 evaluate_bash_segment()   逐段匹配规则
  → 合取式汇总：任一段 deny → deny；全部段 allow → allow；否则 ask
```

关键点是**合取式汇总**：只要有一段拿不到 allow（返回 `ask` 或 `None` 都算），整条命令就是 `ask`，即弹窗。

**生成侧只看第一段。** `packages/agent/harness_agent/host/run_coordinator.py` 的 `_generate_permission_rule()` 返回类型是单个 `PermissionRule`：

```python
def _generate_permission_rule(
    tool_name: str, tool_args: Mapping[str, object]
) -> PermissionRule:
    ...
    if tool_name in {"execute", "monitor"} and command:
        resource = _extract_command_rule(command)
```

而 `bash_parser.extract_command_rule()` 在 AST 遍历中命中第一个 `command` 节点即 `return`，不再看后续节点。签名本身就无法表达"一条命令对应多条规则"。`_record_approval_rule()` 相应地只处理一条。

**实测证据。** 对 `echo hello> "C:\...\hhh.txt" && dir /b "C:\...\新建文件夹"`：`extract_segments()` 正确拆出两段，但 `extract_command_rule()` 只产出 `echo hello *`，第二段无任何规则。

### 目标流程

```text
用户选择 本会话允许 / 本项目允许
  → _record_approval_rule(tool_name, tool_args, decision)
  → _generate_permission_rule(tool_name, tool_args) -> list[PermissionRule]
        ├─ execute / monitor：extract_segments(command) 拆段
        │     └─ 每段 strip_wrappers() 后 extract_command_rule() → 一条规则
        ├─ write_file / edit_file / apply_patch / delete_file：单条（现状不变）
        ├─ web_fetch：单条域名规则（现状不变）
        └─ 其他工具：单条通配（现状不变）
  → 遍历规则列表逐条写入
        ├─ approve_thread：去重后 append 进 _session_rules
        └─ approve_project：逐条 save_rule(scope="project")
```

### 关键 invariant

1. **批准闭环**：一次批准产生的规则集合，必须让同一条命令在下次执行时整体命中 allow。因为汇总是合取式，漏掉任何一段都会让整条命令重新弹窗，所以逐段生成是正确性要求而非优化。
2. **拆分口径一致**：生成侧与评估侧必须使用同一个 `extract_segments()` 与 `strip_wrappers()`，不得各自实现。拆分口径一旦分叉，会出现"规则存了但匹配不上"或"规则比用户批准的范围更宽"两类问题。
3. **不扩大授权范围**：逐段生成只覆盖用户本次实际批准并执行的那些段，不对未出现过的命令生成规则。
4. **单命令行为不变**：非链式命令拆分后只有一段，产出恰好一条规则，与改造前完全一致。

### 为什么不选"弹窗展示全部规则由用户逐条确认"

任务文档初稿曾把它列为备选。不采纳：用户批准的是"执行这条命令"，命令的每一段本来就都会被执行，逐段记录并未授予任何用户未批准的操作；而增加逐条确认会让链式命令的审批交互显著变重，与「本项目允许」的降噪目的相悖。授权粒度问题由 `extract_command_rule()` 的粒度改造解决，不在本节重复处理。

### 公开 interface 与错误模式

```python
def _generate_permission_rule(
    tool_name: str, tool_args: Mapping[str, object]
) -> list[PermissionRule]:
    """从被批准的工具调用上下文生成 allow 权限规则列表。

    Shell 工具按链式命令分段逐段生成；其余工具生成单元素列表。
    """
```

调用方只有 `_record_approval_rule()`，改为遍历写入。按仓库当前发布阶段原则，直接改签名并迁移调用方与测试，不保留返回单条的旧入口或兼容 wrapper。

错误与边界模式：

- `extract_segments()` 返回空列表：不生成任何规则，`_record_approval_rule()` 遍历空列表即无副作用，不得写入通配规则兜底。
- 某段经 `extract_command_rule()` 得到空字符串：跳过该段，其余段照常生成。下次执行该命令仍会弹窗，属于可接受的保守降级，不得用 `*` 填充。
- tree-sitter 解析失败：沿用 `extract_segments()` 已有的引号感知 fallback，不新增分支。
- 多段归约为相同规则（如 `dir a && dir b`）：写入前去重，`.harness/settings.json` 中不出现重复条目。
- `save_rule()` 中途失败：已写入的规则保留，不回滚。下次遇到未写成功的段会重新弹窗，属于安全方向的降级。

## 决策 2：只读白名单覆盖 Linux / macOS / Windows 三平台

### 通俗说明

- **现在的状况**：`default` 模式下有一份"只读命令白名单"，命中就不弹窗直接执行。但这份名单里全是 Linux/macOS 的命令（`ls`、`cat`、`pwd` 之类），一个 Windows 命令都没有。
- **造成的后果**：同一个项目在 macOS 上开发时体验正常，切到 Windows 就变成"每敲一条命令弹一次窗"，因为 `dir`、`type`、`where` 这些等价命令全都不在名单里。
- **准备怎么解决**：把三个平台各自的只读命令都补进名单，并且按**当前运行的操作系统**决定启用哪一份——因为有些命令名在不同系统上含义不同，混在一起放行会有安全漏洞。
- **改完后的变化**：三个平台上的常用只读命令都能直接执行，不再弹窗；同时不会因为跨平台同名命令而误放行有写入副作用的操作。

### 已确认现状

实测当前 `is_safe_command()` 的判定结果（`packages/agent/.venv` 环境）：

| 命令 | 平台 | 当前是否自动放行 |
| --- | --- | --- |
| `ls -la`、`cat a.txt`、`pwd` | Linux / macOS | 是 |
| `dir`、`type a.txt`、`where python`、`findstr foo` | Windows cmd | 否 |
| `sw_vers`、`vm_stat` | macOS | 否 |
| `Get-ChildItem`、`Get-Content a.txt`、`Test-Path a` | PowerShell | 否 |

`get_command_root()` 基于 tree-sitter-bash，但对 PowerShell cmdlet 与 macOS 命令都能正确取到根命令（实测 `Get-ChildItem -Path .` → `Get-ChildItem`，`sw_vers` → `sw_vers`），`extract_segments()` 也能正确处理 PowerShell 的 `;` 与 `|`。因此**解析层不构成障碍，缺的只是名单本身**。

### 关键 invariant

1. **按宿主平台门控**：白名单按 `sys.platform` 选择启用的集合。同名命令在不同平台语义不同，无条件合并会产生放行漏洞（见下方「同名命令的跨平台冲突」）。
2. **只列举，不用前缀规则推断**：不得用"以 `Get-` 开头即只读"这类前缀启发式判定 PowerShell cmdlet。必须显式列举，未列举的一律走审批。
3. **白名单不覆盖安全底线**：命中白名单只跳过 HITL 弹窗，`evaluate_safety_floors()` 与 `has_dangerous_args()` 仍然生效。任何带重定向、写副作用或危险参数的命令即使根命令在白名单内也必须弹窗。
4. **可测试性**：平台判定必须可注入。`is_safe_command()` 及其下层增加显式 platform 参数（默认取宿主平台），使三平台的名单都能在任意 CI 机器上被测试覆盖。

### 名单设计

**跨平台通用**（保留现有，三平台语义一致）：`ls`、`cat`、`pwd`、`whoami`、`head`、`tail`、`wc`、`uniq`、`tr`、`cut`、`echo`、`uname`、`df`、`du`、`which`、`file`、`stat`、`id`、`groups`、`hostname`、`printenv`、`basename`、`dirname`、`realpath`、`readlink`。

**Linux 追加**：`free`、`uptime`、`lscpu`、`lsblk`、`lsb_release`、`arch`、`nproc`、`vmstat`。

**macOS 追加**：`sw_vers`、`vm_stat`、`hostinfo`、`machine`、`arch`、`md5`、`system_profiler`。

**Windows 追加**（cmd）：`dir`、`type`、`cd`、`where`、`findstr`、`ver`、`vol`、`tree`、`systeminfo`、`tasklist`、`driverquery`、`fc`、`comp`。

`cd` 纳入白名单已确认安全，有代码依据：`execute` 每次调用都新建 subprocess，`cwd` 固定取自 backend 初始化时的 workspace root，不存在跨调用保持的状态。

```python
# deepagents LocalShellBackend.execute()
result = subprocess.run(command, shell=True, ..., cwd=str(self.cwd))
```

`self.cwd` 只在 `FilesystemBackend.__init__` 赋值一次，Harness 侧 `create_execution_context()` 传入的是 `root_dir=workspace`。因此 `execute("cd subdir")` 之后再 `execute("pwd")`，工作目录仍是 workspace root。`cd` 既不能改变后续调用的行为，也不能用来逃逸工作区，等价于一条空操作。既然三平台的 `cd` 都是如此，它同时纳入通用集合而非仅 Windows 集合。

`where` 纳入 Windows 集合已确认，但**必须附带 ScriptBlock 防护**：PowerShell 中 `where` 是 `Where-Object` 的别名，而 `Where-Object` 接受 ScriptBlock，`Get-ChildItem | where { rm x }` 可执行任意代码。防护方式是在白名单判定中拒绝任何包含 `{` 的命令段——由于 `extract_segments()` 已按 `|` 拆段，`where { ... }` 会成为独立一段并被该规则拦下。该防护对所有 PowerShell cmdlet 一体适用，不是 `where` 专属补丁。

**Windows 追加**（PowerShell cmdlet，显式列举）：`Get-ChildItem`、`Get-Content`、`Get-Location`、`Get-Item`、`Resolve-Path`、`Split-Path`、`Join-Path`、`Test-Path`、`Select-String`、`Measure-Object`、`Select-Object`、`Sort-Object`、`Compare-Object`、`Format-Table`、`Format-List`、`Out-String`、`ConvertTo-Json`、`ConvertFrom-Json`、`Get-Date`、`Get-Command`、`Get-Member`、`Get-Variable`、`Get-Alias`。

PowerShell 的 `ls`/`cat`/`pwd`/`echo`/`dir`/`type` 别名由上面的通用集合与 Windows 集合共同覆盖，无需单独处理。

### 必须排除的命令与理由

以下命令**不得**进入白名单，需在实现中以注释或测试固化理由：

| 命令 | 平台 | 排除理由 |
| --- | --- | --- |
| `ForEach-Object`、`Where-Object` | PowerShell | 接受 ScriptBlock，可执行任意代码。注意 `where` 作为其别名已纳入 Windows 集合，靠 ScriptBlock 防护兜底 |
| `Invoke-Expression`、`Invoke-Command`、`Start-Process` | PowerShell | 直接执行任意命令 |
| `Tee-Object`、`Out-File`、`Export-*` | PowerShell | 写文件 |
| `time` | Windows cmd | 无参数时交互式提示修改系统时间，会挂起 |
| `set` | Windows cmd | 仅无参数时只读；`set X=Y` 修改环境 |
| `attrib` | Windows cmd | 仅无参数时只读；`+r`/`-r` 修改文件属性 |
| `assoc`、`ftype`、`path` | Windows cmd | 仅无参数时只读，带参数写注册表或环境 |
| `chcp` | Windows cmd | 带参数修改代码页 |
| `more` | 三平台 | 交互式分页，会挂起非交互执行 |
| `diskutil`、`systemctl`、`ip` | macOS / Linux | 只有部分子命令只读，其余具破坏性；需子命令门控，本次不纳入 |
| `sysctl` | macOS / Linux | `-w` 写内核参数；如需纳入必须先做参数门控 |

### 同名命令的跨平台冲突

这是必须按平台门控而非无条件合并的直接原因：

- **`sort`**：Unix 上只输出到 stdout；Windows 上 `sort /O out.txt` 会写文件。`sort` 目前已在白名单中，**在 Windows 上是一个既有的放行漏洞**。本次必须处理：Windows 集合中的 `sort` 需排除 `/O` 参数，或干脆不纳入 Windows 集合。
- **`date`**：Unix 上只打印日期；Windows cmd 上无参数 `date` 会交互式提示修改系统日期并挂起。`date` 目前已在白名单中，**在 Windows cmd 下会导致工具调用卡死**。本次必须处理：Windows 集合排除 `date`，或只允许 `date /t`。
- **`find`**：Unix 上是文件查找（`-exec` 可执行任意命令，已由 `has_dangerous_args()` 拦截）；Windows 上是文本查找，只读。两者都可放行，但危险参数检测规则不同。
- **`type`**：Windows 上打印文件内容；Unix shell 内建 `type` 查询命令类型。两者都只读，无冲突。
- **`where`**：Windows cmd 上是 `where.exe` 查找可执行文件；PowerShell 中 `where` 是 `Where-Object` 的别名。前者只读，后者接受 ScriptBlock。已确认纳入 Windows 集合，并以「命令段包含 `{` 即不放行」的 ScriptBlock 防护兜底，不引入宿主 shell 探测。

### 附带发现：POSIX 分词会破坏 Windows 路径

`safe_commands._tokenize_segment()` 使用 `shlex.split()`（POSIX 模式），对未加引号的 Windows 路径会吃掉反斜杠：

```text
dir C:\Users\PC\Desktop      -> ['dir', 'C:UsersPCDesktop']
dir "C:\Users\PC\Desktop"    -> ['dir', 'C:\\Users\\PC\\Desktop']    # 加引号才正确
type C:\Users\PC\a.txt       -> ['type', 'C:UsersPCa.txt']
```

分词结果只用于 `has_dangerous_args()` 与 `_extract_git_subcommand()`，根命令判定走的是 tree-sitter，因此不影响白名单命中判断本身。但危险参数检测建立在被破坏的 token 上，属于潜在漏检。实现时应在 Windows 平台使用 `shlex.split(s, posix=False)` 或等价的非 POSIX 分词，并补一条断言"带反斜杠路径的危险参数仍能被检出"的测试。

### 可观察验收（决策 2）

- Windows 上 `default` 模式执行 `dir`、`type <文件>`、`findstr <模式> <文件>`、`Get-ChildItem`、`Get-Content <文件>` 均不弹窗直接执行。
- macOS 上 `sw_vers`、`vm_stat` 不弹窗；Linux 上 `free -h`、`uptime`、`lscpu` 不弹窗。
- `dir > out.txt`、`Get-Content a.txt > b.txt` 仍然弹窗（安全底线优先于白名单）。
- Windows 上 `date`（无参）与 `sort /O out.txt` **不**自动放行。
- `ForEach-Object`、`Invoke-Expression`、`attrib +r`、`set X=Y` 不自动放行。
- 三平台名单均可在单一 CI 机器上通过注入 platform 参数被测试覆盖。
- 带反斜杠路径的危险参数（如 `find C:\x -exec ...`）仍被 `has_dangerous_args()` 检出。

## 决策 3：规则自匹配修复采用方案 B（统一前缀匹配）

### 通俗说明

- **现在的状况**：批准一条命令后，系统把它总结成规则时会在末尾加一个星号（比如 `git status` 存成 `git status *`）。但匹配时那个星号前面的空格是"必须真实存在"的，导致再次执行 `git status` 反而匹配不上自己存的规则。
- **准备怎么解决**：不再追加星号，规则就存成纯前缀（`git status`），匹配时按"命令的开头若干个词是否与规则一致"来判断。
- **改完后的变化**：批准过的命令下次原样执行能正确命中；`git status --oneline` 这类带更多参数的同类命令也能命中，符合用户批准时的预期。

### 决策内容

`extract_command_rule()` 不再追加 `" *"`，输出纯前缀字符串。匹配侧保持现有的双分支不变：

```python
if "*" in rule.resource:
    matched = matches_command_glob(rule.resource, segment)
else:
    matched = matches_command_prefix(rule.resource, segment)
```

- 自动生成的规则不含 `*`，走 `matches_command_prefix()` 的 token 前缀匹配。
- 用户手写在 `settings.json` 里的含 `*` 规则（如 `Bash(git *)`）仍走 glob，行为不变。

不采用方案 A（改 `matches_command_glob()` 让结尾 ` *` 可匹配空）的理由：方案 A 需要在 glob 转正则时对结尾做特殊处理，等于给 glob 语义打补丁，且会让"用户手写的 `git *` 是否应匹配裸 `git`"这个问题变得含糊。方案 B 让自动生成规则与手写规则各自走语义清晰的匹配器，不引入特例。

### 关键 invariant

1. **自匹配闭环**：`matches_command_prefix(extract_command_rule(cmd), cmd)` 对任意 `cmd` 必须为真。这是决策 1 与决策 3 共同的验收基准。
2. **前缀不得退化为裸根命令**：见下方安全约束。

### 安全约束：禁止生成裸根命令规则

方案 B 与「位置参数不进入规则」（任务文档 §2）组合后会产生一个新的过度授权风险，必须一并处理。

风险链条：`rm foo.txt` 被批准 → 去掉位置参数后规则为 `rm` → 前缀匹配下 `rm` 命中 `rm -rf /` → 该命令自动执行且**不经过任何安全检查**。

之所以无法兜底，是因为已确认的现状：

```python
# runtime/agent.py，L4 allow 分支
if effect == "allow":
    return sensitive or outside_write
```

L4 在 L3.1 之前 `return`，因此 allow 规则命中时 `evaluate_safety_floors()` **不会被调用**；而 `evaluate_safety_floors` 在任何执行层中间件里都不存在。`default` 模式下 `AutoDestructiveGuardMiddleware` 未注册（只在 `auto` 模式注册），`DenyRulesMiddleware` 只拦 deny 规则，`WorkspaceBoundaryMiddleware` 对 `execute` 只拦 `/.harness`，`ShellAllowListMiddleware` 仅在显式配置 `shell_allow_list` 时才存在。仓库中甚至有一条测试固化了该行为：

```python
def test_allow_rule_beats_auto_filter(self):
    rules = [PermissionRule(tool="execute", resource="rm *", effect="allow")]
    ...
    request = _make_request("execute", {"command": "rm -rf /"})
    assert called is True
```

结论：一条过宽的 allow 规则在 `default` 模式下没有任何后续防线。已确认**同时实施**下面两条约束，两者覆盖的是不同的风险路径，缺一不可。详见「决策 4」。

## 决策 4：allow 规则的双层防护（约束 A + 约束 B）

### 通俗说明

- **要解决什么**：批准过一条命令之后，系统存下的规则可能比用户当时看到的那条命令宽得多。极端情况是批准"删除某个文件"，结果规则宽到能放行"删除整个磁盘"。
- **两层防护分别管什么**：第一层管"自动生成的规则不能太宽"；第二层管"就算规则宽了，命令里出现了当初没批准过的危险动作，也要重新问一次"。
- **为什么两层都要**：第一层拦不住用户自己手写的宽规则；第二层拦不住 `rm -rf /` 这种"危险性来自参数而非命令结构"的情况。两层各有盲区，合起来才闭合。

### 约束 A：规则生成侧禁止裸根命令规则

维护一个"不得单独成规则"的根命令集合，至少包含 `rm`、`del`、`erase`、`rmdir`、`rd`、`mv`、`move`、`cp`、`copy`、`chmod`、`chown`、`attrib`、`dd`、`kill`、`taskkill`、`curl`、`wget`、`ssh`、`scp`。

当 `extract_command_rule()` 去掉位置参数后只剩裸根、且该根命令在此集合中时，**不生成规则**。此次批准只对当次调用生效，下次同类命令仍会弹窗。宁可多问一次，不可放行 `rm -rf /`。

集合之外的命令（如 `dir`、`git`、`npm`）允许生成裸根规则，因为它们的破坏性来自子命令而非裸根本身，而子命令会被保留进规则。

### 约束 B：L4 allow 分支加入安全底线检查（按剩余部分判定）

**不能**简单地对整条命令跑 `evaluate_safety_floors()`——那样会直接毁掉本功能。原因是底线里的 `exec_risk` 覆盖 `git commit`/`rebase`/`merge`、`npm run`/`test`/`start`/`exec`、`npx`、`make`，`write_side_effect` 覆盖任何 `>` 重定向。若整条命令一律判定，用户对 `git commit -m x` 点「本项目允许」后，规则虽然存下了，但每次 `git commit` 都会触发 `exec_risk` 而重新弹窗，规则永远不生效。而 `git commit` 恰恰是用户最想免审批的命令之一。

已确认的精确形式是**按剩余部分判定**：

```text
命中的 allow 规则 rule.resource（纯前缀）
  → 从命令中剥掉该前缀，得到 remainder
  → 对 remainder 跑 evaluate_safety_floors()
  → 触发底线 → 强制弹窗；未触发 → 按原逻辑放行
```

判定依据是"这个风险是不是用户批准规则时就已经知情的"：

| 场景 | 规则 | remainder | 底线 | 结果 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `git commit --amend` | `git commit` | `--amend` | 不触发 | 放行 | git hooks 风险内含于规则本身，用户批准时已知情 |
| `echo evil > ~/.bashrc` | `echo` | `evil > ~/.bashrc` | `write_side_effect` | 弹窗 | 重定向是规则之外新增的写副作用 |
| `npm install express` | `npm install` | `express` | 不触发 | 放行 | |
| `npm run deploy` | `npm install` | 不匹配该规则 | — | 弹窗 | 前缀不同，规则根本不命中 |
| `rm -rf /` | `rm` | `-rf /` | 不触发 | 放行 | **约束 B 拦不住，由约束 A 兜底** |

最后一行是两条约束必须并存的直接证据：`rm` 的危险性来自参数，不属于任何一条底线，只能靠约束 A 在生成侧就不产出 `rm` 这条规则。

### 适用范围与边界

- 约束 B 只对 `execute` / `monitor` 且 `command` 非空的调用生效；其他工具的 allow 分支行为不变。
- 含 `*` 的用户手写规则（如 `Bash(git *)`）无法简单剥前缀。此类规则统一按"整条命令跑底线检查"处理——手写宽规则的用户应当接受更严的复核，且这类规则不是本功能自动产生的。
- 约束 B 不改变 L2 deny、L3.5 敏感路径、越界写入这三条既有短路逻辑的优先级，只在 `effect == "allow"` 分支内追加判定。

### 对既有测试的影响

`packages/agent/tests/policy/test_approval_policy.py::test_allow_rule_beats_auto_filter` 断言 `AutoDestructiveGuardMiddleware` 在 allow 规则命中时放行 `rm -rf /`。该测试针对的是**执行层中间件**的契约，不是 L4 预检，实施后仍然成立（预检会先弹窗，中间件只看到已批准的调用）。但应在该测试补一条注释说明这一分层关系，避免后续读者误以为 `rm -rf /` 可以无审批直达执行。

## 决策 5：规则保留哪几个词（子命令与位置参数的判定）

### 通俗说明

- **要解决什么**：批准一条命令后，要把它压缩成一条规则。压缩得太狠（只剩 `rm`）会放行危险操作；压缩得不够（把完整文件路径也写进去）会导致换个文件就不认，用户得反复批准。要定的就是"保留到第几个词为止"。
- **一个先决约束**：方案 B 用的是"命令开头的若干个词是否与规则一致"来匹配，所以**规则必须是命令开头连续的几个词**，不能跳着挑。这把问题简化成了一件事：**从左往右数，保留前几个词。**
- **判断依据**：从第二个词开始往右看，遇到"像子命令的词"就继续保留，遇到"像文件路径、参数值、开关"的词就停下。

### 词的分类

从左往右扫描，每个词归为三类之一：

| 类别 | 判定 | 例子 |
| --- | --- | --- |
| 子命令词 | 匹配 `^[A-Za-z][A-Za-z0-9_-]*$`，且不含 `.` `/` `\` `:` `~` `*` `?` `=` | `status`、`commit`、`install`、`rev-parse` |
| 开关 | `-` 开头；**或**在 Windows 平台上匹配 `^/[A-Za-z][A-Za-z0-9]{0,7}$` | `-la`、`--force`、`/b`、`/s` |
| 操作数 | 其余全部（路径、文件名、URL、带引号的串、数字） | `"C:\a\b.txt"`、`./run.sh`、`https://…`、`3000` |

注意 `express`、`pods` 这类词在**形态上**属于子命令词，它们被丢弃不是靠词形，而是靠下面的位置规则。词形只负责把路径、文件名、URL 这类明显的操作数挡在外面。

Windows 开关的识别必须按平台门控。在 Unix 上 `/` 开头的词是绝对路径（`/etc/passwd`），不能当开关；在 Windows 上 `/b`、`/all` 才是开关。平台参数在决策 2 中已经引入，此处复用同一个参数，不新增机制。限定 1–8 个字母且不含第二个 `/`，可以把 `/usr/local/bin` 这类路径排除在外。

### 保留规则

```text
第 1 个词（命令根）：始终保留
第 2 个词起，逐个判断：
  ├─ 是开关或操作数 → 停止，不再保留
  └─ 是子命令词 →
       ├─ 它是第 1 个子命令词 → 保留，继续看下一个
       └─ 它是第 2 个及以后的子命令词 →
            ├─ 其后紧跟开关 → 保留（说明它是子命令，不是操作数）
            └─ 其后没有开关   → 丢弃并停止（说明它是操作数）
最多保留 3 个词（命令根 + 2 层子命令）
```

"第一个子命令词无条件保留"是关键：它区分了 `git status` 的 `status`（子命令，必须保留，否则规则退化成 `git`，会放行 `git push --force`）和 `npm install express` 的 `express`（第二个子命令词且其后无开关，是操作数，应丢弃）。

**特例**：`run`、`exec`、`x`、`dlx` 这类"转发执行"子命令之后的那个词必须保留（`npm run build` → `npm run build`），因为 `npm run` 本身等价于"执行任意脚本"，规则不能停在这一层。这是一个明确列举的小集合，不做推断。

### 工作示例（同时作为实现的测试矩阵）

| 命令 | 规则 | 说明 |
| --- | --- | --- |
| `dir "C:\Users\PC\Desktop"` | `dir` | 路径是操作数，丢弃 |
| `dir /b "C:\Users\PC\Desktop"` | `dir` | `/b` 是 Windows 开关，停止 |
| `type "C:\a\hhh.txt"` | `type` | |
| `ls -la` | `ls` | |
| `git status` | `git status` | 第一个子命令词无条件保留 |
| `git commit -m "fix"` | `git commit` | `-m` 是开关，停止 |
| `npm install express` | `npm install` | `express` 是第二个子命令词且其后无开关 |
| `npm run build` | `npm run build` | `run` 属转发执行特例 |
| `docker compose up -d` | `docker compose up` | `up` 之后紧跟 `-d`，保留 |
| `kubectl get pods` | `kubectl get` | `pods` 是操作数 |
| `cargo build --release` | `cargo build` | |
| `python script.py` | 不生成规则 | `script.py` 含 `.` 是操作数 → 只剩裸根 `python` → 命中约束 A |
| `rm foo.txt` | 不生成规则 | 同上，`rm` 在约束 A 集合中 |

### 与约束 A 的衔接

决策 4 的约束 A 集合需要补充**解释器与远程执行类**命令，因为它们的裸根规则等价于放行任意代码：`python`、`python3`、`node`、`bun`、`deno`、`ruby`、`perl`、`php`、`bash`、`sh`、`zsh`、`powershell`、`pwsh`、`cmd`、`ssh`、`docker`（`docker run` 可挂载宿主目录）。

`docker` 需要注意：按上表 `docker compose up` 会保留三个词，不会退化成裸根，因此不受影响；但 `docker ps` → `docker ps` 也正常。只有 `docker <操作数>` 这种形态才会退化成裸根 `docker`，届时按约束 A 不生成规则。

### 环境变量前缀

`NODE_ENV=test npm run build` 这类带环境变量前缀的命令，生成侧与匹配侧必须使用同一个 `strip_wrappers()` 处理后再比较，否则规则 `npm run build` 不是原始命令的词前缀，会匹配失败。这是决策 1 invariant 2（拆分口径一致）的直接推论，实现时需有对应测试。

## 决策 6：不做死规则检测，改为可诊断日志

### 通俗说明

- **要解决什么**：`.harness/settings.json` 里现在躺着几条永远匹配不上任何命令的废规则（旧版缺陷的产物）。要决定是自动跳过它们、还是只提示、还是不管。
- **结论**：不自动跳过、不自动改写，只在日志里给出足以自查的诊断信息。
- **为什么**：判断一条规则是否"永远匹配不上"在一般情况下无法可靠计算，猜错就会静默禁用用户依赖的规则；而一条废规则本身是安全的（顶多多问一次，不会放行任何东西）。用错误的自动化去修一个无害的问题，风险大于收益。

### 具体做法

1. **加载规则时不做任何过滤或改写。** 用户的 `settings.json` 是用户的配置，不静默变更。
2. **弹窗时输出未命中诊断。** 当审批弹窗被触发、且当前存在同工具的 allow 规则却一条都没命中时，向结构化日志写一条 debug 级记录，包含：被评估的命令、参与匹配的规则列表、以及每条规则未命中的原因（前缀不符 / glob 不符）。这直接回答用户最初的困惑——"我明明点了本项目允许，为什么还问我"。
3. **启动时提示旧版残留。** 若某条规则的 resource 同时满足"以 ` *` 结尾"和"包含 `:` 或 `\`"，它是旧版缺陷的确定性产物（自动生成的规则不该含绝对路径），记一条 info 日志说明该规则可能已失效、可以手工删除。仅提示，不改变行为。

### 为什么不做自动检测

曾考虑用"规则能否匹配它自己去掉 ` *` 后的形式"来判定，但会误伤：用户手写的 `Bash(git *)` 去掉 ` *` 得到 `git`，`git *` 匹配不上 `git`，会被误判为废规则——而它其实是一条完全正常、能匹配 `git status` 的规则。没有可靠判据，因此不做。

### 边界

- 诊断日志属于既有的脱敏结构化日志通道，遵循现有约束：不记录凭据，命令内容按既有规则截断。
- 不新增用户可见的界面提示，不新增配置项。

# ZC-141 Agent Plugins 1.0.0 完整支持与多格式共存设计

关联任务：[ZC-141](../task/ZC-141.md)

## 通俗问题说明

Harness 已经能安装和运行一部分 Agent Plugins，但“文件看起来像插件”“严格满足 portable core”与
“至少有一项能力能在 Harness 中安全工作”目前混在同一套状态里。一个坏组件可能把整体显示为
invalid，另一个有效组件又允许启用；已有安装还缓存旧校验结果，单纯修改 Adapter 不会自动生效。

Agent Plugins 1.0.0 不是 Harness 唯一支持的格式，也不是用来替代已有 Claude/Harness 能力的格式；
它是必须完整实现的一等 portable 标准。外部格式可以继续增加，但必须先各自完成格式判断，再统一
转换为 Harness 内部 descriptor，不能用另一个 Adapter 掩盖 Agent Plugins 的规范错误。

本设计把判断拆成三层：

1. 核心 manifest 能否安全确定 Plugin 身份和规范版本；
2. 每个独立组件是否有效、是否受 Harness 支持、是否实际 effective；
3. 安装后的进程或网络连接是否成功。

用户要求的“宽松”落在第二层：坏 Skill 或 MCP server 被隔离，其他有效能力继续；它不表示忽略
核心身份、安全路径或进程边界，也不把运行时连接失败伪装成格式错误。

本任务的产品目标是“双轨保留”：Agent Plugins 1.0.0 成为完整支持的一等 portable 标准，同时
Claude Plugin、Hybrid、`com.za38.harness` 及其现有 Command、Agent、Team、Hook、LSP、Monitor
等能力继续属于 Harness 的正式能力范围。工程验收中的“不回归”只是验证手段，表示完成新标准实现后，
这些既有能力的安装、识别、启用、运行和管理行为仍然可用；它不表示把既有能力降为可选或仅做兼容兜底。

## 已确认产品决策

### 决策 0：Agent Plugins 完整支持优先，多格式并行共存

Adapter 层固定为：

```text
AgentPluginsV1Adapter ─┐
ClaudePluginAdapter ───┼→ canonical PluginDescriptor → Harness Runtime
Harness namespace ─────┤
future adapters ───────┘
```

- AgentPluginsV1Adapter 覆盖全部适用于 Harness 的 1.0.0 MUST/MUST NOT，并为每条规范要求保存测试
  追踪；Skill 和 MCP 都是一等实现，现有 stdio、Streamable HTTP、SSE 全部纳入验收。
- Claude Plugin、hybrid 和 `com.za38.harness` 不降级、不删除；其 Command、Agent、Team、Hook、
  LSP、Monitor 等已交付能力继续保留。
- 声明 canonical Agent Plugins `$schema` 的包先按该规范判断 portable core；规范标记为 fatal 的
  错误不能通过 Claude fallback 被重新包装成“有效 Agent Plugins”。
- Hybrid 只在 portable core 和补充格式分别通过各自身份规则后合并；client extension 不改变
  portable core 的规范含义。
- 未来格式通过新的 Adapter 接入，不让 Server、Runtime、CLI 或 registry 直接判断外部格式。
- Google 示例中的 client-specific 目录按上述 Adapter 图旁路处理；其存在不能导致 portable package
  被降级，也不能把客户端私有能力冒充为 Agent Plugins 1.0.0 标准组件。

### 决策 1：不新增 `conformance`

Agent Plugins 规范要求的是 package/client 行为，不要求管理 API 暴露名为 `conformance` 的字段。
当前本地管理只需要回答“能否安装、能否启用、哪些组件生效、哪里有问题”。继续使用：

- 插件级 `compatibility`；
- 插件级 `can_enable`；
- 组件级 `status`、`effective`、`diagnostics`；
- 稳定错误码。

未来 Marketplace 若需要认证、筛选或发布者声明，再单独评估正式合规字段；本任务不预留无调用方的
协议枚举。

### 决策 2：规范有效性与 Harness 可用性分离

Agent Plugins 的 Skill、MCP 和 client extension 都是可选的。一个只有合法 manifest、没有组件，
或只包含其他客户端 namespace 的包，仍可能是规范有效的 Agent Plugins package，不能因为 Harness
当前没有 effective 组件就把它判成格式 invalid。

- `plugins.validate` 返回规范解析和组件报告。
- `plugins.install` 接受规范有效的包并始终以 disabled 写入 registry，即使当前没有 effective 组件。
- `plugins.set_enabled(enabled=true)` 必须至少存在一个 `effective=true` 组件；否则返回稳定错误
  `PLUGIN_NO_EFFECTIVE_COMPONENT`。
- `compatibility` 表示 Harness 可用程度，不承担 Agent Plugins 规范认证语义。

> 2026-08-14 决策：工程尚未发布，旧开发构建产生的 v1 registry 数据不作为保留对象，
> v1→v2 迁移机制整体移除，相关的单记录隔离语义随之删除；移除前的完整设计保留在
> [「已撤销的 registry v1→v2 迁移」](#已撤销的-registry-v1v2-迁移) 一节。

### 决策 3：核心失败关闭，组件局部宽松

失败边界固定如下：

| 层级 | 例子 | 结果 |
| --- | --- | --- |
| Plugin 核心致命 | `plugin.json` 不可解析、不是 object、缺少/不支持 `$schema`、name 非法、受约束字段类型错误 | validate/install 拒绝，不发现或执行组件 |
| Plugin 核心非致命 | 未知顶层字段、非 object `extensions` | 报告并忽略，继续发现组件 |
| 组件类型无效 | `skills` 不是目录、`mcp.json` 顶层或 schema 无效 | 该组件类型 invalid，其他类型继续 |
| 单条组件无效 | 一个 `SKILL.md`、一个 MCP server variant 无效 | 跳过该条并报告，同类型其他条目继续 |
| 客户端不支持 | transport 或 extension namespace 未实现 | unsupported/skip，不视为整个 Plugin 格式无效 |
| 运行时失败 | MCP 启动、连接、认证或 handshake 失败 | server runtime failed，其他组件继续，静态 descriptor 不倒退为 invalid |

### 决策 4：registry 只承认当前版本，不保留旧版本兼容路径

新 portable Adapter 成为唯一 Agent Plugins 1.0 生产实现。registry 只有 v2 一种 canonical 形状，
不存在 legacy parser、双写、feature flag 或旧记录缓存分支；未发布期间产生的旧开发版本 registry
（v1）不读取、不迁移，按版本或结构无效失败关闭，用户删除 Plugin 根目录后重新安装。
（原「决策 4：直接迁移」已随 2026-08-14 迁移机制移除而撤销，见
[「已撤销的 registry v1→v2 迁移」](#已撤销的-registry-v1v2-迁移)。）

## 目标流程与关键 invariant

```text
local directory / ZIP
  → PluginStore.stage（既有路径、链接、大小、压缩比安全检查）
  → Adapter format selection
      ├─ portable core manifest gate
      ├─ Claude adapter
      └─ hybrid identity merge
  → complete Agent Plugins requirements + independent component reports
  → PluginDescriptor
      ├─ compatibility
      ├─ can_enable
      └─ capability fingerprint
  → spec-valid package installs disabled
  → explicit fingerprint confirmation
  → immutable ExtensionCatalogSnapshot
  → SkillRegistry + McpConfigSnapshot
```

关键 invariant：

1. 安装报告和 Host 运行使用同一 canonical component inventory，不重复猜测外部格式。
2. 任意一个组件失败不能阻止独立有效组件；核心 manifest 失败则不得扫描或执行任何组件。
3. 规范有效的 package 可以没有 effective 组件并安装为 disabled；`can_enable=true` 必然存在至少一个
   `effective=true` 组件。
4. `compatibility=invalid` 不得同时出现 `can_enable=true`。
5. unsupported 不等于 invalid；runtime failed 不回写静态格式状态。
6. package 内容始终从 digest 验证的不可变 store 读取，Plugin data 与 package 分离。
7. 任何能力重算导致的 capability fingerprint 变化都要求显式重新确认，不能静默扩大权限。

## compatibility 聚合语义

| 状态 | 条件 | can_enable |
| --- | --- | --- |
| `ready` | 至少一个 effective 组件；发现的 portable 组件均 supported 且无无效条目 | `true` |
| `recognized` | 格式和身份有效，但只有 adapted 组件，或当前没有 Harness-effective 组件且不存在格式错误 | 取决于是否存在 effective 组件 |
| `partial` | 至少一个 effective 组件；同时存在 invalid 条目、invalid/unsupported 组件类型或未支持能力 | `true` |
| `invalid` | 存在 invalid 组件或无效条目，且没有任何 effective 组件 | `false` |

核心 manifest 的致命错误不会产生 `PluginDescriptor`，因此通过 RPC error 表达，而不是伪造一个
`compatibility=invalid` descriptor。

组件 `count` 只统计通过静态校验的条目；被跳过条目进入 diagnostics。组件存在但有效条目为零时，
该组件 `effective=false`。若同一组件类型同时包含有效和无效条目，组件状态保留可运行事实并通过
diagnostics 表达坏条目，插件聚合必须仍为 `partial`；实现可增加内部 issue severity，但不新增公开
`conformance`。

## portable manifest 与 Skill 设计

### Manifest

- `$schema` 必须是本地支持的 canonical 1.0.0 identifier，用于选择固定解释规则。
- name 接受 `a-z`、`0-9`、`-`、`.`，长度和首尾、连续字符按规范校验。
- `version` 只要求 JSON string；SemVer 是推荐，不作为拒绝条件。
- `author` 是 closed object，只允许 string 类型的 `name/email/url`；其余 metadata 只做规范规定的
  JSON 类型校验，不猜测 URL、email、SPDX 的真实性。
- 未知顶层字段报告后忽略；`extensions` 非 object 报告后整体忽略。
- 未实现的 extension namespace 不读取、不校验其内容；`com.za38.harness` 继续按自身版本规则处理。

### Skills

- 只查看 `skills/` 的直接子目录及其中名为 `SKILL.md` 的普通文件，不递归发现。
- `skills/` 缺失不是错误；存在但不是预期目录类型时只让 Skill 组件类型 invalid。
- 每个 `SKILL.md` 使用 Agent Skills 方言校验；一个文件失败只跳过该 Skill。
- Script/reference/asset 仍通过既有虚拟文件和 package boundary 按需读取；校验阶段不执行脚本。

## MCP 校验与运行设计

### 静态配置

- `mcp.json` 存在时必须选择与 Plugin 相同版本的 canonical schema，并按 closed top-level schema
  解释；空 `mcpServers` 是合法但不 effective 的 MCP 组件。
- 每个 server 使用 closed discriminated union；字段未知、类型错误或 variant 混用只跳过该 server。
- server name 只执行规范/Schema 明确约束，不额外施加 Plugin name 的 kebab-case 规则。
- 客户端未支持的 transport 记录为 unsupported 并跳过，不连带无效化其他 server。
- Hybrid 双 manifest 的 MCP 各自独立加载：任一 manifest 的顶层致命错误（`mcp.json` 坏 JSON、
  unknown 顶层字段、`$schema` 不匹配、`mcpServers` 非 object，或 Claude 侧 `.mcp.json`/manifest
  path/inline `mcpServers` 根节点无效）只使该 manifest 的 server 不进入运行快照并记录稳定诊断，
  另一 manifest 的有效 server 继续进入同一快照；与决策 3 的逐 server/逐组件隔离一致，不因
  hybrid 身份而连带丢弃。

### stdio

- `command` 是单一 executable token，不经 shell 解析，也不进行 placeholder expansion。
- `./` 相对可执行文件从 Plugin root 解析；裸命令使用客户端选定的 executable search 规则。
- 未声明 cwd 时使用 Plugin root；显式 cwd 只展开 `${PLUGIN_ROOT}`、`${PLUGIN_DATA}`，解析后必须
  满足允许的路径和数据边界。
- args、env、cwd 只展开上述两个变量；未知 `${...}` 不进行宿主环境替换。
- 先构造客户端最小基础环境，再覆盖 manifest env，最后由客户端强制写入正确的 `PLUGIN_ROOT` 和
  `PLUGIN_DATA`，插件不能伪造二者。

### Streamable HTTP 与 SSE

- url、header name 和 header value 是字面配置，不执行 placeholder 或宿主环境展开。
- Harness 生成的授权/协议 header 按大小写不敏感名称覆盖插件 header。
- 未经明确用户授权，不把插件配置 header 经跨源 redirect 或 legacy SSE endpoint event 转发。
- OAuth/凭据发现由客户端管理；认证失败属于连接失败，不改变静态 Plugin validity。

## 已撤销的 registry v1→v2 迁移（历史记录）

> 状态：**已撤销，2026-08-14**。工程尚未正式发布，用户确认无需保留未发布期间旧开发构建
> 产生的 v1 registry 数据；为避免长期维护 legacy 路径，v1→v2 迁移机制及其测试整体移除。
> 移除后 registry 只有 v2 一种 canonical 形状：旧开发版 v1 文件按版本或结构无效失败关闭
> （`PLUGIN_REGISTRY_INVALID`），用户删除 Plugin 根目录后重新安装插件。
> 本节保留移除前的设计要点作为决策历史；对应实现与测试曾在工作集中存在
> （`packages/agent/tests/test_plugin_migration.py`、`PluginStore.migrate_registry`、
> `PluginManager._reindex_plugin`），已随移除删除，不再维护。

移除前的迁移设计要点（不再生效）：

1. 获取现有跨进程 registry exclusive lock 后重读 v1，不在无锁快照上写入。
2. 在内存中构建完整候选状态；逐记录验证 store 路径和 package digest。
3. portable/hybrid 包使用新 Adapter 重算 metadata、components、diagnostics 和 capability fingerprint；
   Claude-only 包复用当前 canonical Adapter/记录语义，不借机扩大范围。
4. 保留 plugin ID、source ID/label、installed timestamp、package store 和 data 位置。
5. 重算失败是单记录隔离事件：保留记录供 inspect/update/remove，设置 disabled、清除 trusted
   fingerprint、清空 effective inventory，并写入稳定迁移诊断；不删除 package 或 data。
   该隔离记录在 list/inspect 中按「compatibility 聚合语义」表聚合为 `invalid`，`can_enable` 为 false。
6. 新 fingerprint 与旧值不同、旧记录不再 can_enable，或重算产生新的安全诊断时，设置 disabled 并
   清除 trust。只有 fingerprint 和可用性均未变化的记录才可保留 enabled/trusted。
7. 所有记录处理完成后才用临时文件、flush/fsync 和同目录原子替换写入新 registry version。
8. I/O、锁、digest 或序列化失败时不替换 v1；Host 失败关闭并给出可恢复错误，不留下部分 v2。
9. v2 写入成功后生产代码只读写 v2；保留有界、只读的迁移备份（`registry.json.pre-v2-migration.bak`）。

撤销理由：迁移只服务未发布期间的历史开发数据；保留它会引入一条永不再触发的生产代码路径、
诊断文本比较带来的保守 trust 撤销语义（评审发现项 #3），以及相应的文档与测试维护成本。
与「决策 4：registry 只承认当前版本」一致。

## 公开 interface 与错误模式

本任务默认不改变 JSON-RPC 方法集合，也不新增 `conformance`。现有 `plugins.validate/list/inspect/
install/set_enabled/remove` 继续返回脱敏 JsonObject；字段的聚合语义按本设计收敛。

至少需要稳定区分以下错误：

| 错误码 | 含义 | 恢复动作 |
| --- | --- | --- |
| `PLUGIN_SCHEMA_UNSUPPORTED` | 核心 schema 缺失或本地不支持 | 使用受支持的 canonical schema |
| `PLUGIN_MANIFEST_FIELD_INVALID` | 核心受约束字段违反规范 | 修复指定 manifest 字段 |
| `PLUGIN_NO_EFFECTIVE_COMPONENT` | 包可 validate/install，但没有 Harness 可运行组件，不能 enable | 增加受支持组件或保持 disabled |
| `PLUGIN_MCP_SCHEMA_UNSUPPORTED` | MCP schema 缺失、版本不匹配或不支持 | 修复 `mcp.json` schema |
| `PLUGIN_COMPONENT_INVALID` | 组件类型或条目被隔离 | 查看 component diagnostics |
| `PLUGIN_CAPABILITY_CONFIRMATION_REQUIRED` | 能力变化撤销 trust | inspect 后确认新 fingerprint |

## 可观察验收

- 同一包含一个有效 Skill、一个坏 Skill 和一个有效 MCP server 的包可安装、可启用，整体为 partial，
  两个有效组件进入下一 Host 快照，坏 Skill 有稳定诊断。
- 规范有效的空组件包、空 MCP 或只有其他 client namespace 的包可 validate/install 为 disabled；
  enable 返回 `PLUGIN_NO_EFFECTIVE_COMPONENT`，但不得将 package validity 标为 invalid。
- name 含合法句点、非 SemVer string version 的规范包不会被误拒绝。
- MCP 的错误 variant、未知字段和 unsupported transport 只影响相应 server；连接/认证失败只显示为
  runtime failed。
- 固定提交的 Spanner `0.3.4` 与 AlloyDB `0.2.0` 静态 fixtures 可从目录/ZIP 导入；原生客户端
  manifest 共存不改变 portable root 语义，未知 namespace 仅被忽略或报告。
- Claude-only、hybrid 补充组件、Harness Command/Agent/Team/Hook/LSP/Monitor、目录/ZIP staging、
  store tamper 检测和 namespace 冲突测试继续通过。

## 非范围

- Plugin Marketplace、Git/GitHub/HTTP 网络来源、自动更新、签名、发布者身份和依赖求解。
- Google Agents CLI、Data Agent Kit 或其云端安装/认证流程；它们只用于互操作形状参考。
- OAuth 用户界面、通用凭据引用格式或把插件 header 当作秘密存储。
- project/managed scope、运行中 Plugin 热重载或改变“下一 Host 生效”的生命周期。
- 不把 Agent Plugins 1.0 portable core 之外的 Command、Agent、Team、Hook 宣称为标准组件；这些能力
  继续通过 Claude/Harness extension 支持，不在本任务中删除或降级。
- 为认证或市场筛选新增 `conformance`；该决策只在未来分发功能设计中重新评估。

## 回滚思路

- 代码提交按 fixture/状态、Adapter、MCP runtime、文档验收保持可审查，但作为一张 Task 一起发布，
  不对用户暴露中间语义。
- registry 只有 v2 一种 canonical 形状；未发布期间旧开发构建的 v1 registry 按版本无效失败关闭，
  删除 Plugin 根目录后重新安装即可恢复。

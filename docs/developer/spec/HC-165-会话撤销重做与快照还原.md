## 1. 核心目标与行为规格

为 Harness Code 建立会话级时光机机制（`/undo` 与 `/redo`），允许开发者在当前 Thread 内将对话上下文与工作区文件精确回退到历史某一轮（User Turn），并支持在输入新 Prompt 前即时重做（Redo），消除长对话中因单次回合偏离而导致整个 Thread 报废的体验断点。

---

## 2. 状态机与生命周期设计

```text
               ┌───────────────────────┐
               │    Normal State       │
               │  (普通正常对话状态)      │
               └──────────┬────────────┘
                          │
          /undo 选中 Turn │ /redo 恢复
                          ▼
               ┌───────────────────────┐
               │    Reverted State     │ ◄─── 未提交新 Prompt 前可随时 /redo
               │  (暂存回退态，待截断)    │
               └──────────┬────────────┘
                          │
             用户提交新 Prompt (Turn N+1)
                          │
                          ▼
               ┌───────────────────────┐
               │    Cleanup Truncation │
               │   (物理清理旧分支，固化)  │
               └──────────┬────────────┘
                          │
                          ▼
               ┌───────────────────────┐
               │    Normal State       │
               │ (/redo 失效，新时间线)  │
               └───────────────────────┘
```

### 状态转换不变量 (Invariants)
1. **Reverted 暂存态不变量**：
   - 处于 Reverted 暂存态时，被截断的旧 Turns 并不从数据库中立即物理删除，而是被逻辑标记；
   - 界面上 Timeline 与 Context 投影只渲染到目标 Turn，输入框重获焦点；
   - 此时 `/redo` 处于可用状态，`/undo` 仍可继续往前挑选更早的 Turn。
2. **Commit Truncation（新时间线固化）不变量**：
   - 一旦在 Reverted 态下调用 `run.start`（用户提交了新 Prompt），系统在启动 Run 之前必须先原子化执行 `cleanup`，将目标 Turn 之后的所有 Run、Transcript 和 Checkpoints 永久删除；
   - 此时暂存态标记清除，`/redo` 在 Command Registry 中立即转为 `disabled`。
3. **Running 互斥不变量**：
   - 当会话有活跃 Run 正在进行（`activeRun: true`）或有未决审批交互（`hasPendingInteraction: true`）时，`/undo` 与 `/redo` 均处于 `disabled` 状态，禁止在流式生成中回退。

### 3.2 交互流程 (Two-stage Interaction Flow)

1. **第一阶段：历史回合选择（`SearchPicker`）**
   - 用户输入 `/undo` 或 `/rewind`；
   - 弹出 `SearchPicker<TurnItem>`，列出历史所有的 User Turns（倒序展示，包含 `Turn #ID`、Prompt 文本摘要、相对时间和发生变更的文件数统计）；
   - 用户按 `↑`/`↓` 选择，按 `Enter` 确认进入第二阶段，按 `Esc` 退出。
2. **第二阶段：还原选项与确认（`DialogShell`）**
   - 选中某个 Turn 后，弹出确认对话框，展示选中的 Prompt 完整预览及改动统计（如 `3 files modified, +42 -10`）；
   - 提供 3 项选项：
     1. **`both`（推荐）**：同时回退代码与对话（Restore code and conversation）
     2. **`conversation`**：仅回退对话（Restore conversation，保留当前工作区代码）
     3. **`code`**：仅还原代码（Restore code，保留对话上下文）
   - 用户确认后，Controller 驱动 Sidecar 执行快照恢复与上下文指针调整。

## 4. Git 树隐式快照与工作区还原机制

### 4.1 Git Checkpoint 机制
- **快照时机**：在每个 Run 启动时（即 Agent 执行任何 Tool 之前），以及每个 Run 结束时（Tool 全部执行完毕）；
- **生成方式**：在 Git 仓库内执行 `git write-tree`，生成一个不可变的 Tree OID（例如 `4b825dc642cb6eb9a060e54bf8d69288fbee4904`），并将该 Tree OID 与对应的 `thread_id`、`turn_id` 记录在内部 Session 数据库中；
- **纯隐式**：不创建 commit，不创建 tag，不移动当前 Git 分支 HEAD，不产生 reflog 污染。

### 4.2 还原执行策略 (Restore Strategy)
- 当用户选择还原代码（`both` 或 `code`）时：
  1. 检查工作区是否处于干净状态或可安全恢复状态；
  2. 调用 `git read-tree <target_tree_oid>` 与 `git checkout-index -a -f` 将文件树恢复至目标状态；
  3. 清理在目标 Turn 之后新建但现已不存在的文件（`git clean -fd` 仅针对 Agent 创建的未跟踪文件）；
  4. 广播工作区刷新事件，使 TUI 文件树和编辑器同步刷新。
- **非 Git 仓库降级**：若当前目录不是 Git 仓库，在第二阶段 Dialog 中将 `both` 和 `code` 选项置灰，提示 `当前目录非 Git 仓库，仅支持纯对话上下文回退`。

2. **IPC/RPC 契约测试**：
   - 验证 `threads.list_turns`、`threads.undo`、`threads.redo` 在 Python sidecar 与 TypeScript client 之间的端到端调用。
3. **集成回归测试**：
   - 验证用户在 Reverted 态下输入新 Prompt，旧 Turns 是否被干净物理清除。

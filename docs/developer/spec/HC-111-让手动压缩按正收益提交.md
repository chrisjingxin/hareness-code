# HC-111: InteractiveController Feature 拆分设计方案

## 通俗说明

- **现在的状况**：`InteractiveControllerImpl` 是一个 1290 多行的单体（God Object），里面同时混合了对话运行、时间线渲染投影、审批确认交互、Thread 切换、模型切换、Skill 启停、MCP 工具管理、斜杠命令解析与 Catalog 状态刷新这 9 大类完全不同的功能。修改其中任何一个子功能都需要在这个巨大的庞然大物里穿梭，测试和重构成本很高。
- **准备怎么解决**：把这 9 大功能拆分到独立的 9 个子模块中（放置在 `packages/cli/src/interactive/features/` 目录下）。每个模块只关注自己的专属职责，`InteractiveControllerImpl` 退化为一个不到 300 行的薄协调器（Thin Orchestrator），只负责把意图路由给相应的子 Feature 模块。
- **改完后的变化**：子 Feature 之间**零直接依赖**，各自独立可以轻松编写单元测试与状态防崩溃校验；主 Controller 结构清晰明了，且对外部（TUI 和 Web）接口和体验 100% 保持行为零变化。

## 目录结构与 9 大 Feature 划分

```text
packages/cli/src/interactive/features/
  ├── catalog-feature.ts      # 管理 Catalog loadable 状态、epoch、刷新协调
  ├── command-feature.ts      # Registry、解析、availability、semantic operation
  ├── interaction-feature.ts  # Pending request、timeout、校验、fail-closed 回写
  ├── mcp-feature.ts          # MCP 状态、添加、删除
  ├── model-feature.ts        # 模型列表、当前选择、默认模型同步
  ├── run-feature.ts          # 启动、取消、事件流消费、终态收敛
  ├── skill-feature.ts        # Skill 列表、arm/clear、启停控制
  ├── thread-feature.ts       # Thread 列表、打开、恢复、generation 防迟到
  └── timeline-feature.ts     # Sequence 校验、message/tool/interaction 因果投影
```

## 关键架构不变性 (Invariants)

1. **零交叉依赖**：`interactive/features/` 目录下的各个 Feature 模块严禁互相 `import`（禁止跨 Feature 直接调用）。所有跨模块交互必须通过统一的 `InteractiveController` 进行编排或共享 `state` 存储。
2. **纯状态投影**：`interactive/state.ts` 继续保持为 Timeline/Interaction 的纯函数 Reducer；Feature 仅管理各自的运行时私有状态。
3. **控制器退化**：`packages/cli/src/interactive/controller.ts` 的总行数压缩至 **≤300 行**，仅保留路由派发、snapshot 组装和 Feature 初始化/销毁。

## 拆分与测试方案

- **Feature Context**:
  每个 Feature 提供 `init(ctx)` 与 `dispatch(intent, ctx)`，其中 `ctx` 包含 standard ports (`gateway`, `clock`, `scheduler`, `idGenerator`) 和当前 `state` 引用。
- **测试迁移与分发**:
  - 将庞大的 `controller.test.ts` 按 9 大 Feature 拆分为 9 个聚焦的 Feature 测试文件（如 `run-feature.test.ts` 等），确保覆盖成功与失败/拒绝路径。
  - 保留精简版的 `controller.test.ts` 进行集成级验证。

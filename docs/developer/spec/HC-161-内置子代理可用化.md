# HC-161 内置子代理可用化规格

关联任务：[HC-161](../task/HC-161-内置子代理可用化.md)  
调研：[161-内置子代理可用化](../research/161-内置子代理可用化.md)  
架构入口：[架构总览](../architecture/架构总览.md)、[扩展与插件机制设计方案](../architecture/扩展与插件机制设计方案.md) 第 5.4–5.5 节

用户结果与验收以 Task 为准。本文只规定行为、公开 interface、错误语义和 invariant。Plan / Todo 确认后撰写，路径与 Task 同名。

## 1. 通俗目标

主 Agent 已经能用 `task` 派出 `general-purpose`，但那只是「能跑」：生产目录里看不到 `explore`，`/agents` 只列 Plugin Agent，child 内部写文件和跑命令不会再走父审批。用户文档还在讲已经不存在的 `plan` 子代理和 `.harness/agents` 自定义 Agent。

做完之后，用户能看到的变化是：

- `/agents` 同时列出 `general-purpose`、`explore` 和已启用的 Plugin Agent，并标明来源和工具边界。
- 主 Agent 的 `task` 能派出这两个内置角色，名称、说明和真正能执行的目标是同一份名单。
- `general-purpose` 派出后在工作区改文件不再一路弹窗（父为 `default` 时内部按 auto-edit）；跑命令、碰敏感路径仍会问，卡片写明是哪个子代理。拒绝后是子代理改方案，不是整次 Run 被掐掉。
- `explore` 只能读和搜。启动它不弹委派审批；写文件、Shell、网络、MCP 既看不见也不能伪造执行。
- 子代理拿得到当前工作区、`AGENTS.md` 和模型，但看不到父对话里的闲聊。`general-purpose` 另外继承 Skill 索引和 MCP；`explore` 没有这两样。做完只把最终结果交回主 Agent。

## 2. 已确认假设

来自已确认 Task 与需求核对，Spec 不得改写：

1. 只交付 `general-purpose` 和 `explore`。不交付 `plan` 子代理。
2. 不实现项目级或用户级 `.harness/agents`。Plugin Agent 继续走现有受信 Plugin catalog。
3. 两个内置角色都使用父 Run 已冻结的 ModelProfile，不给子代理单独选模型。
4. 同步 `task`：深度固定 1，同一父 Run 最多 4 个并发 child，可取消，硬超时，只把终态和最终文本回给父模型。
5. 不实现后台 SubAgent、fork、resume、mailbox、Agent Team、IRC、worktree。
6. child 的完整中间消息和推理不写入父 Transcript；只补齐审批身份、必要工具活动和最终结果。
7. `explore` 不扩大到网页调研、Shell 只读命令或 MCP。
8. 未发版：删除旧 Registry、`plan` 声明和虚假文档路径，不留 alias / fallback / 双写。

需求核对后补进规格、与 Task 不冲突的实现假设：

- 「不再绕过受控 Delegation」不是说今天的 `task` 还没进 `AgentDelegator`。生产 `general-purpose` 已经走 Delegator。本任务要补的是：`explore` 进入同一条生产链，并且 child 的工具和审批不再走 DeepAgents 默认子图。
- `enter_plan_mode` / `exit_plan_mode` 仍在主 Agent 常驻 schema 里，但是图内空转：只改本地 `PlanModeState`，不会切换 Host 审批模式，也不会挂上 `PlanModeMiddleware`。它们与 Compose 的 `plan` 阶段无关。本任务只禁止子代理调用它们，不删除主 Agent 这两个工具。
- Plugin Agent 的目录、Managed 派发和最终结果回传保持可用。Plugin child 若需要审批或 `ask_user`，仍 fail closed（`MANAGED_AGENT_INTERACTION_UNAVAILABLE`）。Plugin 定义不能把审批改松。本任务不修 Plugin Interaction 桥。
- 内置子代理不注册 `ask_user`。提问只发生在主 Agent。
- `general-purpose` 不抄 Oh My Pi 的 child yolo：父为 `default` 时内部按 `auto-edit`；已更松或更严的父模式只跟父走，不得再放宽。
- 界面继续同时只展示一张待处理卡；多张请求排队，禁止后到的请求把先到的 fail-closed 丢掉。

## 3. 术语

```text
Dispatch Catalog
└─ Host 启动时冻结的可派发目录。内置角色 + 已启用 Plugin Agent。
   同时驱动 /agents、task 工具说明、执行前解析。

Builtin role
├─ general-purpose    Inline，通用多步骤
└─ explore            Inline，严格只读搜索

Parent Run
└─ 已冻结 ModelProfile、RunContextSnapshot、审批模式、dynamic deny rules

Child execution
├─ 独立 AgentExecution 身份（execution_id / agent_id）
├─ 新对话：只有这次 task 文本，没有父 message history
└─ 同一份冻结 snapshot（工作区事实、AGENTS.md、审批、模型）
   ├─ general-purpose 另含父 Skill 索引与 MCP
   └─ explore 不含 Skill 索引、不含 MCP

Role bound
└─ 角色自己声明的工具上限。还要和父 EffectiveCapabilityView 求交，只能更窄。

Forced exclusions
└─ 任何内置 child 都不可拥有：task、ask_user、enter_plan_mode、exit_plan_mode、memory_save
```

不要再使用作为生产路径的词：`runtime/subagents.py` 的 `AgentRegistry`、`.harness/agents`、内置 `plan` 子代理、DeepAgents 声明式 `_create_default_subagents` 后备。

## 4. 模块与 seam

一项功能一份 Spec。下面是实现时的模块边界，不是平行文档树。

| 模块 | 职责 | 调用方必须知道的 interface | 依赖 |
|---|---|---|---|
| dispatch-catalog | 内置定义 + Plugin 合成一份可派发目录 | 列出摘要、按 ID 解析、未知则失败 | Plugin catalog |
| child-capability | 角色上限 ∩ 父能力，schema 与执行同一份结果 | 输入父视图 + 角色，输出 child 视图 | dispatch-catalog |
| inline-child-runtime | 为内置角色编译并运行隔离 Inline 子图 | 只接受 DelegateAgent；不暴露模型/工具扩权入口 | child-capability |
| child-interaction-bridge | 把 child 的审批/目录信任交给父 Host Interaction，带上 child 身份 | 与现有 Host interaction 同一种请求；多请求排队 | inline-child-runtime |
| delegation-lifecycle | 深度门、并发 4、排队、取消、硬超时、finally 释放 | 现有 AgentDelegator.execute；超额从拒绝改为排队 | 已有 Delegator |

深度原则：调用方（`task` 工具、`/agents`、Delegator）只看见 catalog ID 和任务文本。角色提示词、工具求交、HITL 桥接、许可排队都藏在对应模块里。

禁止再增加一套 BuiltinRegistry 与 AgentCatalog 并行。禁止 child 复用可能绑在父图上的 HITL/工具实例来「顺便」继承审批。

## 5. 顶层流程

```text
Host 启动
  → 生成 Dispatch Catalog（builtin 先写入，再合并 Plugin）
  → /agents、agents.inspect 读这份目录
  → 主 Agent 构图：task 说明 = 目录里当前可派发 ID
  → 为 general-purpose / explore 注册 Inline DelegationTarget
  → 为 Plugin 注册 Managed DelegationTarget（行为不变）

主模型调用 task(subagent_type, description)
  → 用当前目录解析 ID；未知或不可用则稳定失败，不猜测
  → 若目标是 explore：委派启动自动通过（见 8.2）
  → 若目标是 general-purpose 或 Plugin：按父审批模式处理这次 task 本身
  → AgentDelegator：校验深度 1、占用或排队并发许可
  → 派生子 execution，绑定冻结 ModelProfile 与 RunContextSnapshot
  → Inline child 只拿到 task 文本作为新对话
  → child 工具：schema 不可见的一律执行拒绝
  → general-purpose 风险工具 / 目录信任 → 父 UI，卡片标明 child
  → 成功/拒绝/失败/取消/超时 → 释放许可与 child 资源
  → 父模型只收到最终文本（或结构化错误）
```

## 6. Canonical catalog

### 6.1 谁进入目录

启动快照固定包含：

1. `general-purpose`（source=`builtin`）
2. `explore`（source=`builtin`）
3. 当前已启用 Plugin 中解析成功的 Agent（source 保持现有 Plugin 标识）

`main` 不是可派发目录项。Compose 阶段图、Team coordinator 也不进入 `/agents`。

内置 ID 保留：`main`、`general-purpose`、`explore`。Plugin 声明这些 ID 时：忽略该 Plugin Agent，写入 catalog diagnostic，内置定义不被覆盖。不采用旧 Registry 的 project > user > builtin 覆盖。

### 6.2 同一份快照的三个消费者

| 消费者 | 必须看到 |
|---|---|
| `agents.list` / `/agents` | 全部可派发项：id、来源、用途、工具边界 |
| `agents.inspect` | 同一摘要；不返回 Prompt 正文、绝对路径或 Plugin 文件内容 |
| 生产 `task` 工具 description | 同一组 ID 和用途说明 |
| `AgentDelegator` 执行前解析 | 同一组 ID；miss 则 `DELEGATION_TARGET_NOT_FOUND` |

禁止 task 说明里有、执行时没有，或 `/agents` 有、task 没有。目录在 Host 启动时冻结；Run 中途不重新扫描 Plugin 或重写内置定义。

### 6.3 公开摘要形状

在现有 `agentSummary` 上增加两个字段（当前未发版，直接改协议并再生两端类型，不做兼容别名）：

```text
kind: "builtin" | "plugin"
tools: string[]     # 角色声明的工具上限
```

约定：

- `explore`：`tools` 为 `["glob","grep","ls","lsp","read_file"]` 的排序列表。
- `general-purpose`：`tools` 为空数组，表示「父能力减去强制排除项」；`purpose` 必须写明排除了哪些工具。
- Plugin：`tools` 为其声明白名单；未声明则为空数组，语义保持现有「再与父 Policy 求交」。
- `model_profile_id`：两个内置角色固定为 `inherit`，表示使用父 Run 已解析模型，不在 catalog 里再绑一个 Profile。
- `requested_skills` / `requested_mcp_servers`：内置角色均为空。实际可见性由 7.2 运行时求交决定：`general-purpose` 随父；`explore` 两者都空。不靠 Plugin 声明。

`/agents` 展示至少包含：id、kind/source、description 或 purpose、工具边界。`general-purpose` 显示「继承父能力，排除 task / ask_user / enter_plan_mode / exit_plan_mode / memory_save」。`explore` 列出五个工具名。

## 7. 角色定义

### 7.1 给主模型看的 description

生产 `task` 工具必须使用下面两段中文说明，不再使用 DeepAgents 英文 `DEFAULT_GENERAL_PURPOSE_DESCRIPTION`。

**general-purpose**

```text
通用多步骤子代理。继承父 Agent 的工作区能力，但不包含委派、向用户提问、计划模式切换工具和跨会话记忆写入。适合研究、搜索和实现；当文件或关键词搜索前几次没有把握时，优先交给它。它看不到父对话历史，最终只回一份完整结果。
```

**explore**

```text
只读代码定位与结构调查子代理。只能使用 ls、read_file、glob、grep、lsp。适合按文件名、符号或内容搜索，以及回答代码在哪、结构如何连接。需要改文件、执行命令、访问网络或向用户提问时不要用它。
```

### 7.2 能力求交

计算一次，同时裁剪模型可见 schema 和执行入口。

```text
输入：父 EffectiveCapabilityView、角色 ID、本 Host 实际存在的工具实现
  → 取角色上限
  → 与父视图求交（只能更窄）
  → 去掉 Forced exclusions
  → 去掉本 Host 没有实现的名字（不在 schema 里留死工具）
  → 输出 child EffectiveCapabilityView
```

角色上限：

| 角色 | 上限 | MCP | Skill 索引 | 网络 | Shell |
|---|---|---|---|---|---|
| general-purpose | 父工具全集 | 随父视图 | 继承父冻结索引 | 随父视图 | 随父视图 |
| explore | 仅 `ls` `read_file` `glob` `grep` `lsp` | 无 | 不注入 | 无 | 无 |

Forced exclusions 对两个角色都生效。因此 `general-purpose` 即使父 Agent 拥有 `task` / `ask_user` / `enter_plan_mode` / `exit_plan_mode` / `memory_save`，child 也不得拥有。

`explore` 额外强制：

- 最终 schema 与执行 registry 只能是上限与父视图、本机实现的交集。
- 若 Host 未注册 `lsp`，则 `explore` 的 schema 和执行都不包含 `lsp`，目录 `tools` 仍声明角色上限含 `lsp`，inspect/diagnostic 可说明当前 Host 未提供；不得把 `execute` 顶上这个空位。
- 系统提示不包含父 Skill 索引；`capability_view.skill_ids` 为空；不为 explore 挂载 Skill 虚拟目录。工作区里碰巧存在的 `SKILL.md` 仍可当普通文件被 `glob`/`read_file` 搜到，但不因此获得新工具。
- 无 MCP、无 `tool_search`。伪造 `write_file` / `edit_file` / `delete_file` / `execute` / `web_search` / `web_fetch` / `task` / `ask_user` / MCP / 自定义工具：执行入口稳定拒绝，错误不泄漏未授权 schema。

`explore` 的五个只读工具在 child 上视为常驻，不走父 Agent 的 deferred/`tool_search` 揭示。父 Agent 没 reveal 过 `lsp`，不妨碍 explore 使用它（在 Host 实现存在时）。

`general-purpose` 继承父冻结的 Skill 索引和 MCP 工具（再减 Forced exclusions）。MCP 在 default / auto-edit 下仍按现有规则视为风险工具，8.1 的 auto-edit 放宽只覆盖工作区普通文件写入，不覆盖 MCP。

### 7.3 子代理系统提示词

两份提示词是本仓库内置定义，不再拼接 DeepAgents `DEFAULT_SUBAGENT_PROMPT`。实现放在 agent 包内的内置资源中，catalog fingerprint 包含其 digest。下面是必须遵守的正文，允许为文件边界、Snapshot 规则做与主 Agent 同步的附录，但不得改写角色意图。

**general-purpose**

```text
你是主 Agent 派出的通用子代理，只完成这次交办的任务。

调用方只能看到你的最终回复，看不到中间推理和工具输出。最终回复必须让父 Agent 不必再翻你的过程就能继续工作，按需包含：结论、关键证据、改过的文件、做过的校验、未完成项或阻塞。不要复述全部工具输出。

规则：
- 不要扩大范围，不要做没被要求的重构或文档。
- 先查看相关代码和现状再修改。优先编辑已有文件；非必要不新建文件；未经明确要求不要写 README 或其他 *.md。
- 你继承父 Run 已冻结的工作区、AGENTS.md、Skill 索引和审批规则。你不能向用户提问；缺少证据就在最终回复里写明不确定和缺口。
- 不要尝试委派其他子代理、切换计划模式或写入跨会话记忆。
```

其后必须追加现有 `_LOCAL_SUBAGENT_BOUNDARY_PROMPT` 中的本机文件边界、`/.harness/` 只读和 Snapshot 编辑规则（与主 Agent 保持同一份文本来源，避免两套说法）。

**explore**

```text
你是只读代码搜索子代理。用尽可能少的上下文，给父 Agent 一份可交接的调查结果。

你只能使用 ls、read_file、glob、grep、lsp。没有写文件、命令执行、网络访问、MCP、Skill 目录或向用户提问的能力。只搜当前工作区和 AGENTS.md，不要按主 Agent 的工作流 Skill 行事。

做法：
- 先用 glob、grep 或 lsp 定位，再按需 read_file。不要整文件通读，除非文件很小。
- 尽量并行调用工具。
- 第一次搜索落空时，必须再换一种模式、路径或符号查询，才能断言目标不存在。
- 按任务需要自行判断深度：点查关键文件、跟进口与核心实现，或沿依赖把相关符号查清。

最终回复必须包含：
- 简短结论
- 相关文件的工作区虚拟路径和关键符号
- 这些部分如何连接
- 仍不确定的缺口

不要复述读过的整段代码，只引用对结论必要的片段。不要尝试修改仓库。
```

explore 同样追加本机文件边界中「只能读当前工作区、使用 `/` 虚拟路径」的约束；不要把「禁止写文件」当成唯一防线。

## 8. 审批与 Interaction

### 8.1 child 有效审批模式

内置 child **不得比父更松**。唯一允许的产品放宽：父为 `default` 时，`general-purpose` 内部按 `auto-edit` 运行，避免每次写文件再弹一次。不允许做成 Oh My Pi 那种 child yolo（批准 `task` 即授权 Shell）。

计算：

```text
输入：父审批模式、角色 ID
  → explore：不启动 HITL（见 8.2）；内部无风险工具
  → general-purpose 且父为 default → child 模式 = auto-edit
  → 其余 → child 模式 = 父模式
```

| 父审批模式 | general-purpose child | explore child |
|---|---|---|
| default | 内部 **auto-edit**：工作区内非敏感写/改自动；`execute`、敏感路径、目录信任仍问 | 不弹审批 |
| auto-edit | 与父相同，不额外放宽 | 不弹审批 |
| auto | 与父相同的分类器与 deny 兜底 | 不弹审批 |
| yolo | 与父相同，不弹 Harness 人工确认 | 不弹审批 |
| plan（审批模式） | 与父相同，写/执行硬拒绝 | 只读工具可运行 |

dynamic deny 在 child 工具入口仍然不可绕过，且不受上述放宽影响。用户拒绝某次 child 工具调用后，拒绝结果作为该 child 的 tool result 返回，child 继续推理；默认不得把拒绝升级为取消父 Run。

工作区内自动放行的写入仍作为有界工具活动进入父时间线（带 `agent_id`），只是不挡执行。

### 8.2 启动 `task` 本身

`task` 对父 Agent 仍是委派工具：

- 目标解析为 `explore`，且这次执行将使用的 child 能力视图满足 7.2 的只读约束 → 启动自动通过，不弹委派审批。若实现缺陷导致 explore 能力视图含非只读工具，必须 fail closed，不得自动通过。
- 目标为 `general-purpose` → 按父模式处理这次 `task` 调用。`default` 下必须审批；卡片必须写明目标 Agent ID、任务摘要，以及「可在工作区改文件，普通写入过程中不再询问；执行命令和敏感路径仍会询问」。
- 目标为 Plugin → 按父模式处理这次 `task` 调用。Plugin child 内部要再审批时仍 fail closed（8.3），因此这次派出审批不能被理解成「此后无人值守写入」。
- 父已是 yolo / auto 等不弹 `task` 的模式时，派出本身也不弹，内部仍走 8.1。

### 8.3 child Interaction 桥

本任务只有 `general-purpose` 会向用户发审批或目录信任，且仅限 8.1 仍要求询问的操作（`execute`、敏感路径、工作区外目录信任）。工作区内非敏感 `write_file` / `edit_file` / 非敏感 `delete_file` 在 child 为 auto-edit 时不走 Interaction。

- 仍弹出的 HITL 与目录信任必须到达现有 TUI/Web Interaction，使用现有 `interaction.approval` / `interaction.directory_trust`。
- 请求必须带 `agent_id`（子代理 ID）、`execution_id`（child）、`parent_execution_id`（父）。协议这些字段已存在，CLI/Web 必须读出来。
- 审批卡可见信息：子代理名称、真实工具名、关键参数；文件类必须有与主 Agent 相同质量的 Diff。标题不能只写「需要审批」，至少写成「子代理 general-purpose 需要审批」或等价中文。
- 拒绝、拒绝并反馈、批准一次/会话/项目的决策集合与主 Agent 相同，规则写到父 Run 的同一套 rule store，后续父与 child 共用。
- 内置 child 不发送 `interaction.question`。即使模型伪造 `ask_user`，执行层拒绝。

Plugin child 保持 `FailClosedManagedObserver`：需要 Interaction 时 `MANAGED_AGENT_INTERACTION_UNAVAILABLE`。Plugin 定义不得声明或生效任何比父更松的审批模式（对齐 Grok Build：忽略 plugin `permissionMode`）。本任务不把 8.1 的 auto-edit 放宽套用到 Plugin。

### 8.4 与主 Agent 展示如何共存

当前 CLI 只有一个 `pendingInteraction`，新请求会替换旧请求并把旧的 fail-closed。这与「child 和父都可能要展示」冲突。

本任务规定：

```text
Host 已按 request_id 保存多份 in-flight Interaction
  → CLI/Web 改为 FIFO 队列
  → 屏幕同时仍只渲染队头一张卡
  → 用户答完队头，再展示下一张
  → 新请求入队，不得替换、不得把未回答的请求按失败丢弃
  → 父 Run 取消、失败或完成时，队列剩余请求统一 fail-closed 并唤醒对应 child/父工具
```

顺序按到达时间。不把 child 审批插队到正在回答的 `ask_user` 前面。时间线若展示 Interaction 卡片，必须能按 `agentId` 归入对应活动，避免看起来像主 Agent 自己申请。

这不是多 Dock 并列，也不是子代理专用页面。

## 9. 上下文、模型与运行时

### 9.1 派生规则

```text
输入：父 RunContext、DelegateAgent.task、目标角色
  → 新建 child execution 身份
  → 复制父冻结的 ModelProfile、workspace 事实、AGENTS.md、deny rules
  → general-purpose 再复制父 Skill 索引与 MCP；explore 两者都不复制
  → 按 8.1 计算 child 有效审批模式（不得比父更松，default 下 general-purpose 用 auto-edit）
  → 不复制父 messages / todos
  → 按 7.2 生成 child 工具与 middleware
  → 以 HumanMessage(task) 启动 child 对话
```

child 运行中不得重新读用户模型配置、不得重新扫描 Plugin、不得重新读已经变化的 `AGENTS.md`。下一轮父 Run 才会刷新那些快照。

两个内置角色都是 Inline：不领取独立 AgentEnginePool lease，不创建可恢复 checkpoint namespace。需要独立工具实例和审批上下文，不能借用父图里已绑定父 execution 的 HITL 中间件实例。

### 9.2 父 Transcript 里能看见什么

父时间线只保留现有 `task` 派出卡片，以及带 child 身份的审批 / 目录信任。child 的工具过程、思考和正文不进入父 Transcript，也不作为主模型下一轮上下文。

点进子代理自己的时间线查看过程，由 [HC-162](../task/archive/HC-162-子代理时间线.md) 交付，本任务不停点实现。

`task` 的 tool result 只包含最终文本或稳定错误码。

## 10. 生命周期

由 `AgentDelegator` 统一执行，两个内置角色和 Plugin 共用，不再为 explore 开第二条调度。

| 规则 | 行为 |
|---|---|
| 深度 | 父 depth+1 > 1 则 `DELEGATION_DEPTH_EXCEEDED`。child schema 无 `task`，执行层再拒绝一次。 |
| 并发 | 每个父 execution 同时运行中的 child 最多 4 个。超过则排队，而不是立刻 `DELEGATION_PARALLELISM_EXCEEDED`。父 Policy 的 `max_parallelism` 只能更严，不能放宽过 4。 |
| 取消 | 父 Run 取消时，排队未启动的 child 不得启动；执行中的 child 必须被取消。两者都释放许可。 |
| 超时 | 硬 deadline，默认 300 秒（沿用现有 `DelegateAgent.timeout_seconds`）。到期必须取消实际 child 任务，不能只在模型轮次边界检查。本任务不新增用户配置项。 |
| 释放 | 成功、目标不存在、拒绝启动、执行失败、取消、超时都必须归还并发许可并 finalize child execution。许可泄漏视为验收失败。 |

`explore` 启动不弹审批，不改变上述并发与取消。

|---|---|---|

## 12. Invariant

1. **单一目录**：任意时刻，`/agents` 的 ID 集合、`task` description 中的可派发 ID 集合、Delegator 能解析的 ID 集合三者相等。
2. **只收紧**：child 能力视图是父视图的子集；explore 还是五名前的子集。不存在「提示词只读、执行可写」。
3. **child 不得比父更松**：`general-purpose` 仅在父为 `default` 时内部升到 `auto-edit`；不得升到 yolo。批准 `task` 不等于批准 child 的 `execute` 或敏感路径。
4. **Plugin 不能提权**：Plugin 定义不能把审批改松；需要 Interaction 时 fail closed，不套用内置 auto-edit 放宽。
5. **拒绝回到 child**：用户拒绝 child 工具后，父 Run 仍在跑，被拒绝的是那一次 child 工具调用。
6. **新对话旧环境**：child messages 不含父历史；两者都含冻结 AGENTS / 工作区 / 模型。`general-purpose` 另含 Skill 索引与 MCP；`explore` 不含 Skill 索引、MCP、`tool_search`。
7. **Interaction 不丢请求**：在同一 active Run 内，后到的 Interaction 不得使先到的未应答请求按失败结算。
8. **终态必释放**：任何退出路径都归还并发许可并 finalize child execution。
9. **无第二条发现路径**：删除后，仓库生产代码不得再从 `.harness/agents` 或 `BUILTIN_AGENTS` 旧表加载可执行子代理。

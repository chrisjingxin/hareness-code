# HC-140 重构组合工作模式规格

关联任务：[HC-140](../task/HC-140-重构组合工作模式.md)  
替代设计：[HC-138](../task/HC-138-建立BuildCompose双.md)  
调研依据：[Compose Mode 可行性调研](../research/Compose Mode 可行性调研.md)  
实施计划：[HC-140 Plan](../plan/HC-140-重构组合工作模式.md)  
执行清单：[HC-140 Todo](../todo/HC-140-重构组合工作模式.md)

## 1. Objective

将 Compose 从“一个用户消息触发一个固定五阶段 ComposeRun”重构为“一个 Compose Thread 顺序承载多个持久 ComposeWorkItem”。每个 Work Item 跨 Turn、Run 和 Host 重启持续，以用户工作空间 Markdown 作为需求/规格/计划正文，以 SQLite 作为执行事实，以 readiness gate 而非 `current_stage` 决定下一 Activity。

目标用户是使用企业弱模型和受限上下文的研发人员。成功标准不是模型记住完整对话，而是 Runtime 能在小 ContextPack 下确定回答：当前目标是什么、哪些产物已确认、哪些证据已失效、下一步允许做什么，以及中断后能否安全重试。

## 2. 已确认假设

1. Compose 仍是独立 Mode；本规格不增加 Build 中的 `/compose` 入口。
2. Thread 第一个有效 Run 冻结 `build|compose` Mode。Compose Thread 内可以顺序创建多个 Work Item，但不能普通切回 Build。
3. 同一 Compose Thread 最多一个未终结 Work Item；未终结包含 `active`、`waiting_user`、`blocked`。
4. 用户工作空间可写；默认文档根目录 `docs/compose/`，配置只允许覆盖根目录。
5. Harness 自带原版 required Skill 资产并离线可用；首版不做摘要、重写或自动优化。
6. Compose Activity 首版固定使用 Harness 内置角色，不自动选择 Plugin Agent。
7. 当前项目未正式发布；旧 ComposeRun 内部接口和表数据没有兼容承诺，迁移采用单一 canonical 路径。

## 3. 术语与领域模型

```text
Thread
├─ thread_mode: build | compose（首条有效消息后不可变）
└─ ComposeWorkItem[]（顺序）
   ├─ work_item_id / slug / revision
   ├─ status: active | waiting_user | blocked | completed | abandoned
   ├─ document_refs + confirmed digests
   ├─ readiness snapshot
   ├─ Activity[]
   ├─ EffectIntent / EffectReceipt[]
   ├─ VerificationEvidence[]
   └─ ReviewEvidence[]

Run
└─ 一次用户 Turn 的执行身份，可附着一个 Work Item

Activity
└─ Work Item 中一次有边界的能力执行，例如 grill、spec、plan、implement、verify、review

AgentExecution
└─ Activity 内的一次 Managed Agent 模型/工具循环
```

身份不变量：

- `thread_id` 标识对话容器；`work_item_id` 标识长期研发目标；`run_id` 标识一次用户 Turn；`activity_id` 标识一次可恢复能力执行；`execution_id` 标识一次 Agent 执行。
- Work Item 不以 `run_id` 为主键。一个 Work Item 可关联多个 Run，一个 Compose Thread 可顺序关联多个 Work Item。
- 每个 Run 受理时冻结实际 `work_item_id`，写入 RunExecutionBinding；同一 `run_id` 重试若解析到不同 Work Item，返回冲突。
- Work Item terminal 状态使用 revision CAS 原子提交，不能被普通 Turn 改回未终结。对已完成目标的修改创建带 `amends_work_item_id` 的新 Work Item。

## 4. 顶层流程

```text
run.start(mode=compose)
  → RunCoordinator 受理 Run、owner、cancel、Interaction、sequence
  → ComposeRunAdapter.execute_turn
  → ComposeWorkItemEngine.execute_turn
      1. 解析 Thread mode 与 active Work Item
      2. 解析显式命令、Interaction reply、确定性继续词
      3. 必要时调用 TurnIntentResolver
      4. 读取 SQLite ledger 与 workspace Markdown
      5. 重算 document/workspace digest 和 readiness
      6. 选择一个或多个有界 Activity（受 turn budget 限制）
      7. 强制加载 required Skill
      8. 通过 ManagedAgentExecutor 执行 Agent Activity，或通过确定性 Port 执行 Verify
      9. 校验产物、记录 receipt/evidence、更新 projection
     10. 收敛到 waiting_user、blocked、turn_budget 或 completed
  → RunCoordinator 发送唯一 Run terminal
```

`ComposeRunAdapter` 只是 Host adapter，不拥有 Activity handlers、SQLite 表级操作或 LangGraph 调用。`ComposeWorkItemEngine` 是 deep module，外部 interface 不暴露内部 readiness handler。

## 5. Module、interface 与 seam

### 5.1 ComposeWorkItemEngine

```python
class ComposeWorkItemEngine(Protocol):
    async def execute_turn(
        self,
        request: ComposeTurnRequest,
        ports: ComposeTurnPorts,
    ) -> ComposeTurnResult: ...

    async def inspect(
        self,
        *,
        thread_id: str,
        work_item_id: str | None = None,
    ) -> ComposeWorkItemProjection: ...

    async def abandon(
        self,
        *,
        thread_id: str,
        work_item_id: str,
        expected_revision: int,
        reason: str | None,
    ) -> ComposeWorkItemProjection: ...
```

`execute_turn` 隐藏 Work Item 定位、文档 reconcile、readiness、Activity 选择、Skill 绑定、恢复、retry 和 terminal CAS。Host/CLI 不调用 `run_task_stage()`、`run_review_stage()` 等浅 interface。

### 5.2 ManagedAgentExecutor

Build、Compose 和 Plugin Agent 共用一个 Managed 执行 module：

```python
class ManagedAgentExecutor(Protocol):
    async def execute(
        self,
        request: ManagedAgentRequest,
        observer: ManagedAgentObserver,
    ) -> ManagedAgentResult: ...
```

`ManagedAgentRequest` 至少固定：

- execution ref 与 parent ref；
- 已解析、不可变的 `ResolvedAgentSpec` / AgentEngineProfile；
- 输入消息或结构化 Activity ContextPack；
- checkpoint namespace；
- `passthrough|capture_only|structured` 输出策略；
- Interaction policy、timeout、cancellation token；
- required Skill snapshot references；
- idempotency key。

implementation 统一拥有：AgentEnginePool lease/run lease、AgentExecutionRegistry transition、DeepAgents/LangGraph graph config、共享 `execution_stream`、Interaction resume loop、取消检查、usage、错误归一化和资源释放。调用方不能直接访问 `engine.graph.ainvoke/astream`。

生产 adapter：

```text
BuildRunAdapter       → ManagedAgentExecutor(main, passthrough)
Compose Activity      → ManagedAgentExecutor(fixed builtin role, structured)
Plugin Agent runner   → ManagedAgentExecutor(plugin spec, capture/structured)
```

Compose Workflow 不自动选择 Plugin Agent。只有未来 Workflow 明确声明或用户显式绑定时，才能把 Plugin spec 放入 `ManagedAgentRequest`；HC-140 不提供该用户入口。

### 5.3 文档与执行存储 seam

```python
class ComposeDocumentStore(Protocol):
    async def inspect(self, work_item: WorkItemRef) -> DocumentSnapshot: ...
    async def commit(self, command: DocumentCommit) -> DocumentSnapshot: ...

class ComposeWorkItemStore(Protocol):
    async def load_active(self, thread_id: str) -> ComposeWorkItem | None: ...
    async def load(self, work_item_id: str) -> ComposeWorkItem | None: ...
    async def transact(self, command: WorkItemCommand) -> WorkItemCommit: ...
```

Workspace adapter 只接受工作空间相对路径，使用现有 Snapshot/file contract 完成安全读写。SQLite adapter 借用 `ThreadPersistence` 的连接和 lock，通过事务完成 Work Item revision、Activity、effect receipt、evidence 和 projection 提交。

## 6. Thread Mode 与 Work Item 生命周期

### 6.1 Mode 锁定

- 新 Thread 没有有效消息时可在 Build/Compose 切换。
- 第一个 `run.start` 成功受理时写入 `thread_mode`；之后 `run.start.mode` 必须相同，否则返回 `THREAD_MODE_LOCKED`。
- Compose Work Item 完成不会解除 Mode；用户可在相同 Compose Thread 创建下一个 Work Item。
- HC-140 不提供普通 force-switch。恢复旧 Thread 时从持久化 `thread_mode` 决定 UI Mode，不从最后一条渲染消息猜测。

### 6.2 创建新 Work Item

- Compose Thread 没有未终结 Work Item，且输入是 coding 目标：原子创建 Work Item 和 `docs/compose/<slug>/` 文档 root，再执行 grill Activity。
- `/new-work` 仅 Compose 可见。没有未终结项时进入等待新目标状态；存在未终结项时必须先确认继续当前项或放弃后新建。
- slug 由 Runtime 基于首个目标生成、规范化并解决冲突；数据库保存稳定目录，后续模型不能改名。
- 已完成 Work Item 的修改请求创建新 Work Item，并设置 `amends_work_item_id`；旧 terminal、evidence 和文档审计不被覆盖。

### 6.3 放弃

- `/abandon` 和 Compose UI action 进入同一个 typed confirmation；自然语言“放弃这个任务”只能提出 intent。
- 确认后先取消当前 Run/Activity并收敛 Tool receipt，再用 expected revision CAS 提交 `abandoned`。
- 已写文档、代码、测试和 Artifact 全部保留，不自动回滚、不删除目录。
- `abandoned` 不可 resume；后续修改创建新 Work Item，可通过 lineage 指向旧项。

## 7. Turn Intent 路由

路由优先级不可交换：

```text
1. Protocol Interaction reply（request ID 精确关联）
2. 显式 Command / UI Intent
3. 确定性控制短语（继续、接着做等受限词表）
4. TurnIntentResolver
5. typed clarification
```

结构化 intent：

```text
resume_current | amend_current | start_new_work | side_question | unclear
```

`TurnIntentResolver` 使用独立小 Context，只接收当前 Work Item goal/scope 摘要、pending decision、current activity 和本条消息；不拥有 Tool，不读取完整对话，也不能写状态。其输出必须通过严格 schema。

安全规则：

- `resume_current`：恢复第一个 interrupted、retryable 或未满足 Activity。
- `amend_current`：追加用户 stimulus，相关文档需重建或重新确认，并按 dependency invalidation 使下游 stale。
- `side_question`：走 `/btw` 同一只读临时执行，答案不写主 Transcript、Work Item ledger 或后续 ContextPack。
- `start_new_work`：无未终结项时创建；有未终结项时必须 typed clarification。
- `unclear` 或 classifier error：必须让用户在“修改当前任务 / 开始新任务 / 临时提问 / 取消”中选择，不能猜测执行。

## 8. Workspace Markdown 契约

默认路径：

```text
<workspace>/<compose.docs_dir 或 docs/compose>/<slug>/
├─ task.md
├─ spec.md
├─ plan.md
├─ todo.md
└─ report.md
```

根目录配置必须是工作空间相对、规范化、不可穿越的目录；文件名固定。每份文档包含有界 front matter：`work_item_id`、`kind`、`revision`、`status`、`updated_at`，正文由对应原版 Skill 生成。数据库只存相对路径、content digest、confirmed digest、revision 和 lineage。

权威规则：

- Task/Spec/Plan/Todo/Report 的语义正文以 Workspace Markdown 为准。
- Work Item 生命周期、人工确认、Activity、effect、evidence 和 terminal 以 SQLite 为准。
- 数据库中 confirmed digest 与当前文件 digest 不同，确认立即 stale；Runtime 不把数据库里的旧摘要覆盖回文件。
- Markdown 缺失或 schema 无效时，对应 readiness 为 false；数据库不能从摘要重建正文。
- SQLite Work Item 丢失时允许从完整文档集合导入一个恢复候选，但旧 verification/review/effect 不能视为 fresh，必须重新执行；该导入能力若实现复杂可作为 HC-140 后段验收，不允许伪造证据。

## 9. Readiness 与依赖失效

持久状态保存文档和证据事实，不保存一个只能向前的权威 `current_stage`。每个 Turn 和恢复点调用纯 `ReadinessResolver`：

```text
task_confirmed
  → spec_confirmed
  → plan_confirmed
  → todo_executable
  → implementation_current
  → verification_fresh
  → review_fresh
  → report_current
  → complete
```

判定要求：

- `task_confirmed`：task.md schema 有效，用户确认记录绑定当前 digest。
- `spec_confirmed`：Task 仍 confirmed，spec.md schema 有效，确认绑定当前 task/spec digest。
- `plan_confirmed`：Spec 仍 confirmed，plan.md 与 todo.md 互相一致、无 placeholder、DAG 无环、命令有界，用户确认绑定当前 digest 集合。
- `todo_executable`：所有未完成项具备目标、acceptance、依赖、相关文件或发现策略、focused verification。

计划批准后 todo.md 会按实现、验证与 Review 事实勾选并追加修复项，这是计划
内容的预期演进：`plan_confirmed` 运行时判定以 plan.md digest 为准（批准时
Plan+Todo 双 digest 仍联合写入审计）；todo 勾选变化使 `implementation_current`
等下游证据失效，但不重新触发 Plan gate。
- `implementation_current`：Todo 完成证据绑定当前 task/spec/plan/todo 和 workspace revision；上游修改或相关工作区变化会使其 stale。
- `verification_fresh`：全部 required command 对同一 workspace revision 产生 exit code 0、时间和输出 digest。
- `review_fresh`：Requirement/Code 两个只读、不同 execution 的 Review 均绑定同一文档和 workspace revision，且没有 Required finding。
- `report_current`：report.md 引用当前文档、verification 和 review digest。
- `complete`：以上全部满足，且没有 pending/unknown effect，由 Guard Kernel 以 revision CAS 提交 terminal。

UI `current_activity` 是第一个未满足 gate 的投影，不是另一份事实源。Requirement/Verify/Review finding 生成来源明确的修复 Todo；修复后必须重新计算所有下游 gate。

## 10. Activity 与原版内置 Skill

Harness 新增统一根目录：

```text
packages/agent/harness_agent/skills/builtin/
├─ manifest.json
└─ <skill-package>/
   ├─ SKILL.md
   ├─ references/
   ├─ scripts/
   └─ assets/
```

manifest 记录 reserved ID、display name、upstream URL/revision、license、所有文件 digest、可见 Mode 和用途。Compose required Skill 使用 reserved builtin identity，不允许 project/user/plugin 同名资产遮蔽；Skill snapshot 在每个 Activity 受理时冻结并写 ledger。

首版映射：

| Activity | required Skill | 产物/结果 |
| --- | --- | --- |
| grill / task | `mattpocock:grill-me` | `task.md` + 用户确认 |
| spec | `agent-skills:spec-driven-development` + `mattpocock:codebase-design` | `spec.md` + 用户确认 |
| plan / todo | `agent-skills:planning-and-task-breakdown` | `plan.md`、`todo.md` + 用户确认 |
| implement | `agent-skills:test-driven-development` | 代码、测试、Todo evidence |
| diagnose（按失败触发） | `mattpocock:diagnosing-bugs` | 诊断与修复输入 |
| review | `agent-skills:code-review-and-quality` | 双轴 Review evidence |

Skill 原文中的通用输出路径由 Activity 的用户任务指令覆盖为当前 `docs/compose/<slug>/`，Skill 本体不修改。缺文件、digest/license manifest 不匹配或 required Skill 不可解析时，Activity 进入 stable blocked/failed，不退化为普通 Prompt。

## 11. 三个人工门禁

```text
Task 写入并校验
  → [确认目标与范围 | 提出修改 | 放弃]

Spec 写入并校验
  → [确认行为与 interface | 提出修改 | 放弃]

Plan + Todo 写入并校验
  → [批准实施 | 提出修改 | 放弃]
```

门禁使用 typed Interaction，确认记录保存 `work_item_id + document digest set + user decision + timestamp`。修改必须携带 feedback 并启动同类新 Activity；旧确认保留为审计但不再 fresh。批准实施后无需用户机械输入“继续”，Runtime 自动执行 Implement → Verify → Review → Report，直到需要新决策、blocked、turn budget 或 completed。

## 12. Verification、Review 与 Guard Kernel

- Verification 继续使用 canonical execution backend、Policy、Approval、workspace、sandbox 和读写锁；模型输出不能充当 exit-code evidence。
- 每条 evidence 保存 command digest、工作目录身份、workspace revision、started/finished、exit code、bounded output digest/summary 和执行 adapter 身份。
- Requirement Reviewer 与 Code Reviewer 是两个独立 Managed execution，均使用只读 spec；作者 execution 不得兼任。
- Reviewer 输出必须绑定 Task/Spec/Plan/Todo digest 和 workspace revision；Required finding 创建 fix Todo，Optional/Nit 进入 Report。
- Guard Kernel 是不可绕过的纯/事务模块，唯一有权把用户确认标为 fresh、使 evidence 失效、接受 effect receipt 和提交 Work Item complete/abandoned。

## 13. 中断、429、崩溃与副作用

Activity 状态：

```text
pending | running | waiting_user | retryable_failed | interrupted |
blocked | completed | failed | cancelled
```

恢复规则：

- 用户 Esc/Run cancel：当前 AgentExecution 取消，Activity 记 `interrupted|cancelled`，Work Item 保持未终结；下一次“继续”从安全边界恢复。
- 429/供应商限流：记录稳定 provider error 和 Retry-After，按配置执行有界 retry；预算耗尽后 Activity 为 `retryable_failed`，Work Item 保持可继续。
- Host 正常关闭或异常重启：启动恢复扫描把遗留 `running` Activity 改为 `interrupted`，读取 effect ledger 和 workspace digest 后重算 readiness。
- Agent 模型调用无外部副作用时，可以使用 LangGraph checkpoint 或从 Activity 输入重新执行；不承诺续写半条 token。
- Tool 调用前原子写 `EffectIntent`，完成后写 `EffectReceipt`。相同 idempotency key 的 confirmed receipt 不重复执行。
- intent 无 receipt 时由 Tool adapter reconcile：可证明未执行则重试；可证明已执行则补 receipt；结果未知则 Work Item `blocked` 并请求用户决定。
- 文件写入后以真实重读 Snapshot 作为 receipt；Shell/MCP/未来 Git/远端操作分别定义 adapter-specific receipt，不允许用模型自述补齐。

## 14. Command Registry 与交互

共享 `CommandDefinition` 增加 Mode/Work Item availability：

```ts
type CommandAvailability = {
  workModes?: readonly WorkMode[]
  requiresActiveWorkItem?: boolean
  requiresIdle?: boolean
}
```

| 命令 | Build | Compose | 语义 |
| --- | --- | --- | --- |
| `/btw <question>` | 可见可用 | 可见可用 | 临时只读回答，不进入主上下文 |
| `/new-work` | 隐藏 | 可见 | 无 active 时等待新目标；有 active 时 typed clarification |
| `/abandon` | 隐藏 | active 时可用 | typed confirmation 后终结当前 Work Item |
| `/new` | 可见 | 可见 | 新建 Thread，语义不变 |

补全、命令菜单、Help、TUI/Web action 均消费同一 availability；dispatch 再次复核，防止状态在展示后变化。用户在不适用 Mode 手输已注册命令时返回 `COMMAND_MODE_UNAVAILABLE`，不能把 Slash 文本交给模型。

Work Item projection 至少包含：`work_item_id` 的非敏感短显示、slug/title、revision、status、current_activity、readiness gates、document statuses、pending decision、retry/block 摘要、verification/review freshness。UI 不显示绝对路径、Prompt、完整 Skill、数据库 identity 或原始 Tool output。

## 15. Persistence 与协议

SQLite 继续使用 `~/.harness/threads.sqlite3`、project fingerprint 和 ThreadPersistence 事务锁。建议 canonical 表职责：

```text
harness_compose_work_items
harness_compose_documents
harness_compose_activities
harness_compose_effects
harness_compose_confirmations
harness_compose_verification
harness_compose_reviews
```

表名和列可以在实现前按 SQLite 事务 locality 合并，但 interface 和事实职责不得改变。必须有“每 Thread 最多一个未终结 Work Item”的数据库约束或等价事务检查。

Protocol/Host 至少提供：

- `run.start(mode=compose)` 自动 attach/create Work Item；实际 binding 记录 `work_item_id`。
- 只读 inspect，用于 `threads.open`/恢复时取得 Work Item projection。
- CAS abandon operation，由共享 Command handler 调用。
- `compose.work_item` / `compose.activity` 类型化完整 projection event；命名可在 canonical schema 中一次确定，不保留旧 `compose.state` 双发。
- stable error：`THREAD_MODE_LOCKED`、`COMPOSE_WORK_ITEM_CONFLICT`、`COMPOSE_DOCUMENT_STALE`、`COMPOSE_REQUIRED_SKILL_MISSING`、`COMPOSE_ACTIVITY_INTERRUPTED`、`COMPOSE_EFFECT_OUTCOME_UNKNOWN`、`COMPOSE_EVIDENCE_STALE`、`COMMAND_MODE_UNAVAILABLE`。

旧 `harness_compose_runs/artifacts` 不继续作为生产事实源。迁移保留 Thread/Transcript，不导入旧 Compose terminal/verification 为新 Work Item evidence；旧表直接移除或在 schema rebuild 中废弃，不做运行期 fallback。

## 16. LangGraph 的职责

LangGraph/DeepAgents 负责：

- 一个 Managed AgentExecution 内的模型/工具循环；
- Tool interrupt、Interaction resume；
- execution checkpoint；
- Middleware、Skill、MCP、Tool 和流式事件。

ComposeWorkItemEngine 负责：

- Work Item 长期身份与多 Run attach；
- 文档确认、lineage、readiness 和 invalidation；
- Activity、effect receipt、retry 和 terminal CAS；
- workspace revision、verification freshness 和 reviewer provenance；
- 用户 Turn intent 与 Mode/Command 语义。

HC-140 不把完整 Work Item 实现为 LangGraph 父图，避免与 RunCoordinator owner、外部 Markdown 修改和 Tool effect 形成三套生命周期。未来 WorkflowProgram 可以在 ComposeWorkItemEngine implementation 内使用其他 adapter，但外部 interface 不变化。

## 17. 安全与边界

### Always

- 所有 Agent execution 经过 ManagedAgentExecutor、ResolvedAgentSpec、Policy、WorkspaceBoundary、Sandbox、Tool approval 和取消链。
- 文档路径在 Runtime 规范化并限定工作空间；项目内容、Skill、Tool output 都是不可信输入。
- confirmation、receipt、evidence 和 terminal 用 SQLite 事务和 revision CAS。
- required Skill 使用打包 digest；Work Item ledger 记录实际 snapshot。
- 测试使用 fake model/backend，不使用真实凭据。

### Ask first

- 用户对 Task/Spec/Plan 的语义确认。
- 放弃未终结 Work Item。
- outcome unknown 的副作用如何处置。
- 既有 Policy 要求审批的文件、Shell、MCP、网络或远端操作。

### Never

- 模型直接推进 readiness、确认文档、放弃 Work Item 或宣布 complete。
- Compose 自动选择 Plugin Agent、扩大 delegation allowlist 或跳过 required Skill。
- 把数据库摘要覆盖到用户修改后的 Markdown。
- 对未知副作用自动重试，或把旧 workspace revision 的验证/Review 当作 fresh。
- 保留新旧 Compose 双写、别名和 fallback。

## 19. Testing Strategy

1. 纯领域测试：Work Item lifecycle、readiness、digest invalidation、Turn intent precedence、Activity retry、terminal CAS。
2. SQLite/文件集成：唯一 active、事务回滚、torn effect、外部 Markdown 修改、Host 重启扫描、旧表移除。
3. ManagedAgentExecutor contract：Build passthrough、Compose structured、Plugin delegated、Interaction resume、取消、usage、checkpoint namespace 和资源释放共用同一测试面。
4. Compose tracer bullets：Task gate、Spec gate、Plan/Todo gate、Implement、Verify、Review、Report 分别形成可运行纵向路径。
5. Protocol/Host：Mode 锁定、Run attach、inspect/abandon CAS、事件 revision、稳定错误和 Transcript/side-question 隔离。
6. Interactive/TUI/Web：Command Mode 可见性、dispatch 复核、typed clarification、三个门禁、恢复投影和双端 parity。
7. fake-model E2E：同 Thread 两个顺序 Work Item、继续、amendment、临时问题、放弃、429、取消、崩溃恢复、unknown effect、verification/review stale 和 Build 回归。
8. 每个行为变更实施时按 TDD 先写失败测试；交付前运行项目级检查。

## 21. 非范围

- 自动 Plugin Agent routing、Plugin Mode、公共 Workflow SDK。
- 并行 active Work Item、跨 Thread Work Item 调度、Work Item mailbox。
- Skill 精简优化、自动更新 upstream 或运行时联网下载 Skill。
- 自动 Git commit/push/PR、发布、远端 CI。
- token 中间续写和 outcome unknown 副作用自动重放。
- 旧 ComposeRun 数据与内部接口兼容。

## 22. Success Criteria

- Task 中全部可观察验收通过。
- Call graph 中 Build、Compose Activity、Plugin Managed execution 不再直接各自调用 graph；统一通过 ManagedAgentExecutor。
- 生产代码不再以 `ComposeStateMachine.initial(run_id)` 作为每个 Compose Turn 的入口，也不读取旧 ComposeRun 作为 fallback。
- 同一 Compose Thread 的两个顺序 Work Item、跨 Host 恢复和三类用户输入由 fake E2E 证明。
- 当前文档/workspace revision 改变会自动使 verification/review/report stale，Guard 拒绝 complete。
- 原版 Skill bundle 可离线校验、不可被同名项目资产遮蔽，并有来源/license/digest 记录。
- Build、权限、安全、资源释放、TUI/Web 和项目级检查无回归。

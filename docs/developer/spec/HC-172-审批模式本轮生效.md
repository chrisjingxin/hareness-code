# HC-172 审批模式本轮生效规格

关联任务：[HC-172](../task/archive/HC-172-审批模式本轮生效.md)

用户结果与验收以 Task 为准；本文锁定行为、公开 interface、错误语义和并发不变量。

## 1. 公开 RPC

新增受控方法 `run.set_approval_mode`：

```text
params:  { thread_id, run_id, approval_mode }
result:  { thread_id, run_id, approval_mode, revision }
```

`approval_mode` 只能是协议枚举。方法需要 `run.approval_mode` capability、当前 ControlLease，并且只能由该 Run owner 调用。`revision` 是 Run 内单调递增的非负整数；相同 mode 的幂等调用不增加 revision，成功响应总是返回 Host 实际 mode/revision。

### Protocol 版本决策

本任务直接扩展 canonical Protocol v3.8，不升到 v3.9。当前仓库仍处于预发布阶段，按照 [AGENTS.md](../../../AGENTS.md) 的兼容性原则，v3.8 尚无外部兼容承诺；本次变更属于同一未发布契约的补全，不需要为内部旧调用方保留双路径。`run.set_approval_mode` 明确标记 `min_minor: 8`，协商到 v3.7 或更低的连接在 handler 前稳定返回 `PROTOCOL_MINOR_REQUIRED`；若正式发布前冻结了 v3.8，则后续协议变更必须重新评估升 minor。

稳定错误：`RUN_APPROVAL_MODE_NOT_FOUND`、`RUN_APPROVAL_MODE_NOT_OWNER`、`RUN_APPROVAL_MODE_BUSY`、`RUN_APPROVAL_MODE_CANCELLED`、`RUN_APPROVAL_MODE_TERMINAL`、`RUN_APPROVAL_MODE_PLAN_LOCKED`。错误 data 只含稳定 code/retryable/details，不含 prompt、路径、凭据或工具参数。

## 2. 状态和线性化

Host 为每个活动 Run 保存 `ApprovalModeState(mode, revision)`。初始值来自 RunPreparation 的实际有效策略，而不是仅来自 CLI 请求；`run.started` 仍只记录初始 mode。Host 在 coordinator 锁内按 capability、ControlLease、owner、活动状态、pending Interaction、取消标记和 Plan 约束顺序检查，然后原子更新 mode/revision 并记录一条脱敏 `run.approval_mode.changed` 诊断。

RPC 成功更新点就是线性化点：

```text
请求 → ControlLease → owner/Run/状态检查 → Plan 约束检查 → mode+revision 更新 → 响应
```

更新前已经进入决定或执行的模型/工具调用不撤销、不重放；更新后尚未作决定的边界读取新状态。取消/终态与切换按 coordinator 临界区先后顺序线性化；待审批、问题、目录信任、计划审阅或其它 Interaction 存在时切换失败。

## 3. Core 与运行时

- CLI 空闲时只提交下一轮覆盖；活动且无 pending Interaction 时必须先调用 RPC，成功后以响应的实际 mode/revision 更新 snapshot，失败保持旧 UI 值。
- `RunContext` 持有同一个 Host-owned 状态或其 child 的有界求交视图；模型 prompt、HITL preflight、PlanMode、AUTO classifier/destructive guard、目录信任和 task/child 决策不得读取构图期旧值。
- 共享图在构建时编译安全超集：包含所有模式可能需要的 HITL 通道和 guards，模式切换只改变运行时判断。
- Plan 模式立即硬拒绝未决定的非只读工具；一次 `enter_plan_mode` 触发的 `RunPlanConstraint` 只能收紧，离开用户档位不能绕过它；Plan review pending 时不能切换。
- AUTO 动态进入两阶段分类器/破坏性 guard；共享 Engine 的分类决策按 `(thread_id, run_id, execution_id, tool_call_id)` 隔离，拒绝 streak 也按同一 Run 命名空间隔离，模型后处理、HITL 预检和执行守卫复用同一调用的一次决策；分类器不可用时回退人工审批并 fail closed。离开 AUTO 后分类不再执行。
- 子代理按 `resolve_child_approval_mode(parent_current, child_max)` 计算有效 view；未来调用使用更严格的父模式，正在运行的 child 不取消。Managed child 仍只在恢复成功消费后执行 `on_resume_consumed`。
- RuntimeState 和 compaction snapshot 在 capture 边界读取实际当前 mode，不缓存旧快照中的模式小节。
- 同一活动 Run 的并发模式 RPC 按 Run 串行提交；每次响应以最新已确认 mode 更新 `prePlanMode`，因此进入 Plan 后退出会恢复最后一个服务端确认档位。

## 4. 安全优先级

决策优先级保持：企业硬策略 / Capability / deny / Workspace-Sandbox containment / Plan hard deny 高于审批模式；YOLO 只移除可移除的人工确认，不能绕过硬拒绝。Run owner 的控制面切档与 repository-level trust 是不同概念：unknown/untrusted project 不额外阻止活动 `auto/yolo` 切换，只有已经存在 pending `directory_trust` Interaction 时按通用 `BUSY` 规则拒绝。外部目录工具由独立的 `WorkspaceBoundary`/`directory_trust` 流程约束；外部目录在 YOLO 下自动授予 session 根，切回其它模式后新目录重新走信任卡片。客户端不增加可伪造的 `source`/`user_initiated` 字段；未来若需要仓库信任 ceremony，应由独立的 Host-minted 流程统一覆盖 initialize、idle、run.start 和 active set，不属于本任务。

## 5. 可观察测试

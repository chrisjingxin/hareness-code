# HC-173 Spec：注释回检与关键点增强

## 1. 注释风格标准（全部执行者统一遵守）

以用户确认的样本为基准（`packages/agent/harness_agent/threads/context_pressure.py`、`packages/cli/src/ipc/client.ts`，patch 见 `tmp/review-sample.patch`）。

### 新增注释

- 像给同事讲代码：一两句白话说清「为什么这么写 / 约束是什么 / 踩过什么坑」；能一句说清不写三句。
- 写 why 不写 what。好例：「空闲压缩只认"新一轮对话的第一步"：只有 top_level_initial 能带来真实的用户离开时长，工具执行之间的间隔不算空闲」。反例（禁止）：「调用 compaction 函数处理消息列表」。
- 用代码与文档中已有的名字（Thread、Run、CAS、docstring 等），不自造「XX 机制 / XX 协议」类新词。
- 密度参考：普通文件 0-5 处；复杂文件 5-15 处；万行文件按功能区每段 5-15 处。没有难懂点就一行不加。

### 回检已有注释（逐条量）

| 病灶 | 处置 |
|------|------|
| 黑话堆叠、只有懂全系统的人才懂 | 改写：先一句白话讲清这件事，再补约束 |
| 复述代码 | 删或改写 |
| 夹英文抽象词（transport-neutral、fail closed 等） | 换白话；协议名、代码标识符等专有名词保留原文 |
| 与代码行为不符（过时） | 修正；**不确定是否过时 → 不硬改**，在交付说明中列出 |
| 已白话简洁 | 不动（避免无意义 churn） |

### 红线

- 不改任何代码行为：不动标识符、字符串、控制流、空行结构（注释形态除外）。
- 注释中禁止出现：密钥、内网主机名、账号、个人数据。
- 注释正文避免 `*/`、连续三引号等会提前闭合注释的序列。

## 4. 防误改三层校验（每个执行单元必须全过）

1. **diff 白名单**：`git diff -U0 master` 逐行检查——允许注释行增删改（Python：`#`、`"""` docstring；TypeScript：`//`、`/* */`）；任何代码行（`def`/`return`/`const` 等）的增删改 = 红灯，回滚该文件重做。
2. **strip 等价校验**：Python 侧对 `git show HEAD:<file>` 与工作区版本分别 `ast.parse`，剥离全部 docstring 后比较 `ast.dump`，完全相等才通过；TypeScript 侧正则剥除 `/* */` 与 `//` 后压缩连续空行比对（压缩空行是必须的，否则单行 JSDoc 换多行会误报）。执行前先 `grep -rn "__doc__" harness_agent/` 确认 docstring 运行时用点，涉及处不随意改。
3. **测试**：单元内 focused 测试 + 本包全量（agent：`cd packages/agent && .venv/bin/python -m pytest -q`；cli：`cd packages/cli && bun test` + `bun run typecheck`）。

## 5. 交付物与合并契约

- 每个执行单元在自己的 worktree 工作（`git worktree add ../harness-code-feature-wt-<单元> -b comments-<单元> master`），完成后提交到 `comments-<单元>` 分支，patch 留存 worktree 内 `tmp/review-<单元>.patch`。
- 交付说明必须包含：改动统计（文件数/行数）、校验输出、不确定是否过时而未改动的注释清单。
- 用户逐个检查 worktree，认可后由主会话 `git merge comments-<单元>` 合回 master；每合一个跑全套验证；文件零重叠设计下预期无冲突，越界改动以 master 为准回退重做。

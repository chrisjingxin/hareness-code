## 通俗问题说明

Compose 虽然分为理解、计划、构建、验证和评审五个阶段，但当前每个 Agent 阶段像一个黑盒：界面只知道“现在处于哪个阶段”，不知道模型是否仍在处理、用了什么工具、是否等待审批，也看不到阶段内已经完成的动作。阶段执行几十秒时，用户只能等待。

目标不是公开模型的隐藏思维，而是让 Compose 像 Build 一样展示 Harness 已经真实观测到的执行事件，并补充 Stage、Task、Agent 归属：

```text
阶段开始
  → 模型处理中 / 可公开 Reasoning
  → Tool started / completed
  → Approval 或 Question
  → 校验 artifact
  → 用户可读阶段摘要
  → 下一阶段
```

本文是 HC-138 之后的独立增强设计。HC-138 已交付的最小五阶段 projection 继续作为状态机事实；本文新增运行过程可观察性，不修改它的阶段推进、权限和完成判定。

## 已确认需求

- Compose 的可观察内容与 Build Mode 保持一致，并增加 Stage、Task、Agent 标识。
- 模型运行状态和耗时始终显示；只有 Build 现有安全 contract 已确认可展示的 Reasoning 才能进入 Reasoning 卡片，隐藏 chain-of-thought 不显示。
- Tool、Tool result、Approval 和 Question 实时显示并保持原始顺序。
- TUI/Web 使用统一 Timeline 和阶段分组，不新增独立 Compose 日志窗口。
- 当前阶段状态位于 Timeline 执行位置附近；活动阶段展开，完成阶段默认折叠。
- artifact 原始 JSON 不显示；Runtime 在严格校验后生成阶段摘要。
- 当前会话保留完整的安全执行过程；Thread reopen 恢复有界阶段、Task、Tool 终态、verification 和 Review 摘要，不恢复 Reasoning。
- Stage 工具沿用 Build 的 Policy/Approval；Plan 总体确认和 Verify 独立审批规则保持不变。
- 允许提取 Build/Compose 共用的 execution stream module，但 Build 对外行为必须不变。

## 已确认现状

### Harness

- `BuildRunAdapter` 通过 LangGraph `astream(stream_mode=["messages", "updates"], subgraphs=True)` 取得模型、Tool 和 interrupt，并转换为 `run.progress`、`reasoning.delta`、`content.delta`、`tool.*` 与 Interaction。
- `BuildRunAdapter._stream_agent()` 还直接处理根 Transcript buffer、Tool call correlation 和 Interaction resume，因此它是一个包含多项职责的 implementation，不是可供 Stage 调用的稳定 interface。
- `ManagedStageAgentPort` 当前调用 `engine.graph.ainvoke()`，只读取最后一条消息并解析严格 JSON。调用期间没有 event sink，也没有 child Interaction resume 循环。
- `RunCoordinator` 是唯一 sequence、owner、取消、Interaction 和 terminal owner；`RunLifecyclePort.emit()` 当前把事件 provenance 固定为 root execution。
- v3 Event envelope 已有可选 `execution_id`、`parent_execution_id` 和 `agent_id`，但 Compose UI 不能仅凭这些字段可靠恢复 Build task、attempt 或 Verify command 归属。
- Interactive Core 已能把 Build 的 Message、Reasoning、Tool 和 Interaction 折叠为统一 Timeline；TUI/Web 都只消费同一个 snapshot。
- HC-118 的 Reasoning 规则已经限定运行期展示和 Transcript 隔离。本任务只复用该规则，不新增供应商私有字段识别。
- `compose.state` 是完整、单调 revision 的 Workflow projection；它适合展示阶段事实，不适合承载高频 Tool/Reasoning 流。

### MiMo Code 对照

本地 MiMo Code 源码提供了两点有价值的参考：

1. `packages/opencode/src/session/processor.ts` 把 reasoning、text、Tool 的 start/delta/end 统一转换为 Message Part，再由 UI 消费，Compose 不另建一套渲染协议。
2. `packages/app/src/pages/session/composer/session-request-tree.ts` 会沿父子 session tree 查找 Permission/Question，让子执行的待处理 Interaction 能在父界面回答。

但 MiMo 的 Compose 在 `packages/opencode/src/agent/agent.ts` 中仍是一个 primary Agent，主要通过 `session/prompt/compose.txt` 和 Compose Skills 改变行为。它没有 Harness 的五阶段代码状态机、严格 artifact 和独立 Reviewer。因此 Harness 只借鉴“统一事件流”和“child Interaction 向父界面投影”，不采用 Prompt-only Compose，也不引入 MiMo 依赖。

## 目标流程与关键 invariant

```text
ComposeWorkflow transition
  → 创建 activity scope
  → Stage Agent / Verification 开始执行
      → Shared Execution Stream
          ├─ run.progress + compose_scope
          ├─ reasoning.delta + compose_scope
          ├─ tool.* + compose_scope
          └─ Interaction + compose_scope
      → artifact 正文仅内部捕获
  → Runtime 校验 artifact/evidence
  → compose.summary + compose_scope
  → ComposeStateMachine 推进

Event / Interaction
  → RunCoordinator 分配 sequence / 保持 owner
  → Interactive Core 按 execution + activity 归组
  → TUI / Web 原生 Timeline
```

关键 invariant：

1. `RunCoordinator` 继续唯一拥有 Run sequence、owner、取消、Interaction 和 terminal；Stage execution 不直接发送终态。
2. `compose.state` 继续是阶段推进的唯一 projection；Reasoning、Tool 或 UI activity 不能推动状态机。
3. Build 与 Compose 使用同一个 execution stream module 解释 LangGraph event、关联 Tool 和恢复 interrupt，不复制 translator。
4. 每条 Compose 执行事件具有稳定 `activity_id` 和 Stage/Task/attempt scope；Agent event 使用真实 child execution provenance。
5. Tool correlation 至少包含 execution/activity 身份与 provider tool call ID，不能只用裸 Tool ID。
6. Stage artifact 正文采用 `capture_only`：可以被内部解析和校验，但不能作为 `content.delta`、Reasoning、日志或持久化 activity 公开。
7. 阶段摘要只能由 Runtime 基于已经校验的 artifact/evidence 生成；模型不能借摘要通道绕过字段白名单。
8. 只复用 Build 已允许的 Reasoning 提取路径；未知、加密、供应商私有或无法确认用途的字段继续 fail closed。
9. Child Tool Interaction 必须恢复同一个 graph config、checkpoint namespace 和 execution；用户回答不能重新创建 stage attempt。
10. Compose scope 只增加展示归属，不改变 EffectiveExecutionPolicy、Approval Mode、Plan 门禁或 Verify 收紧规则。
11. 根 Transcript 只保留用户输入和 Compose 最终 assistant 结果；Stage 临时内容与 activity history 不进入 ContextProjector。
12. TUI/Web 只消费共享 Interactive Core；表现层只拥有折叠、滚动和本地焦点状态。
13. 当前会话可以显示协议已截断的 Tool 参数/结果；Thread 恢复只使用更小的审计摘要，不恢复 Reasoning、原始 Tool 参数/结果或 Interaction 正文。
14. blocked、failed、cancelled 保留已完成的安全 activity 和最后 projection；迟到事件、错误 scope 或 terminal 后事件不能复活运行状态。

## 领域模型

### ComposeActivityScope

```text
ComposeActivityScope
├── activity_id       本次 stage invocation 或 verification command 的稳定身份
├── stage             understand | plan | build | verify | review
├── task_id?          Build/fix task 的内部 ID
├── task_title?       已有 Compose task title 的有界展示值
└── attempt           从 1 开始的 stage/task attempt
```

`execution_id`、`parent_execution_id` 和 `agent_id` 继续位于 Event/Interaction envelope，不在 scope 中重复。Verify 不是模型 execution 时仍使用稳定 `activity_id`，并沿用 root execution provenance；界面因此可以按相同结构分组，但不会伪造 child execution。

### ExecutionSignal

```text
ExecutionSignal
├── type              复用 run.progress / reasoning.delta / content.delta / tool.*
├── payload           对应既有严格 payload
├── execution_ref     真实 root 或 child execution
├── agent_id
└── compose_scope?    Build 中为空，Compose 中存在
```

Stage 的模型 `content.delta` 不进入 signal sink；最终完整正文只进入 `ExecutionStreamResult.final_content`，供 artifact parser 使用。Compose Workflow 校验成功后另发 `compose.summary`：

```text
compose.summary
payload = {
  status: "passed" | "failed" | "blocked" | "cancelled",
  text: bounded user-readable text
}
```

该事件必须携带 `compose_scope`。它是展示/审计摘要，不是 assistant 消息，也不能作为下一阶段输入；状态机仍只读取 artifact store。

### ComposeActivityRecord

```text
ComposeActivityRecord
├── run_id / event_sequence / activity_id
├── stage / task_id / bounded task_title / attempt
├── execution_id? / agent_id?
├── kind              summary | tool_terminal | truncation
├── label             bounded Tool 名或摘要标签
├── status
├── bounded_text?     Runtime 摘要；Tool 不保存原始参数/结果
└── created_at_ms
```

activity store 每个 Run 最多保存 500 条、编码后总计最多 1 MiB、单个文本最多 4 KiB。达到任一上限后停止追加普通记录，只原子追加一次 `truncation` 标记；live event stream 仍继续。上限应作为一个 canonical 常量组被 store、restore schema 和测试共用。

## Module、interface 与 seam

### Shared execution stream module

在 `packages/agent/harness_agent/runtime/` 建立一个 deep module。它的外部 interface 保持为一次执行调用：

```text
execute(ExecutionStreamRequest, ExecutionStreamPorts)
  → ExecutionStreamResult(final_content, usage, finish metadata)
```

`ExecutionStreamRequest` 只包含可信 execution ref、graph、初始输入、graph config/context、取消 token 和内容可见策略：

- `passthrough`：Build root 使用，安全 text 产生 `content.delta`。
- `capture_only`：Compose Stage 使用，正文只进入最终结果，不产生正文事件。

`ExecutionStreamPorts` 提供两个调用方向：

- `emit(signal)`：交给调用 adapter，再由 `RunLifecyclePort` 分配 Run sequence。
- `interact(request) → response`：交给 Run owner，返回后由 module 在同一 execution 中构造 resume。

module implementation 隐藏：

- `astream(messages, updates)` 与 resume loop；
- root/nested namespace 筛选；
- Reasoning 安全翻译；
- Tool start/delta/result 的复合身份关联；
- interrupt 提取、并发安全 Tool 自动放行和串行审批；
- usage、取消和完整 final content 捕获。

Build 和 Compose 是两个真实 adapter，因此这个 seam 能产生 leverage：修复 Tool/Reasoning/Interaction 流一次即可同时生效。Build 的 Transcript 捕获是 Build observer 的职责；Compose activity 持久化是 Compose observer 的职责，不把两种历史策略塞进 module 的 public interface。

### Build adapter

`BuildRunAdapter` 继续负责 Skill loaded、Runtime resolution、根 Transcript 语义边界和 Run 完成前 flush。它不再自行解释 LangGraph tuple。Build observer 收到 execution signal 后使用 root provenance、无 `compose_scope` 发出原有事件，并继续捕获完整 assistant/Tool transcript。

迁移不能增加 alias、旧 translator fallback 或双写路径。新 module 覆盖既有测试后，旧私有 stream translator 与重复 correlation state 应删除。

### Compose Stage adapter

`StageAgentPort.run()` 增加 Compose-owned observer interface，而不是导入 Host 类型。Workflow 为每次 invocation 创建 scope，并由 Host 提供的 adapter 把 observer 调用映射到 `RunLifecyclePort`：

```text
StageAgentPort.run(request, observer)
  → Shared execution stream(capture_only)
  → StageResult(parsed final_content)
```

observer 负责：

- 带 child execution provenance 发 scoped signal；
- 请求 scoped Tool Interaction；
- 将可持久化的 Tool terminal/summary 交给 activity store。

Understand/Plan 的 Workflow question 仍由 `ComposeWorkflow` 发起；Stage graph 保持关闭 `ask_user`。Builder/Reviewer Tool approval 则由 shared stream 的 interrupt loop 处理。Reviewer 的只读能力不因能展示 Tool 而改变。

### Verification adapter

Verify 没有模型 stream，但 `ManagedVerificationPort` 已知道 command、审批和 backend 终态。Compose Workflow 为每条命令创建 scope，并把它投影为既有 Tool 语义：

```text
tool.started(name="execute", bounded command preview)
  → interaction.approval（若规则要求）
  → tool.completed(exit status + bounded output summary)
  → compose.summary
```

UI 事件不替代 `VerificationEvidence`；Verify 是否通过仍只由 fresh evidence 决定。

## Protocol 与事件归属

### Event envelope

v3 `eventBase` 增加可选 `compose_scope`，引用严格 `ComposeActivityScope` schema。Build 事件不携带该字段，现有 payload 不变。Compose Stage 发出的 `run.progress`、`reasoning.delta` 和 `tool.*` 使用真实 child `execution_id/parent_execution_id/agent_id`；Workflow/Verify 自身事件使用 root provenance。

新增 `compose.summary` event，payload 严格限制为 status 与有界 text。`compose.state` 不增加高频 activity 数组，避免完整 projection 随每个 token 或 Tool delta 膨胀。

### Interaction envelope

`interaction.approval` / `interaction.question` 的 request envelope 增加与 Event 相同的可选 execution provenance 和 `compose_scope`。Response contract 不变；request ID 仍是唯一关联身份，Run owner 规则、deadline 和 TUI/Web 单输入权保持不变。

Interaction 解决后继续发 `interaction.resolved`，该事件带原 scope。Core 据此只更新对应 activity 内的卡片。

### 顺序与迟到事件

- RunCoordinator 仍对 root 和所有 child activity 使用同一 Run sequence，因此 UI 不自行合并多条时钟。
- `compose.state` 先发布 stage/task running transition，再发布该 scope 的第一个 activity event。
- Core 先按 Run sequence 去重，再校验 scope；非法 scope 丢弃对应内容但不能回退 sequence 或修改另一个 activity。
- terminal 后 Host 拒绝非 terminal event；UI 冻结最后 projection 和已经接受的 activity。

## Interactive Core 与历史恢复

Core 给 Message、Reasoning、Tool 和 Interaction 增加统一的 execution/activity metadata。关联键使用：

```text
(run_id, execution_id or root, activity_id or root, provider_item_id)
```

因此相同 Tool call ID 在不同 Stage、attempt 或 Reviewer 中不会覆盖。Reducer 仍按 event type 调用现有 Message/Reasoning/Tool/Interaction 更新逻辑；scope 只决定归组和关联，不复制一套 Compose reducer。

当前 Run 的完整安全 Timeline 保存在 Interactive state。TUI → Web 接管继续通过 `state.replace/state.patch` 传递同一 snapshot，不查询 Host 或重放事件。

Thread reopen 时，Thread 接口在普通 Transcript 之外返回有界 Compose activity history 与最终 projection：

- 恢复阶段/Task/attempt、Runtime summary、Tool 名与 terminal status；
- verification/Review 继续使用已经校验的 artifact 摘要；
- 不恢复 Reasoning、Tool 原始参数/结果、Interaction 正文或 Stage artifact JSON；
- activity history 只进入 Timeline projector，不进入 `ContextProjector` 或模型消息。

数据库升级沿用现有 Thread schema migration、backup 和 validation 流程，只保留一个 canonical activity table，不对旧 shape 做双写或长期 fallback。开发态旧库按现有 migration 直接升级。

## TUI 与 Web 行为

### 统一 Timeline

Core 暴露 scoped Timeline item；两个 renderer 使用相同语义：

```text
Stage header：理解 / 计划 / 构建 / 验证 / 评审
  Agent + Task + attempt
  Reasoning cards
  Tool cards
  Interaction cards
  Runtime stage summary
```

- active activity 总是展开并跟随新事件。
- completed/failed/blocked/cancelled activity 默认折叠为 header + stage summary；当前会话仍可展开安全详情。
- TUI 使用既有详情切换能力展示/隐藏已完成 activity；Web 支持点击、Enter 和 Space，折叠是 renderer-local state。
- Tool 与 Reasoning 的内部展开继续复用现有行为，不由 Compose group 重新解释。

### 当前阶段活动区

现有 Compose progress 不再插在历史消息之前。TUI 把当前阶段状态放在 `TimelineActivity` 邻近位置；Web 放在 `run-status-live` 邻近位置。自动跟随底部时用户始终能看到：

```text
Compose · 构建 · task-2 · builder · 模型处理中 · 已运行 18s
```

用户主动上滚查看历史时不强制抢回滚动位置；有新事件时沿用现有“回到底部”提示。Plan/Tool Interaction 到来时由既有 Interaction 区获得焦点。

### 可访问性与安全文案

- Stage 状态和 Interaction 使用 `status`/`aria-live`，Tool delta 不逐 token 打断屏幕阅读器。
- reduced-motion 关闭 spinner 动画，但保留文字、耗时和取消入口。
- UI 只显示工作区相对、已经过现有 payload 截断/脱敏的 Tool 信息；scope 不包含绝对路径或内部 Agent 配置。
- 没有公开 Reasoning 时显示事实状态，不生成“正在分析某文件”等猜测文案。

## 阶段摘要规则

Runtime 从已经校验的对象生成固定模板，单条不超过 1,000 字符：

- Understand：目标、约束、验收数量和是否仍需用户决策。
- Plan：方案短摘要、Task 数和下一步是否等待批准。
- Build：Task 名、changed path 数、focused evidence 是否记录，不展示 Builder 自报原文。
- Verify：命令数量、pass/fail/blocked 数和失败命令的有界 label。
- Review：Requirement/Code verdict、Required/Optional finding 数和是否进入 fix loop。

模板只读取对应 validator 已接受的字段。schema invalid 时不读取未校验对象，只生成稳定错误摘要；原始模型输出和 JSON parser 文本不越过 wire。

## 错误、取消与边界行为

- Stage stream 基础设施失败：保留已经完成的 Tool/activity，发送稳定失败摘要，再由 Compose/Run 既有错误码唯一收敛。
- Tool approval reject/timeout：Interaction 卡进入对应终态；Stage 根据 Tool/graph 结果或稳定错误收敛，不自动重启 execution。
- schema invalid retry：第一次 attempt 终态可见，第二次创建新的 activity ID 和 child execution；两次事件不混卡。
- Verify/Review fix loop：新 fix task 使用新的 activity ID，旧阶段记录冻结保留。
- Run cancel：取消 token 同时终止 active stream、child execution 和 backend；最后发布 cancelled projection/summary，不接受迟到 delta。
- Web handoff：active Run 不转移 Host owner；Web/TUI 只切换表现层，pending child Interaction 与 activity state 不重复创建。
- activity store 失败：不得影响 artifact、Tool 或状态机正确性；Run 以稳定可观察性错误 fail closed，不能悄悄声称已保存审计记录。

## 测试方案

### Shared module 与 Build 回归

- 用真实 translator + fake LangGraph async stream 覆盖 text、Reasoning、Tool arguments/result、多个模型回合、interrupt/resume、nested namespace、取消和 malformed chunk。
- 固定 Build golden event sequence，迁移前后比较 Event payload、Transcript records、usage 和 terminal。
- 证明 `capture_only` 返回完整 artifact 正文但不发 `content.delta`，`passthrough` 保持 Build 行为。

### Compose Agent/Host

- 通过真实 `ManagedStageAgentPort → AgentDelegator → shared stream` 路径覆盖 child provenance、Engine lease、registry terminal 和相同 execution resume。
- 覆盖 Understand/Plan、Builder task、两个 Reviewer 和 Verification command 的 scope、attempt、Tool identity 与 Runtime summary。
- 覆盖 Policy deny、Approval approve/reject/timeout、schema retry、fix loop、blocked、failed 和 cancellation。
- 断言 Stage JSON、Reasoning、Tool 原始恢复数据不进入根 Transcript、ContextProjector、日志或 activity table。

### Protocol/Core/Persistence

- Python/TypeScript validator 与 fixture 覆盖有/无 scope、非法 stage、空 activity ID、负 attempt、超长 summary 和 provenance。
- Reducer 覆盖重复/乱序、同 Tool ID 跨 execution、Interaction resolved、终态迟到帧和 Compose/Build 混合相邻 Run。
- migration/restore 覆盖 500 条/1 MiB 上限、唯一 truncation、旧库升级和 activity 不进入模型 context。

### TUI/Web/E2E

- 长历史下 active Compose 状态在底部可见；用户主动上滚不会被强制拉回。
- active 展开、terminal 默认折叠、详情恢复、窄终端、移动 Web、键盘、ARIA 和 reduced-motion 行为一致。
- fake model/backend 走完整五阶段，验证 Reasoning、多个 Tool、child approval resume、Plan approval、Verify、双 Review、失败/取消和 Thread reopen。
- E2E 必须经过 Host、Protocol、Interactive Core 和两个 renderer，不能只注入 `composeState` fixture 证明 DOM 存在。

## 可观察验收

- 用户在任一 Compose stage 都能区分模型等待、Tool 执行、等待 Interaction 和阶段已结束，不再只看到静态五阶段条。
- 所有 activity 都能回答“属于哪个 Stage、哪个 Task、哪个 Agent、哪次 attempt”，且 UI 顺序与 Host sequence 一致。
- Build/Compose 相同的 Reasoning、Tool 和 Interaction 使用同一领域事件与 Core reducer；只有 scope、阶段摘要和恢复策略是 Compose 特有语义。
- 原始 artifact JSON 与隐藏思维不可见；阶段摘要能说明实际完成或失败结果。

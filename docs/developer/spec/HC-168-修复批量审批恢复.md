# HC-168 修复批量审批恢复规格

关联任务：[HC-168](../task/archive/HC-168-修复批量审批恢复.md)
架构入口：[架构总览](../architecture/架构总览.md)

用户结果与验收以 Task 为准。本文只规定批量审批恢复的行为、内部 seam、错误语义和不变量；步骤见 [Plan](../plan/HC-168-修复批量审批恢复.md)，执行清单见 [Todo](../todo/HC-168-修复批量审批恢复.md)。

## 1. 目标流程

一次模型回合返回的动作列表先被划分为安全动作和需要人工决定的动作。完整列表、原始索引和首个 interrupt 身份在 `serial_context` 中固定，wire payload 仍只包含既有协议字段。

```text
初始 interrupt
  → 冻结 all_action_requests / 原始索引
  → _collect_serial_approvals 逐个收集决定
       ├─ approve_once / reject：只写本批 decisions
       └─ approve_thread / approve_project：写 staged rule intent
            └─ 同批后续动作可读 staged overlay，自动得出决定
  → 返回完整 decisions（长度等于初始 action_requests）
  → ManagedAgentExecutor 用 Command(resume=...) 重放
       ├─ astream 成功返回：HITL 已消费，提交 staged intents
       └─ 取消 / 异常 / 未成功返回：丢弃 staged intents
```

`approve_thread` 和 `approve_project` 的规则语义不变；改变的是提交时机。提交时机必须晚于恢复命令被 HITL middleware 成功消费，早于后续需要读取新规则的模型/工具回合。

## 2. 术语与状态

### 2.1 原始批次

原始批次是 LangChain HITL interrupt 中的 `action_requests`，按列表下标定义动作身份。`decisions[i]` 永远对应 `action_requests[i]`；安全动作也必须占据一个决定位置，不能因本地自动批准而缩短列表。

### 2.2 Staged rule intent

待提交规则意图是当前 Run 内存中的规则候选，至少包含：工具名、工具参数、决策作用域和由该调用生成的 `PermissionRule`。它不是 `session_rules`，不写 project settings，也不由共享图的 `rules_provider` 返回。

同一个 Run/恢复批次中相同的规则候选只保留一份；提交和丢弃均可重复调用。意图只属于创建它的 Run，不得跨 interaction、跨 Thread 或跨 Run 泄漏。

### 2.3 Staged overlay

`_collect_serial_approvals` 的本地排队判断可以把当前 Run 的 staged intents 与既有 session/project/user/system 规则合并，用于决定同批后续动作是否自动 allow/deny。overlay 只存在于该收集调用和该 Run 的内存路径；不得写入 Coordinator 全局可见的 session 规则，不得进入 Agent 图构图期或 LangGraph resume 可见的 `rules_provider`。

## 3. 行为规格

### 3.1 收集阶段

1. `_collect_serial_approvals` 使用初始 `serial_context` 的完整动作列表和索引，生成长度固定的 `decisions`。
2. `approve_thread` 只追加 session-scope staged intent；`approve_project` 只追加 project-scope staged intent。
3. `approve_once`、`reject`、`reject_with_feedback` 不追加权限规则。用户拒绝仍按现有语义终止同批后续人工弹窗，并为剩余动作填充 reject。
4. 同批后续调用的自动判定可以命中 staged overlay，因此保留“本线程/本项目允许后同类动作免弹”的体验；该命中只影响本地 `decisions`，不影响原始 interrupt 的 middleware 分类。
5. 收集函数返回的 resume 字典必须包含与原始 `action_requests` 等长的决定列表；不通过删掉已自动决定的动作来规避 LangChain 校验。

### 3.2 恢复提交阶段

1. `ManagedAgentExecutor` 只有在以 `Command(resume=...)` 调用 Agent graph 的一次 stream round 正常返回后，才调用 Run 提供的提交 seam。
2. stream round 抛出异常、收到取消、被超时终止或未进入成功返回边界时，不调用提交 seam；外层 Run 清理路径必须清空当前 Run 的 staged intents。
3. 提交 seam 将 session intent 去重后加入 `RunCoordinator._session_rules`；project intent 通过现有 `save_rule(..., scope="project")` 写入 project settings，保持原有错误传播和 fail-closed 语义。
4. 提交成功后清空已消费 intents；重复调用不得重复写内存规则或 project settings。提交过程中出现 project 持久化异常时异常继续向既有 Run 失败路径传播，并清理尚未提交的 staged intent。
5. Run 取消、owner 断连、Run 失败、Run 完成清理以及重复恢复路径都必须最终清理 staged intent。

### 3.3 其它审批入口

child 的独立 Interaction 若产生 `approve_thread` / `approve_project`，也必须复用 Run 级提交边界；它不能直接修改 Coordinator 全局规则。`directory_trust` 不属于 PermissionRule，不进入本规格的 staged rule intent。

## 4. 内部 interface/seam

| seam | 责任 |
| --- | --- |
| `RunState` staged rule storage | 保存当前 Run 的有界待提交意图；不属于协议和持久化模型 |
| `RunCoordinator._stage_approval_rule(run, ...)` | 从决定生成并去重 staged intent；不改变全局/持久状态 |
| `RunCoordinator._commit_staged_approval_rules(run)` | 在恢复成功边界提交并清理；复用现有规则生成/保存语义 |
| `RunCoordinator._discard_staged_approval_rules(run)` | 取消、失败、未消费时幂等清理 |
| `ManagedAgentRequest` resume-success callback | 由 Executor 在成功执行 resumed stream round 后触发，不解释规则内容 |
| `BuildRunAdapter` / lifecycle port | 把 callback 绑定到当前 RunCoordinator，保持 adapter 不直接管理规则存储 |

这些是进程内实现 seam，不新增 Protocol 字段、CLI 参数或兼容 alias。

## 5. 错误语义与安全边界

- LangChain `ValueError` 不得被捕获后吞掉；若决定长度和 hanging calls 仍不一致，Run 继续走现有失败终态，测试应暴露该错误。
- staged intent 不是授权事实；恢复未成功消费前不能被下一个模型回合、另一个 Run 或规则诊断读取。
- project settings 写入失败不降级为 session allow，不静默改成 `approve_once`，不伪造成功终态。
- 用户拒绝的动作只产生 LangChain `reject` 决定；不产生 allow/deny 规则。
- 原始 action request 的工具名、参数、调用 ID 和列表顺序不被重写；不修改第三方 middleware。

## 6. 非目标

- 不改变 approval payload schema、Interaction method、TUI/Web 展示和协议版本。
- 不重写 `execution_stream` 的 interrupt 提取或串行收集职责。
- 不把 staged overlay 做成共享 Agent 图的第二套长期规则来源。

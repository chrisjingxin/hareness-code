# 配置架构

Harness Code 使用 TOML 作为用户可维护的配置格式。环境变量仍是秘密的默认来源；唯一字面量例外是用户级 `~/.harness/config.toml` 模型 Profile 中的 `api_key` 降级值。Token、认证 Header、企业凭据以及其他来源的 API Key 仍必须通过明确的 `*_env` 字段引用环境变量。

## v1 契约

每个生效的 TOML 文件必须包含：

```toml
[config]
version = 1
```

当前已实现区段为 `[models]`、`[approval]`、`[execution]` 和 `[runtime_pool]`。`[models]` 包含多个命名的 OpenAI-compatible Profile、`default_profile` 以及可选 `[models.roles]`。固定 `provider = "openai-compatible"`；`provider_label` 仅用于脱敏 TUI 展示。角色只允许 `planner`、`executor`、`reviewer`、`tester`、`summarizer`，未绑定角色回退到默认 Profile。每个 `[models.profiles.<name>]` 可设置 `context_window_tokens`；默认 `128000`，显式值最小 `16384`，并通过 `config show` 的 `context_window_source` 说明来自默认还是 TOML。能力未声明时兼容为 `tool-calling`、`streaming`；显式能力必须来自 `tool-calling`、`streaming`、`vision`。

每次 `run.start` 都解析脱敏的实际 primary 模型；请求的 Thread 选择、实际模型绑定与首条消息索引在同一 SQLite 事务受理。绑定只含 Profile ID、Provider 标签、模型名、能力、窗口、来源和 Runtime Profile 摘要，绝不含 endpoint、Header、API Key 或环境变量值。当前 Single Agent Runtime 仅纳入 `primary ← executor` 的模型指纹；未来 topology 才将实际使用的额外角色纳入同一 Runtime Profile Key。模型名称、endpoint、超时、重试、窗口、能力、固定 Header 名称/值和环境变量名只参与哈希；数据库和诊断只保存不可逆组件指纹，绝不保存 API Key、认证 Header、原始工作区路径或完整提示词。`thread_id`、消息、审批、PromptEpoch 正文和 run ID 不属于配置身份，不能进入该 Key。

## Agent canonical model 与 TOML adapter

长期领域边界以 [ADR 0001](adr/0001-agent-domain-model.md) 为准：
`ProviderDefinition` 描述模型服务连接，`ModelProfile` 描述模型和推理参数，
`ExecutionPolicyDefinition` 描述执行权限，`AgentDefinition` 组合任务指令、默认模型与
Policy，`ThreadExecutionSelection` 保存 Thread 对未来 Run 的选择，
`RunExecutionBinding` 保存一次 Run 的实际事实。

这不是新的 TOML v2，也不改变当前用户文件。现有
`[models.profiles.<name>]` 是兼容输入 adapter：它的 `base_url`、`api_key_env`、
`headers`、`headers_env`、timeout 和 retry 投影为临时 `ProviderDefinition`；`model`、
reasoning/调用参数、capabilities、context window 和展示标签投影为 `ModelProfile`。当前一个
TOML Profile 可暂时投影为一个 Provider + 一个 Model，后续独立 Provider 配置仍必须保持相同
凭据与脱敏规则。

当前 `[models.roles]` 与 `ModelRouter` 是 Runtime 编译兼容层，不产生独立 RoleDefinition。
在 Single Agent 路径中，`executor` 是 root Agent 的物理模型来源。ZC-078 以
`ThreadExecutionSelection` 保存下一次 Run 的选择，并按 Run 保存实际 `RunExecutionBinding`；
旧的首次 Thread binding 仅作为恢复旧记录时的只读回退。`[agents]` 和 `[policy]` 继续是计划中区段：
ZC-080 必须先按 ADR 的 AgentDefinition/ExecutionPolicyDefinition 设计、信任边界和安全交集
落地，不能以当前 TOML 未知区段绕过 Manifest。

用户模板位于 [config.toml](../user/examples/config.toml)。它是注释完整的长期配置表面，不是工作区配置样例。

## 来源与优先级

长期优先级为：managed 策略锁 > CLI 参数 > `HARNESS_*` 环境变量 > `--config` > 已信任项目本地 > 已信任项目共享 > 用户配置 > 默认值。managed 策略无论来源顺序都不能被下层放宽。

| 来源 | 当前状态 | 可配置范围 |
| --- | --- | --- |
| 系统 managed TOML | 计划中，[ZC-038](tasks/ZC-038.md) | 企业不可覆盖策略 |
| CLI 参数 | 已实现 | 当前仅 `--sandbox`，高于普通环境变量 |
| `HARNESS_*` 环境变量 | 已实现 | 模型、审批和执行临时覆盖 |
| `--config <PATH>` | 已实现 | 用户明确选择的可信 TOML |
| `~/.harness/config.toml` | 已实现 | 用户模型、审批和执行设置 |
| `.harness/config.local.toml` | 计划中，[ZC-037](tasks/ZC-037.md) | 仅可信项目的受限本地偏好 |
| `.harness/config.toml` | 计划中，[ZC-037](tasks/ZC-037.md) | 仅可信项目的受限共享设置 |

当前未实现项目可信机制，因此只要工作区内出现上述任一项目配置，启动会在模型初始化前失败。用户必须把配置移至用户目录，或显式传入该文件的 `--config` 路径。显式传入代表用户已确认该文件来源。当前 `.gitignore` 继续忽略这两个项目路径，ZC-037 实现可信共享配置时再调整 Git 追踪策略。

## 交互式受控写入

`ConfigChangeService` 是 TUI Settings/Permissions Manager 与后续正式 CLI 的唯一配置写入口；它在协议 v2.8 的 `config.write` capability 下提供固定流程：

```text
config.details → config.preview → config.commit(expected_revision)
```

服务端只写入用户级 `~/.harness/config.toml`，并仅允许如下字段：

| 字段 | 生效范围 |
| --- | --- |
| `models.default_profile` | 后续新建 Thread；提交后刷新默认目录，不影响已有 Run/Thread 选择 |
| `approval.mode` | 重启 sidecar 后 |
| `execution.backend` | 重启 sidecar 后，且既有远端 factory 必须完整有效 |
| `runtime_pool.max_profiles`、`idle_ttl_seconds`、`close_timeout_seconds`、`pin_default_profile` | 重启 sidecar 后 |

`preview` 不产生写入，只返回脱敏字段 diff 与文件内容 SHA-256 revision。`commit` 必须在同一锁内重新读取 revision、完整执行 TOML v1/`load_config()` 校验，再以临时文件、`fsync`、同目录 rename 和目录 `fsync` 原子替换；成功写入的用户文件固定收紧到 `0600`。任何 CAS 冲突、解析失败、权限失败或写盘失败均保留原文件。

下列内容永远不能走该接口：`api_key`、`api_key_env`、Header/`headers_env`、任意环境变量、模型 endpoint、远端 Provider factory/参数、MCP 和任意未知路径。显式非用户配置、工作区内显式项目配置、环境/CLI 覆盖和 managed lock 都会使相应字段 fail closed。审计只记录操作类型、字段名、结果、时间和 revision 摘要，不记录值、TOML 原文或秘密。ZC-038 接入 managed 配置后只向该服务注入锁字段集合，不另建写入通道。

## 安全规则

- 不自动加载项目 `.env`，也不支持 `$VAR` 或 `${VAR}` 的通用插值。
- `api_key_env` 和 `headers_env` 的值必须是大写环境变量名。非空 `api_key_env` 始终优先；只有用户级 TOML 可提供非空 `api_key` 降级值。
- Unix 上只要用户 TOML 存在 `api_key`，文件就不得存在 group/other 权限；该规则在环境变量覆盖密钥时也会执行。Windows 不使用 POSIX mode 校验 ACL。
- 最终密钥不进入 JSON-RPC、日志、TUI、提示词或本地 Shell 环境；脱敏摘要只显示 `environment` / `toml` / `missing` 来源。
- 固定 Header 只能保存非秘密值。`Authorization`、`Cookie`、`X-Api-Key` 等认证 Header 必须使用 `headers_env`。
- 远端 sandbox factory、MCP、Hook、Extension 和 Plugin 都不得因为克隆项目自动导入、下载或执行。
- 后续 managed TOML 路径固定为 macOS `/Library/Application Support/Harness/managed.toml`、Linux/WSL `/etc/harness/managed.toml`、Windows `%ProgramData%\\Harness\\managed.toml`；企业分发机制不在当前阶段实现。

## 维护方式

`packages/agent/harness_agent/config_manifest.py` 是字段状态、来源许可和通用安全规则的唯一实现来源。增加任一配置字段时必须同步更新 Manifest、解析器、模板、用户文档、本文档和对应任务；未实现字段只能以注释形式出现在模板中。

## RuntimePool 边界

`[runtime_pool]` 仅配置 sidecar 内存中可重建的 Runtime，不改变 thread 持久化语义。允许的字段及范围为：`max_profiles = 1..64`（默认 `8`）、`idle_ttl_seconds = 60..86400`（默认 `1800`）、`close_timeout_seconds = 1..120`（默认 `15`）与 `pin_default_profile`（默认 `false`）。配置不接受环境变量或 CLI 覆盖，避免瞬态进程环境意外放大资源占用。

Pool 到达容量时，只会按 LRU 淘汰 `IDLE`、无 lease/run/queue 且未固定的 Runtime；TTL sweep 使用相同条件。没有安全候选时返回 `RUNTIME_POOL_CAPACITY_EXHAUSTED`，禁止以临时 Runtime 绕过上限。Thread 选择不同模型只会生成或复用对应的 Profile，不能把此前默认 Profile 全局标记为 `DRAINING`；旧 Runtime 继续服务已有 lease 和其他 Thread，最终仍按容量、TTL 或显式关闭回收。sidecar 退出的顺序固定为“停止/取消 run → 关闭 RuntimePool（单 Runtime 受 close timeout 限制）→ 关闭 ThreadStore”。

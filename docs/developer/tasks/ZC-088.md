## 背景

`ThreadStore` 是当前持久化核心，使用一个用户级 SQLite 文件同时承载：

- project-scoped Thread 索引；
- LangGraph checkpoint；
- Run 受理与执行绑定；
- PromptEpoch；
- Runtime Profile 记录与 legacy Thread 绑定；
- Context artifact、summary 与状态。

把这些事实放在同一数据库是正确方向：Run 受理可以原子更新 Thread 索引和 binding，project fingerprint 也能统一隔离 checkpoint 与 Harness 自有表。问题不在“文件太大”，而在它向调用方暴露了过多表级知识。

## 当前存在的问题

### 1. interface 近似数据库操作清单

`ThreadStore` 当前约 1,386 行，公开方法包括：

```text
record_message
record_run_start
get_latest_run_execution_binding
refresh_thread
get/save_model_bindings
load_context_messages
get/save_prompt_epoch
get/save_runtime_profile
archive/read_context_artifact
save_context_summary
context_state / set_context_state
list_threads / open_thread
checkpointer / graph_config / close
```

调用方必须知道应该按什么顺序组合这些方法。interface 没有隐藏生命周期复杂度。

### 2. 事务边界泄漏给 AgentHost

Run 开始时，AgentHost 先解析模型和 Runtime Profile，再调用 `record_run_start()`；Run 结束后还要记得调用 `refresh_thread()`。Context middleware 则分别读取消息、归档 artifact、保存 summary、更新 state。

“哪些写入必须同成同败”“失败后需要刷新什么”由调用方掌握，而不是持久化 module 自己保证。

### 3. 多个调用方知道 schema 的历史层次

Server 会直接调用：

- v6 Run execution binding；
- v5 model binding；
- v4/v5 Runtime Profile binding。

当前路径因此理解多个 schema 世代。legacy 表不是 SQLite implementation 的内部 adapter，而是业务 interface 的一部分。

### 4. Context 读写不是一个完整状态转换

`ContextWindowMiddleware` 和虚拟文件 adapter 分别调用 message、artifact、summary 和 state 方法。一次压缩成功需要多步写入，但 interface 没有表达完整的“提交 Context rewrite”操作。

### 5. 类型与损坏诊断混在存储方法中

Run selection、actual primary binding 等领域值以 mapping 进入 ThreadStore，存储层再次检查字段。这样 persistence 同时承担领域构造和 JSON/SQLite 编码，却又不能保证上游使用相同类型。

### 6. 测试容易穿过 interface

现有测试大量逐方法验证表读写。内部 schema 或事务重排会迫使测试重写，即使外部 Thread/Run 行为没有变化。

## 为什么现在要修改

- [ZC-089](ZC-089.md) 需要一个清晰的 persistence seam；否则 Run module 仍要编排十多个存储方法。
- 当前已有 v4、v5、v6 兼容路径，再继续增加表级方法会让 legacy 永久扩散。
- Context 压缩、Run 受理和 Thread 恢复都属于已实现核心能力，任何事务错误都可能造成不可恢复或错误历史。
- SQLite 有真实的本地临时数据库测试 adapter，适合直接通过新 interface 做集成测试，不需要为每张表建立 mock repository。

## 目标设计

保留一个 SQLite implementation，但把 external interface 改成生命周期操作。建议目标形状如下，名称可以在实现时按调用图微调：

```python
class ThreadPersistence:
    async def accept_run(self, command: AcceptRun) -> RunAcceptance: ...
    async def open_thread(self, thread_id: str) -> ThreadSnapshot: ...
    async def load_run_state(self, thread_id: str) -> PersistedRunState: ...
    async def commit_context(self, command: CommitContextRewrite) -> ContextSnapshot: ...
    async def close(self) -> None: ...
```

LangGraph checkpointer 是第三方要求的 adapter，可由该 module 提供受 project namespace 约束的内部入口，但调用方不能直接操作 Harness 自有表。

内部结构：

```text
Thread lifecycle interface
  ├─ current schema implementation
  ├─ legacy read adapter
  ├─ LangGraph checkpoint adapter
  └─ SQLite transaction / migration
```

关键所有权：

- [ZC-086](ZC-086.md) 构造类型化 selection 与 binding；本 module 只做持久化、幂等和损坏诊断。
- [ZC-089](ZC-089.md) 决定何时开始/取消 Run；本 module 原子记录受理事实。
- Context module 决定压缩内容；本 module 原子提交 artifact、summary 和 state。
- Protocol 和 TUI 永远不知道表名、schema 版本或 legacy 读取顺序。

## 实施步骤

1. 建立“调用方 → 当前 ThreadStore 方法 → 所属生命周期”的矩阵，确认真正需要的 external interface。
2. 定义类型化 command/result：Run acceptance、Thread snapshot、persisted run state、Context rewrite。
3. 先让现有 SQLite implementation 实现新 interface，暂时在内部调用旧方法，保证行为不变。
4. 迁移 AgentHost、Context middleware、虚拟文件和 Runtime builder 到生命周期操作。
5. 将 v4/v5 读取顺序和 schema migration 移入内部 legacy adapter；外部只看到 typed current state 或明确的 unavailable/unknown。
6. 合并每个生命周期内可原子执行的 SQL，特别是 Run 受理与 Context rewrite。
7. 删除不再可达的表级公开方法和逐方法测试，改用临时 SQLite 通过 external interface 验证。
8. 对现有数据库 fixture 运行升级、恢复、损坏、关闭和并发测试，禁止破坏性迁移。

## 范围

- 设计面向生命周期的最小 interface，替代调用方直接组合约 27 个表级方法。
- 把 Thread 索引、checkpoint、Run 受理、PromptEpoch、Context artifact/summary 和 legacy 读取保持在一个 implementation 内。
- 将 schema migration 与 legacy adapter 设为内部 seam，不暴露给业务调用方。
- 保持现有 SQLite 文件、权限、project 隔离和事务原子性。

## 非范围

- 不拆成一表一个 repository。
- 不新增 Thread Manager、Timeline、Replay、Fork 或 Rewind。
- 不改变持久化位置，不删除或重写用户数据。

## 验收清单

- [ ] Server、middleware 和虚拟文件不再依赖表级组合顺序。
- [ ] Run 受理相关写入仍在一个事务内。
- [ ] Context rewrite 的 artifact、summary 和 state 不会留下部分提交。
- [ ] legacy 兼容只存在于 module implementation。
- [ ] external interface 不暴露表名、schema 版本或原始 JSON mapping。
- [ ] 测试通过生命周期 interface 验证恢复、冲突、损坏和关闭。

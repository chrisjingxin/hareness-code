## 背景

Harness 已经区分两个领域事实：

- `ThreadExecutionSelection`：当前 Thread 对下一次 Run 的可变意图。
- `RunExecutionBinding`：某次 Run 实际使用模型的不可变事实。

当前 JSON-RPC v3 的 `run.start` 可以携带 `model_selection`，SQLite 也保存了 requested selection、actual primary binding 和 Runtime Profile ID。但这条能力是分阶段叠加出来的，领域知识没有集中在一个 module 中。

当前调用链大致为：

```text
TUI threadModelSelection
  → run.start.model_selection
  → AgentHost._resolve_run_model_bindings()
  → ModelRouter / legacy ThreadModelBindings
  → AgentHost._resolve_runtime_profile()
  → ThreadStore.record_run_start(raw mappings)
  → run.started.primary_model
  → TUI actualModelProfile
```

## 当前存在的问题

### 1. 选择优先级由 Server 私有方法拥有

`AgentHost._resolve_run_model_bindings()` 同时解释：

1. 本次请求显式选择；
2. 最近 Run 恢复的 Thread 选择；
3. v5 legacy Thread 模型绑定；
4. 全新 Thread 的配置默认值。

这属于模型选择领域规则，却位于 transport/protocol implementation 中。任何非 JSON-RPC 调用方都必须复制或绕过这套规则。

### 2. 同一个概念存在多种表示

- `model_router.py` 使用 `ThreadModelBindings`。
- `server.py` 在 `ActiveRun` 上保存 `requested_model_selection`、`primary_model_binding` 等原始 `dict`。
- `thread_store.py` 的 `RunExecutionBinding` 仍把 selection 和 primary binding 暴露为 `dict`。
- Protocol 使用生成类型。
- TUI 同时维护 `threadModelSelection` 与 `actualModelProfile`。

调用方需要知道各字典字段、来源字符串和兼容分支，interface 几乎和 implementation 一样复杂。

### 3. 校验、脱敏和持久化构造分散

模型可用性由 `ModelRouter` 校验；Run binding 字段由 Server 拼装；SQLite 再用 `_validate_run_selection()` 与 `_validate_actual_primary_binding()` 二次解释。来源值如 `thread-primary`、`thread-recovered`、`legacy-binding`、`config-default` 也由 Server 手写。

新增或修正一种来源时，需要同时修改多个 module，容易出现“运行模型正确，但历史记录或 TUI 展示错误”。

### 4. legacy 兼容泄漏到当前路径

`_thread_model_binding_summary()`、`get_model_bindings()`、`get_runtime_profile()` 和 ModelRouter 的 record 转换都暴露给 Server。当前调用方必须理解 v4/v5 表结构，legacy 不再是 persistence implementation 的内部细节。

### 5. 测试依赖 Server private implementation

模型优先级、恢复和绑定测试需要通过 `AgentHost` 私有方法或大型 run.start setup 才能覆盖。测试不能直接表达“给定选择与历史，应该产生什么不可变执行事实”。

## 为什么现在要修改

- [ZC-089](ZC-089.md) 要提取 Run lifecycle；若模型解析仍属于 Server，新的 Run module 只能继续调用 Server private 方法或复制规则。
- 当前已经同时存在新 Run binding 与两代 legacy 记录，继续增加兼容分支会快速放大迁移风险。
- 多前端共享 Protocol 后，实际执行事实必须完全由 Python Core 确认，TUI/Web 不能各自推断。
- 这是纯领域计算为主的 in-process module，可以先建立稳定 interface，不需要新增远程 port 或依赖。

## 目标设计

建立 `execution_binding.py`，用一个纯函数作为主要 interface。解析没有可变状态，也没有第二种 implementation，因此不建立 Resolver class、factory 或 repository port：

```python
def resolve_execution_binding(
    config: Za38Config,
    requested: ThreadExecutionSelection | None,
    persisted: PersistedBindingState,
) -> ResolvedExecutionBinding: ...
```

该 module 定义以下不可变 Python 类型：

- `ThreadExecutionSelection`：使用 `root_model_profile_id` 表达下一次 Run 的根模型选择；Protocol adapter 负责与现有 `primary_profile` 互转。
- `SelectionOrigin`：类型化区分本次请求、最近 Run、v5 legacy 和配置默认；Protocol 投影仍使用现有 `thread-primary`、`thread-recovered`、`legacy-binding`、`config-default` 字符串。
- `SafeModelProfile`：只保存 Profile ID、模型名、Provider 展示名、窗口、能力、默认项和可用状态，不包含 endpoint、Header、API Key 或环境变量名。
- `PersistedBindingState`：保存最近 Run、可选 legacy 模型记录和“只有旧 Runtime 指纹”的状态，不暴露 SQLite 表名或原始 mapping。
- `ResolvedExecutionBinding`：保存最终选择、实际 `ModelProfile`、安全摘要和来源；Runtime builder 直接消费其中的实际模型。
- `RunExecutionBinding`：保存 thread/run ID、选择快照、实际模型摘要、来源、Runtime Profile ID 和创建时间。

`ResolvedExecutionBinding` 在 Runtime Profile 生成后构造 `RunExecutionBinding`。因此 Runtime、持久化和 Protocol event 都从同一次解析派生，不再分别选择模型：

```text
run.start 输入 ─┐
配置 snapshot ──┼→ resolve_execution_binding()
持久化状态 ─────┘          │
                           ├→ RuntimeProfile builder
                           ├→ RunExecutionBinding → ThreadStore
                           └→ Protocol projection → TUI / Web
```

解析顺序固定为：

```text
run.start 显式选择
  → 最近 Run 保存的 Thread 选择
  → v5 legacy executor 绑定
  → 当前 models.default_profile
```

无 `ModelCatalog` 的旧单模型配置只能使用其配置默认模型；显式选择 Profile 时返回 `MODEL_CATALOG_UNAVAILABLE`。Profile 不存在、API Key 缺失或缺少当前根 Agent 所需能力时继续使用现有稳定错误并 fail closed。

当前 Protocol 只有一个模型选择入口。`legacy_model_profile` 参数没有调用方，它与对应的双输入冲突分支直接删除，不把不存在的兼容场景固化进新 interface。

### 持久化与 legacy

SQLite 继续由 `ThreadStore` 单独实现，不为唯一数据库建立抽象 interface。`ThreadStore` 提供类型化的 binding state，并让 `record_run_start()` 直接接收 `RunExecutionBinding`；canonical JSON 只存在于 SQLite adapter 内部。

兼容规则固定为：

- `harness_run_execution_bindings` 按当前 v6 字段读取，不改变 JSON 形状。
- `harness_thread_model_bindings` 只读取 `executor` 作为旧根模型；其余角色只用于 legacy 展示，不重新进入当前 Runtime 解析。
- 只有 `harness_thread_runtime_profiles` 指纹而无法恢复 Profile ID 时，返回 `legacy/unknown`，不得用当前默认模型伪装历史事实。
- 不回填、不重写、不删除旧记录，`PRAGMA user_version` 保持 6。
- 只供测试构造 legacy 数据的公开写接口不再保留；兼容测试直接建立旧 schema fixture。

### Server、Protocol 与后续角色

`ActiveRun` 保存类型化 resolution、Run binding 和 Runtime Profile，删除 `model_bindings`、`requested_model_selection`、`primary_model_binding` 三组原始状态。`AgentHost` 只编排读取、解析、Runtime 构建、持久化和 wire 投影，不再拥有优先级、source 或 legacy 规则。

`run.started.primary_model` 继续是当前 Run 的权威事实，`models.list.last_run_binding` 继续用于历史恢复。JSON-RPC v3 schema 和生成类型不变，生产 TUI 不新增状态或推断规则。

本任务只建立当前内置主 Agent 的 root binding。它不保留 `ThreadModelBindings` 的完整角色映射；ZC-091 通过 `ResolvedAgentSpec` 解析角色模型，ZC-093 再扩展 `RunExecutionBinding.executions[]`、Policy 事实和 execution 状态，不要求本任务预建空执行树。

## 实施步骤

1. 在 `execution_binding.py` 定义上述类型、纯函数 interface、legacy 解码和安全 Protocol/SQLite 投影。
2. 将 `_resolve_run_model_bindings()` 与 `ModelRouter` 的有效 root 解析收进该 module，删除完整角色 binding 和无调用方的 `legacy_model_profile` 分支。
3. 将 selection 和 actual primary binding 的领域校验移到类型构造阶段；ThreadStore 只负责 SQL、JSON 编解码和损坏诊断。
4. 让 `_resolve_runtime_profile()` 只消费 `ResolvedExecutionBinding` 的实际模型，不再读取 Thread 或重新解析。
5. 让 `record_run_start()` 接收类型化 `RunExecutionBinding`，保持现有事务、幂等和冲突语义。
6. 让 `models.list`、`run.started` 和 TUI 通过现有 Protocol 类型消费同一结果的投影。
7. 用 module interface 的表格化测试替代 Server private 规则测试，并保留 Server、SQLite 和 TUI 的集成回归。

## 范围

- 定义 root 模型选择与不可变 Run binding 的最小类型化 interface。
- 将选择优先级、legacy 映射、Profile 可用性、source、脱敏和 binding 校验集中到一个生产实现。
- 让 Runtime builder、ThreadStore 和 Protocol adapter 消费同一个 resolved result。
- 保持 JSON-RPC v3、SQLite schema v6、TUI 行为和现有配置格式不变。

## 非范围

- 不实现 Planner、Executor、Reviewer、Subagent、Agent Team 或 Agent catalog 运行路径。
- 不实现 `RunExecutionBinding.executions[]`、Policy 绑定或 execution 状态机；这些由 ZC-093 完成。
- 不新增模型选择方式、Provider、Protocol 字段或 UI。
- 不删除、回填或重写 legacy 数据，不升级 SQLite schema。
- 不通过 Agent catalog 构建或替换当前内置主 Agent。

## 测试设计

- Module 表格测试：显式选择、最近 Run、v5 legacy、全新 Thread 默认和旧单模型配置。
- 失败测试：未知 Profile、缺少 API Key、能力不足、损坏 current/legacy 记录和无可用配置。
- 安全测试：SafeModelProfile、SQLite JSON 和 Protocol payload 不包含 endpoint、API Key、Header 或环境变量名。
- SQLite 测试：v4/v5/v6 升级读取、类型化往返、相同 Run 幂等、不同内容冲突和 legacy unknown。
- Server 集成测试：模型切换、Thread 恢复、`models.list`、`run.started` 和 Runtime builder 使用同一解析结果。
- 项目检查：Python 全量测试、TypeScript 测试、`bun run typecheck`、`bun run project:check` 和 `git diff --check`。

## 版本影响

无版本变化。本任务不改变用户可见行为、配置、JSON-RPC schema 或 SQLite schema。

## 实现结果

- 新增 `execution_binding.py`，以一个纯函数集中根模型优先级、可用性、脱敏、legacy 转换和不可变 Run binding 构造。
- `ThreadStore` 改为读写类型化 binding，v5 模型快照和 v4 Runtime 绑定只在 SQLite adapter 内解释。
- `AgentHost`、Runtime Profile、`models.list` 和 `run.started` 消费同一个 resolved result，不再保存或拼装模型相关原始 dict。
- 删除 `ModelRouter`、`ThreadModelBindings`、legacy 模型写入口及无调用方的双输入冲突分支。
- JSON-RPC v3、SQLite schema v6、TUI 行为和配置格式均未改变。

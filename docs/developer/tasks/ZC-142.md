## 背景

Harness Code 的本机文件工具由
[workspace_boundary.py](../../../packages/agent/harness_agent/policy/workspace_boundary.py)
的 `WorkspaceBoundaryMiddleware` 守卫。它要求所有路径参数以 `/` 开头，拼接到唯一工作区根后
`resolve()` 再做 `relative_to()` 包含检查，然后把结果改写成 backend 虚拟路径交给
DeepAgents 的 `LocalShellBackend` 与 Harness 的 `LocalTextMutationBackend`。

这条链路上只有一个工作区根：`AgentHost._workspace` 在进程启动时固定，向下传给执行上下文、
backend、快照与 CAS，并参与执行资源池的 fingerprint。

## 当前存在的问题

1. **工作区外路径全部硬拒绝，读写都没有例外。** `_resolve_path_string` 对越界路径直接抛
   `ValueError`，转成 `status="error"` 的 ToolMessage。用户想让 Agent 读隔壁仓库、读
   `~/.harness/config.toml`、往共享目录写产物，都只能退出进程换 `--cwd` 重开。
2. **审批完全无法放行。** 同一校验被 `allows_approval()` 复用挂在 HITL 的 `when` 回调上，
   越界调用连审批卡片都不会出现，用户没有任何交互手段可以补救。
3. **没有额外工作目录的概念。** 配置中没有允许目录列表，没有斜杠命令，没有启动参数；
   `trust_gate.py` 的 `trusted_directories` 解决的是另一个问题（当前工作区能否切到 auto/yolo）。
4. **提示词与用户文档明确承诺了这个限制**（`system_prompt.md` 第 21–22 行、
   `_with_execution_context()` 第 419–420 行、`docs/user/安全与沙箱.md`），改行为必须同步改这些描述。

后果是一类完全合法的日常需求（跨仓库参考、读全局配置、写共享产物）在产品上无解，而三个主要竞品
（Claude Code、Qwen Code、Grok）都提供了放行路径。

## 为什么现在要修改

- 这是用户可直接感知的能力缺口，且没有任何 workaround，只能重启换目录。
- 越晚做成本越高：允许根集合会渗透到边界判定、backend 选根、快照键、审批记录五处，等这些地方各自
  长出更多单根假设后再改，迁移面会继续扩大。
- 与既有工作正交：不改 `PreparedFileMutation`、CAS 与审批决策通道，只在其上游引入“路径属于哪个根”
  这一层判定。

## 目标设计

完整设计见 [ZC-142 设计](../designs/ZC-142.md)。核心结论：

```text
工具调用（/ 虚拟路径 或 OS 绝对路径）
  → WorkspaceRootRegistry.resolve()
  ├─ 主根           → 现有行为，完全不变
  ├─ 已信任额外根   → 改写为内部挂载路径 /@ext/<root-id>/<rel>
  └─ 未授权外部路径 → 目录信任审批卡片 → 按决策注册根 → 再走上一分支
```

关键设计点：

- 新增 `WorkspaceRootRegistry` 作为“哪些目录被允许”的唯一事实源，按引用注入边界中间件、多根
  backend、mutation backend 和 `RunCoordinator`；**不参与执行资源池 fingerprint**，保证中途加根
  立即生效且不重编译图。
- 模型使用真实绝对路径寻址外部文件；`/@ext/<root-id>/...` 仅为内部形式，所有面向模型与用户的输出
  都投影回真实绝对路径。
- 授权即扩根：信任之后该目录与主工作区等价，不再区分“越界读”和“越界写”，一律回到既有审批模式矩阵。
- Protocol 新增 `directory_trust` presentation；**decisions 枚举不变**，五项决策语义映射为
  仅本次 / 加入本会话 / 加入本项目 / 拒绝。
- 硬边界不放宽：deny 规则优先、敏感路径写入仍强制弹窗、`..`/UNC/符号链接逃逸仍拒绝、
  根目录与系统目录不可注册、子 Agent 只继承不扩张。

## 实施计划

按真实依赖排序，每一步都形成可验证的纵向结果。

### 第 1 步：WorkspaceRootRegistry 与路径判定

- **改什么**：新增 `packages/agent/harness_agent/policy/workspace_roots.py`，实现 `WorkspaceRoot`、
  `ResolvedPath`、`TrustCandidate`、`ExternalPathNotTrusted` 与 `WorkspaceRootRegistry`
  （`resolve` / `trust_candidate` / `trust` / `roots` / `to_display`）。包含统一的路径规范化
  （POSIX 分隔符、Windows 大小写折叠、realpath）、判定优先级、不可注册目录黑名单、嵌套吸收。
- **为什么**：后续所有层都消费这一个判定结果；先把纯逻辑与规则固定下来，避免各层各写一套。
- **如何验证**：新增 `packages/agent/tests/policy/test_workspace_roots.py`，覆盖主根解析、额外根前缀
  优先、POSIX 遮蔽、Windows 大小写、`..`/UNC 拒绝、根目录与系统目录拒绝、嵌套吸收、once 单次消费。

### 第 2 步：边界中间件接入 registry

- **改什么**：`WorkspaceBoundaryMiddleware` 与 `WorkspacePathPolicy` 改为委托 registry 判定；
  `_backend_path` 改为使用 `ResolvedPath.backend_path`；拒绝文案区分“非法路径”与“需要信任但不可注册”；
  `allows_approval()` 对可信任的外部路径返回 True。构造点 `runtime/agent.py` 改为注入 registry。
- **为什么**：这是唯一的路径入口，必须先切换到新判定，后续 backend 与审批才有一致的输入。
- **如何验证**：`packages/agent/tests/policy/test_workspace_boundary.py` 现有用例全部保持通过
  （主根行为不变），新增外部路径产生可信任候选、不可注册目录仍硬拒绝的用例。

### 第 3 步：多根读写执行通道

- **改什么**：在 `CompositeBackend` 之上增加按 `/@ext/<root-id>/` 前缀在调用时向 registry 查根的
  路由（按 root_id 懒创建并缓存 `LocalShellBackend`）；`LocalTextMutationBackend` 支持按 root_id 选根，
  `_resolve()` 的 containment 语义、原子写、`O_NOFOLLOW` 与 CAS 不变；补充 `to_display()` 回显投影。
- **为什么**：没有这一步，即使判定放行，外部路径在 backend 层仍然无法解析。
- **如何验证**：新增测试覆盖外部根下 read/ls/glob/grep 与 write/edit/delete 全链路；两个根下同名
  相对路径的快照键与 CAS 不串用；工具结果与错误文案中不出现 `/@ext/`。

### 第 4 步：审批链路与 presentation 生成

- **改什么**：`approval_policy.py` 把只读文件工具加入 HITL 集合并让 `plan` 返回只读工具的
  interrupt_on；`_make_approval_preflight` 第一步改为区分“不可信任 → False 硬拒绝”与
  “可信任 → True 进入信任审批”；生成 `directory_trust` 审批描述与 presentation，复用现有
  `ApprovalPresentationStore`；`yolo` 在执行层自动授予 session 级根。
- **为什么**：卡片必须由既有 HITL 通道发出，不能新开第二条审批链路。
- **如何验证**：新增用例覆盖五种模式 × 外部读/写的预检结论；plan 只读弹窗且写仍被
  `PlanModeMiddleware` 拒绝；工作区内读取不弹窗（回归）。

### 第 5 步：Protocol 契约

- **改什么**：`packages/protocol/schema/v3.json` 把 `approvalRequest.payload.presentation` 改为
  `oneOf`，新增 `directoryTrustPresentation`；重新生成 `packages/protocol/src/generated.ts`。
- **为什么**：Python 已能产出 presentation，需要稳定跨进程形状后 CLI 才能消费。
- **如何验证**：正反 fixtures（缺字段、未知 kind、额外字段、空字符串）；生成类型与 Python 载荷一致；
  `bun run typecheck` 通过。

### 第 6 步：决策落地与持久化

- **改什么**：`RunCoordinator` 在决策回写时按 `presentation.kind == "directory_trust"` 调用
  `registry.trust(...)` 而非生成 `PermissionRule`；新增 `.harness/settings.json` 的
  `additional_directories` 读写（复用 `permission_rules.py` 的“读现有 JSON → 保留其它字段 → 追加 →
  原子写”模式）；`AgentHost` 启动时加载 user/project 层额外根。
- **为什么**：这一步才让“加入本会话/本项目”真正产生效果。
- **如何验证**：三种作用域分别产生 once/session/project 效果；落盘后其它字段保留；落盘失败降级为
  session 且本次仍放行；新进程启动后 project 根直接可用。

### 第 7 步：CLI 两端文案

- **改什么**：`packages/cli/src/presentation-shared/interaction-policy.ts` 按 presentation kind 提供
  决策文案；TUI `timeline.tsx` 与 Web 交互表单新增目录信任卡片分支，显示待信任目录、目标路径、
  发起工具与遮蔽提示；未知 kind 降级为通用卡片。
- **为什么**：用户看到的必须是“是否把 X 目录加入工作区”，而不是通用的“需要审批”。
- **如何验证**：`cd packages/cli && bun test` 覆盖 kind 分支与降级；TUI 手工验证卡片文案与选项。

### 第 8 步：提示词与文档

- **改什么**：`system_prompt.md` 第 21–22 行、`_with_execution_context()` 第 419–420 行改写为
  “主工作区用 `/` 虚拟路径；工作区外使用真实绝对路径并会触发一次目录信任确认”；已信任根清单按
  `RunContextSnapshotMiddleware` 的既有做法在模型调用边界动态追加；更新
  `docs/user/安全与沙箱.md`、`docs/user/配置.md` 与 `docs/developer/architecture/架构总览.md`。
- **为什么**：静态提示词里写死的旧承诺会直接误导模型，动态清单是模型知道新根的唯一途径。
- **如何验证**：文档描述与行为矩阵一致；中途加根后的下一次模型调用能在上下文中看到该根。

### 第 9 步：项目级检查

- **改什么**：无功能改动，补齐证据。
- **如何验证**：`bun run typecheck`、`bun run test`、
  `cd packages/agent && .venv/bin/python -m pytest -q`、`bun run project:check` 全部通过，
  结果写入本任务 `test_evidence`。

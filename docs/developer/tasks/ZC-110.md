## 背景

手动 `/compact` 会调用摘要模型，耗时可以接近当前 Model Profile 的请求超时。
它不是 Agent Run，但同样会读取并改写当前 Thread 的模型投影，因此在完成前
必须拥有明确的界面操作态和服务端 Thread 占用。

## 当前问题

```text
用户提交 /compact
→ TUI 没有记录进行中操作，Composer 继续接收“你好”
→ context.compact 超过通用 30 秒 RPC 超时
→ 客户端删除 pending request，但服务端仍在执行
→ run.start 在串行 stdio 后排队并也超时
→ 服务端最终完成 Run，UI 却显示失败
→ 迟到响应被误报为 Unknown JSON-RPC response id
```

同时，`RunCoordinator.idle_thread()` 在整次模型压缩期间持有全局锁，
会让不同 Thread 的 Run 受到无关阻塞。

## 解决方案

1. TUI 增加显式 `pendingOperation`，`/compact` 发送前进入、成功或失败后在
   `finally` 退出；为什么：它不是 Run，不能伪造 `activeRun`；验证：状态与 Controller 测试。
2. Composer 和 Controller 同时实施门禁；为什么：失焦只是展示层保护，不能防止鼠标、
   重复 Enter 或并发 intent 绕过；验证：压缩 pending 时提交普通消息和第二个 `/compact`。
3. `context.compact` 和 `run.start` 不再使用会产生幽灵执行的本地 30 秒接受超时；
   transport 关闭和服务端/模型 deadline 仍负责失败封口。
4. AgentClient 有界保留已超时 request ID，只忽略对应的迟到响应；真正从未发出的 ID
   仍报协议错误。
5. Coordinator 用目标 Thread reservation 取代跨模型调用持有的全局锁；同 Thread
   `run.start`/watch/compact 互斥，其他 Thread 仍可受理。

## 范围

- TUI `/compact` 进行中状态、输入门禁和安全状态文案。
- AgentClient 长耗时请求与迟到响应生命周期。
- RunCoordinator 的同 Thread 维护占用。
- TypeScript/Python 直接回归和用户/架构文档。

## 非范围

- 不修改压缩算法、摘要 Prompt、压力阈值或检查点数据形状。
- 不新增消息排队；压缩期间的新输入必须拒绝，不延后自动执行。
- 不新增 Protocol method 或改变 JSON-RPC v3 payload。
- 不调用真实模型完成自动化验证。

## 验收清单

- [x] `/compact` 发送后立即显示“正在压缩上下文”并让 Composer 失焦。
- [x] pending 期间普通消息不进入 prompt history、Transcript 或 `run.start`。
- [x] pending 期间第二个 `/compact`、`/resume`、`/model` 和 `/web` 均按空闲要求拒绝。
- [x] 压缩成功、skipped、failed 或 transport 关闭都会退出 pending 状态。
- [x] 合法长压缩不再因 CLI 通用 30 秒超时失败。
- [x] 已超时 ID 的迟到响应被有界忽略，真正未知 ID 仍产生协议诊断。
- [x] 维护占用期间同 Thread Run 返回 `THREAD_BUSY`，不同 Thread Run 仍可完成。
- [x] reservation 在成功和异常路径都只释放一次。

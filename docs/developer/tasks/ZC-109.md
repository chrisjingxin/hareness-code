## 背景

当前迁移器能够严格识别 schema v1-v6 的历史表结构，并且 PromptEpoch 表在 v2-v6
都有明确的逐版本列契约。但迁移入口和实际转换分支只允许 v6 携带 PromptEpoch。
因此仓库曾真实生成、结构仍完全合法的 `v3 + harness_prompt_epochs` 数据库会在启动时
返回 `CHECKPOINT_MIGRATION_LEGACY_TABLE_UNEXPECTED`。

## 当前问题

输入、判断和结果如下：

```text
本机 v3 数据库
→ 严格 schema 校验通过
→ 发现 PromptEpoch
→ 入口只接受 v6
→ Host 失败关闭，CLI 显示 THREAD_STORE_UNAVAILABLE
```

数据库没有损坏，但用户只能换用空 HOME 或手工移走历史数据库才能启动。直接删除数据库
会丢失 Thread 历史，不应作为代码缺陷的默认处理方式。

## 解决方案

1. 用一个明确谓词定义 PromptEpoch 的合法历史来源为 v2-v6；为什么：这与现有逐版本
   schema 契约一致，同时不放宽到缺少契约的版本；验证：单元测试覆盖上下界。
2. 父进程入口和 migration child 使用同一谓词；为什么：避免父子对同一数据库得出不同结论；
   验证：合法 v3 可以进入 child，v7+ 在备份和写入前拒绝。
3. 对合法来源统一执行现有单向 adapter；为什么：PromptEpoch 只转换为 legacy snapshot，
   不恢复生产双读或双写；验证：最终 snapshot 可读、旧表删除、无可证明 Run 时不伪造绑定。
4. 保留 verified backup、事务提交和失败恢复；为什么：本地历史不可逆；验证：备份仍为原始
   schema，最终数据库完整性为 `ok`，二次打开幂等。
5. 更新用户排障和架构说明；为什么：同事需要区分可迁移旧库和异常残留表；验证：项目文档检查通过。

## 范围

- 严格合法的 v2-v6 PromptEpoch 一次性迁移。
- v3 真实历史形状的回归测试。
- v7 及更高异常残留表的失败关闭保护。

## 非范围

- 不处理 migration child terminate/kill/reap 与临时文件回收；这些仍属于 ZC-108。
- 不支持未知表、畸形列、损坏数据库或 schema v7+ 的 PromptEpoch adapter。
- 不保留 PromptEpoch 生产读写、alias、fallback 或双写。
- 不修改 Protocol、CLI 或上下文压缩行为。

## 验收清单

- [x] 严格合法的 v3 数据库可以自动升级到当前 schema。
- [x] 升级前生成 `pre-v3-migration.bak`，备份保持 v3 且完整性为 `ok`。
- [x] PromptEpoch 转为 legacy RunContextSnapshot，旧表在成功事务中删除。
- [x] 缺少旧 Run binding 时不创建伪造 binding。
- [x] v7、v8、v9、v10 和当前 schema 异常残留 PromptEpoch 时原样拒绝。
- [x] 迁移后的数据库可再次打开，且 Thread/Transcript 行为不回退。

## 背景

当前 TUI 已有几个方向正确的 module：

- `state.ts` 用 reducer 处理 AgentEvent sequence、消息、工具时间线与终态；
- `commands.ts` 用 Command Registry 统一命令声明、解析和可用性；
- `command-dispatcher.ts` 将稳定命令 ID 转换为结构化 `CommandResult`；
- `overlays.tsx` 复用 SearchPicker 与 DialogShell；
- `AgentClient` 隐藏 JSON-RPC 关联和 Run 生命周期。

但这些 module 还没有覆盖完整用户工作流。`app.tsx` 仍是最终编排中心，当前约 1,397 行并维护十多个 `useState`。

## 当前存在的问题

### 1. Thread 状态分成 reducer 与 React 局部状态两套

消息、运行状态位于 `state.ts`；模型选择、实际模型、Skill 选择、Thread/Model/Skill Picker、Dialog、命令菜单和展开状态位于独立 `useState`。

一次 `/resume` 或 `/new` 需要同时清理多个状态源。原子性依赖某个 callback 是否记得更新所有字段。

### 2. CommandResult 仍由根组件解释领域流程

`applyCommandResult()` 在 `app.tsx` 中继续处理多种结果。尤其 `/mcp` 的子命令解析、参数校验、`mcpStatus/add/remove` 调用和错误展示仍全部位于 React module。

Command Registry 和 Dispatcher 因此只覆盖了命令的一半 interface，根组件仍需知道每个命令的业务步骤。

### 3. `/model` 是隐藏在组件中的多步事务

模型确认后，组件需要：

1. 更新当前 Thread 选择；
2. 查询 `config.details`；
3. 构造 changes；
4. `config.preview`；
5. `config.commit`；
6. 更新默认标记；
7. 处理“当前选择成功但默认写入失败”的部分成功状态。

这是一条明确的工作流，却由 `useCallback`、多个 loading 字段和视图状态共同表达。

### 4. Picker/Dialog 状态机重复分散

Skill、Thread、Model Picker 各有 visible/loading/query/selectedIndex/error 等状态，快捷键处理器还要按浮层优先级逐一分支。Overlay 复用了渲染，但没有复用打开、加载、选择、关闭和错误恢复的状态转换。

### 5. 领域测试被迫渲染 OpenTUI

验证 `/mcp`、`/model`、`/resume` 或 focus 恢复通常需要 `testRender()` 整个 TUI。测试同时受到 React 调度、renderer 尺寸和 textarea focus 影响，难以区分工作流错误与表现错误。

### 6. React 根组件成为所有变化的热点

新增或修正一个命令通常会同时修改 command、app callback、快捷键、Overlay props 和 interaction test。代码 locality 较差，多个独立工作流容易发生状态交叉回归。

## 为什么现在要修改

- 当前命令与工作流已经足够多，根组件继续增长会让后续架构修复也必须修改 React 热点。
- Protocol/AgentClient 已经提供稳定 seam，TUI 可以只依赖 AgentClient，无需知道 transport。
- 先把当前行为收进一个 deep module，后续是否新增功能都能通过同一 interface 验证。
- 多前端只共享 Protocol 与 AgentClient；本任务明确只整理 TUI 表现层，不尝试让 Web、CLI 和 TUI 共享一套 UI 状态。

## 目标设计

建立表现层内部的 `TuiController` 或等价 module。这里的 controller 不是 Harness 领域中的 Session，不新增持久化 `Session` 概念。

建议 external interface：

```ts
interface TuiController {
  getSnapshot(): TuiSnapshot
  subscribe(listener: (snapshot: TuiSnapshot) => void): () => void
  dispatch(intent: TuiIntent): Promise<void>
  applyAgentEvent(event: AgentEvent): void
  close(): Promise<void>
}
```

controller 接收 `AgentClient`、prompt history 和 `/web` launcher 等现有依赖，内部复用 reducer、Registry、Dispatcher 与 Overlay state。React 只把键盘、输入和点击转换为 `TuiIntent`，再把 `TuiSnapshot` 渲染成现有组件。

```text
keyboard / textarea / renderer
          ↓ intent
TuiController
  ├─ Command Registry + Dispatcher
  ├─ current event reducer
  ├─ Thread / model / MCP workflows
  └─ Picker / Dialog state
          ↓ snapshot
React/OpenTUI adapter
```

职责划分：

- Controller：命令计划、异步 AgentClient 调用、Thread 原子切换、模型 CAS、MCP 参数解析、浮层状态转换。
- React adapter：renderer ref、textarea focus、终端尺寸、实际组件树与视觉动画。
- `state.ts`：继续作为事件时间线 reducer，不需要重写。
- AgentClient：继续拥有 Run/Protocol 生命周期；Controller 不接触 JSON-RPC ID 或 transport。

## 实施步骤

1. 将现有 `useState` 分为“工作流状态”和“纯渲染状态”，形成迁移清单。
2. 定义 `TuiIntent` 与 `TuiSnapshot`，先包装现有 reducer，不改变视图 props。
3. 把命令 resolve/dispatch 和 `applyCommandResult()` 迁入 Controller。
4. 将 `/mcp` 子命令解析与 AgentClient 调用迁入命令工作流。
5. 将 `/model` 当前选择 + 默认配置 CAS 迁入单一工作流，显式表示完整成功、部分成功和失败。
6. 将 `/resume`、`/new` 和 Run 终态后的 Thread 状态清理改为 Controller 内的原子转换。
7. 统一 Picker/Dialog 的打开、加载、选择、错误和关闭状态；Overlay 组件保持不变。
8. 将 React 根组件改为 snapshot 渲染与 intent adapter，最后迁移快捷键。
9. 新增不渲染 React 的 Controller 测试；保留少量真实 OpenTUI 测试验证 focus、键盘、窄终端和视觉 wiring。

## 范围

- 复用现有 event reducer、Command Registry、Dispatcher 和 Overlay，不引入全局状态库。
- 工作流 interface 接收用户 intent、Agent event 和 AgentClient result，输出不可变 snapshot。
- 把 Thread 切换、命令执行、模型 CAS、MCP 参数解析和 Picker/Dialog 状态转换移出 `app.tsx`。
- React adapter 继续拥有 renderer ref、textarea focus、终端尺寸和实际组件布局。

## 非范围

- 不新增 Slash Command、页面、Web UI 或设置项。
- 不重写现有 reducer、Overlay 或 AgentClient。
- 不创建一命令一 class 的浅层 handler。

## 验收清单

- [ ] 完整命令与 Thread 工作流可不渲染 React 进行测试。
- [ ] `app.tsx` 不再解释领域命令结果或组合多步 RPC。
- [ ] 焦点、键盘、窄终端和时间线渲染回归通过。
- [ ] 工作流 interface 不暴露 React 类型、JSON-RPC ID 或 transport 细节。
- [ ] 不新增 Harness `Session` 领域对象或持久化概念。

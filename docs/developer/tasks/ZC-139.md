## 背景

当前审批 diff 最多显示 200 行或 16 KiB，但单个 exact-string 参数可达 64 KiB，完整文件
可达 2 MiB。超限时审批文案会显示“diff 因上限截断”，但调用仍可被批准并提交。

Snapshot 和 CAS 可以证明“提交的是准备时的内容”，但不能证明用户看到了全部变更。

## 用户结果

```text
准备文件 mutation
  → 生成完整变更摘要
  → 判断当前审批通道能否完整展示
  → 可完整检视才进入审批
  → 否则零写入并要求拆小变更
```

## 需要确认的设计

- 在实施前创建同 ID Design，确认首版采用“超限直接拒绝并要求拆小”，还是提供可完整检视的受控 artifact/paging 通道。
- 设计必须分开“人工授权需完整展示”与“auto-edit 模式本来不进入逐次审批”的语义。
- 敏感路径即使命中 allow 规则也会强制审批，不得因 diff 超限退化为自动放行。

## 范围

- `FileMutationService` 的 diff 表示、HITL preflight/description 和稳定错误。
- default/auto-edit/auto/yolo 与敏感路径的组合策略回归。
- TUI/Web 审批文案、故障排查和安全文档。

## 非范围

- 不改变 Snapshot、exact-string、Tool Call 指纹或 backend CAS 语义。
- 不通过简单提高内存上限伪装解决了完整审批。
- 不让文件工具在审批失败后退化为 shell 写入。

## 验收清单

- [ ] 人工审批无法完整展示 diff 时，调用不进入可批准状态且文件字节不变。
- [ ] 错误结果只提供一个确定恢复动作，弱模型可拆小编辑后重试。
- [ ] 未截断 diff 的审批、已授权自动模式和敏感路径底线不回归。
- [ ] 审批参数与最终提交内容仍由同一 fingerprint/plan 一次性绑定。
- [ ] 用户文档、开发者文档和 focused/full 回归记录完整。

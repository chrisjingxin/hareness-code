## 背景

当前 `PromptComposer` 创建 `PromptEpoch`，`ThreadPersistence` 以 `thread_id` 保存一份不可变记录。`AgentHost._create_run_context()` 恢复旧 Thread 时优先读取这份记录，因此用户在同一 Thread 内修改：

- `~/.harness/AGENTS.md`；
- `<workspace>/.harness/AGENTS.md`；
- 环境描述或其他受支持上下文；

后续 Run 仍会使用第一次运行时的内容。与此同时，`RunContext` 已经是每次 LangGraph 调用的显式输入，具备把生效边界调整为“顶层 Run”的基础。

本任务对应 `REQ-CTX-001`、`REQ-CTX-002`、`REQ-CTX-007` 和 `REQ-CTX-008`。

## 当前存在的问题

### 1. Thread 生命周期与资源生命周期绑死

Prompt 前缀只要 Thread 不变就永远不变，但 AGENTS、环境和未来动态上下文都有独立版本，不能要求用户新建 Thread 才刷新。

### 2. Run 准备不是一个一致快照

`AgentHost._prepare_run()` 解析模型、Profile 和 Skill snapshot；真正的 PromptEpoch 却在 acquire AgentEngine 后由 `_create_run_context()` 创建或恢复。一个 Run 的能力视图、系统提示和持久化绑定不是同一准备结果。

### 3. Prompt 内容顺序没有显式权限模型

当前 Prompt 以固定字符串拼接，但没有把“权限层级”和“变化频率”建模。未来加入动态记忆时容易把低可信内容放进稳定安全前缀，或让高频块造成无意义缓存抖动。

### 4. Run binding 不能回答使用了哪版上下文

`RunExecutionBinding` 保存模型与 Runtime Profile，但没有绑定本次实际 system prompt 的快照 ID。

## 为什么现在要修改

- [ZC-098](ZC-098.md) 建立了 Run 级规范记录和受理事务，适合同时绑定本次上下文事实。
- `RunCoordinator` 已经在受理前调用单一 `PreparationProvider`，无需把文件刷新散落到 Server、Middleware 和工具中。
- 后续 Skill 热更新和压缩后恢复都需要一个 Run 内固定、Run 间可变化的上下文身份。

## 目标设计

新增 Host-scoped `ContextLifecycle`，每次顶层 Run 只准备一次：

```text
读取当前支持的上下文来源
→ 校验来源与权限层级
→ 按“权限优先、同层稳定优先”排序
→ 生成确定性 System Instruction
→ 按内容摘要复用或创建 RunContextSnapshot
→ 与 Run binding、用户记录一起原子受理
→ 本 Run 全程只使用该快照
```

建议领域值：

```python
ContextBlock(
    key,
    authority,
    stability,
    content,
    digest,
)

RunContextSnapshot(
    snapshot_id,
    blocks,
    system_prompt,
    system_fingerprint,
    created_at_ms,
)
```

固定顺序：

```text
1. Harness 核心策略与 DeepAgents 基础规则
2. 实际审批、Sandbox、Policy 和工具能力边界
3. 稳定环境信息
4. 用户级与项目级 AGENTS
5. 当前 Skill 索引
6. Run 级动态内容；未来长期记忆也只能进入这里
7. 模型工作投影与当前用户输入
```

安全与缓存约束：

- AGENTS、Skill 和未来记忆都是低可信参考，不能改变 EffectivePolicy、Sandbox 或真实工具列表。
- 内容与顺序不变时必须生成相同 fingerprint，并复用已持久化快照。
- 快照只保存规范化块、摘要和必要正文；不得保存凭据、不必要的绝对路径或 Header。
- 本任务允许 `ContextLifecycle` 接收已有动态块，但不创建空的 Memory Provider 或长期记忆接口。

## 实施步骤

1. 建立当前 `PromptEpoch` 字段到 ContextBlock 的映射，明确哪些是核心策略、能力边界、环境、AGENTS 和 Skill。
2. 新增 `context_lifecycle.py`，集中读取来源、排序、截断、计算摘要并生成 `RunContextSnapshot`。
3. 调整 `PromptComposer`，保留确定性渲染与 Token 工具函数，删除“一个 Thread 只能有一个永久 epoch”的职责。
4. 扩展 `RunPreparation`，让模型绑定、AgentEngineProfile、Skill snapshot 和 RunContextSnapshot 来自同一次准备。
5. 扩展 `ThreadPersistence.accept_run()`，原子持久化或复用快照，并让本次 Run binding 引用 `snapshot_id`。
6. 将 `RunContext.prompt_epoch` 替换为 RunContextSnapshot；Middleware 每次模型调用都从当前 RunContext 注入同一 system prompt。
7. 在顶层 Run 准备时重新观察 AGENTS：内容修改、文件删除和来源新增在下一 Run 生效；Run 开始后的变化不影响当前执行。
8. 明确刷新错误：文件在扫描与读取间异常变化、越界、symlink 或无法验证时在模型调用前失败，不允许一个 Run 混用新旧块。
9. 将旧 PromptEpoch 转换为 legacy RunContextSnapshot 以保护现有数据，随后删除生产路径的 `load/persist_prompt_epoch` 和双写。
10. 更新架构与用户文档，说明“同 Thread 下一 Run 生效，当前 Run 内固定”的边界。

## 范围

- AGENTS、稳定环境、当前能力说明和已有 Skill 索引的 Run 级快照。
- 同一 Run 的所有模型调用、工具续跑、重试和 Interaction 恢复使用同一快照。
- 快照持久化、Run binding 审计和 legacy PromptEpoch 单向迁移。
- 保持现有 JSON-RPC v3 请求形状。

## 非范围

- 不在本任务实现 Skill Catalog 重新扫描；先绑定本次传入的现有 immutable Registry，热更新由 ZC-100 完成。
- 不实现长期记忆检索、Embedding、向量数据库或跨 Thread 注入。
- 不实现 OpenCode Context Epoch update 消息链。
- 不允许在同一 Run 的工具循环中热切换系统规则。

## 验收清单

- [ ] 修改、删除或新增 AGENTS 后，同一 Thread 的下一顶层 Run 使用新内容。
- [ ] Run 执行中继续修改文件时，该 Run 的所有模型调用仍使用启动时快照。
- [ ] System Instruction 先按权限层级、再按稳定程度确定排序，内容不变时 fingerprint 不变。
- [ ] Prompt 中的能力说明与本次 AgentEngineProfile 的真实工具视图一致。
- [ ] AGENTS 或未来动态块不能扩大 EffectivePolicy、Sandbox 或工具能力。
- [ ] 每个已受理 Run 能通过 snapshot ID 审计实际 system prompt 版本。
- [ ] Context 刷新失败发生在首个模型调用前，且不提交半套 Run 状态。
- [ ] 生产代码不再写入旧 PromptEpoch；legacy 数据只通过单向迁移读取。

## 版本影响

本任务改变 AGENTS 在现有 Thread 中的生效时间和本地持久化 schema。实现完成时必须更新用户文档并记录迁移证据；版本只能通过 `bun run version:set` 修改。

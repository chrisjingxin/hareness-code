## 背景

一次 Coding Agent 会话可以固定 Skill catalog、MCP connection、工作区和模型目录，但每个 Agent 只应看到其中被授权的子集。

目标权限计算为：

```text
managed / 全局硬边界
  ∩ 父 Agent delegation envelope
  ∩ 目标 Agent ExecutionPolicy
  = EffectiveExecutionPolicy
```

当前 `create_harness_agent()` 仍按根 Agent 的 approval mode、WorkspaceBoundary、Shell allow-list 和全部 MCP 工具统一构图。生产路径没有角色级 Tool、Skill、MCP 和文件权限视图。

## 当前存在的问题

### 1. 隐藏工具和阻止执行没有统一来源

只从模型 tool schema 中删除 `write_file`，不能阻止伪造或上游错误产生的 tool call；只在执行时拒绝，又会让模型反复计划不可用工具。两层必须消费同一个 Policy 结果。

### 2. Deep Agents 内置文件工具不是普通附加工具

文件工具由 FilesystemMiddleware 注入。仅过滤 `create_harness_agent(tools=...)` 传入的 MCP 工具，不能移除 write/edit/delete/execute。

### 3. 当前 Policy 主要是 approval mode

AgentEngineProfile 的 `policy_fingerprint` 当前主要包含 approval mode，不能表达角色的 Tool allow/deny、文件读写路径、Shell、网络、隔离和 delegation 边界。

### 4. 已有 Agent catalog 尚未形成生产 seam

ZC-085 不再预设删除 `agent_catalog.py`。本任务必须在真实 resolver 和 tool execution seam 上判断哪些 Agent/Policy 类型与交集逻辑可以直接保留，并删除仍无调用方的 Plugin/parser 部分；不得把整个 catalog 原样接入生产。

## 为什么现在要修改

- 多图的主要价值之一是按角色固化最小权限；没有执行层 Policy，多张图只是在缓存不同 Prompt。
- ZC-091 会提供唯一 ResolvedAgentSpec，可以让能力视图和 Profile 指纹来自同一结果。
- delegation 上线前必须证明子 Agent 权限只能缩小，否则父子 Agent 会形成提权通道。

## 目标设计

建议建立一个小的 Policy evaluator：

```python
resolve_effective_policy(
    global_boundary,
    parent_envelope,
    target_policy,
) -> EffectiveExecutionPolicy
```

再由 capability resolver 生成：

```text
Session capabilities
  ∩ EffectiveExecutionPolicy
        ↓
EffectiveCapabilityView
├─ built-in filesystem operations
├─ Shell commands
├─ MCP tool names
├─ additional tools
├─ Skill IDs
├─ filesystem paths
├─ network hosts
└─ delegation targets / depth / parallelism
```

同一个 view 同时驱动：

1. 构图时可见的工具和 Skill；
2. Tool schema；
3. 实际工具调用前的 fail-closed guard；
4. AgentEngineProfile 指纹；
5. AgentExecutionBinding 中的 Policy 事实。

## 实施步骤

1. 从 ADR 提取最小 ExecutionPolicy 和 EffectiveExecutionPolicy 类型，只实现当前可执行的 Tool、filesystem、Shell、MCP、Skill、approval 和 delegation 字段。
2. 实现确定性的交集算法；缺失、损坏和无法判断的规则一律收紧或拒绝。
3. 为 Deep Agents 文件工具建立角色级 read/write 操作视图，Planner 可只保留 ls/read/glob/grep。
4. 对附加工具和 MCP 工具按稳定名称与 schema 生成允许集合。
5. 在工具执行入口增加统一 Policy Guard，拒绝未暴露但仍到达执行层的 tool call。
6. 把 WorkspaceBoundary、Shell allow-list、approval mode 与新 Policy 的职责对齐，删除重复或互相矛盾的判断。
7. 将有效能力视图指纹接入 ZC-091 的 ResolvedAgentSpec。
8. 用恶意 Prompt、伪造 tool call、父窄子宽、路径穿越和 MCP 未授权工具覆盖 fail-closed 行为。

## 范围

- 角色级 Tool、Skill、MCP、filesystem、Shell 和 delegation 能力收敛。
- 构图可见性与执行时授权使用同一个 EffectivePolicy。
- 保持本地 shell 不是 OS sandbox 的现有说明，不把 Policy 误称为进程隔离。
- 为内置测试角色提供只读与可写 Policy fixture，不开放用户配置。

## 非范围

- 不实现 Plugin 安装或项目 Agent 文件。
- 不新增网络工具、MCP OAuth 或 managed policy 管理界面。
- 不把 Skill `allowed-tools` 当作安全权限。
- 不依靠 Prompt 约束替代执行时校验。

## 验收清单

- [ ] 只读 Agent 的模型 schema 中没有写文件、删除和 execute。
- [ ] 伪造的未授权 tool call 在执行前被稳定拒绝。
- [ ] 子 Agent 的有效权限不会超过全局边界或父 delegation envelope。
- [ ] MCP 和 Skill 只暴露角色允许的子集。
- [ ] 实际能力视图变化会改变 AgentEngineProfile，描述文字变化不会误改权限。
- [ ] 用户文档明确 Policy、HITL 与真正 sandbox 的区别。

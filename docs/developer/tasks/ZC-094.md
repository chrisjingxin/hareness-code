## 背景

同一个 `AgentHost` 可以按 Profile 编译多张 AgentEngine 图，但这些图访问的是同一个
Host 启动时绑定的 workspace。旧实现让每张图各自创建 `AsyncRWLock`，并且需要 HITL
审批的工具会直接跳过锁；因此两个图在用户批准后仍可能同时修改同一目录。

## 解决方式

`AgentHost` 在启动时创建一把 `AsyncRWLock`，并在构建每张默认 AgentEngine 图时注入
`ConcurrencyGuardMiddleware`。调用路径为：

```text
模型发起 tool call
  → HITL（如需要，先等待用户审批）
  → ConcurrencyGuardMiddleware 获取 Host 共享读/写锁
  → 工具执行
  → 释放锁
```

- 只读工具共享读锁，保留并行读取。
- 写工具、未知工具与 `task` 获取写锁。`task` 的默认子图可能写同一 workspace，且不继承
  主图 guard，所以父调用必须覆盖整个同步子 Agent 生命周期。
- `create_harness_agent()` 未收到锁时仍为独立库调用创建局部锁；生产默认路径始终注入
  Host 共享锁。

## Lite 边界

- 一个 Host 固定绑定一个 workspace；不同工作目录通常由不同 Host 承载，因此不互相阻塞。
- 远端 sandbox 在没有稳定资源 ID 前同样使用 Host 锁，保守地串行化工具执行。
- 两个独立进程若同时指向同一物理目录，当前不会协调；不实现跨进程锁。
- 不实现 `WorkspaceExecutionScheduler`、resource key、lease、worktree/sandbox 并行规则或
  文件冲突解决。这些能力只有在实际出现可识别资源域或吞吐瓶颈时再单独设计。

## 验收清单

- [x] 不同 `ConcurrencyGuardMiddleware` 注入同一锁时，读取可以并行，写入会阻塞跨图读取。
- [x] `task` 按独占工具处理，取消写入后锁会释放。
- [x] 默认 AgentEngine builder 为不同 Profile 注入同一 Host 锁。
- [x] 审批等待期间不持锁，批准后的实际工具执行仍受锁保护。
- [x] 用户与开发者文档说明 Host 边界和不支持的跨进程场景。

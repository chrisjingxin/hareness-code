# ZC-104：Web Interactive Adapter 与 React 工作台

原始需求：[ZC-104：实现 Web Interactive Adapter 与 TUI 功能对齐](../tasks/ZC-104.md)

前置方案：[ZC-102：单实例 Web Handoff 与 TUI 接管生命周期](ZC-102.md) · [ZC-103：Interactive Core 与 TUI 迁移](ZC-103.md)

后续验证：[ZC-105：真实 Browser E2E](../tasks/ZC-105.md)

## 通俗说明

当前 `/web` 页面已经能安全接管 TUI，但页面本身仍是一段直接操作 DOM 的最小脚本。它自己启动 Run、读取 Event、弹出浏览器 `confirm/prompt`，因此既缺少 Thread、模型、Skill、MCP 和完整 Interaction，也绕开了 ZC-103 刚建立的共享交互语义。

本任务把页面改成 React DOM 工作台，但不在 Web 中再造一套业务层：

```text
浏览器事件
  → Web Interactive Adapter（draft、面板、焦点、展开状态）
  → InteractiveController（Run、Thread、命令、Interaction、catalog）
  → InteractiveSnapshot
  → React DOM presentation

Browser handoff 动作
  → WebHandoffPort（ready、Thread 报告、归还、退出）
  → ZC-102 Coordinator / Agent Host control
```

改完后，从空首页发送第一条消息、恢复或切换 Thread、选择模型和 Skill、管理 MCP、处理审批/多问题、取消 Run、返回 TUI 与退出 Harness 都走同一套共享规则。TUI 和 Web 只在输入方式与布局上不同，不会出现两个客户端各自解释 Slash Command 或 Event 的情况。

## 已确认现状

- `packages/cli/src/web/app.ts` 同时承担 fragment 解析、WebSocket transport、认证、Host control、Run 消费和 DOM 更新，页面只能处理文本增量和 `tool.started`。
- `packages/cli/src/web/html.ts` 内嵌全部样式与静态表单；`bundle.ts` 和 `server.ts` 只处理一份 JavaScript 资源，CSP 仍允许 inline style。
- ZC-102 已提供 lifecycle-first bootstrap、单实例 handoff、Host holder 校验、关闭/刷新收敛与 nullable `thread.changed`；这些安全边界继续保留。
- ZC-103 已交付 `InteractiveController` 的 `dispatch / getSnapshot / subscribe / close` interface，Run、Timeline、Thread、模型、MCP、Slash Command 和完整 Interaction schema 已在共享 Core 内。
- 当前 `InteractiveAgentPort.listSkills()` 固定使用 `include_disabled: false`，共享 intent 只有 `skill.arm/skill.clear`。原始需求明确要求 Skill 启停，所以必须先补共享语义，不能由 Web 直接调用 `skills.set_enabled`。
- 当前交互式 TUI 没有请求 `skills.manage`；Web 要管理 Skill，必须在自己的 initialize capability 中显式请求该能力。TUI 不因此获得新的管理权限或改变现有界面。
- `react@19.2.6` 已存在，但 `react-dom`、`lucide-react` 都不是当前直接依赖；任务中“现有 `lucide-react`”与仓库事实不符。`marked@17.0.1` 目前只是 OpenTUI 带入的传递依赖，Web 若使用必须声明为直接依赖。
- 当前 lifecycle 的 `ready` 没有携带最终 Thread，也没有 Browser 可等待的 `active` 确认；如果初始 Thread 恢复失败，或 Browser 在 Coordinator 锁定 TUI 前启用输入，页面状态可能与 TUI 恢复状态短暂不一致。
- `/quit` 在共享 Core 中返回 `request-exit`，但当前 Browser lifecycle 没有把退出请求传回 CLI 的消息，不能完整满足“退出 Harness”。

## 目标与关键 invariant

- Web 的 Run、Thread、模型、Skill、MCP、compact、命令解析和 Interaction 只能通过 `InteractiveController.dispatch()` 执行；Web presentation、Web Adapter 不得直接调用对应 Agent RPC。
- Web Adapter 只拥有表现状态：draft、搜索词、当前面板、移动端抽屉、命令菜单选中项、Tool 展开、Interaction 表单草稿、滚动意图和临时通知。
- WebSocket transport、attachment 认证和 lifecycle 属于 bootstrap/infrastructure，不进入 React component，也不进入 `InteractiveController`。
- 浏览器在收到 lifecycle `active` 前只能显示只读的“正在接管”状态；`active` 表示 Host 已确认 matching attachment holder，且 Coordinator 已锁定 TUI。
- 初始 Thread 必须通过共享 `thread.open` 恢复。恢复成功或失败后的最终 `currentThreadId` 随 `ready` 一次性报告，后续变化才使用 `thread.changed`。
- 浏览器一次只运行一个 active Run，不请求 `run.multithread`；active Run 或 pending Interaction 时禁止返回 TUI和切换 Thread。
- `/web` 因 Browser 不请求 `host.attach` 而从命令菜单隐藏，防止嵌套 handoff；其余已协商命令继续使用共享 Registry。`/quit` 映射为 lifecycle 退出请求，不让 Browser 直接终止进程。
- Thread ID、Interaction request ID、Tool ID 只作为内部 key 使用；Thread 列表和页面标题不直接展示内部 ID。
- Markdown、用户输入、Tool 参数与输出都视为不可信文本；不得使用 `dangerouslySetInnerHTML`，不得执行 raw HTML，也不得自动加载远端图片。
- 页面关闭、刷新、lifecycle shutdown、Agent socket 断开和 React 卸载最终都只执行一次资源收敛；Controller、AgentClient、两个 WebSocket 和 React root 均可重复关闭。
- 响应式布局改变组件排布，不改变 Adapter/Core 状态，不按 viewport 创建第二套业务分支。

## Web Interactive Adapter

Web Adapter 与 TUI Adapter 采用相同的四方法形状，便于通过 interface 测试，不把 React state 当成业务事实：

```ts
export interface WebInteractiveAdapter {
  getSnapshot(): WebAdapterSnapshot
  subscribe(listener: (snapshot: WebAdapterSnapshot) => void): () => void
  dispatch(intent: WebIntent): Promise<void>
  close(): Promise<void>
}

export type WebAdapterOptions = {
  controller: InteractiveController
  handoff: WebHandoffPort
  frameScheduler?: WebFrameScheduler
}
```

`WebAdapterSnapshot` 至少包含：

- `interactive`：原样引用最近的 `InteractiveSnapshot`，不复制 Timeline reducer。
- `draft` 与命令菜单：菜单 items 只调用共享 `filterCommandMenuItems(snapshot.commands, draft)`；availability 不在 Web 重算。
- `activePanel`：`threads/models/skills/mcp/status/help | null`，以及各面板的搜索词、提交中与局部错误。
- `sidebarOpen`：只代表窄屏抽屉是否打开；viewport 判断由 CSS 完成。
- `expandedTools`：按 Tool ID 维护折叠状态。
- `interactionDraft`：按当前 request ID 保存完整 approval feedback 或全部 question answers；request ID 改变时原子重置，不能把旧答案提交给新 Interaction。
- `leaving` 与 `transientNotice`：归还/退出期间禁用重复动作，并显示脱敏结果。
- `scrollRequest`：只表示新消息或显式跳到底部；实际 DOM scroll position 留在 presentation。

`WebIntent` 使用稳定 ID 和 typed input，不携带 DOM event、HTMLElement 或完整 catalog DTO。至少覆盖 draft/submit、命令选择、面板开关与搜索、Thread/模型/Skill 选择、Skill 启停、MCP 添加/删除、Interaction 表单更新与提交、confirmation、Tool 展开、取消、返回 TUI、退出 Harness。

关键映射规则：

- `submit` 把原始 draft 交给 `input.submit`；普通消息、`//` 转义、未知命令和 Slash 参数错误都由共享 Core 解释。只有成功发出意图后才清空 draft。
- `InteractiveResult.present` 打开对应 Web panel，并触发共享 `catalog.refresh`；不读取 RPC。
- `request-handoff` 在 Browser 正常不会出现；若异常出现，只显示“当前页面不能再次打开 Web”的本地通知，不启动第二次 handoff。
- `request-exit` 调用 `WebHandoffPort.requestExit()`；页面不调用 `process.exit`，也不直接关闭 Python Host。
- Thread、模型、Skill、MCP 点击只回传 stable ID/typed input；Controller 必须再次按当前 snapshot 校验 availability、busy 和对象存在性。
- Controller 高频流式发布由 Adapter 使用 `requestAnimationFrame` 合并为每帧最多一次 presentation publish，始终发布最新 snapshot；Interaction、连接关闭和 leaving 状态立即 flush。该批处理不丢 Event，也不修改 Core 状态。

## Interactive Core 的最小补充

ZC-104 不重写 ZC-103，但要补齐原始需求已经要求、当前 interface 缺失的 Skill 管理 seam：

```ts
type InteractiveIntent =
  | /* 现有 intent */
  | { type: "skill.set-enabled"; skillId: string; enabled: boolean }

interface InteractiveAgentPort {
  listSkills(includeDisabled: boolean): Promise<SkillsListResult>
  setSkillEnabled(skillId: string, enabled: boolean): Promise<SkillsSetEnabledResult>
}
```

- catalog refresh 使用 `include_disabled: true` 获取权威全集；共享命令菜单仍只加入 `enabled && userInvocable` 的 Skill，所以 TUI 现有选择语义不变。
- `skill.set-enabled` 先检查 `skills.manage`、无 active Run/Interaction、目标仍存在，再调用 port；成功后刷新 catalog，以服务端返回后的新列表为准。
- 禁用当前 armed Skill 时同时清除 `selection.armedSkill`；失败时保留原状态并发布脱敏 notice。
- Web 中无 `skills.manage` 时仍可查看和选择已启用 Skill，但启停控件不渲染或明确禁用；不得用失败 RPC 探测权限。
- 该变更同时补 Interactive Core 单元测试和 AgentClient adapter 测试，不在 Web 层出现 `skills.set_enabled` method string。

除上述缺口外，ZC-104 不扩大 `InteractiveController` external interface，不把 Web ready、layout 或 handoff 状态塞入共享 snapshot。

## Browser handoff interface 与生命周期

Browser 侧使用窄 interface 隔离 Host control 与 lifecycle：

```ts
export interface WebHandoffPort {
  activate(threadId: string | null): Promise<void>
  reportThread(threadId: string | null): void
  returnToTui(): Promise<void>
  requestExit(): Promise<void>
  close(): void
}
```

- `activate` 发送最终 Thread 的 `ready`，并等待 Coordinator 返回 `active`；Promise 完成后才能启用 composer 和管理动作。
- `reportThread` 只在 active 后发送变化，连续相同值去重；`null` 是新建/清空后的正式状态。
- `returnToTui` 先调用 `host.control.release` 并确认 owner，再发送 `released`。active Run 或 pending Interaction 由 Adapter 在本地阻止，Host control 仍作为最终防线。
- `requestExit` 发送 lifecycle `exit.requested`。Coordinator 统一 revoke attachment、等待 owner 恢复，再调用 CLI root 注册的退出 handler；未确认 owner 前不得直接退出 sidecar。
- `close` 只关闭 Browser 侧资源，不伪造 `released`；页面关闭仍由 Coordinator 按 `browser-close` cleanup。

内部 lifecycle 消息调整为：

```ts
type LifecycleServerMessage =
  | { type: "accepted" }
  | { type: "active" }
  | { type: "shutdown"; reason: LifecycleShutdownReason }

type LifecycleBrowserMessage =
  | { type: "ready"; thread_id: string | null }
  | { type: "thread.changed"; thread_id: string | null }
  | { type: "diagnostic"; stage: WebBootstrapStage; error_name: string; error_message: string }
  | { type: "released" }
  | { type: "exit.requested" }
```

状态机按以下顺序收敛：

```text
opening
  → accepted
  → Browser 认证 attachment
  → initialize + host.control.acquire
  → 创建 Controller，无 initialThreadId
  → 有初始 Thread 时 await thread.open
  → React 首次 commit（界面仍禁用）
  → ready{最终 thread_id}
  → Coordinator 校验 matching holder、锁定 TUI
  → active
  → Browser 启用输入

active
  → thread.changed       更新 TUI 后续恢复目标
  → released             归还并恢复 TUI
  → exit.requested       回收 attachment 后退出 Harness
  → socket close/error   取消未收敛 Run并恢复 TUI
```

Coordinator 在 `ready` 到达时先保存最终 `thread_id`，再查询 Host holder；校验成功后发布 `active` snapshot 并发送 `active` ack。`opening` 只接受一次 `ready`，`active` 只接受 `thread.changed/released/exit.requested`；未知字段、超限帧和乱序消息继续 fail closed。

`diagnostic` 只允许在 `opening` 阶段发送固定 bootstrap stage、最长 80 字符的错误名和最长 200 字符的脱敏摘要；它不改变状态机。CLI 默认只把 stage 和错误名写入 `~/.harness/debug/*.jsonl`，设置 `HARNESS_LOG_LEVEL=debug` 后才写摘要。消息不允许携带 endpoint、token、Thread ID、原始 frame、Prompt 或 Tool 数据。

CLI 的退出 handler 由 `runTui`/`WebAwareRoot` 在挂载时注册到 Coordinator，卸载时取消；Coordinator 只在 owner 已恢复且本次 `exit.requested` 仍是当前 handoff 时调用一次。这样退出仍沿用现有 renderer → coordinator → Agent stop 的正常关闭路径。

## Bootstrap、能力与资源所有权

Bootstrap 顺序不能因 React 化而改变安全边界：

1. 同步解析 URL fragment，并立即用 `history.replaceState` 清除 hash；校验失败时不创建任何 WebSocket。
2. 建立 lifecycle socket，等待 `accepted`；此时页面只显示安全的连接状态。
3. 连接 loopback Agent endpoint，发送一次 attachment token 完成认证；token 不进入 React props、Adapter snapshot、日志或 error 文案。
4. `AgentClient.initialize` 请求 Browser 实际会使用的 capability，并注册 approval/question handler。
5. `host.control.acquire` 必须返回当前 attachment ID；否则 abort。
6. 用 `AgentClientInteractiveAdapter`、`InteractiveRuntime` 创建共享 Controller；初始 Thread 通过 `await controller.dispatch({type: "thread.open"})` 恢复。
7. 创建 Web Adapter 和 React root；首个 React effect 表示 handler 已挂载，然后调用 `handoff.activate(controller.getSnapshot().currentThreadId)`。
8. 收到 `active` 后解除页面只读状态，并开始监听 `currentThreadId` 变化。

Browser 请求能力固定为：

```text
host.control
run.cancel
threads.read
config.read + config.write
context.manage
models.read + models.select
skills.read + skills.manage
mcp.read + mcp.manage
```

同时声明 `handles: [approval, question]`。不请求 `run.multithread` 和 `host.attach`；缺少某项协商能力时由共享 snapshot 隐藏或禁用对应入口，页面不得自行假设成功。

资源释放顺序为：停止 Adapter publish与 Thread 报告 → unmount React root → `controller.close()` → `AgentClient.destroy()` → 关闭 Browser sockets/supervisor listener。所有步骤幂等；`pagehide`、shutdown、Agent close 和 bootstrap catch 可以重复触发同一 close gate。

## 页面信息架构与视觉规范

视觉方向采用“克制的本地开发工作台”：像代码审阅器和终端之间的编辑型界面，信息密度高但留白明确。禁止营销式 hero、渐变、玻璃拟态、悬浮装饰、大圆角和层层卡片。

### 桌面 1440×900

```text
┌─────────────────────────────────────────────────────────────┐
│ project / branch        model · approval · status    actions │
├──────────────┬──────────────────────────────────────────────┤
│ New Thread   │                                              │
│ Search       │  Timeline（内容列最大约 880px）              │
│ Thread list  │  message / tool / interaction                │
│              │                                              │
│              ├──────────────────────────────────────────────┤
│              │  selected Skill / composer / send-or-cancel │
└──────────────┴──────────────────────────────────────────────┘
                         右侧 utility drawer：model/skill/MCP
```

- 左栏宽度约 260px，可折叠；只展示 Thread 摘要、更新时间和消息数，不展示 `thread_id`。
- 中央 Timeline 是唯一主视觉区，内容列限制最大阅读宽度，背景保持平整；User message 用轻微暖色带区分，Assistant 不包大卡片。
- model、Skill、MCP、status/help 使用 360–400px 右侧 drawer，不挤压 composer；确认操作使用小型 modal。
- Composer 固定在主列底部，textarea 自动增长到约 8 行；左侧显示 armed Skill，右侧按钮在 idle 时发送、运行时变为取消。

### 移动端 390×844

- 主界面只有 Timeline + sticky composer；Thread sidebar 与 utility panel 都是全高 drawer。
- 顶栏保留菜单、当前模型缩写、连接状态和更多操作，不把桌面所有标签压进一行。
- Interaction 卡在 Timeline 尾部，并在需要回答时固定到 composer 上方；键盘弹出后主按钮仍可见。
- 使用 `env(safe-area-inset-*)`，主要触控目标不小于 44px；长 URL、代码和 Tool 输出只能横向滚动或断行，不能撑破 viewport。

### 颜色、字体与动效

- 使用 CSS custom properties 提供浅色和 `prefers-color-scheme: dark` 两套 token；不在业务状态中保存主题。浅色基底为暖灰白，深色基底为近黑石墨，琥珀/铜色只用于当前选中、运行与主要动作。
- 正文优先本机 `Avenir Next / Segoe UI Variable / PingFang SC`，代码使用 `SFMono-Regular / Cascadia Code`；页面不请求远端字体或图像。
- 圆角控制在 4–6px，以 1px 分隔线和排版建立层级。Lucide 图标必须配文字或 `aria-label`，不能用 Unicode 符号替代。
- 只使用 120–180ms 的 drawer、focus 和状态过渡；遵守 `prefers-reduced-motion`。流式状态可有低调 cursor，不做循环装饰动画。

## Timeline、Markdown 与 Interaction

### Timeline

- `message`：按 kind 区分 user/assistant/system；流式内容只更新当前 Assistant 项，已完成项用稳定 key 和 `React.memo` 避免重渲染。
- `tool`：默认显示名称、状态和耗时/摘要；展开后显示参数与输出，使用 `<pre>`、最大高度和独立滚动。不同 Tool ID 永不合并。
- `interaction`：历史项保留已允许、已拒绝、已回答、超时或终态失效状态；当前待处理表单从 `snapshot.interaction` 渲染完整 schema。
- 自动滚动只在用户距底部阈值内发生；用户向上阅读时显示“有新输出”按钮，不抢走 scroll position。
- `role="log"` 只对新增完成项使用 `aria-relevant="additions"`；token 增量不逐字发送 live announcement，运行状态另用 `aria-live="polite"`。

### 安全 Markdown/GFM

- 将 `marked` 作为直接依赖，仅使用 lexer 生成 token，再把允许的 token 递归转换为 React element；不把 HTML 字符串交给 DOM。
- 支持标题、段落、强调、列表、引用、表格、任务列表、行内代码、fenced code 和安全链接。
- `html` token 以普通文本显示；raw HTML、script、事件属性和 SVG 字符串都不会成为 DOM。
- 链接只允许 `http:`、`https:` 与明确需要的 `mailto:`，外链使用 `target="_blank" rel="noopener noreferrer"`；非法 scheme 显示为普通文本。
- Markdown image 只显示 alt 和安全链接，不自动发起远端图片请求，避免模型输出触发网络请求或信息外带。
- User、Tool、错误和 MCP 文本始终通过 React text node 或 `<pre>` 渲染。

### Approval 与 Question

- Approval 按服务端 `decisions` 动态显示按钮；只有存在 `reject_with_feedback` 时展示反馈输入。提交期间锁定重复点击，Controller 仍负责 decision allowlist 与 stale request 校验。
- Question 一次展示全部 questions。单选用 radio，多选用 checkbox，`allowOther` 才出现自由文本；所有必答项完成后一次提交完整 `answers` map。
- deadline 显示剩余时间，但本地倒计时只用于展示；真正 timeout 和 fail-closed 仍由 InteractiveController scheduler 决定。
- request ID 改变、Run 终态、连接关闭或 Controller 清空 Interaction 时，Web Adapter 同步清除表单草稿并恢复焦点到 composer。

## 面板与主要行为

- Thread：打开面板时刷新 catalog；支持搜索、新建、恢复和切换。active Run/Interaction 时“新建/切换”显示共享 disabled reason，不关闭当前面板或发送 RPC。
- Model：显示 Profile、Provider、实际模型和 unavailable reason；选择语义继续是“当前 Thread 下一次 Run + 尝试同步未来新 Thread 默认”，不把同步失败误报成当前选择失败。
- Skill：选择已启用且 user-invocable 的 Skill 作为下一条消息的 armed Skill；管理列表可查看 disabled 项，并在 `skills.manage` 存在时启停。
- MCP：展示连接状态、工具数和脱敏错误；添加表单明确区分 stdio command/args 与 HTTP URL/SSE，最终只产生 typed `mcp.add` intent；删除使用 stable name。
- Status/help/version：复用共享命令产生的 Timeline notice 或只读 panel 数据，不在 Web 拼装第二份运行状态文案。
- Command menu：输入单个 `/` 前缀时打开，支持上下键、Enter 与 Escape；`//` 不打开。disabled item 显示共享 reason，未知命令由 Core写入同语义 notice。
- 键盘：Enter 发送、Shift+Enter 换行、Escape 先关闭最上层 drawer/dialog/menu，再取消 Run；`Ctrl/Cmd+K` 可打开命令菜单，但不新增业务命令。
- 返回 TUI：按钮在 active Run/Interaction 时禁用并解释原因；归还开始后整个页面只读，失败可在 attachment 仍有效时重试。
- 退出 Harness：顶栏更多操作和 `/quit` 都走 `request-exit`；Coordinator 开始 cleanup 后页面保持只读直到 shutdown，不伪装成普通返回。

## 错误、断线与安全边界

- bootstrap 错误由 React 外的最小 fatal view 显示统一脱敏文案；不显示 endpoint、token、attachment ID、原始 JSON-RPC frame 或完整企业路径。
- lifecycle shutdown/close 后显示“本次 Web 接管已结束”，禁用所有输入且不自动重连。attachment token 单次使用，刷新只能让 Coordinator cleanup，用户需从 TUI 再执行 `/web`。
- Agent connection `protocol-error/closed` 使用共享 connection snapshot；页面停止新操作并保留已渲染历史供用户阅读。
- catalog 单项失败只在对应 panel 显示 retry，不覆盖其他 panel、Timeline 或当前 Thread。
- React Error Boundary 只包 presentation；捕获异常后触发统一 abort/cleanup，并显示不含 snapshot 正文的错误页。
- HTML shell 不含 inline script/style。CSP 收紧为 `script-src 'self'`、`style-src 'self'`、`connect-src ws://127.0.0.1:*`，继续保留 `default-src 'none'`、`base-uri 'none'`、`form-action 'none'`、`frame-ancestors 'none'` 和 no-store/no-referrer/nosniff。
- Protocol 校验器由 canonical Schema 在 `protocol:generate` 阶段生成独立静态函数；Browser 不运行 `Ajv.compile`，因此不需要为 CSP 增加 `unsafe-eval`。源码模式每次从 `app.tsx` 即时构建，不能让旧 `dist/web.js` 掩盖新代码。
- 静态 server 只增加 `/web/app.css` 白名单；不提供目录读取、source map、任意文件或 fallback 路由。

## 构建与依赖决策

需要新增并登记以下直接依赖：

- `react-dom`：版本必须与 `react@19.2.6` 完全一致；同时增加匹配 React 19 的 `@types/react-dom`。
- `lucide-react`：固定使用企业 registry 可用版本，记录到依赖版本清单；只导入实际使用图标，让 Bun tree-shake。
- `marked@17.0.1`：从传递依赖提升为直接依赖，避免 Web Markdown 行为受 OpenTUI 依赖树变化影响。
- `happy-dom`：仅作为 Web presentation test 的 dev dependency；使用 React `createRoot/act` 与原生 DOM 事件，不再额外引入 Testing Library。

如果企业 registry 未提供 `lucide-react` 或 `happy-dom`，执行线程必须停在依赖门禁并回报，不得临时改用 CDN、远端字体、手写一套不一致图标或跳过 DOM 测试。

`bundle.ts` 从返回单个字符串改为返回 `{ script, style }` 的 `WebAssets`。开发时一次 Bun build 收集 JS/CSS output，生产构建产出稳定的 `dist/web.js` 与 `dist/web.css`；`server.ts` 分别按正确 content type 服务。`html.ts` 只保留 metadata、stylesheet link、`#root` 与 module script。

## 按依赖排序的实施步骤

### 1. 建立依赖、资源与分层门禁

- 改什么：登记 React DOM、Lucide、Marked、Happy DOM，调整 Web build 为 JS+CSS，并新增 Web architecture test。
- 为什么：后续页面必须先有稳定的渲染、样式和测试入口，避免组件实现后再反向迁移构建管线。
- 如何验证：`bun install --frozen-lockfile` 可复现；开发内存 build 和生产 `dist` 都恰好得到 JS/CSS；architecture test 拒绝 Web application/presentation 直接依赖 IPC。

### 2. 完成 lifecycle 的 active ack、最终 Thread 与退出闭环

- 改什么：扩展严格 lifecycle message、Supervisor 的 `waitForActive`、Coordinator 的 final Thread 保存和 exit handler；补 `WebHandoffPort`。
- 为什么：React 页面只有在 Host 与 TUI 都确认接管后才能可写，初始恢复失败也必须把 `null` 正确交回 TUI，`/quit` 才有宿主语义。
- 如何验证：状态机测试覆盖正常 ready→active、初始恢复失败、乱序/重复帧、nullable Thread、release、exit、close、timeout；exit handler 只在 owner 恢复后执行一次。

### 3. 补共享 Skill 管理语义

- 改什么：扩展 `InteractiveAgentPort`、`InteractiveIntent` 与 Controller，catalog 改为包含 disabled Skill。
- 为什么：原始需求要求启停，Web 不能绕过 Core 直接发受控 RPC。
- 如何验证：有/无 `skills.manage`、启用、禁用 armed Skill、RPC 失败、晚到刷新和 TUI 菜单仅显示 enabled Skill 均有 Core 测试。

### 4. 拆分 Browser bootstrap 与 transport

- 改什么：把 `WebSocketRpcTransport`、attachment auth、资源 close gate 从旧 `app.ts` 移出；composition root 按既定顺序创建 AgentClient、Controller、Adapter 和 React root。
- 为什么：认证凭据和 socket 生命周期不能渗入 React，页面组件也不能拥有 AgentClient。
- 如何验证：fragment 在任何 socket 前清除；认证 abort 立即关 socket；capability 精确；初始 Thread 通过 Controller 恢复；active 前所有动作禁用。

### 5. 实现 Web Interactive Adapter

- 改什么：实现表现 snapshot、语义 intent、共享 Result 映射、Thread 报告、Interaction draft 和 frame batching。
- 为什么：React component 应只渲染 snapshot 与发送 intent；这也是与 TUI parity 可独立验证的 seam。
- 如何验证：使用 fake Controller/WebHandoffPort 逐项断言 intent 与副作用，不需要 DOM 或真实 Agent。

### 6. 实现 React 工作台与安全渲染

- 改什么：按桌面/移动信息架构实现 Timeline、Composer、Thread drawer、utility panels、Interaction、dialog 和 Markdown renderer。
- 为什么：一次完成可操作主流程和清晰信息层级，避免按 RPC 功能堆叠孤立组件。
- 如何验证：Happy DOM 测试关键 DOM intent、焦点/ARIA、完整 question、动态 approval、Tool 展开、命令菜单和 raw HTML inert；人工检查长文本、空状态和错误态。

### 7. 收紧 HTML/CSP 并接入统一关闭

- 改什么：HTML 变为无 inline 内容的 root shell，server 增加 CSS route，Error Boundary/pagehide/shutdown 共用 close gate。
- 为什么：React 化不能削弱 ZC-102 的本地安全边界，也不能遗留 Agent socket 或 Controller listener。
- 如何验证：server/CSP 测试、重复关闭测试、页面刷新/关闭定向测试；HTML 中不存在 inline style/script 与凭据占位。

### 8. 补用户文档与任务证据

- 改什么：实施完成后更新 `docs/user/交互使用.md` 与 `docs/user/故障排查.md`，说明新工作台、运行中限制、刷新不恢复和重新 `/web` 的方式。
- 为什么：用户需要能观察和理解接管/归还，不应把一次性 URL 或内部 Thread ID 当作操作入口。
- 如何验证：文档链接检查、任务定向测试、项目级检查和 ZC-104 范围的 open-code-review；真实 Browser 端到端矩阵仍由 ZC-105 承担。

## 测试方案

### Interactive Core

- Skill 全量 catalog、能力门禁、启停、armed Skill 清理、失败保持和 generation 竞态。
- 既有 command、Thread、Run、Interaction 契约回归，确认新增 Skill 项不改变 TUI 行为。

### Web Adapter

- 普通输入、Slash、`//`、未知命令、command menu selection 都只产生预期 Core intent。
- `present/request-handoff/request-exit` 三类 Result 映射；Browser 不会递归 handoff。
- Thread 从 `null → id → null` 的 lifecycle 去重报告；active Run/Interaction 禁止切换与归还。
- approval feedback、全部 question answers、stale request draft 清理。
- 流式快照一帧最多发布一次，connection/Interaction/leaving 可立即发布；close 后无事件。

### Bootstrap 与 lifecycle

- fragment 清除发生在 socket 创建前；只接受精确 loopback endpoint。
- accepted 前不连 Agent，active 前不启用 UI；initial Thread 成功/失败都随 ready 报告最终值。
- acquire holder 不匹配、ready timeout、乱序帧、Browser close、shutdown、release、exit requested 全部走一次 cleanup。
- exit handler 等待 owner，重复 exit 不重复调用；恢复超时保持 TUI 锁定并继续后台查询。

### React presentation

- 空首页、恢复历史、流式 Assistant、每次独立 Tool、completed/cancelled/failed 状态。
- desktop sidebar、mobile drawer 的 DOM 状态；390px 下没有固定宽度控件撑破 root。
- model/Skill/MCP/status/help panel 的 loading/empty/error/disabled 状态。
- dynamic approval、multi-question/multi-select/other、deadline、重复提交锁定。
- Markdown GFM、非法 scheme、raw HTML、Tool output 和用户输入均不能生成可执行 DOM。
- keyboard、focus restore、aria label/live region、reduced motion class/token。

## 可观察验收

- 从空首页发送第一条消息后出现新 Thread，Timeline 流式更新，返回 TUI 后恢复同一 Thread；清空后返回则恢复空首页。
- Thread、模型、Skill 和 MCP 的所有动作都能在 Web 使用，并可从测试证明它们进入共享 `InteractiveIntent`，Web 代码没有平行 RPC/command switch。
- 所有当前已协商 Slash Command 与 TUI 产生相同 semantic result；`/web` 在 Browser 按 capability 隐藏，`/quit` 能经 Coordinator 正常退出 Harness。
- Tool 可逐项折叠；Markdown 支持任务要求的 GFM，但插入的 raw HTML/script、非法链接和远端图片不会执行或自动加载。
- Approval 只展示服务端允许的 decision；Question 可一次回答所有单选、多选和 other 项，timeout 后不能再提交。
- active Run/Interaction 时 Thread 切换和返回 TUI 有明确禁用原因；取消后恢复可用。页面关闭/刷新会结束本次 handoff，不自动重连。
- 1440×900 与 390×844 的浅/深色页面中，顶栏、Timeline、Interaction 和 composer 不重叠，长文本/Tool 输出不撑破 viewport，键盘焦点清晰可见。
- Server 只服务 HTML、JS、CSS 与当前 handoff lifecycle 白名单；HTML/CSP 不允许 inline script/style，页面和错误信息不泄漏 attachment credential。

## 非范围

- 不实现 settings、permissions、任意 TOML 编辑、API Key/Header/环境变量编辑。
- 不实现远程 Web、登录、多租户、daemon discovery、跨机器访问或 attachment URL 输出。
- 不实现刷新后恢复 active Run、Event replay、离线队列或自动重连。
- 不改变 Protocol v3 的业务方法、Run/Event/Interaction 数据形状；这里新增的 `active/exit.requested` 仅属于 CLI 内部 lifecycle。
- 不改变 TUI 的视觉布局、快捷键或现有产品语义；共享 Skill seam 只补能力，不给 TUI 自动增加启停 UI。
- 不在 ZC-104 承担 ZC-105 的真实浏览器端到端矩阵、安装包或发布流程。

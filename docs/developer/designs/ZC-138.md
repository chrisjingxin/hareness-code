# ZC-138：安全初始化已有空文件设计

> 原始需求：[ZC-138](../tasks/ZC-138.md)

## 通俗问题说明

Harness 已经把“创建新文件”和“修改已有文件”分成两条安全路径：`write_file` 只创建不存在
的文件，`edit_file` 必须先读取已有文件，再用当前 Thread 的 Snapshot 修改模型实际见过的
内容。两条规则分别成立，但在目标文件已经存在且内容为空时会形成死角：`write_file` 因目标
存在而拒绝，`edit_file` 又因 `old_string` 为空而拒绝。

本设计不增加第三个写工具，也不让空字符串成为一般插入位置。唯一新增语义是：

```text
read_file 证明“这个已有文件的完整文本仍然为空”
  → edit_file(snapshot_id, old_string="", new_string="初始内容")
  → 把整个空文档替换为初始内容
  → 展示有界 diff 预览，用户仍可允许或拒绝
  → compare-and-replace 提交
  → 重读实际文件并返回新 Snapshot
```

因此，空 `old_string` 不是“在文件开头插入”，而是“只在当前文档恰好为空时，替换整个空
文档”。同一个调用用于非空文件时必须拒绝且零写入。

## 实施前已确认现状

- `CanonicalEditFileSchema` 已固定为
  `file_path + snapshot_id + old_string + new_string`，主 Agent、declarative 子 Agent 和
  inline worker 通过同一 `FileToolContract` 使用它。
- `read_file` 可以为零字节文件和只含 UTF-8 BOM 的空文本建立 Snapshot。空文档没有源行，
  因而其 `seen_lines` 为空；Snapshot 仍绑定 Thread、canonical path、backend identity、
  完整字节 hash 和文本元数据。
- `_prepare_edit()` 在本任务实施前会在解析 Snapshot 前直接拒绝空 `old_string`，所以无法利用空文档的
  完整版本证明。
- `write_file` 已使用 create-if-absent，目标存在时返回 `FILE_ALREADY_EXISTS`；该行为是
  用户防覆盖边界，不应为本功能放宽。
- `FileMutationService` 已固定 current/proposed、expected identity 和完整参数指纹，生成
  最多 200 行、16 KiB 的有界 diff 预览，并在批准后执行一次性 CAS commit。
- `edit_file` 提交后已经重读实际内容，按实际版本计算 `changed_range`、建立新 Snapshot，
  并沿用有界局部窗口、diagnostics 和 `POST_WRITE_DRIFT` 语义。

## 设计决策

### 复用 `edit_file`，不新增初始化工具

`edit_file` 保持现有参数形状。模型先读取空文件，然后提交：

```text
edit_file(
  file_path: string,
  snapshot_id: string,
  old_string: "",
  new_string: string,
)
```

仅当以下条件全部成立时，空 `old_string` 才表示初始化：

1. Snapshot 能在当前 Thread、路径和 backend 下解析；
2. backend 当前完整文本仍与 Snapshot identity 一致；
3. Snapshot 的 `line_count == 0`，且当前 `TextDocument.content == ""`；两者经完整 identity
   校验绑定到同一版本；
4. `new_string` 规范化后不等于当前内容，并满足单参数与完整 mutation 的硬上限；
5. Policy/Approval 允许该次 `edit_file`；
6. backend 能以 prepare 时的 expected identity 执行 compare-and-replace。

这里的“空”按解码后的规范文本判断。只含 UTF-8 BOM 的文件内容也是空文本；初始化继续保留
BOM 和原文件 mode。空文件没有可授予的源行，所以此分支不伪造 `seen_lines`；空 Snapshot
本身已证明模型看到了完整的零行文档，内容 identity 校验替代普通替换的行区间校验。

不新增 `initialize_file`，原因是它会把同一个用户结果扩展为 `write_file`、`initialize_file`、
`edit_file` 三选一，还要复制工具目录、Policy、并发、审批和子 Agent 接入。复用受限
`edit_file` 可以保留一条 mutation pipeline，并让参数 fingerprint 自动覆盖本次初始化的全部
模型输入。

### 非空文件仍要求非空精确原文

当 `old_string == ""` 但 Snapshot 对应的当前文档非空时，返回 `INVALID_EDIT`。实现不得调用
`str.find("")`、不得选择文件开头或结尾，也不得进入一般唯一匹配和 `seen_lines` 判断。

错误判断顺序必须保留版本事实：

- 空 Snapshot 对应的文件在 prepare 前已变为非空，返回 `STALE_FILE`；
- 调用者读取的本来就是非空当前版本，却提交空 `old_string`，返回 `INVALID_EDIT`；
- 空文件以 `new_string=""` 初始化，返回 `NO_CHANGES`；
- `new_string` 或拟议完整内容超过既有硬上限，返回既有大小错误并零写入。

普通非空 `old_string` 完全沿用 ZC-131 的唯一精确匹配和已读范围校验，不增加一般插入、
zero-width range、`replace_all` 或 `edits[]`。

### 审批展示是有界预览，批准仍绑定完整计划

初始化与普通编辑共用 `FileMutationService.prepare()`。完整 current/proposed 内容、expected
identity 和 `mutation_fingerprint("edit_file", args)` 仍保存在一次性 prepared plan 中；批准后
提交的不是审批框里可见的文本片段，而是该指纹绑定的完整 proposed content。

审批描述展示路径、操作、总增删行数和最多 200 行、16 KiB 的 unified diff 预览。超过上限时
必须明确标记省略，但 `approval_preflight()` 仍成功，表现层继续提供允许/拒绝选项；终端高度
造成的隐藏也不改变这一行为。审批文案不得再声称可见预览就是完整拟议内容，应明确：

```text
以下是拟议内容的有界 diff 预览；批准将提交本次调用已固定的完整拟议内容。
```

预览截断不是 mutation 错误，也不新增 `APPROVAL_DIFF_TOO_LARGE`。参数指纹、Snapshot、
Policy、输入/文件大小硬上限和 CAS 仍是执行边界；其中任一失败都保持零写入。计划无论提交
成功、冲突或 I/O 失败都只消费一次，同一批准不能重放。

### 提交和结果不增加第二种形状

初始化仍是 `MutationOperation == "edit"`，通过
`compare_and_replace_text(path, expected_identity, proposed_content)` 提交。`write_file` 继续只走
create-if-absent，不接受 Snapshot，也不覆盖已有空文件。

成功结果沿用现有 `edit_file` 形状，不增加 `initialize_file` 专用响应：

- `snapshot_id` 绑定提交后实际重读内容；
- `changed_range` 从空文本到实际内容计算，首个新增范围从第 1 行开始；
- `shown_lines` 和 `content` 仍受 200 行、32 KiB 结果窗口限制，只有完整显示的源行进入新
  Snapshot 的 `seen_lines`；
- diagnostics 仍是提交后的有界只读摘要；
- 保存钩子改变拟议内容时沿用 `POST_WRITE_DRIFT`，后续只能使用实际 Snapshot。

空文件没有既有换行风格；`new_string` 继续使用当前 edit normalization，CRLF/CR 输入在没有
既有风格时规范为 LF。只含 BOM 的空文本保留 BOM，文件权限由 backend 原有 replace 路径保留。

## 目标流程

```text
edit_file args
  → 校验 canonical keys、路径、Snapshot ID、参数类型与大小
  → 计算完整参数 fingerprint；复用或拒绝已消费计划
  → 在当前 Thread/path/backend 解析 Snapshot
  → 读取 backend 当前完整 TextDocument，并校验 Snapshot identity
  → old_string 为空？
       ├─ 当前规范文本为空：proposed = normalized new_string
       └─ 当前规范文本非空：INVALID_EDIT，零写入
  → proposed no-op / mutation 大小校验
  → 固定 prepared plan 与有界 diff 预览
  → Policy / Approval（预览截断仍可允许或拒绝）
  → 以 expected identity compare-and-replace
  → 重读实际内容，计算 changed_range，创建新 Snapshot
  → 返回有界上下文、diagnostics 或 post-write drift
```

## 关键 invariant

1. **创建边界不变**：`write_file` 永远 create-only；已有文件无论是否为空都不能通过它覆盖。
2. **空匹配只代表空文档整体**：空 `old_string` 只在 Snapshot 和当前内容都为空时有效，绝不
   表示非空文件中的位置。
3. **Snapshot 作用域不变**：Thread、path、backend 和完整内容 identity 任一不匹配都不能
   prepare 可执行计划。
4. **零行不伪造已读范围**：空文档无需也不得制造虚拟源行；初始化的 prior-read 证明来自空
   Snapshot 的完整 identity。
5. **批准绑定完整拟议内容**：有界 diff 只是预览；真正授权对象由 prepared plan 和完整参数
   fingerprint 固定，改参后新旧计划同时失效。
6. **CAS 边界不变**：批准到提交之间文件变化返回 `COMMIT_CONFLICT`，不支持安全 CAS 的
   backend 返回 `BACKEND_CAS_UNSUPPORTED`。
7. **实际落盘才是结果**：新 Snapshot、changed range 和后续可编辑行只依据 commit 后重读。
8. **接口唯一**：不新增工具名、Protocol 方法、兼容 alias、一般插入语义或平行 mutation
   service；主 Agent 和所有子 Agent 共享同一 schema 与实现。

## 公开错误模式

| code | 本功能中的触发条件 | 唯一恢复动作 |
| --- | --- | --- |
| `INVALID_EDIT` | 当前非空版本使用空 `old_string` | 从已读内容复制非空且唯一的 `old_string` |
| `NO_CHANGES` | 空文件的 `new_string` 仍为空 | 不再重试相同调用 |
| `SNAPSHOT_REQUIRED` / `SNAPSHOT_EXPIRED` | 缺少或已淘汰空文件 Snapshot | 在当前 Thread 重新读取目标文件 |
| `SNAPSHOT_SCOPE_MISMATCH` | Snapshot 属于其他 Thread、路径或 backend | 在当前 Thread 重新读取目标路径 |
| `STALE_FILE` | 空 Snapshot 后文件已变化 | 重新读取当前文件后按其实际内容编辑 |
| `EDIT_TEXT_TOO_LARGE` | 单参数或拟议完整内容超过既有硬上限 | 缩小本次初始内容；不得以审批预览上限代替硬上限 |
| `COMMIT_CONFLICT` | 批准后、CAS 前文件 identity 变化，或计划已消费/改参 | 重新读取并形成新审批 |
| `BACKEND_CAS_UNSUPPORTED` | backend 不能安全 compare-and-replace | 切换到支持该 contract 的执行模式 |
| `COMMIT_FAILED` | backend I/O 或提交后重读失败 | 检查当前状态后重新读取 |

`INVALID_EDIT` 需要补充稳定短消息和唯一下一步；其余 code 沿用 ZC-131，不为初始化增加同义
错误码。

## 测试与验收

### Contract 回归

- 零字节文件先读后以空 `old_string` 写入初始内容，返回实际 Snapshot 和正确
  `changed_range`，新 Snapshot 可直接继续普通编辑。
- 只含 UTF-8 BOM 的空文件可初始化并保留 BOM；本机文件 mode 保持不变。
- 非空文件即使已完整读取，也不能以空 `old_string` 初始化；文件字节不变并返回
  `INVALID_EDIT`。
- 空 Snapshot 在 prepare 前变为非空返回 `STALE_FILE`；审批后变化返回
  `COMMIT_CONFLICT`，恢复原样后旧调用仍不能重放。
- 跨 Thread/path/backend、Snapshot 过期、空到空 no-op、单参数和 mutation 超限全部零写入。
- 远端 provider 有原生 CAS 时走同一 edit；只有完整读取但没有 CAS 时返回
  `BACKEND_CAS_UNSUPPORTED`。

### Approval 与运行时回归

- 初始内容产生的 diff 小于上限时显示新增内容和总行数。
- diff 超过 200 行或 16 KiB 时显示明确截断标记，`approval_preflight()` 仍为 true，允许/拒绝
  选项不因预览长度消失。
- 同一 Tool Call 在审批后修改 `new_string`，原计划和新参数都返回 `COMMIT_CONFLICT`。
- 主 Agent、declarative 子 Agent 和 inline worker 看到相同 `edit_file` schema；提示词明确
  “空文件先读后以空 `old_string` 初始化”，不引导模型改用 `write_file` 覆盖。

### 弱模型证据

ZC-133 在实施前已有 `empty-file-insert` fixture，但 exact-string simulator 会把空 `old_string`
判为非法。本任务已让 replay、真实模型 prompt 与 simulator 携带生产必需的 `snapshot_id`，并让
该 fixture 反映受限空文档语义，同时保持非空空匹配为安全失败。由于
模型提示和允许值发生变化，应在用户已明确授权真实企业 Profile 时复用 ZC-131 的 opt-in
评测；没有授权或凭据时只运行离线 fixture/replay，并在 Task 中明确记录真实评测未运行，
不得伪造通过。

## 非范围

- 不支持在非空文件开头、结尾或任意位置使用空 `old_string` 插入。
- 不引入显式 insert action、zero-width range、按行编辑、批量 `edits[]` 或 `replace_all`。
- 不改变 `write_file` create-only、Snapshot 生命周期、审批模式、Protocol v3 或 TUI
  Interaction 数据形状。
- 不解决外部进程恰好发生在本机最终 CAS 检查与 rename 之间的已知残余竞态。
- 不自动 formatter，不编辑 Notebook、二进制、图片、PDF 或不可无损解码文本。

## 风险与退出条件

- 弱模型可能把空 `old_string` 误用于普通文件；稳定 `INVALID_EDIT` 和单一步骤提示必须让它
  回到“复制非空原文”，不能静默解释为插入。
- 超过 64 KiB 的初始 `new_string` 仍受单参数硬上限约束；需要更大初始化不是放宽预览或 CAS
  的理由，未来只有在真实指标证明必要时再单独调整工具输入边界。
- 如果真实 Profile 评测显示受限空字符串仍显著诱发非空文件误用，停止切换生产语义并回到
  Design 重新评审；不得现场新增第二个初始化工具或兼容分支。

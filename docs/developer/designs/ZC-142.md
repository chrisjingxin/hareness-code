# ZC-142：工作区外目录信任授权设计

> 原始需求：[ZC-142](../tasks/ZC-142.md)

## 通俗问题说明

现在只要文件工具碰到项目目录以外的路径，一律报错，用户没有任何补救手段。想让 Agent 读一下隔壁
仓库、读 `~/.harness/config.toml`、把产物写到共享目录，都只能退出进程换 `--cwd` 重开。

期望的效果和 Claude Code 一致：Agent 第一次碰到外部路径时，弹一张卡片问“是否把 `D:/data` 加入
工作区”。用户同意后，这个目录就和项目目录完全等价，后续读写不再有边界限制，也不再重复询问。

```text
read_file("D:/data/app.toml")
  → 该路径不在任何允许根内
  → 弹出目录信任卡片：待信任目录 D:/data
  → 用户选择“允许 / 拒绝”
  → D:/data 成为额外工作根
  → 本次读取成功，后续该目录下的读写按普通工作区规则处理
```

关键取舍：**被授权的是“目录”，不是“某个工具的某次调用”**。授权之后不存在“工作区内”和“工作区外”
两套读写规则，只有一套；边界判定只回答“这个路径属不属于某个允许根”。

## 已确认现状

- [workspace_boundary.py](../../../packages/agent/harness_agent/policy/workspace_boundary.py) 的
  `WorkspacePathPolicy._resolve_path_string` 要求路径以 `/` 开头，拼接到唯一 workspace 后
  `resolve()` 再 `relative_to()`；任何越界路径、`..` 段、UNC 路径一律抛 `ValueError`，转成
  `status="error"` 的可纠正 ToolMessage。**读与写都没有放行分支。**
- 同一校验被 `allows_approval()` 复用挂在 HITL 的 `when` 上，因此越界调用连审批卡片都不会出现；
  模块 docstring 明确写着“审批只能决定工作区内的已授权操作”。
- `_backend_path()` 把校验后的宿主路径转回 `/rel` 形式交给 backend，模型可见路径与 backend 路径
  当前是同一套 `/` 虚拟命名空间。
- 单根假设贯穿全栈：deepagents `FilesystemBackend.cwd`、`LocalShellBackend(root_dir=workspace)`、
  [text_backend.py](../../../packages/agent/harness_agent/threads/text_backend.py) 的
  `LocalTextMutationBackend._root`、`AgentHost._workspace`、执行资源池 fingerprint（含 workspace 哈希）、
  CLI `WorkspaceExplorer`。
- `CompositeBackend` 已有按前缀路由的能力，当前只用于挂载只读的 `/.harness`，是多根的现成扩展点。
- HITL 集合 `_DEFAULT_HITL_TOOLS` / `_AUTO_EDIT_HITL_TOOLS` / `_AUTO_HITL_TOOLS` 只包含
  `execute`、写文件工具、`task`、`web_fetch`、`monitor`、`task_stop`；**只读文件工具不在其中**，
  且 `interrupt_on_for_approval_mode` 对 `plan` 和 `yolo` 直接返回 `None`（不建 HITL 通道）。
- 审批载荷由 `RunCoordinator._collect_serial_approvals` 组装，decisions 固定五项；
  `presentation` 从 run 级 `ApprovalPresentationStore` 按“工具名 + 参数指纹”取回，
  协议侧 `approvalRequest.payload.presentation` 目前只允许 `fileDiffPresentation`。
- `_record_approval_rule` 在 `approve_thread` / `approve_project` 时生成 `PermissionRule`；
  文件类工具生成的是 `resource="*"` 的工具级通配规则。
- `trust_gate.py` 的 `trusted_directories` 管的是“当前工作区本身可不可信”（决定能否切到 auto/yolo），
  与本设计的“额外工作目录”是两套独立概念，不合并、不互相推导。
- 系统提示词 [system_prompt.md](../../../packages/agent/harness_agent/runtime/prompts/system_prompt.md)
  第 21–22 行与 `_with_execution_context()` 第 419–420 行明确禁止盘符路径、声明越界不可通过审批绕过。
- `RunContextSnapshotMiddleware` 已经在模型调用边界动态追加审批模式事实，是“把可变事实告诉模型”的
  既有做法，额外根清单可复用同一 seam。

## 目标与非目标

### 目标

- 文件工具访问未授权的外部绝对路径时，产生一张专门的目录信任审批卡片，而不是直接报错。
- 用户授权后该目录成为额外工作根，读写与主工作区完全等价，同目录后续访问不再询问。
- 目录信任只保留“允许（本会话信任）/ 拒绝”两个决策；允许即注册会话级额外根，不落盘。
- 中途新增的根立即生效，不重编译 Agent 图、不使执行资源池失效。
- 主工作区内的既有行为（`/` 虚拟路径写法、审批矩阵、快照与 CAS）逐字节不变。

### 非目标

- 不做 `/add-dir` 斜杠命令，也不做 `additional_directories` 启动参数或 config.toml 字段；本期唯一
  入口是审批卡片。
- 不改 `execute` 的路径策略，shell 的 cwd 仍是主工作区。
- 不引入 OS 级沙箱；边界仍是应用层 containment。
- 不改 `PermissionRule` 的匹配语义，也不在本设计内修复文件类工具生成 `resource="*"` 的既有粒度问题
  （与本功能正交，另行处理）。
- 不支持在远端沙箱模式下扩根（该模式本就跳过 `WorkspaceBoundaryMiddleware`）。
- 不提供撤销已信任目录的界面；用户手工编辑 `.harness/settings.json` 即可。

## 目标流程与职责

```text
工具调用（file_path 可能是 / 虚拟路径或 OS 绝对路径）
  → WorkspaceRootRegistry.resolve()：判定属于主根 / 已信任额外根 / 未授权外部路径
  ├─ 主根            → 现有行为，完全不变
  ├─ 已信任额外根    → 改写为内部挂载路径 /@ext/<root-id>/<rel>，交给多根 backend
  └─ 未授权外部路径  → HITL 预检返回“需要审批”
        → approval_details 组装 directory_trust 载荷
        → RunCoordinator 发出 interaction.directory_trust（独立交互类型，不复用审批五项决策）
        → 用户决策
           ├─ allow_session  → 注册到会话级根集合（卡片文案为“允许”）
           └─ deny           → 可纠正 ToolMessage
        → 执行时 registry 已包含该根，走上面的“已信任额外根”分支
```

职责边界：

- `WorkspaceRootRegistry` 是唯一的“哪些目录被允许”事实源，边界中间件、多根 backend、审批记录三处
  共用同一实例，不各自维护副本。
- `WorkspaceBoundaryMiddleware` 只做“判定 + 路径改写 + 拒绝”，不负责发起交互。
- 交互由既有 HITL 串行收集通道发起，`RunCoordinator` 在决策回写时调用 registry 注册，不新增第二条
  审批链路；目录信任是与 `approval`、`question` 平级的独立交互类型，共享同一请求/响应基础设施。
- Protocol 只描述“待信任的目录是什么、因为哪个工具的哪个路径”，不携带策略结论。

## 路径寻址与判定规则

模型对外部路径使用**真实绝对路径**（`D:/data/app.toml`、`/home/me/lib/x.py`）；`/@ext/<root-id>/...`
是纯内部形式，模型和用户都看不到。

判定顺序（`WorkspaceRootRegistry.resolve(raw_path)`）：

1. `/.harness` 前缀 → 只读虚拟命名空间，行为不变。
2. 命中任一**已注册额外根**的绝对路径前缀 → 外部根路径。
3. 以 `/` 开头 → 按主根虚拟路径解释（保持现有全部行为）。
4. Windows 盘符绝对路径，或 POSIX 绝对路径且不满足第 3 条的可用解释 → 未授权外部路径，进入信任流程。

规则说明与取舍：

- **额外根前缀优先于主根虚拟解释**。POSIX 下存在理论歧义：主根为 `/home/me/proj`、额外根为 `/data`
  时，`/data/x` 既可解释为 `<主根>/data/x` 也可解释为 `/data/x`。取“额外根优先”是因为额外根是用户
  显式授权的少量目录，且必须可达；注册时如检测到 `<主根>/<同名子路径>` 存在，目录信任卡片与注册结果
  中显式提示该遮蔽事实。Windows 盘符路径不存在此歧义。
- 判定前统一规范化：分隔符转 POSIX、Windows 上大小写折叠、`realpath` 解析符号链接。**注册与匹配
  必须使用同一个规范化函数**，否则大小写或短名差异会造成绕过。
- `..` 段、UNC 路径在任何形态下继续硬拒绝，不因目录已信任而放宽。
- 已信任根内的符号链接若 `realpath` 后落在所有允许根之外，仍然拒绝——信任是对“目录子树”的授权，
  不是对“可以从该目录跳出去”的授权。
- 待信任目录 = 目标文件所在目录；目标本身是目录时（`ls`、`glob`/`grep` 的 `path`）即该目录本身。
  信任是递归的：信任 `D:/data` 等于信任其全部子目录。

拒绝注册为额外根（即使用户在卡片上选择同意也不注册，改为拒绝并说明原因）：

- 文件系统根 `/`、Windows 盘符根 `D:\`；
- 用户 home 目录本身（其子目录可以）；
- `/etc`、`C:\Windows`、`C:\Program Files` 等系统目录；
- 不存在的目录、非目录、UNC 路径；
- 主工作区内部路径（本就无需信任）。

嵌套处理：新根落在已有根内则不重复注册；新根包含已有根则吸收，避免根集合无限增长。

## WorkspaceRootRegistry 公开 interface

```python
@dataclass(frozen=True)
class WorkspaceRoot:
    """一个被允许访问的目录根。"""
    root_id: str        # 主根固定为 "primary"；额外根为 realpath 的稳定短哈希
    path: Path          # 规范化后的绝对真实路径
    scope: RootScope    # "primary" | "once" | "session" | "project" | "user"

@dataclass(frozen=True)
class ResolvedPath:
    """路径判定结果。"""
    root: WorkspaceRoot
    backend_path: str   # 主根为 /rel；额外根为 /@ext/<root-id>/<rel>
    display_path: str   # 面向模型与用户的路径：主根为 /rel，额外根为真实绝对路径

class WorkspaceRootRegistry:
    def resolve(self, raw: str, *, run_id: str | None = None) -> ResolvedPath: ...
    def trust_candidate(self, raw: str) -> TrustCandidate: ...      # 计算待信任目录并校验可注册性
    def trust(self, directory: Path, scope: RootScope, *, run_id: str | None = None) -> WorkspaceRoot: ...
    def roots(self) -> tuple[WorkspaceRoot, ...]: ...
    def to_display(self, backend_path: str) -> str: ...             # /@ext/... 回显为真实绝对路径
```

`resolve()` 对未授权外部路径抛 `ExternalPathNotTrusted(candidate)`，携带待信任目录，供预检和审批
描述使用；对非法路径继续抛现有 `ValueError`。

生命周期与注入：

- registry 由 `AgentHost` 创建并持有，启动时加载 project/user 层持久化根；主根来自 `AgentHost._workspace`。
- 按引用注入 `WorkspaceBoundaryMiddleware`、多根 backend 解析器、`LocalTextMutationBackend`、
  `RunCoordinator`。**registry 内容不参与执行资源池 fingerprint**，因此中途加根不会导致图重编译或
  池失效——这是“加根立即生效”的关键。
- `once` 作用域的授权按 `run_id` + 目录记录，单次消费，run 结束清理。同一批次里对同一目录的第二次
  调用会再次询问，这是可接受且明确的行为。
- 子 Agent 共享同一 registry 的**只读视图**：继承已信任根，但不能发起信任审批（子图不经过主图 HITL），
  未授权外部路径在子 Agent 中仍硬拒绝。

## 多根 backend 与 mutation 通道

- 读取/列举/搜索：在现有 `CompositeBackend` 之上增加运行时解析的额外根路由。路由不能在构造时固定
  （根会中途新增），因此按 `/@ext/<root-id>/` 前缀在调用时向 registry 查根，再委派给对应根的
  `LocalShellBackend(root_dir=root.path, virtual_mode=True)`（按 root_id 懒创建并缓存）。
- 写入/编辑/删除：`LocalTextMutationBackend` 增加按 root_id 选根的能力，`_resolve()` 的
  “拼接后必须 `relative_to(root)`”不变，只是 root 由 registry 决定。原子写、`O_NOFOLLOW` 语义、
  同目录 rename 与 CAS 全部保持原样。
- 快照与 CAS 键使用 backend 路径，`/@ext/<root-id>/...` 天然带根身份，不同根下的同名相对路径不会
  互相覆盖。
- **回显投影**：所有面向模型和用户的路径（工具结果、错误文案、目录信任载荷的 `target_path`、
  diff header）必须经 `to_display()` 转回真实绝对路径；`/@ext/...` 不得泄漏到进程之外。

## 审批交互与 Protocol 设计

### HITL 通道调整

- 只读文件工具（`ls`、`read_file`、`glob`、`grep`）加入 HITL 集合，预检**仅当**该调用命中未授权外部
  路径时返回“需要弹窗”；工作区内读取继续不进审批，行为不变。
- `plan` 模式从“返回 `None`”改为返回只读工具的 interrupt_on 集合，配同一预检。写入类工具不进 plan
  的 HITL 集合，仍由 `PlanModeMiddleware` 先行拒绝，不产生“批准了也执行不了”的假审批。
- `yolo` 仍不建 HITL 通道；外部路径由执行层自动授予 `session` 级根并记录日志。
- `_make_approval_preflight` 的第一步不再是“越界一律不弹窗”，改为：越界且**不可信任**（非法路径、
  不可注册目录）仍返回 False 由执行层硬拒绝；越界且可信任则返回 True 进入信任审批。

### Protocol 变更

目录信任**不复用** `interaction.approval` 的五项决策与 presentation 机制，新增与 approval/question
平级的独立交互类型 `interaction.directory_trust`（protocol v3 minor bump 3→4）：

```ts
// 请求载荷（全部必填，非空字符串）
type DirectoryTrustRequest = {
  interrupt_id: string
  directory: string        // 待信任目录的真实绝对路径
  target_path: string      // 触发本次请求的完整目标路径
  tool_name: string        // 发起访问的工具名
  access: "read" | "write" // 读或写意图，决定卡片文案
  shadows_workspace: boolean // 是否会遮蔽主工作区内的同名路径
  decisions: DirectoryTrustDecision[]
}

// 独立决策枚举，不使用审批的五项；只保留允许（本会话信任）与拒绝
type DirectoryTrustDecision = "allow_session" | "deny"

// 响应
type DirectoryTrustResponse = { decision: DirectoryTrustDecision }
```

约束：

- payload `additionalProperties: false`；`access` 为枚举；`directory`、`target_path` 等字符串字段
  均要求非空。
- `approvalRequest.payload.presentation` 不再承载目录信任，回退为可选的 `fileDiffPresentation`；
  旧 `directoryTrustPresentation` oneOf 分支从 schema 删除，不留双路径。
- 能力协商：客户端 initialize 的 `capabilities.handles` 必须声明 `"directory_trust"`；未声明时
  host 端不发送该交互，直接按拒绝处理（fail-closed）。
- 超时、取消、连接断开一律响应 `deny`；`approve_thread` 等旧枚举值作为 decision 被协议校验拒绝。
- CLI/TUI/Web 各自新增独立分支，不与审批卡片共用文案：TUI/Web 卡片标题“目录信任”、问题
  “是否将此目录加入白名单？”，选项“允许 / 拒绝”，
  点击即刻回写决策（无额外输入框）。

### 决策落地

`RunCoordinator` 用独立的 `_record_directory_trust` 方法处理目录信任决策，调用
`registry.trust(directory, "session")` 而不是生成 `PermissionRule`：`allow_session` → `session`。
审批侧 `_record_approval_rule` 只处理 `approve_thread` / `approve_project`，目录信任不经过它；
文件 diff 与其它工具的既有规则记录路径不受影响。

## 持久化与作用域

project 层 `.harness/settings.json` 新增与 `permissions` 并列的数组字段：

```json
{
  "permissions": ["Write"],
  "additional_directories": ["D:/data", "D:/code/shared-lib"]
}
```

- 读取合并顺序：system（只读）→ user → project，去重后与主根一起构成允许根集合。
- 写入只发生在 project 层，复用 `permission_rules.py` 中既有的“读现有 JSON → 保留其它字段 → 追加
  → 原子写”模式；不新造配置文件。
- 不进入 `config.toml`——那里只放审批模式与分类器，且项目级 config.toml 本就不受支持。
- 与 `trust_gate.py` 的 `trusted_directories` 互不影响：后者决定“当前工作区能否用 auto/yolo”，
  前者决定“哪些目录可访问”。文档中必须并列说明，避免用户混淆。

## 审批模式矩阵

| 模式 | 外部路径读 | 外部路径写 | 信任之后 |
| --- | --- | --- | --- |
| `plan` | 目录信任卡片（新增只读 HITL 通道） | 仍由 `PlanModeMiddleware` 拒绝，不弹窗 | 读按工作区内规则，写仍被 plan 拒绝 |
| `default` | 目录信任卡片 | 目录信任卡片，随后文件变更卡片 | 与工作区内完全一致 |
| `auto-edit` | 目录信任卡片 | 目录信任卡片，随后按 auto-edit 免弹 | 与工作区内完全一致 |
| `auto` | 目录信任卡片 | 目录信任卡片，随后进入四层过滤器 | 与工作区内完全一致 |
| `yolo` | 自动授予 session 级根，不弹窗 | 自动授予 session 级根，不弹窗 | 与工作区内完全一致 |

矩阵只描述“目录第一次被访问时怎么获得信任”。信任之后不存在第二套规则，一律回到既有模式矩阵。

## 关键 invariant

1. **单一事实源**：允许根集合只有 `WorkspaceRootRegistry` 一处；边界判定、backend 选根、审批记录
   共用同一实例，不存在第二份副本或推导结果。
2. **信任需要人工确认**：除 `yolo` 外，任何目录成为额外根都必须经过一次用户决策；模型输出、项目文件、
   工具结果都不能触发自动扩根。
3. **信任是目录级、递归、无读写区分**：授权后该目录子树与主工作区等价，不再区分越界读与越界写。
4. **主根行为不变**：所有 `/` 虚拟路径调用的解析结果、backend 路径、快照键与改造前完全一致。
5. **硬边界不放宽**：deny 规则优先、敏感路径写入仍强制弹窗、`..`/UNC/符号链接逃逸仍拒绝、
   `/.harness` 只读、系统目录与根目录不可注册。
6. **内部路径不外泄**：`/@ext/<root-id>/...` 只存在于 backend 与快照键中，任何面向模型或用户的
   输出都经 `to_display()` 投影为真实绝对路径。
7. **加根不重建运行时**：registry 不参与执行资源池 fingerprint 与图编译输入，中途加根立即生效且不
   打断进行中的 Run。
8. **子 Agent 只继承不扩张**：子图共享只读根集合，不能发起信任审批。
9. **fail-closed**：交互超时、连接断开、客户端未声明 `directory_trust` handles 能力、载荷缺失或
   畸形都视为拒绝（目录信任响应 `deny`），绝不默认信任。

## 错误与降级语义

| 情况 | 可观察结果 | 后续行为 |
| --- | --- | --- |
| 外部路径且目录可注册 | 目录信任卡片 | 按决策处理 |
| 外部路径但目录不可注册（根目录/系统目录/不存在） | 可纠正 ToolMessage 说明为何不能信任 | 不弹窗，硬拒绝 |
| 含 `..` 或 UNC 的路径 | 现有边界拒绝文案 | 不弹窗，硬拒绝 |
| 已信任根内符号链接逃逸到未信任位置 | 边界拒绝，说明 realpath 落在允许根外 | 硬拒绝 |
| 交互超时或客户端断开 | 目录信任视为 `deny`，审批视为 `reject` | 不注册，硬拒绝 |
| 子 Agent 遇到未授权外部路径 | 现有边界拒绝文案 | 硬拒绝，不弹窗 |
| 远端沙箱模式 | 无额外根概念 | 行为不变 |
| POSIX 下额外根遮蔽主根同名路径 | 卡片与注册结果显式提示遮蔽 | 按“额外根优先”执行 |

## 模型侧提示词

- `_with_execution_context()` 与 `system_prompt.md` 中“必须使用 `/` 虚拟路径”“禁止盘符路径”
  “越界不能通过审批绕过”的表述需改写为：主工作区用 `/` 虚拟路径；确需访问工作区外文件时使用真实
  绝对路径，会触发一次目录信任确认。
- 已信任的额外根清单是会话内可变事实，按 `RunContextSnapshotMiddleware` 的既有做法在模型调用边界
  动态追加，不写进静态系统提示词（否则中途加的根模型看不到）。

## 可观察验收与测试

- **Python 边界**：主根 `/` 路径解析结果与改造前逐项一致；外部路径未授权时抛可信任候选、非法路径
  仍抛 `ValueError`；已信任根的 backend 路径映射与回显投影双向正确；符号链接逃逸、`..`、UNC、
  系统目录注册全部拒绝；Windows 大小写折叠与 POSIX 遮蔽用例。
- **Registry**：五种作用域的注册与查询、once 单次消费、嵌套吸收、project 落盘与重载、加根后
  fingerprint 不变。
- **审批链路**：五种模式 × 外部读/写的预检结论；plan 只读 HITL 通道存在且写仍被拒绝；yolo 自动授予；
  `allow_session` 决策回写产生 session 效果；超时与断连回退 `deny`。
- **多根执行**：外部根下的 read/ls/glob/grep 与 write/edit/delete 全链路；两个根下同名相对路径的
  快照与 CAS 不串用；敏感路径写入在已信任根内仍弹窗。
- **Protocol**：`interaction.directory_trust` 独立请求/响应正反 fixtures（缺字段、额外字段、
  空字符串、`approve_thread` 等非本枚举 decision）；approval 不再接受 directory_trust presentation；
  生成的 TS 类型与 Python 载荷一致。
- **CLI**：TUI 与 Web 的目录信任独立卡片文案与选项、决策回写、超时/取消/未声明 handles 时
  fail-closed `deny`。
- **项目级**：`bun run typecheck`、`bun run test`、`cd packages/agent && .venv/bin/python -m pytest -q`、
  `bun run project:check`。

## 回滚思路

registry 为空额外根时，判定第 2 条永不命中，第 4 条把所有外部路径判为未授权，若同时把只读工具移出
HITL 集合并让预检对外部路径返回 False，即完全回到当前的硬拒绝行为。`interaction.directory_trust`
是独立请求方法，host 端停止发送后客户端不会再看到目录信任卡片；客户端不声明 handles 能力也会
fail-closed 为拒绝，无需改动前端。已落盘的 `additional_directories` 在回滚后被忽略而非报错。

## 附录：竞品对照（本方案取舍依据）

| 维度 | harness-code（现状） | claude-code | qwen-code | grok-build |
| --- | --- | --- | --- | --- |
| 外部读 | 全模式硬拒绝 | 弹窗可授权 | 降级为 ask | 全模式直接允许 |
| 外部写 | 全模式硬拒绝 | 弹窗可授权 | 降级为 ask | 弹窗 / 按模式放行 |
| 扩根交互 | 无 | 弹窗会话级扩根 + `/add-dir` 落盘 | 只能 `/directory add`，弹窗内无扩根选项 | 明确不支持 |
| 允许根来源 | 单一 cwd | cwd + `permissions.additionalDirectories` | cwd + `context.includeDirectories` | 单一 cwd + 可选 OS 沙箱 |
| 持久化位置 | 无 | 三级 settings 文件 | 项目/用户 settings.json | 按 cwd 的 permission.toml |

取舍：

- 采用 **claude-code 的“授权即扩根”语义**——用户同意后目录进入允许根集合，而不是生成一条目录级
  工具规则。理由是本仓库的边界判定发生在 backend 选根之前，扩根是唯一能让外部路径真正可达的方式；
  用规则表达会出现“规则允许但 backend 无法解析该路径”的割裂。
- 不采用 **qwen-code 的目录级 allow 规则**，也不采用其“弹窗里不给扩根入口”的做法——后者会迫使用户
  记住并手动执行命令，与本任务的产品目标相反。
- 不参考 **grok-build**：读全放行不符合本仓库既有的安全基线。

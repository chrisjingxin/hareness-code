# ZC-103：Interactive Core 与 TUI 迁移

原始需求：[ZC-103：提取共享交互内核并迁移 TUI](../tasks/archive/ZC-103-legacy.md)

相关方案：[ZC-102：单实例 Web Handoff 与 TUI 接管生命周期](ZC-102.md)

后续任务：[ZC-104：实现 Web UI Adapter 与 TUI 功能对齐](../tasks/ZC-104.md)

## 通俗说明

现在的 `TuiController` 同时做两类事情：一类是所有交互界面都必须一致的业务，例如发送消息、接收流式事件、处理审批和提问、恢复 Thread、选择模型、管理 Skill/MCP、解释 Slash Command；另一类只是终端界面自己的体验，例如 draft、光标、Prompt history、Picker 选中行、快捷键、滚动和 Tool 卡片展开。

如果 ZC-104 直接复用 `TuiController`，Web 会被迫理解 OpenTUI 状态；如果 Web 另写一套，Run、Interaction 和命令语义又会分叉。本任务把第一类逻辑提取为深模块 Interactive Core，以 `InteractiveController` 作为统一 interface，现有 TUI 迁移成第一个 Interactive Adapter：

```text
OpenTUI 输入 ─→ TUI Adapter ─┐
                            ├→ InteractiveController → AgentClient adapter → Python Host
未来 Web 输入 ─→ Web Adapter ─┘

InteractiveController snapshot
  ├→ TUI Adapter → OpenTUI presentation
  └→ Web Adapter → React DOM presentation（ZC-104）
```

改完后，TUI 的用户行为不变，但 Run、Timeline、Interaction、Thread、catalog 和 Slash Command 只剩一个 canonical 实现。ZC-104 只需要把浏览器动作映射成同一组 intent，并渲染同一份领域 snapshot。

术语固定如下：Interactive Core 是 TUI/Web 共用的进程内交互语义层；`InteractiveController` 是该层唯一对外 interface；TUI 与 Web 都是 Interactive Adapter。它们都不是持久化领域对象，不写入 SQLite，也没有独立 ID。持久化身份仍只有 project、thread 与 message；Web 接管生命周期继续使用 handoff。

## 已确认现状

- `packages/cli/src/tui/application/controller.ts` 约 1445 行，既直接调用 `AgentClient`，又维护 draft、Prompt history、菜单、Picker、Dialog、滚动请求和 Tool 展开状态。
- `state.ts` 的 Timeline、Run、Interaction 和 sequence reducer 已经不依赖 React/OpenTUI，可以直接迁移为共享实现，但 `TuiState`、`TuiSnapshot` 命名和 `threadId?: string` 仍绑定当前 TUI 形状。
- `commands.ts` 的 Registry、解析、capability/busy 可用性和未知命令建议已基本表现层无关；`command-dispatcher.ts` 的 `CommandResult` 仍以 TUI 执行副作用为前提，且 compact 的成功/失败 closure、MCP 分支和 Web callback 由旧 Controller 解释。
- `AgentClient` 已经 transport-neutral，stdio 与 WebSocket 共用同一实现；但当前 Controller 通过 EventEmitter、通用 `request()` 和类型断言建立测试 fake，依赖面不够明确。
- `app.tsx` 已正确保留终端尺寸、OpenTUI refs、textarea buffer、焦点和滚动，这些职责不应进入共享 module。
- 当前 Interaction 只展示 question 的第一题，approval 没有按服务端允许的 decisions 校验，`reject_with_feedback` 固定发送空反馈，也没有按 `timeout_ms` 收敛界面状态。这些语义若留到 adapter，会让 TUI/Web 再次分叉。
- Thread 恢复已经采用“RPC 全部成功后原子替换”的基本顺序，并用 epoch 避免部分 stale 结果；模型选择也已区分“当前 Thread 下一次运行”和“未来新 Thread 默认值”，迁移时必须保持。
- 当前测试覆盖 Controller 的 MCP、模型、Thread、Interaction、Web handoff 恢复和部分 OpenTUI 行为，但测试对象仍是 TUI 专用 snapshot；缺少完整 question schema、Interaction timeout、connection close、catalog 部分失败和 adapter 契约测试。

## 目标与关键 invariant

- `InteractiveController` 是 Interactive Core 唯一业务入口；TUI/Web Adapter 不直接调用 Run、Thread、模型、Skill、MCP、compact 或配置写 RPC。
- 外部 interface 固定为 `dispatch / getSnapshot / subscribe / close`。Run handle、Interaction resolver、epoch、timer、AgentClient EventEmitter 和 JSON-RPC 方法名都隐藏在实现内部。
- `currentThreadId` 在共享 snapshot 中始终是 `string | null`；`null` 明确表示空首页，不用 `undefined` 承载业务状态。
- 一次交互运行时最多一个 active Run、一个待处理 Interaction 和一个待确认的 destructive action；重复或 stale intent 不得绕过这些状态。
- Event 只接受当前 `(thread_id, run_id)`，按 sequence 丢弃重复/倒序帧；缺口产生脱敏 notice 后继续，唯一终态封口后不再更新该 Run。
- approval/question 完整保留 Protocol schema，adapter 只采集答案；允许的 decision、单选/多选、other answer、feedback、request ID 和 timeout 由共享 Controller 校验与收敛。
- Thread 切换、模型/Skill/MCP catalog 刷新和配置写入的晚到结果必须按 generation/revision 丢弃，不能覆盖新 Thread 或已关闭 Controller。
- Command Registry、解析、可用性和执行只有一条路径。未知 `/command` 不提交给模型，`//text` 只去掉一个前导 `/`。
- Catalog 的单项失败只影响对应 catalog，不清空 Timeline、当前 Thread、其他 catalog 或已选择模型。
- TUI adapter 只拥有表现状态；删除共享 module 后，业务复杂度会重新散落到 TUI 和未来 Web，证明该 module 具有实际 depth。
- 用户可见文案继续使用 Thread 与 handoff；不得把 Interactive Core 或 `InteractiveController` 误写成可恢复“会话”或新领域实体。

## Module 与 seam

### 目标文件结构

共享 module 从 `tui/` 下移到 CLI 顶层，避免未来 Web 反向依赖终端目录：

```text
packages/cli/src/interactive/
  controller.ts              # external interface、factory 和工作流 implementation
  types.ts                   # intent、result、snapshot、catalog 和 Interaction DTO
  state.ts                   # Timeline/Run/Event 的纯 reducer
  commands.ts                # Command Registry、解析、可用性和菜单领域项
  command-dispatcher.ts      # stable command ID → semantic operation
  runtime.ts                 # 脱敏运行环境和 /status 语义
  agent-port.ts              # InteractiveAgentPort 与 AgentClient production adapter

packages/cli/src/tui/application/
  adapter.ts                 # TUI 表现状态和 InteractiveResult 映射
  prompt-history.ts          # 终端 Prompt history 与 JSONL
  shortcuts.ts               # OpenTUI 键盘语义
```

实现时可在不扩大 interface 的前提下合并过小文件，但职责方向必须保持：`interactive/` 不依赖 `tui/`、`web/` 或 DOM，`tui/application/` 不依赖 `ipc/`。

### 依赖方向

```text
index.ts（composition root）
  → AgentClient
  → AgentClientInteractiveAdapter
  → createInteractiveController
  → createTuiAdapter / runTui

tui/presentation → TuiAdapterSnapshot
tui/application  → InteractiveController interface
interactive      → @za38/protocol + InteractiveAgentPort
interactive      ✕ tui / web / React / OpenTUI / DOM
```

`InteractiveAgentPort` 是内部 remote-owned seam：生产 adapter 包装 `AgentClient`，interface 测试使用内存 adapter。它不是让 UI 直接选择 transport 的扩展点，也不暴露底层 `request(method, params)`。

## `InteractiveController` interface

```ts
export interface InteractiveController {
  getSnapshot(): InteractiveSnapshot
  subscribe(listener: (snapshot: InteractiveSnapshot) => void): () => void
  dispatch(intent: InteractiveIntent): Promise<InteractiveResult | void>
  close(): Promise<void>
}

export type InteractiveControllerOptions = {
  agent: InteractiveAgentPort
  runtime: InteractiveRuntime
  initialThreadId?: string | null
  scheduler?: InteractiveScheduler
}
```

- `getSnapshot` 同步返回最近一次不可变 snapshot，供 `useSyncExternalStore` 和无渲染测试共用。
- `subscribe` 只发布新 snapshot；listener 在回调中取消订阅不影响当前发布。
- `dispatch` 是唯一行为入口，完成 intent 自身必须等待的工作后返回。后台 Run/Event 和 catalog 更新通过后续 snapshot 发布。
- `close` 可重复调用；停止接收 intent、使所有 generation 失效、卸载 Agent listener、清理 timer，并 fail closed 未完成 Interaction，但不关闭外层持有的 AgentClient/transport。
- Controller 关闭后的 `dispatch` 是无副作用 no-op，避免 React 卸载与异步回调竞争时产生未处理异常。

### Intent

Intent 使用稳定领域 ID，不把选中行、DOM event 或 OpenTUI key 传入共享 module：

```ts
export type InteractiveIntent =
  | { type: "input.submit"; value: string }
  | { type: "command.execute"; commandId: string; argument?: string }
  | { type: "run.cancel" }
  | { type: "catalog.refresh"; catalog: "threads" | "models" | "skills" | "mcp" }
  | { type: "thread.open"; threadId: string }
  | { type: "model.select"; profileId: string }
  | { type: "skill.arm"; skillId: string }
  | { type: "skill.clear" }
  | { type: "mcp.add"; input: InteractiveMcpInput }
  | { type: "mcp.remove"; name: string }
  | { type: "interaction.respond"; requestId: string; response: InteractiveResponse }
  | { type: "confirmation.resolve"; confirmationId: string; confirmed: boolean }
```

- `input.submit` 统一处理普通消息、Slash Command、未知命令和 `//` 转义。TUI/Web 不得在提交前各自再写一套解析分支。
- `command.execute` 用于命令菜单选择，只接受 snapshot 已发布的 canonical command ID；alias 只在文本解析入口归一化。
- catalog、Thread、模型、Skill 和 MCP intent 只携带稳定 ID/typed input；Controller 必须从自己的当前 snapshot 重新确认对象仍存在且可用，不能信任 adapter 回传完整 DTO。
- Interaction response 不携带 Protocol `request_id` 字段；Controller 用当前 request 组装 wire response，防止 adapter 产生身份不匹配。

### Result

绝大多数 intent 只更新 snapshot。只有必须由宿主或表现层完成的动作返回小型结果：

```ts
export type InteractiveResult =
  | { type: "present"; target: "threads" | "models" | "skills"; initialQuery?: string }
  | { type: "request-handoff"; threadId: string | null }
  | { type: "request-exit" }
```

- `present` 只要求 adapter 打开对应 Picker；items/loading/error 已位于共享 snapshot。query、选中索引、焦点和布局仍由 adapter 持有。
- `request-handoff` 由 TUI adapter 调用 ZC-102 的 `WebHandoffCoordinator.open`；共享 Controller 不依赖 Web module。
- `request-exit` 由当前宿主决定如何卸载/关闭；Controller 不销毁 Host。
- destructive command 的确认不是 closure 或回调，而是 snapshot 中的稳定 `confirmation`，adapter 通过 `confirmation.resolve` 回写。

## `InteractiveSnapshot`

共享 snapshot 只包含两个 adapter 都需要理解的事实：

```ts
export type InteractiveSnapshot = {
  readonly currentThreadId: string | null
  readonly activity: InteractiveActivity
  readonly activeRun: ActiveRun | null
  readonly timeline: readonly TimelineItem[]
  readonly interaction: InteractiveInteraction | null
  readonly confirmation: InteractiveConfirmation | null
  readonly lastRun: RunSummary | null
  readonly runtime: InteractiveRuntime
  readonly connection: InteractiveConnectionState
  readonly commands: readonly InteractiveCommandItem[]
  readonly catalogs: {
    readonly threads: LoadableCatalog<ThreadSummary>
    readonly models: LoadableCatalog<ModelProfile>
    readonly skills: LoadableCatalog<SkillSummary>
    readonly mcp: LoadableCatalog<McpServerSummary>
  }
  readonly selection: {
    readonly requestedModelProfileId: string | null
    readonly actualModel: ModelProfile | null
    readonly armedSkill: SkillSummary | null
  }
}

export type LoadableCatalog<T> =
  | { status: "idle"; items: readonly T[] }
  | { status: "loading"; items: readonly T[] }
  | { status: "ready"; items: readonly T[] }
  | { status: "error"; items: readonly T[]; message: string }
```

### 状态约束

- `InteractiveActivity` 使用稳定 kind 表达 `home/idle/starting/running/waiting-interaction/cancelling/completed/cancelled/failed/restoring`，同时提供共享的简短 `label`；adapter 不按中文状态字符串反推行为。
- `timeline` 保留 message/tool/interaction 的协议顺序。Tool 展开与折叠不进入 snapshot。
- `connection` 区分 `open/protocol-error/closed`；错误只保留脱敏摘要。连接关闭后不再允许新 Run/RPC。
- `commands` 已经过 capability、Thread、active Run 和 Interaction 可用性计算；缺 capability 的命令不出现，临时不可用命令携带 disabled reason。
- catalog snapshot 不包含搜索 query、selected index、visible 或 terminal-specific loading 文案。
- `requestedModelProfileId` 表示下一次 Run 的选择，`actualModel` 表示最近 `run.started` 的实际绑定；两者不能互相覆盖。

## Interaction 完整语义

### Approval

snapshot 必须保留 `description`、结构化 `requests`、服务端允许的 `decisions`、`requestId` 和 `deadlineAtMs`。Controller 只接受当前 request 允许的 decision：

- `reject_with_feedback` 携带 adapter 收集的反馈；其他 decision 不发送多余 feedback。
- adapter 提交不在 allowlist 的 decision 时不发送响应，并发布脱敏校验 notice。
- 新 Interaction 到达时若已有 pending Interaction，新请求立即 fail closed，不能覆盖旧 resolver。

### Question

snapshot 保留全部 questions，而不是只抽取第一题。每题至少包含 `id/question/header/body/options/multiSelect/allowOther`。`interaction.respond` 接收完整 `answers: Record<string, string[]>`，Controller 统一校验：

- 每个已声明问题都必须出现；答案字符串去除空值。
- `multiSelect=false` 时最多一个答案。
- `allowOther=false` 时答案必须来自 option value；`allowOther=true` 才接受自由文本。
- 未知 question ID、重复提交或 stale request ID 不产生 RPC。

### Timeout、终态与关闭

收到 request 后按 `timeout_ms` 通过可注入 scheduler 建立本地 deadline：

```text
request accepted
  → snapshot interaction=waiting，启动 deadline
  → 用户有效响应：清 timer，更新 Timeline，resolve wire response
  → deadline 到期：清 Interaction，标记 cancelled，resolve fail-closed response
  → Run 终态/connection close/controller close：abandon inbound request，清 timer并本地收敛
```

approval 的 fail-closed response 为 `reject`；question 为 `answers: {}`。timeout 路径尝试正常 resolve，让 Host 不依赖 UI 永久等待；若 Run 已终结或连接已关闭，则先调用 port 的 `abandonInteraction`，禁止发送迟到响应。

## Run、Event 与 Timeline 流程

```text
input.submit / submit-prompt command
  → 检查 connection、active Run、pending Interaction
  → 解析 selected Skill 与 requested model
  → agent.startRun（先建立 AgentRun event queue）
  → 用返回的 threadId/runId 原子登记 user message 与 active Run
  → 消费该 AgentRun.events
  → 按 sequence 更新 Timeline/Interaction/activity/actual model
  → 唯一 terminal event 清 active Run、timer 和 pending Interaction
```

- 不再同时依赖 AgentClient 全局 `event` listener 和空 drain；当前 Controller 自己启动的 `AgentRun.events` 是 Run event 的 canonical 输入。
- `accepted` 失败或 event stream 异常时，只有当前 Run 可以转为 failed；旧 Run 的错误不能结束新 Run。
- `run.started` 只校准 `actualModel`，不改变下一次 Run 的 `requestedModelProfileId`。
- 一次性 armed Skill 在创建 Run 时消费；请求显式携带的 Skill 优先于 armed Skill。
- connection protocol error/close 形成系统 notice，并 fail closed 当前 Interaction；Run stream 的终态/异常负责封口 active Run。

## Thread 与 catalog 流程

### Thread

- `initialThreadId` 缺省表示不做启动恢复；显式 `null` 进入空首页；字符串调用 canonical `threads.open`。
- Thread 打开前后都校验无 active Run/Interaction，并捕获当前 thread generation。历史、模型选择和实际绑定全部读取完成后再一次性替换 snapshot。
- `threads.open` 成功但 `models.list` 失败时仍可恢复历史；模型 catalog 进入 error，且不能保留旧 Thread 的模型选择/实际绑定。
- 任意 Thread 切换或 `/new` 都递增 thread/model generation，使旧请求晚到结果失效。
- `/new` 有 active Run 时先发布稳定 confirmation；确认后先 cancel 并等待 Host 确认，再清 Thread。取消失败保留原 Thread 和 Timeline。

### Model

- 选择只接受当前 model catalog 中 `available=true` 的 profile ID。
- 先更新当前 Thread 下一次 Run 的 requested selection，再独立尝试 `config.details → preview → commit` 同步未来新 Thread 默认值。
- 默认值同步失败不回滚当前选择，但只展示稳定、脱敏原因；成功后刷新 model catalog。
- legacy immutable binding 由共享 Controller 判断并发布 confirmation/notice，adapter 不解释 binding DTO。

### Skill、MCP 与其他 catalog

- Skill catalog 在 Controller 启动后异步刷新；失败不会阻断消息发送。armed Skill 只能引用当前启用且 user-invocable 的项目。
- MCP status/add/remove 和参数校验进入共享 Controller。Slash 文本与未来 Web typed intent 最终调用同一内部方法。
- 每个 catalog 有独立 generation；刷新 A 不取消 B，Controller close 使全部 generation 失效。
- 搜索、排序后的选中行属于 adapter；共享 module 只发布 canonical items 和状态。

## Slash Command 收敛

现有 Registry 与 parser 迁移到 `interactive/commands.ts`，删除 TUI 命名。Dispatcher 只返回稳定 semantic operation，例如：

```text
system.help      → append-help-notice
system.quit      → request-exit
thread.new       → clear-thread / request-confirmation
thread.resume    → refresh-threads + present(threads)
model.select     → refresh-models + present(models)
skills.open      → refresh-skills + present(skills)
context.compact  → compact-current-thread
mcp.manage       → mcp-status/add/remove
host.web         → request-handoff(currentThreadId)
skill:<id>       → submit-prompt(requestedSkill)
```

- Dispatcher 不返回 RPC method string、success/error closure、React callback 或 TUI local action。
- Controller 解释 semantic operation 并完成所有 Agent effect；adapter 只解释 `InteractiveResult`。
- Command menu 数据由共享 snapshot 发布；TUI 可以按 draft 做显示过滤，但不能重新计算 capability/busy 可用性。
- `/help`、`/status`、参数错误和未知命令仍进入共享 Timeline notice，确保 TUI/Web 文案与行为一致。

## TUI Adapter 设计

`TuiAdapter` 是真实的 Interactive Adapter，不是旧 Controller 的透传 wrapper。它拥有以下终端复杂度：

- textarea draft、光标回填和本地 Prompt history；
- Command menu、Picker 的 visible/query/selectedIndex 和焦点恢复；
- shortcut 解析、OpenTUI refs、terminal dimensions、滚动；
- Tool 卡片的全局详情开关和逐项展开状态；
- 把 `InteractiveResult.present` 映射为 Picker，把 confirmation snapshot 映射为 Dialog；
- 把 `request-handoff/request-exit` 交给 TUI 宿主 callback。

它明确不拥有：

- AgentClient 或任意 JSON-RPC method；
- Run/Event reducer、Interaction resolver/timer；
- Thread、模型、Skill、MCP 请求与错误语义；
- Command Registry 可用性、Slash 解析或业务命令 switch。

TUI snapshot 采用组合而非复制：

```ts
type TuiAdapterSnapshot = {
  interactive: InteractiveSnapshot
  draft: string
  draftCursor?: "start" | "end"
  commandMenu: TuiCommandMenuState
  picker: TuiPickerState
  showToolDetails: boolean
  expandedTools: ReadonlySet<string>
  scrollRequest: number
}
```

`index.ts` 作为 composition root，用 owner `AgentClient` 构造 production port 和 `InteractiveController` factory；`WebAwareRoot` 每次 TUI generation 挂载时创建一套 Interactive Core + TUI Adapter，卸载时先关闭 Adapter，再关闭共享 Controller。TUI 从 Web handoff 返回时把 `string | null` 的 restore Thread 传给新 Controller，不把旧 snapshot 复制到新实例。

## 错误模式

| 场景 | 共享行为 |
| --- | --- |
| active Run 时再次提交消息 | 不调用 `startRun`，追加“当前任务仍在执行”的 notice。 |
| command 缺 capability 或当前 busy | Registry 返回 hidden/disabled；直接执行仍在 Controller 内复核并拒绝。 |
| `run.start` 未 accepted | 当前 Run 转 failed，保留用户消息和可观察错误；不影响后续新 Run。 |
| 重复/倒序 Event | 忽略；sequence 缺口只追加诊断并继续。 |
| stale catalog/Thread/Model 响应 | generation 不匹配，静默丢弃，不覆盖新状态。 |
| 单个 catalog 请求失败 | 对应 catalog 进入 error，其他 snapshot 保持。 |
| Thread 恢复失败 | 保持或回到明确空首页；Web handoff restore 失败不回退到旧 TUI Timeline。 |
| 默认模型同步失败 | 当前 requested model 保留，输出稳定原因；未来默认值不声称成功。 |
| stale/非法 Interaction response | 不发送 RPC；当前有效 Interaction 保持等待或按 timeout 收敛。 |
| Interaction timeout | approval reject、question 空 answers，Timeline 标记 cancelled，清理 timer。 |
| connection close | connection=closed，禁止新 RPC，清理 Interaction；active Run 由 stream error 封口。 |
| Controller close 并发异步结果 | close 幂等，generation/timer/listener 失效，之后不再发布 snapshot。 |

## 按依赖排序的实施步骤

1. **先固定共享 interface 和 contract fixture。** 新增 `interactive/types.ts`、`InteractiveAgentPort`、内存 port 和 controller interface 测试骨架；用当前 TUI 行为构造 message/command/Run/Thread/model/Interaction intent 序列。为什么：先明确 caller 只需理解什么，再迁移实现，避免把 1445 行旧类原样改名。验证：测试只通过四个公开方法和 port 的可观察调用工作。
2. **迁移纯 reducer、runtime 与 Command Registry。** 把 `TuiState` 改为 nullable Thread 的共享 state，迁移 Timeline/Event reducer；把命令 module 和 `/status` 所需 runtime 移到 `interactive/`，删除 TUI 命名和 presentation-specific result。为什么：这些是 Controller 的稳定内核，也是后续工作流的共同语言。验证：现有 state/command/model 测试迁移后保持行为，并新增 null Thread 与 semantic operation 断言。
3. **实现 Run 与完整 Interaction 生命周期。** 通过 port 启动 Run、只消费 `AgentRun.events`，实现 accepted/stream/terminal/close；完整实现 approval decisions、全部 questions、answer 校验、feedback、timeout 和 abandon。为什么：这是 TUI/Web 最不能分叉的核心正确性与安全逻辑。验证：正常、失败、取消、重复/乱序/缺口、终态竞态、timeout 和 close 均通过 interface 测试。
4. **迁移 Thread、Model、Skill、MCP 和 catalog。** 用独立 generation、typed mapper 和 loadable snapshot 收敛列表、恢复、选择、配置同步与部分失败。为什么：adapter 只能渲染 catalog，不能拥有数据/RPC 工作流。验证：Thread 原子切换、模型双路径、stale response、catalog 部分失败和 MCP typed/text 两个入口产生相同 port 调用。
5. **迁移 Slash Command 副作用解释。** Dispatcher 改为 semantic operation，Controller 统一处理 compact、MCP、new、picker request、handoff 和 exit；移除 RPC closure 与 TUI local action。为什么：Registry/执行必须成为真正共享的单一路径。验证：普通文本、`//`、未知命令、alias、capability、busy 与所有 builtin command 在 direct interface 下有确定结果。
6. **实现 TUI Adapter 并替换生产组合。** 新 `TuiAdapter` 只组合共享 snapshot 与终端状态；`app.tsx` 改为从 factory 创建 Interactive Core/Adapter，Presentation 改读 `snapshot.interactive`。为什么：只有现有 TUI 完整通过新 seam，才能证明共享 module 可用。验证：架构测试确认 TUI application 不导入 IPC，OpenTUI 交互测试保持现有可观察行为。
7. **删除旧路径和旧测试形状。** 删除 `createTuiController`、`TuiControllerImpl`、公开 `applyAgentEvent`、TUI 业务 state/command duplicate 和所有 alias/wrapper；旧 Controller 测试替换为 shared interface contract，保留少量 TUI mapping/焦点/键盘测试。为什么：仓库未发版，不允许双写或兼容层掩盖迁移遗漏。验证：全文搜索不存在旧类名、旧业务字段或 adapter 直接 RPC。
8. **更新架构文档与完成证据。** 更新架构总览和 Slash Command 文档，记录 shared module、TUI/Web adapter seam 和依赖方向；按任务范围执行项目检查与 open-code-review，修复高/中优先级问题后再补任务证据。用户文档不变。

## 可观察验收

- TUI 的发送、流式 Timeline、Tool、审批/提问、取消、Thread、Model、Skill、MCP、compact、status 和 Slash Command 全部通过 `InteractiveController`。

- 旧 `TuiControllerImpl`、TUI 业务 reducer、公开 `applyAgentEvent`、RPC closure 和兼容 wrapper 已删除，不存在新旧双写。
- Command Registry 的解析、可用性、参数校验和执行只存在于 `interactive/`；未知 Slash 永不提交模型。
- 全部定向测试、构建、类型检查、项目检查、全量测试和限定范围 OCR 通过并写入 ZC-103 证据。

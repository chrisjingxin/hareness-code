# HC-168 修复批量审批恢复实施计划

关联：[Task](../task/archive/HC-168-修复批量审批恢复.md) · [Spec](../spec/HC-168-修复批量审批恢复.md) · [Todo](../todo/HC-168-修复批量审批恢复.md)

本 Plan 只实现一个垂直、可验收停点：真实 AgentHost 在同一 LangChain HITL interrupt 中恢复 `2 个 write_file + 1 个 task`，并证明规则只在恢复成功消费后提交。执行代理不得扩展到协议/UI 或其它审批策略重构。

## 1. 设计落点

```text
RunCoordinator.RunState
  ├─ staged approval intents（Run 私有）
  ├─ local queued-rule evaluator = persisted + session + staged overlay
  └─ commit/discard seam

BuildRunAdapter
  → ManagedAgentRequest.resume_success callback
  → ManagedAgentExecutor resumed astream 正常返回后触发
  → RunCoordinator commit
```

共享 Agent 图的既有 `rules_provider` 继续只读取正式 session/project/user/system 规则。收集阶段不调用现有 `_record_approval_rule`；只有恢复轮成功返回后，Coordinator 才将 staged intent 正式提交，使下一轮模型/工具看到新规则。

## 2. 依赖有序步骤

### 步骤 A：先固定失败边界

1. 在 `packages/agent/tests/host/test_server.py` 增加真实 `AgentHost + FakeMessagesListChatModel` 集成测试：模型同一回合返回 `write_file(package.json)`、`write_file(tsconfig.json)`、`task(general-purpose)`；逐个提交 `approve_thread`、`approve_project`、`approve_once`，断言没有决策数量 `ValueError`、三个 action 的顺序/身份保持一致、文件和 child 工具可继续执行。
2. 增加恢复异常/取消的测试 seam，断言 staged session/project 规则不落地；扩展 `test_approval_protocol.py` 覆盖 approve_once/reject 无规则和规则提交幂等。
3. 先运行最小测试并保留红测输出，再开始实现。

### 步骤 B：实现暂存与恢复成功提交

1. 在 `RunState` 增加有界 staged intent 存储以及清理状态；用明确的内部数据形状保存作用域、工具名、参数和生成规则。
2. 将串行审批中的 thread/project 记录改为 `_stage_approval_rule`；让 `_evaluate_queued_rule` 只在本地把 staged 规则作为 overlay，不改变 `session_rules` 或 project settings。
3. 为 `ManagedAgentRequest` 增加最小 resume-success callback。Executor 仅在 resumed `astream(Command(...))` 正常返回后调用；异常/取消路径不调用，Coordinator 的 Run 清理路径负责 discard。
4. Build adapter 把 callback 绑定到 Coordinator 的 commit seam；异常/取消由 Coordinator 的 Run 清理路径 discard，child 直接审批也沿用相同 Run 生命周期，不新增平行存储。
5. 提交 project intent 时复用现有 `save_rule`，不吞写入异常；提交结束或失败都清理 staged intent，重复触发保持幂等。

### 步骤 C：扩展验证并停点交付

1. 运行 HC-168 focused pytest，再扩展到相关 `host/test_approval_protocol.py`、`host/test_server.py`、`runtime/test_managed_agent_executor.py` 与审批/委派相关集合。
2. 运行 `bun run typecheck`、`bun run project:check`、`git diff --check`；如环境依赖或已有任务阻塞，区分记录环境限制与代码结果。
3. 增量更新架构总览、HC-168 Todo/Task 的证据，覆盖“恢复成功消费后提交”的不变量。
4. 写中文 `tmp/handoff.md`，列出修改文件、精确命令、结果、设计取舍和未验证项；停在本检查点，不归档、不提交、不推送。

## 3. 可演示停点

### 停点：混合批次审批可恢复

用户/父任务可运行 HC-168 集成测试，看到同一批两个文件写入和一个 task 的三项决定被完整消费，Run 以 `completed` 结束；随后检查 session/project 规则只在恢复成功后出现。取消或恢复失败测试显示 settings 与 session rule 不留下半成品。

## 4. 验证边界

- 使用临时 workspace/config home、FakeMessagesListChatModel 和离线 fixture；不使用真实 API key、真实模型、联网 MCP、Hook 或外部进程。
- 真实 TUI/Web、真实 LangChain 版本差异、full pytest 若受本机缺失 `.venv` 或 loopback/Chromium 权限影响，必须在 handoff 中明确为未验证项，不把环境失败写成通过。

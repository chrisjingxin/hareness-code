## 通俗怎么拆

先用真实 mock graph 证明当前 DeepAgents 能承载验收循环。然后做一条最小但完整的纵向路径：用户能创建、人工审核并保存目标，TUI/Web 都看得到，重启后还在，接受后 Agent 自动继续并看到冻结目标。第二段再补齐修订、暂停、恢复、替换和运行中排队。第三段接上独立 grader 和完成门禁。最后补模型配置、Plan/旁路矩阵、blocked、undo/redo 和全部文档回归。

```text
前置门  DeepAgents 0.6.8 兼容性测试
  │
停点 1  /goal → 人工审核 → 持久化 → 双端展示 → 自动续跑 → Agent 看见冻结目标
  │
停点 2  澄清/驳回/amend/replace/pause/resume/clear + 运行中排队与重启恢复
  │
停点 3  独立 grader → gap → 同 Run 返工 → satisfied → Completion Guard
  │
停点 4  grader 模型/迭代配置 + Plan/旁路/blocked + undo/redo + 完整文档与回归
```

停点按用户能完成的行为切，不按 `protocol/agent/cli` 横切。同一停点内可以有多个小任务，但未贯通到 UI 和真实 Host 前不算可演示。

## 已确认的代码事实

- 当前 Protocol 是 v3.7；`run.start` 仍使用裸 `message`。本任务一次迁到 v3.8 tagged `input`，不保留双形状。
- 当前 Thread SQLite schema 是 v18；本任务迁到 v19，沿 `ThreadPersistence.open()` 的 canonical migration 路径处理，不增加运行时兼容分支。
- `ThreadPersistence`、Compose stores 和 LangGraph checkpointer 共用一个 `aiosqlite.Connection + asyncio.Lock`。Goal store 复用这个 owner 与事务锁，不另开数据库连接。
- `RunCoordinator` 唯一拥有 Run busy、owner、cancel、Interaction 和终态；Goal proposal/continuation 仍使用它，不另建执行生命周期。
- TUI/Web 已共用唯一 `InteractiveController`；Goal 业务状态进入共享 snapshot，表现层只渲染和派发 intent。
- DeepAgents 0.6.8 已导出 `RubricMiddleware`，支持独立 grader、工具、1～20 次循环、`rubric_evaluation_*` stream event 和 `needs_revision → model` 跳转。
- SDK iteration 是 0-based，criterion 由 grader 返回名称，`on_evaluation` 异常会被吞掉，最后一次 `needs_revision` 的 stream event 不会自动改名为 `max_iterations_reached`。Harness adapter 必须完成 1-based 映射、稳定 criterion ID/完整覆盖校验、错误脱敏、上限终态归一化与可靠持久化；完成门禁不能依赖 callback。
- `RubricMiddleware` 的 model/tools/max_iterations 在实例构造时冻结。Goal-backed AgentEngine profile 必须把实际 grader binding、工具视图和迭代上限纳入不可变身份，配置变化只影响后续 Run。

## 停点 1 — 创建、审核、恢复并自动续跑

### 1. Protocol v3.8 与 RunInput 单路径

**改什么：** 在 canonical schema 定义 Goal projection/request/mutation/interaction/event、`goal.read/manage` capability，并把 `run.start.message` 迁为 tagged `input`。运行生成器同步 TS/Python 类型、validator、fixture 与摘要；所有仓库内 client/host/test fixture 一次迁移。

**验证：** `rtk bun run protocol:generate`、`rtk bun run protocol:check`，再跑 Python/TS protocol contract tests。断言旧、混合和越界形状被拒绝，goal 写操作进入现有 `CONTROLLED_OPERATIONS`。

### 2. SQLite v19 GoalStore

**改什么：** 新建 `harness_agent/goals` 领域模型与 `GoalStore`，建立 current/pending/revision/criteria/evaluation/activity/idempotency 表和事务命令；由 `ThreadPersistence` 借出同一 connection/lock。完成 v18→v19 迁移、空 Thread 索引创建、close/reopen 恢复与 fail-closed 校验。

**验证：** 临时数据库测试覆盖 create、读取、CAS、幂等冲突、回滚、project/thread 隔离、无 Transcript 空 Thread、v18 迁移和过新/损坏 schema。

### 3. Host 读取、请求和简单 Proposal

**改什么：** 新建窄 `GoalService` 与 Criteria Agent adapter；`AgentHost` 只做 Protocol 映射、capability/ControlLease gate 和 RunCoordinator 编排。先贯通明确目标的 `create → ready → interaction.goal → accepted/edited/cancelled → apply`；proposal Run 不写 Transcript，review 的 accept/edit 由 Host 再校验并 CAS。

**验证：** 结构化 mock 覆盖 ready、非法 criteria、超限、accept/edit/cancel、迟到 response、无 goal handle 和响应丢失幂等重试。

### 4. Interactive Core 的 GoalFeature

**改什么：** AgentGateway 暴露 typed goal operation；新增 `GoalFeature`、共享 goal state/selector/intent，注册 Build-only `/goal`。Controller 为首次创建分配 `thread_id`，立即显示原始目标命令但不写 Host Transcript，并消费 proposal interaction、Host projection 和 continuation；Web/TUI 不直接拼 RPC。无 AgentEngine 的 proposal 在依赖冻结后提前结束 snapshot 临界区，确保控制面刷新不会饿死反向 Interaction 响应。

**验证：** command、feature、controller、adapter parity 测试覆盖 Build/Compose、无 Thread 创建、capability hide/read-only、接受后 exactly-once continuation。

### 5. TUI 与 Web 的 Review/Goal panel

**改什么：** 两端分别渲染共享 review DTO 和 goal projection：接受、编辑、取消先可用；输入区附近显示状态/objective，裸 `/goal` 打开共享 viewer。键盘、焦点和 Web ARIA 由各原生 renderer 负责。

**验证：** TUI interaction/presentation 测试和 Web React/adapter 测试断言按钮、编辑、Esc、窄屏/长文本、ARIA 与 renderer 无业务分支。

### 6. Goal context 与 continuation

**改什么：** Run preparation 从 SQLite 读取 current goal，生成冻结 binding 和 `goal.state` Dynamic/Run ContextBlock；普通 Build 与 goal continuation 使用同一 RunCoordinator，内部 continuation 不写伪用户 Transcript。Plan/Compose/side question/direct shell 首段先保持 `goal_backed=false`。

**验证：** context/binding/host 测试断言转义与脱敏、revision/digest 冻结、重启恢复、不写隐藏消息、接受后只启动一次 continuation。

**可演示：** `rtk bun run dev`。Build 输入一个明确 `/goal`，检查草案，分别试一次接受、编辑和取消；接受后应自动开始工作，输入区附近出现 active goal。切到 `/web` 应看到同一状态。退出并重启、打开同一 Thread 后 goal 和 criteria 恢复，但恢复本身不启动 Run；下一条普通 Build 消息中 Agent 能依据该目标继续。Compose 菜单没有 `/goal`。

## 停点 2 — Proposal 与完整生命周期

### 7. 澄清、驳回、amend 与 replace

**改什么：** Criteria Agent 加入 readiness 分级、最多两轮澄清和仓库只读预算；review 补 `rejected + feedback`。`amend/replace` 绑定 base identity，新 proposal 未接受前旧 goal 生效，接受后原子切换并保留历史。

**验证：** proposal/service 测试覆盖小歧义 assumptions、大歧义 questions、两轮失败、拒绝重生、旧 revision、replace/amend 差异和工具预算。

### 8. 生命周期命令、排队与重启 reconcile

**改什么：** 实现 pause/resume/clear/cancel_pending、配置以外的 lifecycle transition、单 pending write、运行中持久排队和 Run 终态 reconcile。恢复 reviewing/queued/drafting/clarifying，保证 mutation/continuation exactly once。

**验证：** GoalStore、RunCoordinator/Host 竞态测试覆盖 active Run 冻结旧 revision、并发写拒绝、终态顺序、断连/重启、幂等重放和失效 completion。

### 9. 双端生命周期操作与 activity 恢复

**改什么：** `/goal edit/pause/resume/clear` 接入 GoalFeature，支持无参 `/goal edit` 弹出编辑弹窗，裸 `/goal` 作为查看入口；review 补驳回，viewer/panel 显示 pending、revision、note。Goal activity 进入共享 Timeline projection，不写 Transcript。

**验证：** CLI command/controller/TUI/Web 测试覆盖完整参数矩阵、无参 edit 弹窗、运行中 queued 提示、50 条恢复上限、双端同一 projection。

**可演示：** 用一个有歧义的目标触发问题并回答；在 review 中驳回后重生，再接受。随后演示 edit、replace、pause、resume、clear。让 Agent 运行时输入 edit 或 pause，应显示排队，当前 Run 继续旧 revision，终态后只应用一次；重启后 pending/review 能继续。

## 停点 3 — 独立验收闭环

### 10. GoalRunBinding 与 Rubric adapter

**改什么：** 扩展 execution/engine profile 保存 goal identity、criteria digest、实际 grader fingerprint、迭代上限和窄工具视图；按 goal-backed 条件构造原生 `RubricMiddleware`。Adapter 把 criterion ID 写入 canonical rubric，并归一化 0-based iteration、SDK event、上限和错误。

**验证：** execution binding、agent profile、真实 graph 测试覆盖同一 Run 冻结、不同配置得到不同 profile、无 rubric 时 no-op、needs_revision 跳转和 checkpoint cleanup。

### 11. root-only `update_goal` 与受控复验

**改什么：** 根 Build Agent 常驻 `update_goal(complete|blocked,note)`；子代理、proposal、grader 无此工具。记录当前 root Run 的安全验证 evidence，并只向 grader 暴露只读仓库工具与 `rerun_verification(evidence_id)`；exact command 重跑继续走原 policy/sandbox/审批。

**验证：** capability/policy/tool 测试覆盖 root/child 角色矩阵、无 active goal、complete 仅申请、blocked CAS、任意 command 注入拒绝、一次性批准不升级和 yolo 仍不可写。

### 12. Evaluation 持久化、事件翻译与覆盖校验

**改什么：** `execution_stream` 校验 SDK private event，映射为 Protocol `goal.evaluation`；先事务保存再 fanout。对 criterion ID 做 exact coverage，缺项/重复/未知/矛盾结果按 Spec 收敛；SDK exception 文本脱敏，不能把 provider/SQLite 内容发给 UI。

**验证：** adapter/store/stream tests 覆盖 checking/result、1-based iteration、last needs_revision→max、grader_error、cancel、迟到 event 和异常 payload fail closed。

### 13. Completion Guard 与 Run 终态 reconcile

**改什么：** RunCoordinator 正常终态调用唯一 Completion Guard，在同一 SQLite transaction 校验 run、goal revision/digest、pending invalidation、grading run 和完整 criteria 后提交 complete；失败只写 stale/rejected audit。

**验证：** 每个 AND 条件一个反例；特别覆盖 Agent 自报 complete、旧 checkpoint、取消/failed Run、旧 revision、pending amend/pause/clear、缺项 satisfied 和重复终态。

### 14. TUI/Web grader Timeline

**改什么：** shared Timeline 增加 goal activity item；两端显示 checking、gap、satisfied、failed、grader_error、max iterations，可展开 criteria/gap/model。complete/blocked notice 不作为 assistant message。

**验证：** timeline feature、恢复、TUI/Web renderer 测试覆盖顺序、展开、空 gap、长文本和不污染 Transcript。

**可演示：** 设一个至少包含“改代码”和“跑测试”的目标。让第一次输出故意缺一项，Timeline 应显示 checking 和具体 gap，主 Agent 在同一 Run 自动补做；全部满足后显示 satisfied，Goal 变为 complete。再用 max=1 的测试 fixture 演示未满足时 Run 停止但 Goal 保持 active；取消与 grader error 不得完成。

## 停点 4 — 配置、模式和历史操作收敛

### 15. grader 模型与迭代配置（配置文件化）

**改什么：** 将 grader 模型与迭代上限作为用户配置下沉至 `~/.harness/config.toml` 的 `[goal]` 节（`grader_model` 支持继承或指定 profile；`max_iterations` 默认 3，支持 1～20），并支持环境变量覆盖。不再提供 `/goal model` 与 `/goal max-iterations` 斜杠命令，降低 CLI 复杂度。配置在 Run 受理时解析并冻结至 profile。

**验证：** model resolver/Config/GoalStore 测试覆盖 inherit、独立 profile、环境变量覆盖、未配置回退、非法负数/>20 校验与实际 fingerprint 冻结。

### 16. Plan、旁路与 blocked/resume 矩阵

**改什么：** 收敛 goal-backed 判定：普通 Build active=true；Plan 只投影不 grading；`/btw`、Compose、direct shell、proposal=false；paused/blocked/complete=false。实现 blocked 后普通回复或 resume 恢复 active，并只投影一轮 prior blocker。

**验证：** Host/runtime/CLI 组合测试覆盖每一格 approval/work mode 矩阵，确认 continuation 不选择更宽权限，criteria/grader 永远是主能力子集。

### 17. undo/redo 完成证据失效

**改什么：** Thread undo transaction 同步标 stale evaluation；complete goal 保守恢复 active。Redo 只恢复原会话/文件，不恢复 satisfied；下一次 goal-backed Run 才可重新完成。

**验证：** conversation/code/both 三种 undo、失败回滚、redo、旧 evaluation/迟到 event 测试。

### 18. 文档、架构、项目检查与 review

**改什么：** 更新 `docs/user/交互使用.md`、`模型配置.md`、`安全与沙箱.md`；新增 `docs/developer/architecture/目标闭环.md`，增量更新架构总览和斜杠命令体系。完成全部 focused/full checks，使用 code review skill 对照 Task/Spec/Todo 检查 diff，把证据写回 Task；用户验收后再归档和同步看板。

## 风险与处理

| 风险 | 影响 | 处理 |
|---|---|---|
| SDK `on_evaluation` 只是 advisory，异常会被吞 | 完成状态可能丢失或错误提交 | 只用 stream/final state 作观测输入；GoalStore transaction + Completion Guard 才提交事实 |
| SDK criterion name 不保证稳定 ID 完整覆盖 | 缺项也可能声称 satisfied | rubric 强制 ID；adapter exact-set 校验；缺项、重复、未知一律不能 complete |
| SDK 最后一次仍发 needs_revision event | UI 与持久终态不一致 | adapter 根据 frozen max/iteration 归一化为 `max_iterations_reached` |
| thread-scoped grader 配置与 AgentEngine cache 冲突 | 修改模型后仍用旧 grader | 把实际 grader fingerprint/tools/max 纳入 engine profile key；运行中配置只作用下一 Run |
| `run.start` 改 tagged input 的影响面大 | CLI/Host/fixture 任一遗漏都会断链 | 停点 1 一次迁移，protocol fixture + TS/Python contract test 禁止旧形状 |
| v18→v19 迁移中断 | 用户 Thread 库不可用 | 复用现有 migration lock/backup/poison/recovery；不另建旁路 migrator |
| 自动 continuation 与用户新输入抢 Run | 重复或错误 Run | continuation token 持久化幂等；仅终态且空闲时由 Controller 消费一次 |
| Goal 内容形成持久 prompt injection | 诱导越权 | `goal.state` 明确标为用户数据并转义/脱敏；EffectivePolicy 和工具裁剪在 prompt 外强制 |
| 两端各写一套生命周期 | TUI/Web 行为漂移 | 所有状态、command、intent 和 selector 在 Interactive Core；renderer 只做原生交互 |

## 并行与接力约束

- 前置门、Protocol/RunInput、SQLite migration、Completion Guard 必须顺序完成，不能并行改同一契约。
- 一个停点内，契约冻结后可分别实现 TUI/Web renderer，但两端必须在同一停点合流验证。
- 多个执行 Task 可以接力同一 HC-167；每个执行者只接下一个停点，不拆新的 Task/Spec 文档树。
- 任何实现发现需要改变 RPC、状态、完成语义、权限或依赖版本，立即停止并回写 Spec/Plan，不在 Todo 中现场发明设计。

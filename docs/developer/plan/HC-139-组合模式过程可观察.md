## 通俗方案

Compose 目前只有“阶段进度”，阶段内部的模型、Tool 和审批没有进入 Build 已经使用的实时执行链路。本计划先把 Build 的执行流抽成唯一公共实现，再让 Compose Stage 安全接入；事件经过 Host 和 Protocol 后，由 Interactive Core 统一归组，最后同时展示在 TUI/Web。五个阶段全部接通后，再增加与模型 context 隔离的有界恢复记录。

```text
固定 Build 行为基线
  → 提取共享执行流
  → 固定 scoped Event / Interaction 契约
  → 打通 Understand/Plan 的真实纵向链路
  → Core 归组并由 TUI/Web 展示
  → 扩展 Build/Verify/Review 阶段
  → 持久化安全摘要并恢复
  → 生命周期 E2E、文档与 Review
```

## 启动前提

- Task 与 Spec 已确认，不存在需要执行 Agent 再选择的产品或 interface 方案。
- 实现必须使用 `agent-skills:test-driven-development`：每一步先补失败测试，再写最小实现，最后删除旧路径或重复逻辑。
- 当前仓库的 `scripts/project/tasks.ts` 仍读取旧的 `docs/developer/task/` 和 `ZC-*` 命名。它需要由开发流程维护工作单独迁移后，`task:claim`、`tasks:sync`、`task:complete` 才能管理本 HC-139；不得在 HC-139 中偷偷保留旧 Task 双写来绕过该问题。

## 关键实施边界

- `compose.state` 只表达 Workflow 阶段事实，高频 activity 不写入 projection。
- `RunCoordinator` 继续唯一拥有 sequence、Interaction、取消和 Run terminal。
- Build 与 Compose 共用 execution stream，但 Transcript observer 与 Compose activity observer 分离。
- Stage 模型正文使用 `capture_only`；只有 Runtime 基于校验结果生成的摘要可展示或持久化。
- TUI/Web 只消费 Interactive Core snapshot，不各自解释 Host Event。
- 当前仓库未正式发布，迁移到 canonical 路径后删除旧 translator、旧关联状态和旧数据 shape，不新增 alias、fallback 或双写。

## 步骤 1：建立共享 Execution Stream，并保持 Build 行为不变

**改什么：** 先为 `BuildRunAdapter._stream_agent()` 当前行为建立可比较的 characterization tests，再把 LangGraph `astream`、Reasoning 安全翻译、Tool correlation、interrupt/resume、取消和 final content 捕获迁入 `runtime/execution_stream.py`。Build adapter 只负责 root provenance、Transcript 和 flush；迁移完成后删除旧私有 translator 与重复 correlation state。

**为什么先做：** Compose 若直接复制 Build 流处理，会形成两套难以保持一致的安全和审批逻辑。先固定 Build 基线，可以在最早阶段暴露共享 module 的回归风险。

**主要文件边界：**

- `packages/agent/harness_agent/runtime/execution_stream.py`（新增）
- `packages/agent/harness_agent/host/run_execution.py`
- `packages/agent/tests/runtime/test_execution_stream.py`（新增）
- `packages/agent/tests/host/test_run_coordinator.py`

**为什么此时做：** Stage、Core 和 renderer 必须先共享同一归属语言，否则后续会各自猜测 Stage/Task/attempt，产生不可恢复的关联分叉。

## 步骤 3：打通 Understand/Plan 的真实 Stage 实时链路

**为什么用 Understand/Plan 做第一条纵向切片：** 它们能最早验证 child execution、问题/审批、artifact 隔离和阶段推进，但还不引入 Build retry、Verify evidence 或双 Reviewer 的额外复杂度。

## 步骤 6：覆盖 Builder、Verification 与双 Reviewer

**为什么放在 UI 链路之后：** 这一步不再设计新 transport 或 renderer，只复用已证明的纵向路径，能把关注点集中在 Compose 既有 retry、evidence、只读权限和 fix loop 不变量上。

## 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 抽取共享执行流改变 Build Transcript 或 Interaction | 高 | 步骤 1 先建立 golden event/Transcript 基线，检查点 A 未通过不得接 Compose |
| Child approval 被当成 root interrupt 或重新创建 execution | 高 | 用真实 child checkpoint namespace 做 approve/reject/timeout production-chain 测试 |
| artifact JSON、隐藏思维或 parser 原文越过 wire | 高 | `capture_only` fail closed；摘要只能读取 validator 已接受的对象 |
| 同一 Tool ID 在重试、Task 或 Reviewer 间碰撞 | 高 | Core 使用 Run+execution+activity+provider item 复合身份并覆盖乱序/重复测试 |
| Activity history 污染模型 context 或无限增长 | 高 | 独立 store/projector、统一上限常量、唯一 truncation 和 context 隔离断言 |
| TUI/Web 形成两套 Compose 解释 | 中 | scope/reducer 只在 Core，renderer 只持有布局、滚动、焦点和折叠状态 |
| 新文档规范与现有 task tooling 不一致 | 中 | 先迁移项目管理脚本；不为让旧脚本通过而恢复 `ZC-*` 双写 |

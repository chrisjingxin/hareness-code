## 通俗方案

模型返回的工具调用先经过一个小的模型输出保护 module。结构坏了就把整次响应丢掉，交回已有 Managed executor 重新请求；结构合法但没有 ID，就在 assistant 消息上补一个 ID，后续 ToolNode 和 ToolMessage 复用它。所有重试只有 executor 一处计预算，因而日志、取消和等待时间仍然只有一份。

## 阶段 1：先建立可失败的行为证明（已完成）

1. 新增 middleware 测试，先证明畸形 name/id 会穿透或 capability-policy fallback 造成不安全结果；先固定合法 unknown tool 不被误判。
2. 在 executor 测试中注入 `MALFORMED_TOOL_CALL`、500/429/transport 与取消，先断言当前没有统一恢复或 budget/timing 证据。
3. 添加 Build/Inline fake-agent vertical case：首轮畸形、次轮合法；断言当前失败或污染 transcript，作为 RED 基线。

## 阶段 2：模型输出保护与单一 retry owner（已完成）

1. 新建 `runtime/model_output_guard.py`，实现 sync/async response 校验、ID 规范化和稳定 `MalformedToolCallError`。
2. 将 guard 装配到 root 和 Inline child graph，保留未知/未授权合法调用交给现有 policy/tool seam。
3. 将 `BoundedProviderRetry` 收敛到 runtime canonical module，扩展 5xx、429、transport、malformed 分类和 Retry-After；Compose 迁移到该实现。
4. 在 executor 中清理重试尝试的 session/observer 暂存，写入 retry diagnostic/timing；非 retryable 错误立即抛出。
5. 从 RunPreparation/resolved spec 传递 `ModelSettings.max_retries`，将 OpenAI-compatible SDK `max_retries` 设为 0，避免双重预算。

## 阶段 3（可演示停点，已完成）：Build/Inline 正常恢复

- Build 根 Run：fake model 首轮返回结构化非法 name/id/args，第二轮合法，最终 `run.completed`；普通正文中的 literal `<tool_call>` 保持可见且不触发 guard；Transcript/checkpoint 只有合法 assistant/tool 事实。
- Inline child：同一 guard 和 retry policy 下首轮畸形、第二轮正文或工具成功；child event provenance 不串到 parent Transcript。
- 用户怎么看：运行离线纵向测试，看到 attempt 1 `MALFORMED_TOOL_CALL`、retry wait 与 attempt 2 成功；失败工具片段不出现在 guard 返回的 graph message/Transcript；首片正文在模型仍流式输出时即可见；已完成 Tool 批次仍按既有边界即时可读。

## 依赖与风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| LangGraph streaming 在 middleware 后仍提前发出半条 tool delta | 失败响应污染事件或 checkpoint | 只缓冲 tool signal 到模型节点确认；content/reasoning 保持实时；已公开正文/推理后的临时错误不重放 |
| ChatOpenAI 与 executor 重复重试 | 实际预算指数放大 | SDK `max_retries=0`，所有配置预算只进入 BoundedProviderRetry |
| retry 清理遗漏 session/Transcript 暂存 | 孤儿 assistant/tool 事实 | 每次 attempt 使用可回滚 capture 状态，红测断言 pending/event/checkpoint 为空 |
| 扩展策略错误分类过宽 | 取消/权限错误被重试 | 只允许稳定 MALFORMED、状态码 429/5xx 和明确 transport 类型 |

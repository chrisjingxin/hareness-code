## 1. 通俗怎么拆

```text
停点 1  跨语言契约 + 两端异步 writer + process/initialize 日志
  ↓
停点 2  一次 Build Run 能看清 Run/Runtime/Context/Model/Tool/Persistence/IPC
  ↓
停点 3  Compose/child/Plugin/MCP 和故障降级覆盖，DEBUG 脱敏红线通过
  ↓
停点 4  harness logs 可列 Run、合并时间线、过滤、JSON、cursor 分页
  ↓

  ↓
review      对照 Task/Spec/Todo 复核
```

每个停点都是纵向可见结果，不按 CLI/Protocol/Agent 水平分层硬拆。

## 2. 依赖顺序

```text
Diagnostic Log v1 schema/generator
  ├─→ TypeScript contract → CLI runtime
  └─→ Python contract     → Agent runtime
                                 ↓
                 config/initialize/process 接入
                                 ↓
                 Run-scoped DiagnosticLog.child()
                                 ↓
       Run/Runtime/Context/Model/Tool/Persistence/IPC
                                 ↓
                    Compose/child/Plugin/MCP

稳定 JSONL contract + 样本
  → discovery/parser → list/timeline/filter/JSON → cursor
```

- Query 不能早于 v1 文件契约。
- 生命周期 owner 不能早于 runtime，避免 queue/writer 知识泄漏到业务代码。
- 三平台契约测试从停点 1 开始；停点 5 补真实 runner 证据和总收口。

## 3. 已锁定做法

- 业务代码继续写 `log.debug/info/warn/error`；`diagnostic-log-integration` 是现有 owner 的接入职责，不是新的集中打点框架。
- Diagnostic Log v1 与 JSON-RPC v3 独立版本化；`InitializeResult.diagnostics` 按未发版内部 Protocol 直接升级。
- CLI 不解析 TOML：先用 env/default bootstrap，initialize 后用 Agent 返回的 effective settings 重配置同一 writer。
- CLI/Agent 分开写 segment。Active segment 先 close 再 rename，retention 不碰 active/orphan。
- 热路径只做内存校验/编码/入队；正常关闭最多等待 2 秒。
- 耗时由真实 owner 用 monotonic clock 计算，query 不用 wall timestamp 猜。
- Transcript、CompressionCheckpoint 和 LangGraph Checkpoint 边界不改：不改 SQLite schema、不让日志进事务、不用日志恢复或修补事实。
- `harness logs` 在 `startAgent()` 之前短路，不创建 logger、不读 SQLite、不写日志。
- 不引入新依赖；若必须引入原生文件锁/ACL 库，先停止并回写 Spec 请用户确认。

## 9. 风险与处理

| 风险 | 处理 |
|---|---|
| 事件一次接入太多 owner | 停点 2/3 分开；每个 owner 先做单元失败测试，再做链路测试 |
| logger 自身影响被测性能 | 热路径仅入队，slow writer 压测，耗时由 owner monotonic clock 计算 |
| 日志变成 Transcript/Checkpoint 影子库 | 不改 SQLite/事务，不记正文，query 不读 SQLite，日志失败不影响业务 |
| CLI/Agent contract drift | 单一 schema generator + digest + 互验 fixture + `protocol:check` |
| Windows active file 操作失败 | 先 close 再 rename，retention 不碰 active，真 Windows runner 证据 |
| orphan active 使 root 超过 200 MiB | 安全优先：计入容量/查询报告但不自动删；未来需活性证据时另立 Task |
| 256 KiB 与 JSON 完整性冲突 | 预算并减少 events，不硬切 bytes |
| 仓库无公开三平台 CI | 用企业 runner/等价主机记真实证据；缺少任一 OS 时阻塞完成 |

## 10. 实施边界

本 Plan 无待决设计项。如实现中需要改变事件契约、queue 容量、配置字段、脱敏边界、cursor 语义、SQLite schema 或引入新依赖，必须停止并先修订 Task/Spec/Plan。

即使后续有多个执行 Thread 接力，Diagnostic Log schema/generated 产物、`InitializeResult.diagnostics`、Run 时间账本、cursor 编码和 Task/Todo 证据收口也必须串行修改。

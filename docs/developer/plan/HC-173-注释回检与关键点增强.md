# HC-173 Plan：注释回检与关键点增强

按真实依赖排序；每步有可验证产出。执行模式为用户指定的并行 worktree（替代串行停点交付，见 Task 已确认决策 4）。

## 阶段 0：风格样本（已完成，2026-09-11）

- 产出：`tmp/review-sample.patch`（context_pressure.py + client.ts）；strip 校验、pytest、bun test、typecheck 全过；**用户已确认**。
- 意义：该样本全文作为所有并行执行者的风格基准，内嵌进其工作指令。

## 阶段 1：文档链（本步）

- 产出：task/spec/plan/todo 四份同名文档 + `bun run tasks:sync` 更新看板。
- 验证：`bun run project:check` 文档链接与编号检查通过。

## 阶段 2：并行 worktree 注释（核心阶段）

- 依赖：阶段 0 的风格样本、阶段 1 的 Spec 标准。
- 8 个单元并行，划分与契约见 Spec 第 3、5 节；每个单元 = 建 worktree → 注释回检与增强 → 三层校验 → 提交 `comments-<单元>` 分支 → 留 patch 与交付说明。
- 验证：各单元在自己的 worktree 跑本包测试；agent 单元跑 pytest、cli 单元跑 bun test + typecheck。

## 阶段 3：用户检查合回

- 依赖：阶段 2 各单元完成。
- 用户逐个检查 worktree（直接看 diff 或 patch）→ 认可后主会话 merge 回 master，每合一个跑全套验证（pytest 全量、bun test 全量、typecheck）。
- 不认可的单元：子代理返工或主会话重做后重审。

## 阶段 4：终验与清理

- 依赖：阶段 3 全部合并。
- 产出：全套验证（含 `bun run project:check`）、`tmp/handoff.md` 交接记录、worktree 与临时分支清理、Task 状态更新。
- 回滚思路：任一单元合并后发现问题，`git revert` 该 merge 提交即可独立回退，不影响其他单元。

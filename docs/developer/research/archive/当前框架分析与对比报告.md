## 一、项目总体定位

Harness Code（命令名 `harness` / `za38`）是一个面向企业研发场景的终端 Coding Agent。采用 **TypeScript CLI (Bun/OpenTUI)** + **Python Sidecar (deepagents/LangChain/LangGraph)** 的双进程架构，通过 stdio 上的 **JSON-RPC v2** 协议通信。当前版本为 `0.1.0`，处于源码开发阶段。

## 七、关键入口文件分析

### 7.1 `server.py` — JSON-RPC 服务端（1478 行）

- **`AgentHost`** 类是整个 Python sidecar 的核心控制面
- 管理方法分发表：`initialize`、`run.start`、`run.cancel`、`context.compact`、`config.show`、`config.path`、`threads.list`、`threads.open`、`skills.*`（7 个方法）、`shutdown`
- **`ActiveRun`** 数据类封装一次执行的隔离状态（thread_id、run_id、sequence、usage、cancellation_token 等）
- 支持 **双向 JSON-RPC**：服务端可向客户端发送 `request`（审批/问答交互），客户端回复 `response`
- **AgentEnginePool** 机制：按 Profile 复用 deepagents 图，支持多 thread 共享同一 AgentEngine
- 事件流：`run.started` -> `content.delta` / `tool.started` / `tool.delta` / `tool.completed` -> `run.completed` / `run.failed` / `run.cancelled`
- Windows 兼容：使用后台线程阻塞读取 stdin 替代 IOCP

### 7.2 `agent.py` — Agent 内核（434 行）

- **`create_harness_agent()`** 是核心工厂函数，组装 deepagents 图
- 中间件栈按顺序：PlanModeMiddleware -> AskUserMiddleware -> WorkspaceBoundaryMiddleware -> ShellAllowListMiddleware -> PromptEpochMiddleware -> ContextWindowMiddleware
- 使用 `create_deep_agent()` 创建 LangGraph 编译图
- 支持子 Agent（general-purpose subagent），继承计划模式和工作区边界
- 通过 `_without_deepagents_summarization()` 排除 DeepAgents 内建压缩，确保 ContextWindowMiddleware 是唯一历史重写入口
- **`create_prompt_epoch()`** 创建不可变的 system prompt 前缀，包含执行环境、memory 快照、skill 索引和工具指纹

## 一、工具调用实现（Tool Calling）

### 核心文件
- `d:\code\tst\hareness-code\packages\agent\harness_agent\agent.py`
- `d:\code\tst\hareness-code\packages\agent\harness_agent\server.py`

### 架构设计

工具系统基于 **DeepAgents 框架**的内建工具集，而非自行注册。在 `agent.py` 第 47-57 行定义了静态工具契约：

```python
_BUILTIN_TOOL_SHAPES = (
    {"name": "ls", "parameters": {"path": "string"}},
    {"name": "read_file", "parameters": {"file_path": "string", "offset": "integer", "limit": "integer"}},
    {"name": "write_file", "parameters": {"file_path": "string", "content": "string"}},
    {"name": "edit_file", "parameters": {"file_path": "string", "old_string": "string", "new_string": "string"}},

    {"name": "grep", "parameters": {"pattern": "string", "path": "string", "glob": "string"}},
    {"name": "execute", "parameters": {"command": "string", "timeout": "integer"}},
    {"name": "write_todos", "parameters": {"todos": "array"}},
    {"name": "task", "parameters": {"description": "string", "subagent_type": "string"}},
```

共 9 个内建工具，涵盖文件操作（ls/read_file/write_file/edit_file）、搜索（glob/grep）、命令执行（execute）、任务管理（write_todos）和子 Agent 委派（task）。

### 工具执行流

工具调用通过 **中间件链（Middleware Chain）** 层层拦截：

1. **PlanModeMiddleware** — 计划模式下只放行只读工具
2. **AskUserMiddleware** — 注入 `ask_user` 交互工具
3. **ShellAllowListMiddleware** — Shell 命令白名单校验
4. **WorkspaceBoundaryMiddleware** — 工作区路径边界强制
5. **HumanInTheLoop (HITL)** — 通过 `interrupt_on` 配置需审批的工具集
6. **ContextWindowMiddleware** — 模型调用前的上下文预算管理

工具执行结果在 `server.py` 的 `_translate_stream_event` 方法（第 981-1039 行）中被翻译为协议事件：`tool.started`、`tool.delta`、`tool.completed`，并通过 `_truncate_text` 对输出做 UTF-8 安全截断（上限 `MAX_TOOL_PAYLOAD_BYTES = 1MB`）。

### 额外工具注入

`create_harness_agent` 接受 `tools` 参数注入额外工具（如 MCP 工具），同时 `AskUserMiddleware` 通过 `self.tools = [_ask_user]` 动态注入 `ask_user` 工具。

## 二、上下文管理（Context Management）

### 核心文件
- `d:\code\tst\hareness-code\packages\agent\harness_agent\context_window.py`
- `d:\code\tst\hareness-code\packages\agent\harness_agent\prompting.py`

### 分层压缩状态机

`ContextWindowMiddleware` 实现了一个精密的**四级阈值分层状态机**（第 199-244 行）：

| 阈值 | 动作 | 说明 |
|------|------|------|
| < 50% | `within_budget` | 无需操作 |
| 50%-60% | `report` | 仅报告状态 |
| 60%-80% | `soft_dehydration` | 将旧的大工具结果归档，替换为首尾各 200 字符预览 |
| 80%-90% | `summary` | 保留最近 2 个 user turn，对旧历史生成结构化摘要 |
| >= 90% | `forced_summary` | 仅保留最近 1 个 user turn 的强制摘要 |

### 关键设计决策

1. **完整 turn 原子性**：`_cutoff_for_recent_turns` 确保 assistant tool-call 与对应结果绝不会被拆开（第 480-485 行）。
2. **20% 最低节省率**：`_saves_enough` 要求压缩至少节省 20% 才执行改写，避免压缩反而增大上下文（第 488-490 行）。
3. **熔断器**：连续 3 次压缩失败后打开熔断器（`circuit_open`），不再自动重写历史（第 367-376 行）。
4. **溢出恢复**：捕获 `ContextOverflowError` 后先尝试工具脱水，仍不足才强制摘要（第 341-352 行）。
5. **排除 DeepAgents 内建压缩**：通过 `_without_deepagents_summarization` 上下文管理器临时排除框架默认的 `SummarizationMiddleware`，确保 `ContextWindowMiddleware` 是唯一的历史重写入口（第 61-106 行）。

### Token 估算

`prompting.py` 中的 `estimate_tokens` 使用保守的 UTF-8 字节 / 4 估算（第 37-39 行），不伪装成厂商 tokenization。输入预算 = 窗口 - 输出预留（4K-16K，取窗口的 10%）。

### 结构化摘要模板

摘要使用固定章节模板（第 36-45 行）：目标、已确认事实、决策、改动、测试、未决项、归档。摘要长度限制在 2K-12K token，与窗口大小线性相关。

## 三、子 Agent / 多 Agent 模式

### 核心文件
- `d:\code\tst\hareness-code\packages\agent\harness_agent\agent.py`（第 126-151 行）

### 实现方式

通过 DeepAgents 的 `subagents` 参数实现。`_create_default_subagents` 创建继承主 Agent 安全策略的通用子 Agent：

```python
def _create_default_subagents(*, workspace, approval_mode):
    from deepagents.middleware.subagents import GENERAL_PURPOSE_SUBAGENT
    middleware = []
    if approval_mode == "plan":
        middleware.append(PlanModeMiddleware())
    if workspace is not None:
        middleware.append(WorkspaceBoundaryMiddleware(workspace))
    return [{
        **GENERAL_PURPOSE_SUBAGENT,
        "system_prompt": f"{GENERAL_PURPOSE_SUBAGENT['system_prompt']}{_LOCAL_SUBAGENT_BOUNDARY_PROMPT}",
        "middleware": middleware,
    }]
```

关键设计：
- 子 Agent 拥有**独立中间件栈**，计划模式和工作区边界必须重新注册
- 子 Agent 的 system prompt 追加了本机文件边界约束（`_LOCAL_SUBAGENT_BOUNDARY_PROMPT`）
- 内建工具 `task` 用于触发子 Agent 委派
- 远端沙箱模式下不创建带工作区边界的子 Agent

### Skill 系统（技能委派）

`d:\code\tst\hareness-code\packages\agent\harness_agent\skills.py` 实现了完整的 Skill 注册/发现/加载系统：

- **四级来源**：builtin（内置）、user（`~/.harness/skills`）、project（`.harness/skills`）、market（企业市场安装）
- **不可变 catalog**：启动时扫描固定，运行时通过 digest 校验拒绝篡改
- **按需读取**：Skill 正文通过 `/.harness/skills/<id>/SKILL.md` 虚拟路径按需读取，不预加载到上下文
- **企业市场**：通过 Python entry point（`harness.skill_marketplaces`）发现 Provider，支持 catalog/fetch/install/remove
- **安全解包**：市场 artifact 的 zip/tar 解包有完整的路径穿越、符号链接、大小限制检查

## 总结：架构全景

Harness Code Agent 是一个**分层安全优先**的编码 Agent 内核，其核心架构可概括为：

1. **传输层**：stdio JSON-RPC v2 双向协议（`server.py`），支持事件流、反向交互请求和能力协商
2. **运行时层**：`AgentEnginePool` 按 `AgentEngineProfile` 管理共享编译图的构建、租约、有界缓存和确定性关闭（`agent_engine.py`）

5. **持久化层**：用户级 SQLite 保存 LangGraph checkpoint、线程索引、归档和 AgentEngineProfile 绑定（`thread_persistence.py`）
6. **安全层**：工作区边界、Shell 白名单、审批模式、Unicode 安全、配置来源控制、虚拟文件系统隔离形成纵深防御

## 三、IPC 通信模式（`packages/cli/src/ipc/`）

### 3.1 JsonRpcPeer 双向 Peer

`d:\code\tst\hareness-code\packages\cli\src\ipc\client.ts` 实现了完整的双向 JSON-RPC Peer：

**传输层**：
- 基于 stdio 的 **JSONL（换行分隔 JSON）** 分帧
- 使用 `StringDecoder` 保留跨 chunk 的 UTF-8 字符完整性
- 无换行缓冲区超过 `MAX_FRAME_BYTES` 时触发 `protocolError` 并关闭连接
- 写入时检查帧大小限制，高水位触发时等待 `drain` 事件（背压控制）

**请求-响应关联**：
- 每个出站请求分配字符串 ID（`req-1`, `req-2`, ...），存入 `pending` Map
- 支持超时保护（默认 30 秒，shutdown 为 2 秒）
- 远端错误封装为 `JsonRpcRemoteError`，保留 `code`、`message`、`data`

**服务端反向请求**：
- Agent 可通过 `request` 方法发起审批/问答请求
- `setRequestHandler` 注册处理器，返回清理函数
- 校验 `request_id` 与 JSON-RPC `id` 一致性
- `abandonInteraction` 在取消或超时后停止回写已失效的响应

**事件分发**：
- `event` 通知经 `assertEventEnvelope` 校验后，同时触发 `"event"` 通用监听器和 `event.type` 特定监听器
- 区分三种入站消息：Notification（无 id 的 method）、Request（有 id 的 method）、Response（有 id 无 method）

## 四、流式实现

### 4.1 事件流架构

流式通信采用**服务端推送通知**模式：

1. 客户端发送 `run.start` 请求，服务端立即返回 `{ thread_id, run_id, accepted: true }` 确认
2. 服务端在后台 `asyncio.Task` 中执行 Agent 运行，通过 `event` 通知推送流式事件
3. 每个事件携带单调递增的 `sequence` 号，客户端据此检测重复帧、乱序帧和序号缺口

### 4.2 流式事件处理（TUI 状态归约）

`d:\code\tst\hareness-code\packages\cli\src\tui\state.ts` 是核心状态机：

- **`content.delta`**：增量追加到末尾 assistant 消息；工具之后收到文本时创建新的回答项（保持时间线因果关系）
- **`thinking.delta`**：仅更新状态为"正在思考"，不渲染内容
- **`tool.started` / `tool.delta` / `tool.completed`**：工具卡片在时间线中保持首次出现位置，参数和输出分片分别追加
- **`run.completed` / `run.cancelled` / `run.failed`**：终态事件结束流式状态，记录 `RunSummary`（耗时、token 用量、上下文摘要）
- **`context.updated`**：显示上下文管理状态（归档、摘要、预算告警）

### 4.3 Sequence 防护

`acceptSequence` 函数实现三重防护：
- 丢弃旧 run 的事件（thread_id/run_id 不匹配）
- 丢弃重复帧（sequence <= 已见最大值）
- 序号缺口时追加系统通知但不崩溃

### 4.4 无头模式流式

`runTurn` 函数（`index.ts`）监听 `event` 事件，累积 `content.delta` 文本，等待 `run.completed`/`run.cancelled`/`run.failed` 终态。

## 七、错误处理模式

### 7.1 协议层

- **严格白名单校验**：所有 `assert*` 函数拒绝未知字段（`rejectExtra`），防止协议漂移
- **JSON-RPC 标准错误码**：`-32700`（解析错误）、`-32600`（无效请求）、`-32601`（方法不存在）、`-32602`（无效参数）、`-32603`（内部错误）
- **业务错误码**：`-32000`（未初始化/重复运行）、`-32003`（协议不匹配）、`-32004`（连接关闭）、`-32020`（Thread 存储不可用）、`-32030`（运行时池容量耗尽）

### 7.2 IPC 层

- `JsonRpcRemoteError` 保留远端 `code`/`data`，调用方可区分协议、配置和 Agent 故障
- 帧超限触发 `protocolError` 事件并关闭连接
- 连接关闭时拒绝所有 pending 请求
- 反向请求无处理器或校验失败时返回 `-32602` 结构化错误

### 7.3 Python 服务端

- `RpcError` 异常类携带 `code`/`message`/`data`
- `dispatch` 方法捕获 `ValidationError`、`SkillError`、`ThreadPersistenceError`、`AgentEnginePoolCapacityError`、`RpcError` 和通用 `Exception`，分层映射为对应错误码
- stdout 只输出 JSON-RPC，诊断信息写入 stderr/结构化日志
- Windows 平台 stdin 使用后台线程阻塞读取规避 IOCP 限制

### 7.4 TUI 层

- `TuiErrorBoundary`：React 错误边界，异常时渲染可退出的降级页面，**不回显原始异常**（避免泄漏凭据/路径）
- 所有来自 RPC 的数据经 `stringValue`/`numberValue`/`objectRecord` 等安全提取函数处理
- Skill/Thread 摘要经字段校验后才进入 UI（`skillMenuItem`/`threadPickerItem`/`threadOpenResult`）
- 协议错误和连接关闭以系统通知形式追加到时间线
- 提示词历史读写失败安全降级为空历史，不阻塞 Agent 交互

### 7.5 安全边界

- `--resume` 禁止接受 thread_id 参数，只能通过 TUI 选择器操作
- thread_id 不直接渲染到界面
- 审批 payload 中的工具参数经 `safePreview` 安全序列化（防循环引用）
- 错误边界不向 stdout/stderr 写原始错误

核心设计特征：
1. **Schema 驱动的代码生成**确保 TypeScript/Python 两端协议模型始终同步
2. **双向 JSON-RPC**：客户端发请求（run.start 等），服务端发通知（event）和反向请求（request 用于审批/问答）
3. **统一时间线**：消息、工具调用、交互按 sequence 排列，保持因果关系
4. **不可变状态归约**：所有 Agent 事件经纯函数转换为确定性 TUI 状态
5. **分层安全边界**：协议白名单校验 -> IPC 帧限制 -> TUI 安全提取 -> 错误边界信息隔离

# Agent 框架技术能力对比研究报告

## 一、DeepAgents（LangChain 生态）

### 工具调用与协议设计
- **中间件架构**：工具通过两条路径注入 LLM——SDK 中间件（自动注入）和消费者提供的 tools 参数。中间件继承 `AgentMiddleware`，可覆写 `wrap_model_call()` 钩子，在每次 LLM 请求前拦截处理。
- **内置工具集**：`write_todos`（规划）、`ls/read_file/write_file/edit_file/glob/grep`（文件系统）、`execute`（Shell 命令）、`task`（子代理调用）。
- **动态工具过滤**：如 `FilesystemMiddleware` 在调用时根据后端能力动态移除 `execute` 工具。
- **可插拔后端**：`BackendProtocol` 抽象支持 LangGraph State、LangGraph Store（跨线程持久化）、本地文件系统，以及 CompositeBackend（按路径前缀路由到不同后端）。

### 上下文工程
- **三级压缩策略**（按频率递增触发）：
  1. **大工具结果卸载**：超过 20,000 token 的工具响应自动写入文件系统，替换为路径引用 + 前 10 行预览。
  2. **大工具输入截断**：上下文超过 85% 窗口时，截断旧的 write/edit 参数（内容已持久化到文件系统）。
  3. **对话摘要**：当卸载无法释放足够空间时，LLM 生成结构化摘要（含会话意图、已创建产物、下一步），完整历史写入文件系统保留。
- **自主压缩工具**：`compact_conversation` 工具允许模型在合适时机（任务边界、大量上下文消费后）自主触发压缩，而非仅在固定阈值被动触发。
- **模型感知默认值**：通过 LangChain model profiles 获取各模型的 token 阈值，自动计算 trigger/keep 参数。

### 子代理/协作机制
- **SubAgentMiddleware**：通过 `task` 工具调用子代理，子代理自动获得默认中间件栈（TodoList、Filesystem、Summarization 等）。
- **AsyncSubAgent**：连接远程 Agent Protocol 服务器（LangGraph Platform 或自托管），作为后台任务运行，主代理可监控和更新。
- **上下文隔离**：子代理处理多步任务后返回简洁结果，保持主代理上下文清洁。

### 可观测性
- 深度集成 **LangSmith** 追踪平台，追踪每个决策、工具调用和循环轮次。
- 流式输出支持元数据标记（如 `lc_source: "summarization"`）。

### 记忆与规划
- **MemoryMiddleware**：从 AGENTS.md 文件加载记忆注入系统提示。
- **SkillsMiddleware**：注入技能指令到系统消息。
- **write_todos 规划工具**：任务分解、进度追踪、动态调整。
- **长期记忆**：通过 LangGraph Store 实现跨线程持久化。

### 安全模型
- **FilesystemPermission**：声明式访问规则，按声明顺序评估，首条匹配规则生效，默认允许。
- 沙箱后端协议（`SandboxBackendProtocol`）控制 Shell 执行能力。

- **Rust 实现**：高性能 TUI + Agent 运行时，支持交互式、headless（CI/CD）、ACP 嵌入三种模式。
- **ACP（Agent Client Protocol）**：标准化接口，将 Agent 本身作为可被 IDE/编排器驱动的服务。

- **grok-build-0.1 模型**：专为 agentic coding 训练，256K 上下文（声称架构支持 2M）。

### 上下文工程
- **上下文压缩与聊天历史内存管理**：自动优化长会话。
- **子代理 context 分区**：大任务拆成并行小 loop，各自带窄窗口，避免单一上下文过载。

- **Plan 文件**：复杂任务先生成可审计划文件，分离"想"和"做"。

- **主动提醒 + 懒惰检测器**：提升模型任务执行效率。
- **Plan Mode（强制人工审查）**：执行前生成详细步骤计划，支持查看/评论/修改/重写，批准后才执行。可视化子任务图 + 每节点状态。

- **Cost Tracking API**：每个响应包含 `cost_in_usd_ticks` 精确成本。

### 记忆与规划
- **Plan Mode**：强制计划-审查-批准流程。
- **AGENTS.md 兼容**：读取项目指令文件。

- **自动后台运行**：长时间 Bash 命令自动后台执行。

- **Plan-Review-Approve 强制门控**：比 Claude Code/Codex 更严格的人工介入。

## 七、关键洞察

1. **Harness > Model**：所有框架都在验证同一命题——Agent 质量 ≈ 模型质量 × Harness 质量。上下文管理、工具编排、安全边界比纯模型能力更决定实际表现。

2. **上下文工程分化**：DeepAgents 用"卸载-截断-摘要"三级策略；MiMo Code 用"checkpoint 重建 + 预算化注入"；Reasonix 用"前缀缓存稳定性"作为第一设计原则——三种路线各有适用场景。

3. **子代理成为标配**：所有框架都实现了某种形式的子代理/多智能体协作，但粒度不同——Grok Build 最激进（8 并行 + Git worktree），MiMo Code 最完整（生命周期 + 编排 + 自我进化）。

4. **安全模型趋同**：Plan-Review-Approve 门控、权限分级、破坏性操作确认已成为行业共识，差异在于严格程度和可配置性。

5. **协议标准化趋势**：MCP 已成为工具扩展的事实标准；ACP（Grok Build）试图标准化 Agent 本身作为可被驱动的服务；AGENTS.md 成为跨 Agent 可移植的指令文件格式。

# Claude Code 技术架构与能力全面分析

## 一、工具调用系统（Tool Calling System）

### 1.1 工具架构

Claude Code 拥有 **40+ 内置工具**，采用统一的 `Tool` 接口设计（泛型接口，约 40 个属性/方法），每个工具自包含 schema、权限、执行逻辑。使用 **Zod** 做运行时类型校验，同时生成 JSON Schema 提供给 LLM。

核心工具分类：

| 类别 | 工具示例 | 特点 |
|------|----------|------|
| 文件操作 | ReadTool, WriteTool, FileEditTool | 增量编辑，模糊匹配 |
| 搜索 | GlobTool, GrepTool | 结果截断避免上下文爆炸 |
| 系统 | BashTool | 最高风险，每次需确认 |
| Web | WebFetchTool, WebSearchTool | 网络请求 |
| Agent | AgentTool, TeamCreateTool | 子代理生成，上下文隔离 |
| 扩展 | MCPTool, SkillTool | 外部能力接入 |
| 任务 | TaskCreateTool, TaskUpdateTool | 任务管理 |

### 1.2 工具执行机制

采用 **ReAct 循环**（LLM → 观察 → 思考 → 执行）：
- 当模型返回 `<tool_use>` 标签时，引擎拦截消息交给**权限网关**（CanUseToolFn）审计
- 通过后在本地沙箱执行，抓取 stdout/stderr
- 通过 Tool Result 将结果喂回模型，进入下一迭代
- 支持**并发安全**标记（`isConcurrencySafe`）和**只读**标记（`isReadOnly`）

### 1.3 MCP 集成

Claude Code 实现了完整的 MCP（Model Context Protocol）客户端生态：

- **5 层架构**：配置层 → 连接层 → 交互层 → 安全层 → 工具层
- **7 种传输方式**：stdio、SSE、HTTP（Streamable HTTP）、WebSocket、SDK、InProcess、claudeai-proxy
- **6 层配置优先级**（从低到高）：claude.ai 连接器 → 插件 MCP → 全局用户配置 → 项目配置（.mcp.json）→ 本地配置 → 企业配置（独占模式）
- 支持 **OAuth 认证**、自动重连、Elicitation 双向交互
- 官方注册表从 `api.anthropic.com/mcp-registry/v0/servers` 获取

## 二、上下文管理（Context Management）

### 2.1 上下文窗口

- 默认 **200K token**，可通过 `opus[1m]` 或 `sonnet[1m]` 扩展到 **1M token**
- 上下文消耗来源：对话历史 + CLAUDE.md + Skills + MCP 工具定义 + 文件内容 + 子 Agent 结果

### 2.2 压缩策略（三层递进）

| 层级 | 名称 | 触发条件 | 实现 |
|------|------|----------|------|
| Layer 1 | micro_compact | 每轮自动 | 保留最近 3 次工具结果，更早的替换为占位符 |
| Layer 2 | auto_compact | token 超阈值（~50K） | 保存完整对话到 `.transcripts/`，LLM 生成摘要替换 |
| Layer 3 | compact tool | 模型/用户主动触发 | 同 auto_compact 逻辑 |

### 2.3 高级机制

- **History Snip**：消息级裁剪，智能压缩废弃的链式推理
- **Context Collapse**：激进的上下文缩减（Feature-gated）
- **Reactive Compact**：上下文压力驱动的按需压缩
- **FileStateCache**：LRU 缓存，每个 agent 独立，避免重复读取文件
- **Token 预算追踪**：`createBudgetTracker()` 自动续接，+500K 自动继续

### 2.4 错误恢复

- Prompt Too Long → auto-compact / history snip / context collapse
- Max Output Tokens → 重试（最多 3 次）→ 增加 max_tokens
- API Error → 指数退避重试 → Fallback Model 切换

## 三、子代理/多代理系统（Sub-agent / Multi-agent）

### 3.1 Subagents（子代理）

每个子代理拥有**独立上下文窗口**、自定义系统提示、特定工具权限。

**内置子代理：**
- **Explore**：只读，使用 Haiku 模型，快速搜索代码库
- **Plan**：只读，继承主模型，plan mode 下收集上下文
- **General-purpose**：全权限，处理复杂多步骤任务

**自定义子代理**：Markdown 文件定义，放在 `.claude/agents/` 或 `~/.claude/agents/`，支持配置：
- `tools`：限制可用工具
- `model`：指定模型（sonnet/opus/haiku/inherit）
- `permissionMode`：权限模式（acceptEdits/dontAsk/bypassPermissions）
- `memory`：跨对话记忆目录
- `skills`：预加载技能

### 3.2 Agent Teams（多代理团队）

- 启动**多个完全独立的 Claude Code 实例**
- 共享任务列表，可互相发消息
- Lead 主代理统筹 + 多个 Teammate 子代理并行
- 官方最优规模：**2-4 个子代理**
- 子代理之间无直接通信，所有任务由主代理统一调度
- 支持**文件领地隔离**，锁定核心文件避免冲突

## 五、记忆系统（Memory System）

### 5.1 四层记忆架构

| 层级 | 名称 | 写入者 | 特点 |
|------|------|--------|------|
| 第一层 | 上下文内记忆 | 系统 | 当前会话 messages，速度最快但最脆弱 |
| 第二层 | CLAUDE.md | 用户 | 持久指令，每次会话加载，支持多层级作用域 |
| 第三层 | Auto Memory | Claude 自动 | 自动记录学习，MEMORY.md 索引 + 主题文件 |
| 第四层 | Auto Dream | 后台进程 | 清理整合过期记忆（24h+5 次新会话触发） |

### 5.2 CLAUDE.md 层级

- 组织级（IT 管理员部署）→ 用户级（`~/.claude/CLAUDE.md`）→ 项目级（`./CLAUDE.md`）→ 子目录级（按需加载）
- 支持 `@path/to/file` 导入语法（最大深度 5 层）
- `.claude/rules/*.md` 支持路径作用域（`paths: ["src/**/*.ts"]`）

### 5.3 Auto Memory 机制

- 存储位置：`~/.claude/projects/<project>/memory/`
- 索引文件 MEMORY.md（前 200 行每次会话加载）
- 四类记忆：user（角色偏好）、feedback（纠正反馈）、project（决策上下文）、reference（资源指针）
- 设计哲学：记忆视为"提示"而非"事实"，使用前会验证当前代码

## 七、安全控制（Security Controls）

### 7.1 权限模型（Permission System）

三层权限优先级（Deny-First 设计）：
- **Deny**：绝对禁止（最高优先级）
- **Ask**：需要用户确认（默认行为）
- **Allow**：自动放行（用户配置的白名单）

默认只读，修改操作需明确批准。使用静态分析自动放行安全命令（如 `echo`、`cat`）。

### 7.2 沙箱机制（Sandboxing）

基于 OS 级原语（Linux bubblewrap / macOS seatbelt）：

- **文件系统隔离**：只允许读写当前工作目录，阻止修改外部文件
- **网络隔离**：通过 Unix Domain Socket 连接代理服务器，强制域名白名单
- 覆盖所有子进程（脚本、程序、子进程）
- 内部使用减少 **84%** 的权限提示
- 配置：`claude --sandbox`

### 7.3 企业安全

- 企业配置独占模式（启用后其他层级全部失效）
- 托管设置通过 MDM 分发，用户无法覆盖
- 凭据存储：macOS Keychain / Linux 文件 mode 0600 / Windows ACL
- Hooks 机制：`PreToolUse` 拦截破坏性命令，`PostToolUse` 验证输出

### 7.4 设计哲学

- **决策与执行分离**：模型只做决策，工具执行交给框架
- **用户享有最终决策权**：实时反馈 + 关键决策参与 + 事后审计
- 即使 93% 用户都点 Allow，沙箱仍保证即使 prompt injection 成功也无法逃逸

# OpenAI Codex CLI 技术架构综合研究报告

## 一、整体架构

### 1.1 项目概况

Codex CLI 是 OpenAI 开源（Apache-2.0）的终端编程智能体，GitHub 星标超过 97,000，Fork 超过 14,000。项目地址：`github.com/openai/codex`。

### 1.2 技术栈演进

- **初始阶段（2025年4月）**：以 Node.js + TypeScript 构建
- **Rust 重写（2025年底）**：核心引擎用 Rust 重写（`codex-rs` crate），Rust 代码占比约 95%
- **重写动机**：去除 Node.js 运行时依赖、消除 GC 暂停、原生调用平台沙箱 API（无 FFI 开销）
- **最终产物**：自包含二进制文件，运行时无需 Node.js、Python 或 Docker

### 1.3 多组件架构

| 组件 | 语言 | 职责 |
|------|------|------|
| `codex-rs/core` | Rust | 核心引擎：Agent 循环、沙箱、工具执行 |
| `codex-rs/linux-sandbox` | Rust | Linux Landlock + seccomp 沙箱 |
| `codex-rs/core/src/seatbelt.rs` | Rust | macOS Seatbelt 沙箱 |
| `codex-cli` | TypeScript/Node.js | 早期 CLI 层（已大部分迁移至 Rust） |
| SDK | TypeScript + Python | 编程接入接口 |

### 1.4 九层流水线架构

Codex 的核心工作模型抽象为九层流水线：

1. **User（用户层）**：多模态输入（文本、图像、文件引用），多表面接入（CLI/IDE/Web/Slack）
2. **Prompt（提示装配层）**：组装 system.md、AGENTS.md、tools.json、环境上下文，前缀缓存优化
3. **Planner（规划层）**：非独立模块，在 Agent 循环推理中涌现任务分解能力
4. **Agent（代理层）**：Plan-Execute-Observe-Iterate 循环引擎
5. **Sandbox（沙箱层）**：OS 级隔离执行
6. **Tools（工具层）**：Shell/文件/MCP/搜索/浏览器
7. **Git（版本管控层）**：Worktree 隔离，自动分支
8. **PR（交付载体层）**：GitHub 集成，Draft PR
9. **Result（结果层）**：输出验证与迭代闭环

### 1.5 Agent 循环核心机制

Codex CLI 通过 **Responses API** 进行模型推理（端点可配置）。Agent 循环的核心逻辑：

1. 从用户获取输入，纳入提示词
2. 调用模型推理（POST /v1/responses）
3. 模型返回：(a) 最终回复（assistant message），或 (b) 工具调用请求
4. 若为工具调用 → 执行工具 → 将输出附加到提示词 → 重新查询模型
5. 循环直至模型停止发出工具调用，产生终止性 assistant message

每个"回合"（turn）可包含多次模型推理与工具调用的迭代。

## 二、工具调用系统

### 2.1 核心工具集

Codex CLI 的工具设计哲学是 **Shell-first**，没有独立的 read/edit/write 文件工具：

| 工具 | 功能 |
|------|------|
| `shell` / `exec_command` | 执行任意 shell 命令（`cmd` 参数为 argv 数组），支持可恢复会话 |
| `apply_patch` | 结构化 diff 操作：创建、更新、删除文件（一次性多文件补丁） |
| `write_stdin` | 向运行中的 exec 会话写入输入 |
| `web_search` | 原生 OpenAI Responses 网络搜索（可选启用） |
| `image_generation` | 图像生成（特定模型支持） |
| MCP 工具 | 通过 MCP 协议扩展的第三方工具 |

### 2.2 apply_patch 工具

这是 Codex 最核心的文件编辑机制：
- 模型输出结构化 patch 操作（`create_file`、`update_file`、`delete_file`）
- 每个操作包含 `path` 和 `diff`（unified diff 格式）
- 支持多文件一次性修改
- 失败时返回状态和错误信息，模型可自动恢复

### 2.3 沙箱执行模型

所有工具执行都在沙箱约束下进行：
- Shell 命令在 OS 级沙箱中运行
- 文件系统访问受路径白名单限制
- 网络访问默认禁用
- 高危操作触发审批流程

## 三、上下文管理

### 3.1 上下文窗口配置

通过 `~/.codex/config.toml` 配置：

```toml
model = "gpt-5.4"
model_context_window = 1000000        # 模型可用 token 上限
model_auto_compact_token_limit = 900000  # 自动压缩触发阈值
```

- 默认上下文窗口：272K tokens（GPT-5.4/5.6），可推至 1M tokens
- 历史曾为 372K，2026年春缩减至 272K 引发社区争议

### 3.2 两级压缩（Compaction）架构

当 token 累积达到阈值时，Codex 执行两级压缩：

**第一级：Session Memory Compact**
- 检查结构化会话记忆（任务状态、文件编辑历史、关键决策）能否替代完整 LLM 摘要
- 大多数自动压缩走此路径，无需 LLM 调用

**第二级：Server-Side Compact（via Responses API）**
- 调用 `POST /v1/responses/compact` 专有端点
- 返回 `type=compaction` 项，包含 `encrypted_content` 字段（AES 加密的不透明 blob）
- 该 blob 保留模型的潜在理解：工具调用恢复数据、内部状态标记、结构化元数据
- 后续轮次传回时服务端透明解密并组装上下文

**阈值计算公式：**
```
effective_window = model_context_window - min(max_output_tokens, 20000)
threshold = effective_window - 13000
```

### 3.3 压缩后重读机制

压缩后 Codex 会：
1. 注入引导消息（"This session continues from a previous conversation…"）
2. 自动重读最近编辑的最多 5 个文件（总预算 50,000 tokens，每文件 5,000）
3. 确保 Agent 拥有当前代码状态

### 3.4 加密 Blob 设计意图

- **防篡改**：用户无法修改摘要来操纵模型行为
- **更丰富的状态保留**：包含结构化元数据、工具状态、推理轨迹
- **服务端优化**：OpenAI 可迭代压缩算法而无需客户端变更

## 四、子 Agent / 多 Agent 能力

### 4.1 Subagent 系统（2026年3月上线）

Codex 原生支持 **Fan-out 模式** 的子 Agent 并行：

- 最多 **6 个并发子 Agent**（`agents.max_threads = 6`）
- 嵌套深度限制：`agents.max_depth = 1`（子 Agent 不可再嵌套）
- 每个子 Agent 独立上下文窗口，互不污染
- 主 Agent 专注决策，子 Agent 执行后只返回精炼结论

### 4.2 内置 Agent

| Agent | 用途 |
|-------|------|
| `default` | 通用兜底 |
| `worker` | 实现和修复 |
| `explorer` | 代码库探索 |

### 4.3 自定义 Agent

通过 TOML 文件定义（`~/.codex/agents/` 或 `.codex/agents/`）：

```toml
name = "security-reviewer"
description = "专注安全审查"
developer_instructions = "..."
# 可选：model, sandbox_mode, mcp_servers, skills
```

### 4.4 Auto-Review 子 Agent

OpenAI 内部部署使用的 `approvals_reviewer = "auto_review"` 功能：
- 自动审批低风险操作
- 高风险操作仍需人工确认
- 减少用户中断频率

### 4.5 全局配置

```toml
[agents]
max_threads = 6           # 并发线程上限
max_depth = 1             # 嵌套深度
job_max_runtime_seconds = 1800  # 超时
```

### 4.6 沙箱继承

子 Agent 继承父会话的沙箱策略和审批设置（包括会话中动态修改的设置）。

## 六、安全控制

### 6.1 多层防御体系（Defense in Depth）

| 层级 | 机制 | 说明 |
|------|------|------|
| Layer 1 | 进程加固 | 防调试器、禁用 core dump、清除 LD_* 环境变量 |
| Layer 2 | OS 沙箱 | Seatbelt / Landlock + seccomp |
| Layer 3 | 网络控制 | 默认禁用，seccomp 过滤 |
| Layer 4 | 文件系统控制 | 可写区域限制 |
| Layer 5 | 审批流程 | 用户确认 |

### 6.2 三种沙箱模式

| 模式 | 行为 | 适用场景 |
|------|------|----------|
| `read-only` | 只读，不能修改任何文件 | 代码审查、静态分析 |
| `workspace-write`（默认） | 项目目录内可写，网络阻断 | 日常开发 |
| `danger-full-access` | 无限制 | 仅限可信环境 |

### 6.3 平台实现

- **macOS**：Apple Seatbelt（`sandbox-exec`），自定义 `.sbpl` 策略文件，动态策略生成，`.git` 目录自动保护
- **Linux**：Landlock（文件系统门控）+ seccomp（系统调用防火墙）双重防御
- **Windows**：原生沙箱尚未完全实现，推荐 Docker 沙箱

### 6.4 审批策略

```toml
approval_policy = "on-request"  # always / on-request / never
```

- `always`：每个操作都需确认
- `on-request`：越界操作需确认（推荐）
- `never`：全自动（CI/CD 场景）

### 6.5 网络策略（企业级）

```toml
[experimental_network]
enabled = true

denied_domains = ["pastebin.com"]
allowed_domains = ["login.microsoftonline.com", "*.openai.com"]
```

**Harness Code 优势：**
- **最精密的压缩状态机**：4 级阈值 + 20% 最低节省率 + 3 次熔断器，是同类中最保守、最安全的压缩策略
- **PromptEpoch 不可变性**：system prompt 前缀在 thread 首次运行时固定并持久化，恢复时不重新扫描——这比 Claude Code 每次加载 CLAUDE.md 更稳定
- **上下文可观测**：`context.updated` 事件让 TUI 实时展示压缩状态，其他框架无此能力

**Harness Code 不足：**
- **无前缀缓存命中率优化**：Reasonix 将前缀缓存稳定性作为第一设计原则（99.82% 命中），Harness 仅记录指纹未主动优化
- **无自主压缩工具**：DeepAgents 的 `compact_conversation` 允许模型在任务边界主动触发，Harness 只有被动阈值和手动 /compact
- **Token 估算粗糙**：UTF-8/4 是保守估计，Claude Code 使用 tiktoken 精确计数

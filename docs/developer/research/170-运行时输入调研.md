# 170-运行时输入调研

日期：2026-09-04
主题：终端 Coding Agent 在模型采样或工具执行期间继续接收用户输入

## 1. 结论先行

运行期间继续输入是可行的，但不能只把 TUI 输入框从 disabled 改成 enabled。成熟实现都把问题拆成两层：

1. **界面层持续接收键盘输入**：主输入框在普通模型/工具执行期间仍可编辑和提交；仅确认框、全屏弹窗、关机等真正独占输入的状态接管焦点。
2. **执行层按语义路由新输入**：输入可能是本地立即命令、独立旁路问答、同一 Run 的 steering、下一 Run 的 follow-up，或“取消当前 Run 并立刻发送”。这些行为不能共用一个无类型字符串队列。

五个本地竞品源码给出的共同边界是：

- 不在模型流式 token 中途篡改请求，也不把普通用户消息插进尚未闭合的 tool call / tool result 对。
- steering 先进入当前 Run 的 mailbox/queue，在**当前模型采样或工具批次结束后、下一次模型采样前**注入。
- 不能安全 steering 的 Run 类型显式拒绝或降级成下一轮 follow-up，消息不能静默丢失。
- 斜杠命令先分类。可本地执行的命令可立即运行；`/btw` 使用独立 fork；`/goal` 先更新目标状态，再把新目标上下文送入正在运行的 Agent；生命周期类命令则禁用或排队。
- UI 必须展示 pending steer 与 queued follow-up，并允许撤回编辑；取消、请求失败、Run 恰好结束等竞态下要恢复未消费输入。

因此，Harness Code 推荐目标不是“执行时开放输入框”，而是“增加带类型、可确认、可恢复的运行时输入通道”。

## 3. 先统一五种用户意图

| 意图 | 用户预期 | 执行语义 |
| --- | --- | --- |
| 本地立即命令 | 查看状态、改 UI/配置，不打断 Agent | TUI/客户端立即执行，不进入模型上下文 |
| Side question | “顺便问一下”，主任务继续 | 独立 fork/轻量模型调用；不写主 Thread，不使用副作用工具 |
| Steer | 改变当前任务接下来的做法 | 进入当前 Run mailbox，在下一个安全边界作为用户输入注入 |
| Follow-up | 当前工作做完后再做一件事 | 留在跨 Run 队列，当前 Run 完成后启动下一 Run |
| Interrupt and send | 当前方向不对，立刻换任务 | 取消当前 Run，保留输入并作为下一 Run 的第一条消息发送 |

其中，`Esc cancel` 是生命周期动作，不等同于清空输入或清空队列。用户已输入、已排队但尚未被模型消费的内容，应保持可恢复。

## 4. Codex：命令能力表、Run mailbox 与乐观确认

### 4.1 运行期间不是整体禁用，而是逐命令门禁

`codex-rs/tui/src/slash_command.rs` 的 `SlashCommand::available_during_task` 是显式能力表：`Goal`、`Side`、`Btw`、`Status`、`Diff`、`Model`、`Permissions`、`Agents` 等可在 task 进行时运行；`New`、`Fork`、`Compact`、`Review`、`Plan`、`Cd`、`Clear` 等生命周期或上下文切换命令被禁用。相邻测试 `certain_commands_are_available_during_task` 固化了该行为。

`codex-rs/tui/src/bottom_pane/chat_composer.rs` 的 `reject_slash_command_if_unavailable` 只拒绝能力表中不允许的命令，并返回 `'/…' is disabled while a task is in progress.`；`set_task_running` 只更新运行态和 footer，不关闭文本输入。

这说明运行态应该是 command capability 的一个判定维度，而不是整个 composer 的 disabled 条件。

### 4.2 普通 Enter 进入当前 Run，follow-up 另有队列

`codex-rs/tui/src/chatwidget/input_submission.rs` 的 `submit_user_message_with_history_and_shell_escape_policy` 根据 `turn_lifecycle.agent_turn_running` 选择行为：空闲时正常显示并启动 Turn；运行中构造 `PendingSteer`，携带 `client_user_message_id`、原始 `UserMessage`、历史记录和比较键，再提交 `AppCommand::user_turn`。

`codex-rs/tui/src/chatwidget/input_queue.rs` 的 `InputQueueState` 明确区分：

- `pending_steers`：已经提交给 Core、等待确认写入当前 Turn；
- `rejected_steers_queue`：当前 Run 不接受 steering，待 Turn 结束后重试；
- `queued_user_messages`：明确要求下一 Turn 执行的 follow-up；
- `submit_pending_steers_after_interrupt`：用户中断后把未确认 steer 重新作为新 Turn 提交。

`codex-rs/tui/src/chatwidget/input_flow.rs` 的 `maybe_send_next_queued_input` 只在空闲时取一条 follow-up 启动下一 Turn；`codex-rs/tui/src/chatwidget/turn_runtime.rs` 在 Turn 完成后调用它。

`codex-rs/tui/src/bottom_pane/pending_input_preview.rs` 会分区显示“下一个 tool call 后提交”“Turn 结束后提交”“Queued follow-up inputs”，并提供编辑最后一条队列消息的快捷键提示。这不是装饰：它把不同交付承诺直接暴露给用户。

### 4.3 协议使用 expected turn id 防竞态

`codex-rs/app-server-protocol/src/protocol/v2/turn.rs` 的 `TurnSteerParams` 包含：

- `thread_id`；
- `client_user_message_id`；
- `input`；
- `expected_turn_id`。

`codex-rs/app-server/src/request_processors/turn_processor.rs` 的 `turn_steer_inner` 将空 `expectedTurnId` 视为非法请求，并区分“没有活动 Turn”“活动 Turn 已变化”“当前 Turn 不可 steer”等错误。`codex-rs/core/src/codex_thread.rs` 又把 `start_or_steer_turn`、`start_turn_if_idle`、`steer_turn` 分成三个接口，避免客户端把“恰好结束”的旧 Run 输入误送给新 Run。

### 4.4 Core 只在安全边界消费 mailbox

`codex-rs/core/src/session/turn_input.rs` 将新用户输入追加到 active turn 的 pending input。`codex-rs/core/src/session/turn.rs` 明确注释 pending input 是“用户在模型运行时从 UI 提交的消息”，并在一次 sampling（含其工具处理）完成后检查 `has_pending_input`；下一次模型请求构建前再 drain 到历史。也就是说，Codex 的“实时 steer”是同一逻辑 Turn 内的下一次采样，而不是并发启动第二个主模型调用。

### 4.5 `/goal`、`/btw` 与 Esc

`codex-rs/tui/src/chatwidget/slash_dispatch.rs`：

- `/goal` 打开目标菜单；`/goal clear|pause|resume|edit` 作为控制命令本地分发；带新 objective 的 `/goal …` 发送 `SetThreadGoalDraft`，不把原始斜杠文本当普通 prompt。
- `/side` 与 `/btw` 调用 `request_side_conversation`，走独立 side conversation。

`codex-rs/tui/src/chatwidget/interaction.rs` 对 Esc/interrupt 做了分层处理。若当前有 `pending_steers`，先标记 `submit_pending_steers_after_interrupt`，再中断当前 Turn；中断完成后输入会重新提交，而不是随着 Turn 消失。Review/Compact 等不可 steer 的工作则显式提示限制。

## 5. Oh My Pi：最完整的 steer / follow-up 双队列

### 5.1 输入框持续可用，Enter 与 follow-up 快捷键语义不同

`packages/coding-agent/src/modes/controllers/input-controller.ts` 的 `setupEditorSubmitHandler` 在 `session.isStreaming` 时仍处理提交：普通 Enter 调用 `session.prompt(text, { streamingBehavior: "steer" })`。`handleFollowUp` 则使用 `streamingBehavior: "followUp"`；源码注释将其绑定语义描述为 Ctrl+Enter。显式 `/queue` 或 `->` / `=>` shorthand 也进入 yield 后执行的队列；`packages/coding-agent/src/modes/queue-input.ts` 还会把有序列表拆为多条 follow-up。

空输入 Enter 若发现已有 queued message，会 abort 当前 Turn，让队列尽快在 unwind 后继续。`restoreQueuedMessagesToEditor` 会把 steer、follow-up 和 compaction 队列一起恢复到编辑器；中断时只清理不应自动恢复的内部消息，保护用户输入与图片。

### 5.2 Agent 内核本身理解两类队列

`packages/coding-agent/src/session/agent-session.ts` 的 `prompt` 在 streaming 时要求显式提供 `streamingBehavior`，再分别调用 `steer` 或 `followUp`；扩展命令在这之前尝试本地执行，因此可以在 streaming 时立即完成。

`packages/agent/src/agent.ts` 的文档给出严格语义：

- `steer(m)`：当前工具执行后交付，并跳过尚未开始的工具；
- `followUp(m)`：只有 Agent 没有更多 tool call 或 steer、原本将结束时才交付。

两队列都有 `peek`、`pop last`、`clear`，并可配置一次消费一条还是全部消费。

`packages/agent/src/agent-loop.ts` 在开始、每个模型/工具循环边界、最终停止边界分别拉取队列。工具批次执行时对 steer 使用非消费式检测：仅硬中断声明为 interruptible 的等待类工具；普通有副作用工具接收 cooperative steering signal 或先完成，尚未开始的 sibling tool 可跳过。外部 abort 时不 drain steering queue，避免消息被塞进一个注定取消的模型请求后丢失。

### 5.3 `/goal` 与 `/btw` 是不同通道

`packages/coding-agent/src/modes/interactive-mode.ts` 的 `#enterGoalMode` 和 `#replaceGoalFromObjective` 先更新 `goalRuntime` 与本地 goal state；若主 Session 正在 streaming，再调用 `session.sendGoalModeContext({ deliverAs: "steer" })`。这为 `/goal` 给出直接范式：**控制面先提交目标状态，数据面再把目标快照注入当前 Run**。

`packages/coding-agent/src/modes/controllers/btw-controller.ts` 的 `BtwController.start` 不要求主 Session 空闲，而是异步启动 `session.runEphemeralTurn`；`Esc` 先关闭/取消 active BTW 请求。只有把已完成 BTW 答案提升为主分支的 `branch` 动作要求主 Turn 已空闲。

## 6. Qwen Code：界面提示最直白，`/goal` 有专门的中途处理

### 6.1 明确告诉用户 Enter 和 Ctrl+Q 的差别

`packages/cli/src/ui/AppContainer.tsx` 的 `isInputActiveForState` 允许 `StreamingState.Responding` 时输入保持 active。`packages/cli/src/ui/components/Footer.tsx` 直接显示：`Enter to steer · Ctrl+Q to queue`。

`packages/cli/src/ui/hooks/useMessageQueue.ts` 的每条 `QueuedMessage` 带 `deferUntilIdle`：普通 Enter 在 running 时先入队、可在 sampling boundary drain；Ctrl+Q 把消息标成必须等 idle。`packages/cli/src/ui/components/QueuedMessageDisplay.tsx` 展示队列并提示上箭头编辑。

### 6.2 斜杠命令不会被盲目注入模型

`AppContainer.handleFinalSubmit` 的运行时路由为：

- `canRunDuringStreaming` 的本地 slash command 立即执行；当前源码中 `about`、`help`、`settings` 明确 opt in；
- `/btw` 在 Responding 状态并发提交；
- 其余内容进入 message queue；
- `/quit` 特判为立即退出。

`useMessageQueue.drainQueue` 在普通 active turn 只 drain 非 slash 输入；slash command 留到 idle 后重新经过命令解析。Goal turn 是例外：`GOAL_COMMAND_RE` 专门识别 `/goal`，允许目标控制命令在 goal turn 的边界被处理。

### 6.3 当前 Turn 的安全注入点

`packages/cli/src/ui/hooks/useGeminiStream.ts` 的 `drainSteerAtBoundary` 被作为 `getSteerInput` 传给 core。`resolveSteeredMessages` 对普通消息解析 `@` 文件等上下文，并在接受后记录为 mid-turn user message；遇到 `/goal` 则调用 `handleSlashCommand`，不把原始 `/goal …` 文本送给模型。

同文件在 tool responses 构造完成后明确写着“Drain steerable user messages at this sampling boundary and append them after the tool responses as genuine user content”。若 Turn 已 cancel，消息留在队列；解析失败或 abort 也通过 `restore` 返回队列。

### 6.4 `/btw` 真正与主回答并行

`packages/cli/src/ui/commands/btwCommand.ts` 在交互模式中用独立 `btwItem`，不占用主 `pendingItem`，并 fire-and-forget 调用 `runForkedAgent`。工具在 request 级别禁用，且 BTW 有自己的 `AbortController`。因此“可以在执行中输入 `/btw`”不是把它排到主 Run 后面，而是启动可独立取消的旁路请求。

## 7. Claude Code：立即命令与统一优先级队列

### 7.1 active query 期间先尝试 immediate command

`src/utils/handlePromptSubmit.ts` 在 `queryGuard.isActive` 或 external loading 时，先查找 `immediate: true` 的 `local-jsx` 命令并立即加载 UI；否则普通 prompt/bash 输入进入队列。该路由把即时本地命令和要交给模型的输入分开。

`src/commands/btw/index.ts` 将 `/btw` 声明为 `immediate: true`。`src/utils/sideQuestion.ts` 的 `runSideQuestion` 调用 `runForkedAgent`，最多一轮、拒绝所有工具、跳过 cache write，并在提示词中明确主 Agent 继续独立工作。

### 7.2 普通输入可在同一 query 的工具边界送入

`src/utils/messageQueueManager.ts` 使用进程级统一 `commandQueue`，优先级为 `now > next > later`，同级 FIFO；普通用户输入默认 `next`，任务通知默认 `later`。`popAllEditable` 只把用户可编辑消息恢复到输入框，保留任务通知。

`src/query.ts` 在 tool call 完成后、准备递归到下一次模型请求前取 `next` 队列项，将普通 prompt 转为 `queued_command` attachment；源码特别说明不能在 tool result 之间插入普通用户消息。Slash command 被排除，留给 Turn 结束后的 `src/hooks/useQueueProcessor.ts` / `src/utils/queueProcessor.ts` 逐条执行。

`src/components/PromptInput/PromptInput.tsx` 的 Esc 处理顺序也是分层的：先关闭 side question/help 等 UI；存在 editable queue 时先把它拉回输入框；真正 loading cancellation 由更外层请求生命周期处理。这里的关键不是某个固定键，而是 modal、queue edit 和 cancel 必须明确仲裁，不能让 Esc 同时触发多个副作用。

## 8. Grok Build：默认 follow-up，显式“Send now”取消重发

Grok Build 采用与 Codex/Qwen 不同但同样一致的产品选择：运行中普通 Enter 主要表示排队 follow-up，而不是 steer 当前 Run。

`crates/codegen/xai-grok-pager/src/views/agent.rs` 与测试 `prompt_running_submit_hint_is_queue_and_send_now` 固化了提示：Turn running 时 Enter 是 queue；有 composer 文本时展示 `send now` chord；composer 为空但已有 queued follow-up 时，Enter 可把队头立即发送。

`crates/codegen/xai-grok-pager/src/app/agent_view/prompt.rs` 的 `ActionId::InterjectPrompt` 实际产生 `Action::SendPromptNow`：清空 composer，取消当前 Turn，并把文本作为下一 prompt 发送。`crates/codegen/xai-grok-pager/src/app/actions.rs` 也明确区分：

- `Interject`：不取消 Run，保留给 plan-review comment、permission follow-up 等与当前 Turn 紧密关联的输入；
- `SendPromptNow`：用户主动 cancel-and-send，后台任务与队列仍保留。

Server 端 `crates/codegen/xai-grok-shell/src/session/acp_session_impl/prompt_queue.rs` 维护权威 FIFO。对 queued row 的 send-now 在同一个 state lock 内完成移动、版本/owner 校验和广播，避免一条消息既 interject 又作为独立 Turn 再执行。`crates/codegen/xai-grok-shell/src/session/acp_session_impl/interjection.rs` 则把真正 interjection 缓存在 `pending_interjections`，在工具完成和 Turn 最终结束前的安全点 drain；错过 Run 时转成独立 prompt，避免静默搁置。

这个方案证明默认键位可以有不同产品取舍，但内部仍必须区分“当前 Run 注入”和“取消后新 Run”。

## 10. 对 Harness Code 的建议方案

以下是 Research 结论，不替代后续 Task/Spec 中的用户决策。

### 10.1 产品语义

建议采用 Codex/Qwen/Oh My Pi 更适合 Coding Agent 的默认值：

- 运行中输入框保持可编辑。
- `Enter`：提交 steer，改变当前 Run 的后续行为。
- 独立快捷键（可沿用现有键位体系后再确认）：提交 follow-up，明确等当前 Run 完成。
- `Esc`：取消当前 Run，但不清空 draft、pending steer 或 follow-up；modal/BTW/审批框优先消费 Esc。
- 队列区分并标注“将在下一工具边界发送”和“将在本轮结束后发送”，支持至少撤回最后一条进行编辑。

普通 Enter 是否默认 steer 是产品选择，不是架构不变量；即便最终选 Grok 的“Enter 默认 queue”，底层 typed envelope 与安全边界仍相同。

### 10.2 运行时命令能力表

Command Registry 应增加运行态策略，而不是在页面组件里散落 `if (running)`：

| 策略 | 适用示例 | 行为 |
| --- | --- | --- |
| `local_immediate` | `/status`、只读设置/面板 | TUI 立即执行 |
| `side_channel` | `/btw` | 独立请求，不进入主 Run |
| `control_and_steer` | `/goal set/clear/pause/resume` | 先提交控制状态，再向当前 Run 发送目标快照/事件 |
| `steer` | 普通 Enter、模型可理解的命令/Skill | 当前 Run mailbox |
| `follow_up` | 用户明确 queue 的输入 | 下一 Run FIFO |
| `blocked_during_run` | 新建/切换 Thread、危险上下文重置 | 明确提示原因，保留 draft |

`/goal` 不应只是“允许在 running 时解析”。它需要两阶段语义：目标存储更新成功后，生成带 goal id/revision 的模型上下文；若仍是同一 active Run，则 steer，若 Run 已结束则作为下一 Run 的已更新上下文生效。

`/btw` 不应进入主 Run mailbox。它要有独立 request id、取消信号和 UI 状态，主 Run 的 streaming/approval/queue 都不应被它占用；详细工具与持久化约束沿用 Research 147。

### 10.3 跨进程契约

建议为运行时输入建立显式 envelope，至少包含：

```text
runtime_input_id
thread_id
expected_run_id
kind = steer | follow_up
content
created_at / client_sequence
```

服务端返回可观察结果，而不是仅表示 RPC 收到：

```text
accepted_for_current_run(run_id)
queued_for_next_run(position)
rejected(reason)
```

`expected_run_id` 是关键并发保护：用户按下 Enter 到 sidecar 收到请求之间，Run 可能已经完成。客户端可根据明确响应选择自动降级到 follow-up或恢复编辑器，但不能由服务端静默附着到另一个 Run。

如果当前 JSON-RPC 读循环会被一个长 `run` 请求独占，首先要把“Run 生命周期”和“接收控制消息”解耦：Run 在独立 task 中推进，连接读循环继续接收 `runtime_input` / `interrupt` / side question。只开放 TUI 输入而不解耦 sidecar 消息泵，命令仍然无法真正执行。

### 10.4 Agent 侧 mailbox 与安全点

每个 active Run 维护 mailbox，写入与模型/工具循环并发，但消费只发生在确定性安全点：

```text
收到输入
  → 校验 expected_run_id 与 Run 是否 steerable
  → 写入 mailbox 并 ACK
  → 当前模型请求/已开始工具完成
  → 补齐全部 tool result
  → 原子 drain mailbox（FIFO）
  → 记录用户消息并构建下一次模型请求
```

对尚未开始的并行工具可以选择跳过；对已经开始且有副作用的工具默认让其完成。首版不必实现 Oh My Pi 的 cooperative tool interruption，但必须定义“已开始工具不会因 steer 被半途硬杀”的保守边界。

以下工作应声明为 non-steerable：上下文压缩、Review/迁移等需要固定输出 schema 的内部 Run，以及已经进入 terminal commit 的 Run。此时服务端返回结构化拒绝，客户端将输入留在下一轮队列或恢复到 composer。

### 10.5 状态与可靠性不变量

1. 一条 `runtime_input_id` 最多被模型消费一次。
2. ACK 前的乐观 UI 必须能 reconcile；超时不等于失败，不得盲目重复产生两条输入。
3. 取消不消费 mailbox；若输入已从客户端队列移出但未被 Run 接受，必须恢复。
4. follow-up FIFO；steer 也保序。不同类型不得因为共用数组而重排。
5. Slash command 必须在客户端/服务端之一完成类型解析，禁止把未知运行时控制命令直接当自然语言送给模型。
6. 审批/表单等 modal 可以接管按键，但 composer draft 要保留；关闭 modal 后恢复焦点。
7. Thread 持久化应区分“已接受 steer”“仅客户端排队”“BTW 临时请求”，避免恢复会话时重复执行。

## 11. 建议分阶段验证

### 阶段 A：输入解锁与本地/旁路命令

- Running 时 composer 可编辑。
- Command Registry 具备运行态能力表。
- `/btw` 能与主 Run 并行；`/goal` 控制状态可在 running 时更新。
- 普通文本先作为明确的 next-run queue，确保输入绝不丢失。

这是最小闭环，但还不是“实时 steer”。

### 阶段 B：同 Run steering

- 增加跨进程 runtime-input 契约、`expected_run_id`、ACK/reject。
- Python Run 改为 mailbox + safe-boundary drain。
- TUI 区分 pending steer 与 follow-up，处理 Run 恰好结束、不可 steer、取消和断线恢复。

### 阶段 C：工具中途响应与队列体验

- 跳过尚未开始的 sibling tool；按工具声明选择 cooperative interrupt。
- 队列编辑、删除、重排或 send-now。
- 多客户端/恢复场景下使用 version/owner 或等价机制做权威协调。

## 12. 验收时必须覆盖的竞态

- 模型正在 streaming 时连续提交两条 steer，模型按 FIFO 在下一采样看到两条。
- 工具执行时提交 steer：已开始工具产生完整 result，尚未开始工具的处理符合 Spec。
- 提交瞬间 Run 正好完成：输入明确降级到 follow-up 或回到 composer，不丢失、不重复。
- `/goal set` 在 running 时成功更新目标，当前或下一采样看到对应 revision；失败不注入旧/半成品目标。
- `/btw` 运行、关闭或失败不改变主 Run 的 abort controller、transcript 和队列。
- Esc 在 BTW、审批框、普通 running、存在 pending steer 四种状态下只触发预期的一层动作。
- 断线重连、重复 ACK、客户端重试不导致同一 `runtime_input_id` 执行两次。
- non-steerable Run 收到输入时有清晰 UI 提示，且文本仍可编辑或排到下一轮。

## 13. 最终判断

支持执行时输入不只是 TUI 改造，而是 `cli → protocol → agent run loop` 的纵向生命周期功能。竞品已经证明该体验成熟可用；其中最值得直接借鉴的是：

- Codex 的命令能力表、`expected_turn_id` 与 pending/rejected/queued 三态；
- Oh My Pi 的 steer/follow-up 双队列及工具级安全中断边界；
- Qwen Code 的 `Enter to steer · Ctrl+Q to queue` 可见语义和 `/goal` 专门解析；
- Claude Code 的 immediate command 与统一优先级队列；
- Grok Build 的 send-now、权威队列与版本校验。

对 Harness Code，推荐先建立 typed runtime input 与不丢消息的不变量，再开放默认 Enter steering；否则输入框虽然能打字，实际仍会在 Run 竞态、tool result 顺序或取消恢复上产生不可预测行为。
